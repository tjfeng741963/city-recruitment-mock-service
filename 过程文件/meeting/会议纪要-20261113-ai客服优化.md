## 零、一分钟版

客户这次会只关心三件事，按他投入的时间排序：

1. **配置层重复了**——城市管理和厂区管理填了两遍同样的东西，要能一键带过去；节假日管理基本是废的。
2. **AI 不能自由发挥**——邀约流程本来就是固定的，必须做成固定节点模板；现在这套「让 agent 自己判断」导致了已读乱回。
3. **知识库改动要有审批**——文员随手把一句话转成知识库条目、AI 就采纳，新人会把这个库搞乱，必须走组长审批。

此外他从竞品那里看到一个能力，成了这次会的**技术分水岭**：

> 竞品不是云端电脑。**同一台电脑上，网页端和企业微信同时开着、同时能操作、AI 还在自动回复，而且不抢前台。**

他明确把这条当成「我们也得能这样」。这是我们方案要回答的核心问题，单独成文：

## 一、配置层：城市管理 / 厂区管理重复

### 现状问题（客户原话要点）

> 「像城市管理，它不是有两个板块吗？我点了进去，比如说南宁的，你像这些什么区域薪资面试线路、要求，然后通知这些东西，在厂区管理的南宁这里也是有的。为什么还要再在这里再配置一次？」

客户看到的是：**同一份南宁的岗位信息，在两个页面各填一遍。**

### 客户提出的做法

在城市管理页做一个「项目按钮」多选：

```
城市管理 · 南宁  →  [ ] 南宁地铁安检   [ ] 南宁肯德基   [ ] ……
                   勾选后「一键配置」→ 自动把厂区管理里对应的内容带过来
```

他的意图是：城市管理只做**分配**（这个城市有哪些项目在做），厂区管理只做**内容**（这个项目具体什么工价、班次）。不要两处都填。

### 我方的技术解释（涂）

现有设计是按**工作流节点**保留的——竞品每个节点一份配置，所以我们这里每个节点也留了配置项。客户设想的「一键配置」等于**纯智能体判断**，差别在于：

| | 固定模板 | AI 模板 |
|---|---|---|
| 怎么回 | 设什么回什么 | 模型重新组织语言 |
| 花 token | 不花 | 花 |
| 改一条要重训吗 | 不用 | 不用，但要调 prompt |

### 会上达成的结论

1. **可以做一键配置**（涂：「可以，没问题」）。
2. 配置分成两种，界面上要能区分：**固定模板**（不花 token）和 **AI 模板**（花 token），名字要改。
3. **城市 > 厂区**的层级不动：
   > 涂：「如果是业务量大，比如说南宁就有很多个厂可以去招……城市是大于厂区的。」
   客户中途说「城市管理就是厂区管理的分支」，被涂纠正为「城市下面才有厂区」，客户接受。
4. 客户对原版设计的评价，记下来当验收标准：
   > 「我感觉这个逻辑上面就是它原版的做的就不是特别 ok。」
   > 「我们现在改进一下原版的。」（涂）

### 待办

- [ ] 城市管理页加「项目多选 → 一键同步到厂区管理」按钮
- [ ] 「固定模板 / AI 模板」两个概念在界面上分开、命名区分
- [ ] 侧边栏菜单重命名：`账号管理` / `用户设置` / `招聘管理`（客户当场提的）

## 二、节假日管理：先保留，但基本判死

### 客户的困惑

> 「节假日管理，你这个厂区里面都已经有它的这些东西了，还为什么要设置这个东西？」

涂：「我也没明白，但是他有。」——原版就带着，我们只是还原。

### 客户自己找到了唯一有价值的用法（这点很重要）

> 「你像佛山那个项目，它是固定周一到周六这个时间点面试，但是我们今天上午我们就发了通知，这一个佛山的项目面试点，他明天早上是面试不了的。」

也就是说：**项目的常规排期不动，只临时关掉某一天的某个面试点。**

期望的完整形态：

```
节假日/临时调整  →  一键关掉「佛山安检 · 明天上午」
                 →  AI 立刻知道明天早上不要约这个点的人
                 →  自动通知已经约在明天上午的客户
```

客户原话：「除非是他能做到这一个程度，我感觉这模板才是有用的。」

### 结论

- 涂：「先砍掉，没关系。」客户：「也不用说现在删掉了，先提一下这个东西。」
- **保留入口，但不作为近期开发项**；真要做得按上面那个三段式做，否则没意义。

## 三、知识库乱回：这是本次会最实质的技术讨论

### 客户观察到的现象

> 「他其实已经是有的。但是它有点乱码了。然后他已读乱回你知道吗？」
> 「我这里不是说到了在哪里找你吗？然后他没有读上下文的，我才刚约到他怎么可能马上……」

关键：**刚约上就问了不该问的问题，说明模型没读上下文。** 这不是话术问题，是流程控制问题。

### 我方的判断（涂，原话）

> 「他现在有点乱回，他要让另外一个 AI 去监控他有没有乱回？……你要让 agent 什么乱七八糟……**我们不能通过 agent 去回复。我们要一开始用默认的程序来控制，当它发问的时候才用 agent 去监控它，去做一个控制。**」

> 「所以说我们要做一个类似于 Dify 无限画布的那种流程，比如说我第一个节点要干什么，这个节点就是干什么，把这个节点搭好了，我们的新客户端我们就不需要调知识库了，只需要去调节点。」

**这段话是这次会的技术主线，翻译成工程语言：**

| 现在 | 应改成 |
|---|---|
| agent 自由决定说什么 | **程序**决定走到哪个节点、该说什么 |
| 知识库整段塞 prompt | 节点只调自己那一段内容 |
| 出错靠事后发现 | 发送前有一道校验（「另外一个 AI 监控」） |

### 客户的呼应

> 「因为我们那些邀约流程不都是全部按照固定流程去聊的吗？所以没必要……我就直接在这里做一个固定模板。」

> 「就是这个固定模板，它就是你们说的节点，它先发什么后发什么再发什么，基础模板。补充这固定的东西我感觉就可以了，他现在做的感觉没有，他的邀约率会没有这么的好。」

### 结论

- 方向已对齐：**确定性流程 + 节点化配置 + 发送前校验**，不是让 LLM 自由发挥。
- 邀约率是客户的最终判据——他现在认为现在的做法拉低了邀约率。

### 待办

- [ ] 邀约流程做成可视化节点（参考 Dify 画布形态），节点即话术段
- [ ] 发送前加一道校验节点（模型自检「有没有按流程走 / 有没有乱答」）
- [ ] 上下文档位补齐：刚约上之后不许再问城市/邀约

## 四、知识库审批流：客户对「文员乱改」的焦虑

### 触发场景

> 「比如说同一台电脑控制多一个账号的嘛……」
> 「文员他不是老手，他自己去把这个答案去输入了之后他又转换了，没人审批的话，这个东西就会乱。」

### 客户要的形态

```
文员提交一条知识库条目
      ↓
组长（他的直接上级）审批
      ↓
通过才生效，AI 才采纳

主账号（老板）：查看权 + 审批权，全部权限
```

> 「不然那个新人在那里乱回，他那个 AI 又采纳了，知识库被很乱了吗？」
> 「不能说什么都要管理员审批，他都有自己的组长，让他找组长就好。」

### 我方状态

涂：「明白，但还没想到那么深。」

### 待办

- [ ] 知识库条目加 `status = pending/approved/rejected` + `submitted_by` + `approved_by`
- [ ] 审批人按组织层级走（组长 → 主账号兜底）
- [ ] 待处理列表：仿「学生交作业 → 老师批」的交互（客户原话举的例子）

## 六、重中之重：竞品的「不抢前台双端联动」

这段在补充录音里，只有 4 分钟，但是整场会技术含量最高的部分。

### 我方先抛出的限制（涂）

> 「现在属于云上 agent，你扫码的端口，它是在服务器上的。**你本地如果你要扫企业微信，那就会退登，就你把服务器上的挤掉了**，你只能看这个网页，你可以看手机。这样的。接受吗？」

**这一条要限定清楚，别被误读**（2026-11-13 会后澄清）：
涂这里说的是**企微扫码登录的端口**——企微一个账号只能一个客户端在线，云端那台占着，本机客户端就登不上。

它**不是**在说「我们 4222 后台和企微客户端会互踢」。那两者根本不抢同一个登录态，本来就可以同时开着。

### 客户的回答（关键）

> 「他那边是可以微信和同步看的！」
> 「他的微信，这不企业微信比如说也打开，这个也打开，还可以操作。」

### 会后澄清：客户说的「双端」是什么（2026-11-13 补录）

> 「网页端和企微端同时在线：这个说的是我们不是有一个前端嘛，网页有一个网页版，**不是企微的网页版，是我们自己这个软件的网页版** http://119.91.113.100:4222/factories
> 这个跟企业微信它可以同时登录，且它们是双端同步的，然后可以自己回，在我们的网页可以显示，在企业微信上也可以显示」

**所以「双端」= 我们的 4222 后台 + 本机企微客户端。** 客户要的是：AI 回的话在网页上看得到，在企微上也看得到，两边一致。

这一条把「不抢前台」和「双端同步」彻底分成了两件事——详见技术方案文档第 1.1 节。

### 我方反应

> 「可以操作？然后还不会抢前台？**这个我要去问一下他们了。看一下他们什么时候能做成这样？**」

### 客户追问的风控问题

> 「如果说他只能看手机的话，它不会涉及到风控的问题吗？比如说我企业微信登录的电脑端是在云端的 ip，我手机连的 wifi 和云端连的这个 wifi 肯定不一样。」

涂的回答（定调）：

> 「是一样的企业……他现在云上是在广州，然后他本地也是在广州，所以这是没有关系的。都是在广州这个区域。就比如说你企业微信，你出差了，你在你的远程电脑打开企业微信其实是一样的道理。就比如说你现在跑出去了，然后你现在用你的向日葵打开你的电脑，打开企业微信是一个道理。」

### 这条需求的确切定义

客户要的不是「云上有个机器人替我回」，而是：

| 要素 | 要求 | 我们能不能 |
|---|---|---|
| 部署形态 | **不是云端电脑**，是本机 | ✅ 本地客户端已具备 |
| 同时在线 | 我们的 4222 后台 + 本机企微客户端，**也可以同时开着** | ✅ 不冲突 |
| 同时可操作 | 人点得动，AI 也发得出 | ❌ 抢前台 |
| 前台归属 | **不抢前台**，人该干嘛干嘛 | ❌ 全局键盘 |
| 回复方式 | AI 自动回 | ✅ 已有 |
| **两边都能看到** | AI 回的话，网页和企微**都要显示** | ⚠️ 只通了一半 |

**最后一行才是客户这次的真正痛点，而且它跟「不抢前台」不是一个问题：**

- 「两边都能看到」= 数据同步问题 → 不用 hook，补一个上报点（技术方案文档第 6 节第一步）
- 「不抢前台」= 输入机制问题 → 要跑探针，才谈得上选路线

**别为了不抢前台去冒封号风险，回头发现同步本来半天能修。** 完整分析见
`docs/技术方案-不抢前台与双端联动-20261113.md`。

## 八、我方推断（会上未明说，需后续验证）

> 以下不是会上说过的内容，是整理时的判断，标注出来避免和事实混淆。

1. 客户之所以反复强调「不抢前台」，是因为**他自己要用那台电脑办公**。竞品给他的震撼不是「AI 会回」，而是「AI 回的时候我还能干活」。
2. 「双端联动」在他嘴里同时开了网页端和企微端还能操作——说明竞品的网页端很可能不是独立后台，而是**和本地客户端有实时通道**（否则做不到「这边点那边动」）。
3. 客户提的「同一台电脑控制多个账号」，结合审批流需求，说明他打算一台机器上挂多个招聘员账号、多人协作。这对技术方案是额外约束：**不是一人一机，而是一机多号**。
