# 服务端（中心部署版）部署说明

本文对应 `deploy/server/`：把 Python 后端（FastAPI）部署到一台 Linux 服务器，
多台 Windows 客户端通过 HTTP 接入，浏览器直接访问线索看板。

> 仓库根目录的 `Dockerfile` / `docker-compose.production.yml` 是 Node 应用的，与本后端**无关**，不要拿来用。

---

## 1. 架构与端口

```
   Windows 客户端 A ─┐
   Windows 客户端 B ─┼─► nginx :80 ─► backend :8090 ─► postgres :5432
   浏览器（看板）  ─┘        （唯一对外端口）   （仅容器内网 + 127.0.0.1）
```

| 服务 | 镜像 | 端口 | 可见性 |
|---|---|---|---|
| nginx | `nginx:alpine` | `80`（`HTTP_PORT` 可改） | 公网 |
| backend | 本地构建 `city-recruitment-backend` | `8090` | 仅 `127.0.0.1`，公网不可达 |
| postgres | `postgres:16-alpine` | `5432` | 仅容器网络 `internal` |

数据持久化在两个命名卷：`pgdata`（数据库）、`appdata`（`/app/data`，含 `instance.json`）。

### 后端启动时的建表行为

`app/db.py` 在 lifespan 里执行 `Base.metadata.create_all`，并给存量表补列
（`leads` / `devices` 的后加字段用 `ALTER TABLE ADD COLUMN`）。

**因此升级时不需要单独跑迁移**，也不要用 alembic 手工介入。
注意 `create_all` 只建表不改表，删除/改名字段仍需人工处理——正常升级不会遇到。

## 2. 服务器要求

| 项 | 最低 | 建议 |
|---|---|---|
| CPU | 2 核 | 4 核 |
| 内存 | 2 GB | 4 GB（Postgres + 构建时的 uv 解析都吃内存） |
| 磁盘 | 20 GB | 40 GB 以上，另留备份空间 |
| 系统 | 任意 x86_64 Linux（Ubuntu 20.04+ / Debian 11+ / CentOS 8+ 均可） | Ubuntu 22.04 LTS |
| Docker | 20.10+，**含 compose v2 插件** | 24+ |
| 网络 | 能拉 `postgres:16-alpine`、`nginx:alpine`、`python:3.12-slim`；能访问 LLM 接口 | — |
| 端口 | 80 空闲（8090 不能被别的程序占） | — |

安装 Docker（Debian/Ubuntu）：

```bash
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
docker compose version        # 必须有输出，否则装 docker-compose-plugin
```

> 国内服务器拉镜像慢：给 Docker 配镜像加速器（`/etc/docker/daemon.json` 的 `registry-mirrors`），
> 并在 `.env` 里把 `PIP_INDEX_URL` / `UV_DEFAULT_INDEX` 换成阿里云源。

## 3. 一键安装

```bash
cd <仓库根>/deploy/server
chmod +x install.sh backup.sh healthcheck.sh
sudo ./install.sh
```

`install.sh` 依次做：

1. 检查 `docker`、`docker compose`、daemon 连通性；
2. 检查 `HTTP_PORT`（默认 80）与 8090 是否被占用（已有本项目的容器在跑时按升级放行）；
3. `.env` 不存在则从 `.env.example` 复制，并自动生成：
   - `APP_JWT_SECRET` = `openssl rand -hex 32`（32 字节 = 64 位 hex）
   - `APP_SEED_ADMIN_PASSWORD` = 随机 16 位字母数字
   - `POSTGRES_PASSWORD` = `openssl rand -hex 16`
   `chmod 600 .env`；
4. `docker compose up -d --build`；
5. 轮询 `/healthz` 最长 60 秒，失败打印 `backend` 最后 30 行日志；
6. 打印访问地址、管理员账号密码、客户端接入提示。

**管理员密码只打印一次**，同时保存在 `.env` 的 `APP_SEED_ADMIN_PASSWORD`。
请立即存进密码管理器，然后按第 8 节改掉默认值（改 `.env` 对已存在的用户无效，
需在库里改密码或删库重建，见 8.1）。

### 安装后立刻要做的验证

```bash
docker compose ps                     # 三个服务都是 running / healthy
curl -s http://127.0.0.1/healthz      # {"ok":true,"env":"production",...}
./healthcheck.sh                      # 全项检查
```

浏览器打开 `http://<服务器IP>/api/v1/leads/board`，用管理员账号登录。

### 手工安装（不用脚本）

```bash
cp .env.example .env
# 改 POSTGRES_PASSWORD / APP_JWT_SECRET / APP_SEED_ADMIN_PASSWORD
chmod 600 .env
docker compose up -d --build
```

`APP_JWT_SECRET` 生成：`openssl rand -hex 32`。

## 4. 环境变量

全部以 `APP_` 为前缀，由 `backend/app/settings.py` 读取（`env_prefix="APP_"`）。
`.env` 同时被 compose 用于变量替换、通过 `env_file` 注入容器。

| 变量 | 说明 | 生产值 |
|---|---|---|
| `APP_ENV` | 环境标识 | `production` |
| `APP_DATABASE_URL` | 数据库连接 | 由 compose 自动拼：`postgresql+asyncpg://用户:密码@postgres:5432/city_recruitment` |
| `APP_JWT_SECRET` | JWT 签名密钥 | 随机 32 字节 hex |
| `APP_ACCESS_TOKEN_MINUTES` | 令牌有效期 | `480` |
| `APP_SEED_ADMIN_USERNAME` | 首个管理员 | 必须改 |
| `APP_SEED_ADMIN_PASSWORD` | 首个管理员密码 | 必须改（install.sh 自动生成） |
| `APP_OUTBOX_WORKER` / `_INTERVAL` | 发件箱投递 | `true` / `5` |
| `APP_SYNC_WORKER` / `_INTERVAL` | 企微同步（未配置企微自动跳过） | `true` / `15` |
| `APP_LEAD_WORKER` / `_INTERVAL` | 线索扫描 | `false`，灰度再开 |
| `APP_DEVICE_WORKER` / `_INTERVAL` / `_OFFLINE_AFTER` | 设备离线判定 | `true` / `30` / `90` |
| `APP_LLM_BASE_URL` | 大模型地址 | `https://api.deepseek.com/v1` |
| `APP_LLM_API_KEY` | 大模型 Key | 自行填写；留空则降级为模板回复 |
| `APP_LLM_MODEL` | 模型名 | `deepseek-chat`，**不要用 `deepseek-reasoner`** |
| `APP_LLM_TIMEOUT` | 超时秒数 | `30` |
| `APP_KB_SERVICE_TOKEN` | 服务间令牌 | 可选，留空则自动生成到 `/run/kb/service-token` |
| `POSTGRES_USER` / `PASSWORD` / `DB` | 数据库账号 | 由 install.sh 生成 |
| `HTTP_PORT` | nginx 对外端口 | `80` |

> `APP_LEAD_WORKER` 默认关的原因：开启后会把到点的 `booked` 线索批量标成「待核实」，
> 不向客户发任何消息，但会改动历史数据。建议先在一个顾问的小范围数据上确认标签口径再全量开。

## 5. 多客户端接入

每台 Windows 跑 `deploy/client`（采集 + 自动回复），全部指向同一台服务器。

### 5.1 服务器侧：为每台机器注册设备

设备必须先在服务端登记，拿到 `device_token` 才能上报心跳和消息。
接口需要**管理员 JWT**（`POST /api/v1/devices`）。

```bash
# 1) 取管理员令牌
TOKEN=$(curl -s -X POST http://<服务器IP>/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<管理员密码>"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')

# 2) 注册设备（device_code 必须全局唯一，只允许小写字母数字 - _，且以字母数字开头）
curl -s -X POST http://<服务器IP>/api/v1/devices \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"device_code":"pc-office-01","name":"一楼前台"}'
```

返回体里的 `device_token`（形如 `dt_xxx`）就是这台机器的身份，**只在这里出现一次**，请立刻填进客户端。

设备列表：`GET /api/v1/devices`（任意登录用户）。
重复注册同一个 `device_code` 会返回 409。

### 5.2 客户端侧：改三处

编辑每台机器的 `agent/config.json`（由 `agent/config.example.json` 复制而来）：

```json
{
  "server": "http://<服务器IP>",
  "device_token": "dt_从服务端拿到的令牌",
  "device_code": "pc-office-01",
  "brain": {
    "mode": "kb",
    "base_url": "http://<服务器IP>",
    "username": "admin",
    "password": "<管理员密码>"
  }
}
```

要点：

- `server` 和 `brain.base_url` 都要改（前者上报采集/心跳，后者查知识库组织回复）；
- `device_code` **每台唯一**，与 5.1 注册时一致，且必须与 `device_token` 配对，否则心跳 403；
- `deploy/client/config/agent.config.json` 是客户端目录下的模板副本，改动同理；
- 若客户端本机还跑着本地后端，请把那个后端停掉，避免两套数据分叉。

### 5.3 验证接入

```bash
# 服务器上看设备是否上线（心跳间隔 60s，等一轮再看）
docker compose exec -T postgres psql -U recruit -d city_recruitment \
  -c "select device_code,status,wecom_state,last_heartbeat_at from devices order by id;"
```

`status=online` 即接入成功；看板顶部红条消失也代表采集端在线。
超过 `APP_DEVICE_OFFLINE_AFTER`（默认 90 秒）没有心跳，后端会把状态改回 `offline`（只改状态，不动业务数据）。

### 5.4 反向代理与 WebSocket

客户端走 HTTP 80 即可；实时推送走 `ws://<服务器IP>/ws?token=<JWT>`，
`nginx.conf` 已配好 `Upgrade`/`Connection` 头，`proxy_read_timeout 3600s`。

浏览器访问的看板是**同源**请求，不涉及 CORS。
后端 CORS 白名单只放了 `localhost:5173`（本地开发用），
如果要把前端单独部署到别的域名，需要改代码里的 `allow_origins`——本次交付未改动 `backend/`。

## 6. 日常运维

```bash
cd deploy/server

docker compose ps                  # 状态
docker compose logs -f backend     # 后端日志
docker compose logs --tail=100 nginx
docker compose restart backend     # 只重启后端
./healthcheck.sh                   # 体检
```

`healthcheck.sh` 输出：容器状态 → `/healthz` → 数据库连通与
`kb_entry` / `conversations` / `leads` 行数 → `devices` 明细与在线数 → 磁盘水位。
有异常返回非 0，可直接挂到监控。

## 7. 升级与回滚

### 7.1 升级（数据不丢）

```bash
cd deploy/server
./backup.sh                        # 先备份，2 分钟的事
docker tag city-recruitment-backend:latest city-recruitment-backend:$(date +%Y%m%d)
cd <仓库根>
git pull
cd deploy/server
docker compose up -d --build
./healthcheck.sh
```

- 数据在 `pgdata` / `appdata` 命名卷里，`docker compose down`（不带 `-v`）不会删；
- 新表/新列由启动时的 `create_all` + 补列逻辑自动处理，无需迁移；
- 升级期间客户端心跳会失败几十秒，agent 会自动重试，无需干预；
- nginx 用 Docker 内置 DNS 动态解析 backend，backend 重建（IP 变化）后不会 502，
  也不需要手工 `nginx -s reload`。

### 7.2 回滚

回滚前先把镜像打 tag 是唯一前提（见上一步）。

```bash
cd deploy/server
# 方式一：用旧 tag 重新起（.env 里 IMAGE_TAG 或命令行指定）
IMAGE_TAG=20261104 docker compose up -d --no-build backend

# 方式二：代码也回退
cd <仓库根>
git checkout <上一个版本 tag 或 commit>
cd deploy/server
docker compose up -d --build
```

注意：**代码回滚不会回滚数据库结构**。新版本若加过列，旧代码通常仍能跑（多出的列被忽略）；
若新版本做过破坏性变更，必须连数据一起恢复（见 7.3）。

### 7.3 从备份恢复

```bash
cd deploy/server
docker compose stop backend
gunzip -c backups/20261104-0315.sql.gz | \
  docker compose exec -T postgres psql -U recruit -d city_recruitment
docker compose start backend
```

`appdata` 恢复：

```bash
docker compose stop backend
docker compose run --rm -T --entrypoint sh backend -c \
  "rm -rf /app/data/* && tar -xzf - -C /app" < backups/20261104-0315.data.tar.gz
docker compose start backend
```

（`backup.sh` 只备份 PG 和 `/app/data`；当前后端没有文件上传功能，
若后续加入上传，把上传目录一并纳入该脚本即可。）

## 8. 安全

1. **改默认管理员密码**：`APP_SEED_ADMIN_PASSWORD` 只在 `users` 表为空时生效，
   安装后再改 `.env` **不会**改已有账号密码。
   - 正确做法：首次登录后立刻用强密码重建（或直接改库）；
   - 重建方式（会清空业务数据，慎用）：`docker compose down -v` 后改 `.env` 再 `up`。
2. **只开 80**：云安全组只放行 80（及必要的 22）。8090 已在 compose 里绑 `127.0.0.1`，
   即使安全组放开也访问不到；不要为了图省事改成 `0.0.0.0:8090`。
3. **`.env` 权限 600**：`install.sh` 已设置，手工安装请自己 `chmod 600 .env`；
   不要把 `.env` 提交到 Git（根 `.gitignore` 已忽略）。
4. **`.env` 里的 LLM Key / JWT 密钥泄露等于全丢**：换人接管时全部轮换。
5. **HTTPS**：当前只提供 80。若服务器有域名，建议在前面加一层 Caddy/云负载均衡做 TLS；
   没域名时可先用 IP + 安全组限制来源 IP。
6. **JWT 有效期 480 分钟**：离职或设备丢失时改 `APP_JWT_SECRET` 并重启，所有令牌立即失效。
7. **设备令牌**：`device_token` 泄露等于可伪造该设备上报。丢失设备时在库里删除或禁用该行
   （`update devices set status='disabled' where device_code='...'`），并让客户端换新 token。

## 9. 排障

先跑 `./healthcheck.sh`，再按下方对照。

### 9.1 `/healthz` 不通 / install.sh 超时

```bash
docker compose ps
docker compose logs --tail=50 backend
docker compose logs --tail=50 postgres
```

| 现象 | 原因 | 处理 |
|---|---|---|
| backend `Restarting` | 启动异常，多半是 DB 连不上 | 看日志里 `APP_DATABASE_URL` 与密码；确认 `POSTGRES_PASSWORD` 与卷里数据一致 |
| `password authentication failed` | 卷是旧的，`.env` 里密码换过 | 恢复旧密码，或 `down -v` 重建（会清库） |
| `port is already allocated` | 80/8090 被占 | `ss -lntp \| grep -E ':80\|:8090'`，停掉占用者或改 `HTTP_PORT` |
| 构建卡在拉包 | 无法访问 pypi/docker hub | 换镜像源，见第 2 节 |
| `uv.lock` 与 `pyproject.toml` 不一致 | 仓库被改动未更新 lock | 本地 `uv lock` 后提交，或在 Dockerfile 去掉 `--frozen`（不推荐） |

### 9.2 数据库连不上

```bash
docker compose exec -T postgres pg_isready -U recruit
docker compose exec -T postgres psql -U recruit -d city_recruitment -c 'select 1'
```

- `pg_isready` 失败：postgres 没起来或卷损坏，看 `docker compose logs postgres`；
- `database "city_recruitment" does not exist`：`POSTGRES_DB` 与卷里初始化时的不一致
  （初始化只在空卷时执行一次）；
- 能进 psql 但 backend 连不上：检查 `APP_DATABASE_URL` 的主机名必须是 `postgres`（服务名），不是 `localhost`。

### 9.3 看板 401 / 打不开

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面能开、列表 401 | 未登录或令牌过期（默认 8 小时） | 重新登录；确认浏览器与接口同源（都走 80） |
| 页面 404 `看板页面文件缺失` | 镜像里缺 `app/static/leads.html` | 确认 `backend/app/static/` 已提交，重新构建 |
| 页面白屏、控制台 CORS 报错 | 前端被单独部署到别的域名 | 同源部署，或改后端 `allow_origins`（需改代码，本次不含） |
| 502 Bad Gateway | backend 未就绪或崩溃 | `docker compose ps` + 后端日志；nginx 的 `depends_on` 只在启动时生效，后端崩溃后不会自动挡 |

直接验证后端（绕过 nginx）：

```bash
curl -i http://127.0.0.1:8090/api/v1/leads/board
```

### 9.4 设备显示离线

按顺序查：

1. **客户端进程是否在跑**：Windows 上看 `deploy/client/status.bat`，日志 `logs\agent.log`；
2. **配置**：`server` 是否 `http://<服务器IP>`（不要带 `/api`），`device_code` 与 `device_token` 是否配对；
3. **网络**：在客户端机器上 `curl http://<服务器IP>/healthz`，不通就是防火墙/安全组；
4. **令牌**：手工发一次心跳看返回：

   ```bash
   curl -i -X POST http://<服务器IP>/api/v1/devices/pc-office-01/heartbeat \
     -H "X-Device-Token: dt_xxx" -H 'Content-Type: application/json' \
     -d '{"agent_version":"test","wecom_state":"online"}'
   ```

   - 401 = token 不对；403 = token 与路径里的 device_code 不匹配；404 = 设备没注册；
5. **企微状态**：`status=online` 但 `wecom_state=login_required` 表示机器在线、企微掉登录，
   需要在那台 Windows 上手动扫码；
6. **服务器时间**：`date` 与客户端差太多会导致 JWT 校验失败，装 `chrony`/`ntp` 对时。

### 9.5 线索扫描 / 后台任务没动静

```bash
docker compose logs backend | grep '\[boot\]'
```

应能看到 `发件箱 worker 已启动` / `设备离线判定已启动`。
`线索扫描 worker 已启动` 只有 `APP_LEAD_WORKER=true` 时才出现；
`企微未配置，同步 worker 未启动` 表示企微参数缺失，属正常降级。

### 9.6 磁盘涨得快

```bash
docker system df
docker image prune -f            # 清无 tag 的旧镜像（回滚前先确认 tag 还在）
docker builder prune -f
```

日志默认由 Docker json-file 驱动无限增长，长期跑建议在
`/etc/docker/daemon.json` 配 `log-opts: {"max-size":"50m","max-file":"3"}` 后重启 docker。
