# 从企微收藏发送面试位置

2026-11-25 · 已实现岗位面试点保存收藏名称、Agent 画布选点及排定顺序、Dify 定位触发和间隔预览、离线收藏匹配。Windows 读取真实收藏列表、发送原生卡及回执仍待真机验证和接入。

## 现状

截图里的企业微信支持在会话中从「文件 → 收藏」选择已有位置消息。系统已经识别客户发来的定位，岗位页也可以维护多个面试点。当前发送端支持文字、图片和视频。Dify 的面试导航已有高德地图搜索链接。代码里还没有从收藏选择并发送原生位置卡的链路。

收藏列表属于当前登录的企微账号。截图能证明这个账号有这些收藏，其他账号和另一台电脑上的实际可用项需要分别核对。

## 页面入口

唯一的配置位置放在「招聘资料 → 招聘岗位 → 编辑 → 面试与门店」。在每个面试点的地址下方关联「企微位置卡（选填）」。面试点已有的名称、地址、面试时间和到场指引继续作为招聘资料。一处面试点对应一张经确认的位置卡，同一个岗位有多个面试点时可以分别绑定。

```text
面试与门店
└─ 面试点
   ├─ 面试点名称、详细地址、面试时间、到场指引
   └─ 企微位置卡（选填）  收藏名称及地址 · 发送账号验证状态
```

现在可以填写并保存收藏卡显示的名称，然后在「话术流程 → 接待测试」选择任一引擎，输入「发个定位」或带面试点名称的定位问题，查看本轮会建议哪个面试点。页面会提示 Windows 自动发送尚未启用。此预览使用本轮问题里的面试点名称来消除歧义，真实会话的已选面试点和发送账号将在执行阶段核对。定位以收藏卡本身为准，表单里手填的地址只作为现有文字回复的资料。若地图卡只到大楼，文字可补充已核实的楼层、房间及到场指引。对话管理用于核对会话中出现的实际消息。

## 画布中的发送时机

- Agent 在「话术流程 → 编辑流程 → 选择节点 → 发送内容 → 添加一条」把消息类型选为「企微位置卡」，再从当前岗位已绑定的面试点中选一个。用上移、下移安排它在第几条。轮到它后可单独等待 0 到 60 秒，前一条的发送后间隔也会计入计划。节点连接仍可控制是否先等客户回复，再走对应分支。
- Dify 在面试点配置「地址文字后等待」，在「话术流程 → 接待测试 → Dify 工作流」选面试点可带入测试问题。预览会显示已选面试点、收藏名、客户索要定位的触发条件和等待时间。
- 当前 Windows 继续收到可执行的文字、图片和视频。网页会保存位置卡步骤并标明「待接入」。只含位置卡的节点可先保存为停用草稿。

## 发送规则

- Agent 和 Dify 共用岗位的面试点绑定。客户明确要定位或导航，且面试点已确定时，才尝试发送收藏卡。多点且含糊时先请客户选点。
- 仅使用当前接待账号已核验的收藏条目。名字有空格或全半角等写法差异时可归一化比较。搜索无结果或同一匹配等级出现多张位置卡时，不猜选。确有已核实的文字地址时沿用现有回复，Dify 继续提供现有地图链接。发现文字地址与已核实的收藏位置冲突时，先核对再发送文字地址。
- 一旦进入发送且结果不确定，标记「待核对」，避免盲目重发或重复补发。确认发送以后才显示「已发送」，需要在目标会话中读到匹配的新位置消息。对方收到由测试联系人确认。

## 网页、后端和 Windows 的对接方案

```text
岗位面试点保存收藏名称
          ↓
候选人问定位 → Dify / Agent 判断意图 → 后端确认岗位和面试点
          ↓
后端把位置卡动作放进这一轮回复 → Windows 核对账号和目标会话
          ↓
企微收藏搜索 → 唯一同名位置卡 → 发送企微原卡
          ↓
Windows 回读并上报消息 → 后端核对回执 → 网页显示位置卡执行结果
```

### 网页和后端负责配置、选点和下发

1. **保存配置。** 在现有岗位表单中为每个 `interview_points` 条目增加可选的收藏名称 `favorite_title`，沿用岗位保存接口和权限。现有面试点缺少该字段时继续使用原有回复。绑定写在岗位面试点上，两个引擎读同一份资料。页面保存后显示「已保存，待账号核验」。首轮在「话术流程 → 接待测试」按选中的账号核对收藏，记录唯一命中时的标题和显示地址，企微能提供稳定的收藏标识时一并记录。修改收藏名、换接待账号或更换已核验的收藏结果时，重新核验。
2. **确定发哪张。** Dify 和 Agent 可以判断这轮是否在问定位或导航，并提供候选面试点。后端只接受当前招聘会话允许使用、仍启用的岗位及已保存的面试点。只有一个适用点时直接用该点，有多个点时根据会话里已确认的选择来定。仍有歧义就回复可选点，请对方选一个。收藏名称由后端从该点读取，候选人和模型生成的标题、地址或坐标没有下发权限。Dify 沿用当前会话实际选中的岗位，Agent 沿用设备绑定岗位。
3. **形成一条有顺序的动作。** 现有 Windows 客户端通过 `POST /api/v1/agent/chat` 取真实回复，服务端按设备选择 Dify 或 Agent。计划通过同一轮回复附带 `favorite_location` 动作，放在该轮相关文字之后。动作至少携带 `action_id`、`trace_id`、设备、企微账号稳定标识、目标会话 ID、入站消息 ID、岗位与面试点引用、收藏名称和有效期。用设备、账号、会话和入站消息生成稳定动作标识，同一轮重取时沿用。预览在「话术流程 → 接待测试」展示拟发送的动作和依据。Agent 画布固定回复可能在 Windows 本地执行，位置请求须从对应分支调用同一选点和授权逻辑，不能指望固定回复自动经过 `/api/v1/agent/chat`。
4. **约定生效条件。** 只有正式回复、设备报告支持该动作、账号允许发卡且面试点已核验时才下发。旧客户端沿用原有文字回复。正式文字可先说「面试点在……」，避免在位置卡落地前承诺已经发送。如果最终没有提交卡片，可以沿用已核实的文字地址或 Dify 现有地图链接。发现资料和核验过的卡片地点冲突时转人工核对。

### Windows 负责查找、发送和回读

1. **检查上下文。** 在现有串行回复任务里执行位置动作。检查有效期、当前接待账号、当前目标会话、回复范围及人工接管状态。发送前与后端复核这一轮仍可执行，岗位、账号、回复来源或配置变更时停止。用 `action_id` 在本地留执行记录，重复收到时返回先前结果。客户端重启时，如果上次已经进入提交而结果缺失，标记「待核对」。
2. **查收藏。** 在已确认的目标会话打开企微原生「文件 → 收藏」选择框，用后端下发的标题搜索。Windows 必须读到完整结果，并能区分位置卡和其他收藏。优先匹配完整标题。没有原名时，可忽略空格、大小写、全半角和少量排版符号，要求归一化后的名称完全一致并唯一。只命中一段名称、数字或方位不同的结果不采用。多条命中、结果不完整、卡片类型无法确认或已核验的收藏发生变化时停止并返回原因。
3. **提交原生卡片。** 提交前再次核对当前企微账号、会话、选中的卡和提交前该会话最新出站消息。调用企微原生确认动作，只提交一次。收藏选择和提交动作要以真机手测为依据，按仓库 `AGENTS.md` 的 Windows 改动流程评审。现有图片和视频使用文件发送机制，位置卡需从收藏选择框发送。
4. **核对发送。** 提交后刷新消息记录，找目标会话里由同一企微账号发出的、比提交前更新的原生位置消息，并和这次操作关联。能确认时上报真实出站消息 ID。只有通用「[媒体]」、发生超时或无法把新消息归到本次发送时，上报「待核对」，停止补发。回执网络失败时只重试上报，位置卡提交动作不重放。

### 两端如何核对结果

回复计划是位置卡动作的唯一来源，Windows 在原回复序列中执行。现有 `/api/v1/bridge/devices/:code/outbound` 可用来同步实际出站消息。位置动作单独记录状态，按 `action_id` 和 `trace_id` 关联，同一轮文字保留自己的发送结果。计划扩展设备回执，带上 `action_id`、实际账号、会话 ID、是否已提交、结果原因和真实出站消息 ID（取得时填写）。后端按设备凭证查回原动作，再核对账号、会话和消息 ID。一个真实出站消息只生成一条聊天记录。回执先到时保留核对状态，出站记录到达后再确认。位置消息的真机类型尚待识别，普通「[媒体]」不能作为位置卡回执。

| 阶段 | 依据 | 网页显示 |
| --- | --- | --- |
| 配置保存 | 岗位面试点保存成功 | 已保存，可查看账号核验状态 |
| 生成动作 | 后端确认本轮面试点并生成 `action_id` | 已选面试点，等待 Windows |
| 未提交 | Windows 确认零次提交并返回具体原因 | 未发送，例如收藏重名、搜不到、账号不符 |
| 提交结果不明 | Windows 执行过提交，但暂时无法核对真实位置消息 | 待核对，可查看原因 |
| 发送已核对 | 设备回执与同账号、同会话的真实出站位置消息吻合 | 已发送，聊天记录显示位置消息 |
| 对方收到 | 测试联系人确认收到并打开正确地图点 | 手测记录单独确认 |

首轮拿到真机结果后，再按「一个地点、多个地点未选、错字、重名、账号切换、接管、提交后断网、回执重放」验证。Dify 和 Agent 各完成一轮从问定位到对方打开地图的完整测试，其中 Agent 需覆盖直接问答和启用画布的路径。

### 离线匹配程序

匹配程序通过标准输入接收 JSON，只处理调用方提供的结果。以下账号标识和结果均为演示数据，录入实际结果时账号应使用稳定 ID，例如设备绑定的企微账号 ID。`complete` 表示测试人员或后续客户端已经确认结果完整。

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
@'
{
  "expected_account_id": "test-account",
  "favorite_title": "广汽本田龙华店",
  "snapshot": {
    "account_id": "test-account",
    "complete": true,
    "items": [
      { "kind": "other", "title": "广汽本田龙华店" },
      { "kind": "location", "title": "广汽本田龙华店", "address": "深圳市龙华区民治街道龙屋工业区7栋" }
    ]
  }
}
'@ | node scripts/check-wecom-favorite-location.mjs
```

`matched` 表示唯一命中，`not_found` 表示没有同名位置卡，`ambiguous` 表示同名位置卡超过一张，`account_mismatch` 表示当前账号不符，`incomplete_results` 表示搜索结果不完整，`invalid_input` 表示输入无法核对。`matched` 仅验证匹配规则，发送和对方收到各自单独核对。
