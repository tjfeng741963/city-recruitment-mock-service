### 2.2 Windows 客户端代码

仓库中已经有以下流程执行能力：

- `agent/flow_state.py`：SQLite 流程游标、会话状态、发件箱和复聊状态。
- `agent/autopilot.py`：按流程运行、等待闸门、断线恢复、状态对账和复聊调度。
- `agent/brain.py`：读取流程、上报状态、传递已发送节点摘要。
- `agent/reply_store.py`：保留消息发送状态和失败记录。

流程语义已经实现：

- 首次进入只跑流程，不在同一轮再调用普通 chat。
- `await_reply=1` 的节点发送完成后停止，等待客户回复。
- 客户回复后按关键词边或 `any_reply` 边推进。
- `followup` 复聊节点最多发送一次。
- 发送失败、回读不确定、目标会话不明确时进入 `held`，不自动重发。
- 客户端重启时优先恢复游标，不按节点序号盲目重发。
- 北京时间 21:00–09:00 不主动复聊。

### 第二步：备份 Windows 客户端

在升级 Windows 客户端前：

1. 确认只有一个 sender/autopilot 进程。
2. 停止自动回复任务，避免升级过程中发送。
3. 备份 `C:\agent` 程序和配置。
4. 备份 `reply_log.db`、`.greeted.json`、`report_state` 和 `state` 目录。
5. 企微保持登录，远程桌面保持连接且不要锁屏。

不要删除历史账本、不要清空 `.greeted.json`、不要使用批量重试去“制造新客户”。

### 第三步：升级非动作层客户端

只同步经过核对的非动作层文件：

```text
agent/autopilot.py
agent/brain.py
agent/flow_state.py
agent/reply_store.py
```

升级后先保持流程停用，不要马上恢复对外自动发送。启动后检查日志中是否成功读取 flow 配置、是否成功心跳和上报状态。

### 第四步：创建停用测试流程

建议先为一个专用测试岗位创建以下流程，工资和地点必须来自该岗位实际字段：

```text
qualify：招聘要求
  └─ await_reply=true
      └─ any_reply → wage

wage：工资和班次
  └─ await_reply=true
      ├─ timeout → wage_followup
      └─ any_reply → work_place

wage_followup：一次性复聊
  └─ 发送一次后结束

work_place：工作地点和工作内容
  └─ await_reply=true
      └─ any_reply → end

end：结束
```

测试阶段建议把等待时间设为 1–2 分钟，正式流程再改回业务要求的等待时间。复聊测试要避开北京时间 21:00–09:00 静默时段。

### 第五步：使用专用测试微信验收

Daylan 已经存在历史会话，不能用来验证“首次进入流程”。需要同事提供一个从未添加过当前企微的专用测试微信。

验收记录至少包含：

| 场景 | 预期 | 实际 | 结果 |
|---|---|---|---|
| 首次触发 | 只发送 `qualify`，不调用普通 chat |  |  |
| 客户回复 | 只进入 `wage`，不重复 `qualify` |  |  |
| 超时 | 只发送一次 `wage_followup` |  |  |
| 复聊后无回复 | 进入 `expired`，不再发送 |  |  |
| 重启 | 已确认成功的消息不重复 |  |  |
| 发送失败 | 进入 `held`，不自动重发 |  |  |
| 正常追问 | 流程结束后进入普通知识库问答 |  |  |
| 岗位归属 | 回复只使用当前工厂和岗位事实 |  |  |

验收时要区分：好友事件采集时间、客户端轮询时间、发送器耗时、消息实际显示时间。配置里的 `delay_ms=1000` 不能承诺客户一定每秒收到一条。

### 第六步：通过后再启用正式流程

只有在测试表全部通过后，才可以：

1. 按岗位事实整理正式节点文案。
2. 由管理员审核工资、地点、福利和面试要求。
3. 启用正式岗位流程。
4. 先观察日志和一两个测试会话，再扩大使用范围。

## 5. 交接时必须说明的风险

- 这是本地企微库读取和键鼠发送方案，没有接入企业微信官方客户联系 API。
- 设备显示 online 只代表心跳，不等于桌面一定可发送。
- `/flow/greet` 或流程接口返回成功，只代表拿到文案，不代表客户已经收到。
- 客户端发送动作文件属于冻结核心，任何改动都可能导致企微风控、隐藏窗口或重新扫码。
- 流程停用只阻止新流程；已经开始的会话使用自己的流程快照。
- 旧深圳内容保留在历史会话中，不要直接删除或覆盖历史记录。
- 不能通过清库、删除状态或批量重试来掩盖发送失败。

## 6. 回滚方法

### 后端回滚

后端问题使用 Git revert，推送 `main` 触发流水线部署旧行为。禁止 force push 或直接改写远程历史。

### Windows 回滚

1. 停止唯一 sender。
2. 保留新旧 `reply_log.db`、`flow_state.db` 和日志。
3. 从升级前备份恢复客户端文件。
4. 确认旧客户端不再读取新的流程状态后，才允许恢复运行。

不要直接把旧客户端覆盖回去后立即启动，因为旧客户端不认识新的流程游标和状态文件。
