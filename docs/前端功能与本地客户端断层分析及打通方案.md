# 前端功能与本地客户端断层分析及打通方案

> 日期：2026-11-08
> 问题：网页给用户提供了一堆功能，改完之后本地客户端没反应，两边像两套系统。
> 结论：**接口层几乎全实现了，但配置没有下发通道**。前端写的是「设备配置」，客户端读的是「本地 config.json」，中间断了。

---

## 一、先看数据：接口都在，但没人用

### 1.1 前端调用 65 个接口

从构建产物 `public/assets/*.js` 里提取出全部 API 路径，共 **65 个**，覆盖：

```
城市 / 工厂 / 岗位 / 节假日 / 城市链接 / 招聘员
知识库 / 未知问题 / 候选人 / 会话 / 设备 / 规则 / 评估
激活模块（策略/话术/设备/看板）
导入导出 / 报表 / 设置
```

### 1.2 后端声明了 114 个路由

`src/` 下能匹配到 **114 个** `/api/v1/*` 声明。

**对比结论：前端调用的 65 个里，只有 1 个后端没实现**

```
/api/v1/unknown-questions     ← 唯一缺失
```

**所以「接口没实现」不是主要问题。**

### 1.3 但本地客户端只调用 7 个接口

`agent/client.py` 和 `agent/brain.py` 里全部的服务端调用：

```
POST /api/v1/bridge/devices/{code}/heartbeat    心跳
POST /api/v1/bridge/devices/{code}/inbound      消息上报
POST /api/v1/bridge/devices/{code}/claim        领取人工指令
POST /api/v1/bridge/devices/{code}/receipts     回执
POST /api/v1/agent/ingest                       会话同步（8090）
POST /api/v1/agent/commands/{id}/ack            送达确认（8090）
POST /api/v1/kb/answer                          知识库取回复（8090）
```

**前端 65 个，客户端用 7 个，重合的只有「知识库取回复」这一条。**

---

## 二、真正的断层在哪

### 2.1 前端改的设置，客户端根本不读

用户在网页「坐席设备」里能配这些：

| 前端字段 | 后端存哪 | 客户端读不读 |
|---|---|---|
| 合并等待（多消息合并秒数） | `agent_devices.data_json` | ❌ **不读**，用的是 `autopilot.py` 里的 `DEFAULTS` |
| 合并重问 | 同上 | ❌ 不读 |
| 启用追问 / 超时间隔 / 最大次数 | 同上 | ❌ 不读 |
| 静默时段（只收不回） | 同上 | ❌ 不读 |
| 事件检测关键词（不符合/邀约/签到） | 同上 | ❌ 不读，用的是 `response-serializers.ts` 里的默认值 |
| 面试提醒规则 | 同上 | ❌ 不读 |
| Dify URL / Key | 同上 | ❌ 不读（走的是知识库，不走 Dify） |
| 分配账号 | 同上 | ❌ 不读 |

**客户端所有这些行为，硬编码在本地的 `autopilot.py` 常量和 `config.json` 里。**

具体证据：

```
grep -rn "followup\|reminder-config\|agent-rules" agent/*.py   → 0 命中
```

客户端**一行代码都没有**去拉这些配置。

### 2.2 反过来，客户端的行为用户在网页上改不了

| 客户端行为 | 现在怎么改 | 用户在网页能改吗 |
|---|---|---|
| 回复哪些会话（`target`） | 改 `config.json` 再重启 | ❌ |
| 首次/后续回复词（`reply_first`/`reply_next`） | 同上 | ❌ |
| 冷却时间（`cooldown`） | 同上 | ❌ |
| 发送间隔（`interval`） | 同上 | ❌ |
| 回补历史消息的范围 | 同上 | ❌ |

**结果是：改一个冷却时间，要跑到客户电脑上改文件重启。**

### 2.3 知识库是唯一打通的一条路

```
前端改知识库 → 存 PostgreSQL（8090）→ 客户端调 /api/v1/kb/answer → 拿到回复
```

这条链路是通的，所以「改知识库能生效」。**其他所有设置都没有这条路。**

### 2.4 结构性原因

```
┌─────────────────┐        ┌──────────────┐        ┌──────────────┐
│  网页（前端）    │───────→│  服务器       │   ✗    │  本地客户端   │
│  改设置、看数据  │        │  存所有配置   │        │ 读 config.json│
└─────────────────┘        └──────────────┘        └──────────────┘
                                    ↑                      ↑
                              用户以为改这里          实际读的是这里
```

**缺的就是右上角那条边：配置下发通道。**

---

## 三、为什么会出现这个断层

不是设计失误，是演进路径造成的：

1. 项目初期是**复刻目标站**，前端是照抄来的产物，后端照着契约实现
2. 客户端（`agent/`）是**另一条独立路线**，为「读企微本地库 + 键鼠发送」而生
3. 两条线各自跑通，但**中间的配置通道从来没设计过**

`docs/开发路线-双后端与知识库下沉.md` 里写过「知识库下沉」，但只下沉了**回复内容**，没有下沉**行为配置**。

---

## 四、打通方案

### 4.1 核心思路：一次性拉取 + 版本比对

```
客户端启动 → GET /api/v1/bridge/devices/{code}/config   ← 新增
           → 本地缓存，作为运行时配置
           → 每轮心跳比对 version，有变化就重拉
网页改设置 → 服务器更新 data_json → version+1
          → 客户端下次心跳拿到新 version → 重拉配置
```

**为什么不用 SSE 推送**：客户端已经在轮询心跳（30 秒），复用同一条链路最省事，也不需要新增长连接。

### 4.2 需要新增的接口

| 接口 | 作用 |
|---|---|
| `GET /api/v1/bridge/devices/{code}/config` | 返回该设备的运行配置（含 `version`） |

配置内容从已有的 `agent_devices.data_json` 里挑，**不改表结构**。

### 4.3 配置结构

```json
{
  "version": 7,
  "target": "all",
  "cooldown_seconds": 8,
  "interval_seconds": 30,
  "reply_first": "1",
  "reply_next": "233",
  "merge_delay_seconds": 0,
  "merge_requery": false,
  "timeout": {
    "enabled": true,
    "interval_seconds": 300,
    "max_count": 3,
    "scripts": ["你好，还在吗？"]
  },
  "quiet_hours": { "enabled": false, "start": "23:00", "end": "08:00" },
  "event_rules": [],
  "reminder": { "enabled": false, "rules": [] }
}
```

### 4.4 客户端改造

**原则：服务器配置优先，本地 config.json 兜底。**

```python
# 启动时
remote = fetch_device_config(bridge)      # 拿不到就用本地
cfg = merge_config(remote, local_cfg)

# 每轮心跳
if heartbeat.get("config_version") != local_version:
    cfg = merge_config(fetch_device_config(bridge), local_cfg)
```

| 文件 | 改动 |
|---|---|
| `agent/client.py` | 加 `fetch_config()` |
| `agent/autopilot.py` | `load_config()` 后合并远端配置；心跳比对 version |
| `src/modules/messaging/device-bridge.routes.ts` | 新增 `GET .../config` |
| `src/modules/messaging/device-bridge.ts` | 加 `configVersion(code)` |

**不需要改 `send.py`**——动作序列保持冻结。

### 4.5 分阶段落地

| 阶段 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| **一期** | `target` / `cooldown` / `interval` 下发 | 2 天 | 网页能控制「回哪些会话、多快回」 |
| **二期** | 合并、追问、静默时段下发 | 3 天 | 网页上那些开关真正生效 |
| **三期** | 事件检测关键词下发 | 2 天 | 邀约/签到判定跟业务同步，不用改代码 |
| **四期** | 客户端状态回传（存活时长、失败次数、窗口可见性） | 2 天 | 排查从「远程连进去」变「看网页」 |

## 五、顺带解决「本地软件不稳定」

### 5.1 不稳定：四个已知根因

| 根因 | 现状 | 解法 |
|---|---|---|
| 抢前台失败 | 用户在用电脑就失败 | 专用机器/虚拟机（见 `自动化运行方式与前台独占问题.md`） |
| 输入框焦点丢失 | ✅ 已修（`apply_click_input` + 候选点重试） | — |
| 发送假成功 | ✅ 已修（`verify_db=True` + `expect_id`） | — |
| 进程崩了没人管 | ❌ 没有 watchdog | 见 `运维压力与无人值守改造清单.md` |

### 5.2 容易被逆向：本地代码本来就不该有秘密

| 资产 | 在哪 | 客户能否拿到 |
|---|---|---|
| 知识库内容 | 服务器 | ❌ |
| 业务判断逻辑 | 服务器 | ❌ |
| 历史会话/线索 | 服务器 | ❌ |
| 解密与键鼠代码 | 本地 | ⚠️ 来自 MIT 开源项目，本来就公开 |

**打通配置通道同时也在解决「逆向价值」问题**——客户端里越多逻辑搬回服务器，本地代码就越没有偷的价值。

---

## 六、优先级建议

如果只能做一件事：**做 4.5 的一期**（`target` / `cooldown` / `interval` 下发）。

理由：这三个是**最高频的调整需求**。2026-11-08 为了让真实客户能收到回复，`target` 从 `Garbo_C` 改成 `all`，靠的是改 `config.json` 重启——**如果客户有 10 台机器，就是 10 次人工**。

做完一期，这类调整在网页上点一下就行。
