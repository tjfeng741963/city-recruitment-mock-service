# 客户聊天记录补录说明

> 给运营/客户：把历史聊天记录导成规定格式，交给补录脚本抽成候选人档案。
> 脚本只补录**已存在**的会话；系统里已有人工填过的字段不会被覆盖。

## 1. 格式要求（txt 版）

- 会话之间用一行 `=====`（至少 4 个等号）分隔。
- 每个会话开头写头部字段（冒号全半角都行）：
  - `设备:` 设备号，如 `pc-win-01`（可与脚本 `--device` 二选一）
  - `客户昵称:` 必填，和前端对话管理页显示的昵称一致
  - `时间:` 会话时间，如 `2026-11-10 10:20`
- 正文一句一行，**角色前缀必填**：`客户:` 或 `运营:`（写 `我:` 会按客户算，`顾问:` 按运营算）。
- 看不出答案的（客户没说姓名/电话等）不用编，直接留空或写「没说」——脚本抽不到就跳过，不会瞎填。
- 没有客户发言、或漏写「客户昵称」的块会被脚本跳过并在结尾列出，改好再跑一次即可。

参考模板：`backend/scripts/backfill_template.txt`（含一个只有部分字段的示例会话）。

## 2. Excel 版式约定

用 Excel 收集时按三列排版，导出/另存为 txt 前保持这个顺序：

| 列名 | 含义 |
|---|---|
| 会话编号 | 同一个会话的所有行填同一个编号（如 `1`、`2`） |
| 角色 | 只填 `客户` 或 `运营` |
| 内容 | 消息原文，一句一格 |

另存为 txt 后，请按第 1 节补上每个会话的 `=====`、`设备:`、`客户昵称:`、`时间:` 头部（会话编号即会话块顺序）。

## 3. 运营操作步骤

在 `backend/` 目录下执行：

```bash
# 第一步：dry-run（默认）。只打印每个会话将推送的键与值，不写库
uv run python -m scripts.backfill_profiles --input 记录.txt

# 第二步：确认输出没问题后真正写库
uv run python -m scripts.backfill_profiles --input 记录.txt --commit

# 可选：启用 LLM 补抽（DeepSeek，能抽出确定性正则漏掉的城市/性别/岗位/备注）
uv run python -m scripts.backfill_profiles --input 记录.txt --commit --llm

# 块内没写「设备:」时统一指定设备号
uv run python -m scripts.backfill_profiles --input 记录.txt --commit --device pc-win-01
```

行为说明：

- **不覆盖人工值**：推送前脚本先查系统现状，已非空的字段（姓名、电话等）自动从推送体剔除。
- **幂等**：成功过的会话记入 `logs/backfill_state.json`（按「昵称+首条客户消息」指纹），重跑自动跳过；想强制重推就删掉对应指纹条目。
- **404 处理**：定位不到的会话（昵称/会话ID 对不上）只进失败清单，不会新建会话——先在前端对话页确认客户，找到会话ID 后在块头加 `会话ID:` 再重跑。
- **不推进状态机**：补录只补档案字段，不改变会话的流程阶段。

## 4. 脚本依赖的环境变量

| 变量 | 必填 | 说明 |
|---|---|---|
| `FLOW_PROFILE_TOKEN` | --commit 需要 | 与 4222 的 `REA_PROFILE_TOKEN` 同值（X-Profile-Token） |
| `FLOW_PROFILE_URL` | 否 | 4222 地址，默认 `http://127.0.0.1:4222/api/v1/agent/profile` |
| `APP_LLM_API_KEY` / `APP_LLM_BASE_URL` / `APP_LLM_MODEL` | 仅 --llm | 与 8090 主服务共用一套 LLM 配置（OpenAI 协议中转站） |
