# 谈单线索闭环 · 产品视角

> 前提：1–3 个顾问，客户都在微信里，人最终要**到厂**。系统现在产出的是一份 stage 字段，这是数据，不是工作。

## 一句话结论

**这套系统的价值不是"自动判断谈到哪一步"，而是"每天早上告诉顾问今天要接谁、昨天谁还没核实"。**
所以 `stage` 只存人和客户**确认过的事实**，模型只负责提出"该问一句"的疑问，不能替顾问下结论。

## 一、第一屏应该是什么

现在只有 JSON + `by_stage` 计数，不够。`by_stage.booked = 37` 这个数字对顾问没有任何操作含义——
他不知道 37 个人里今天来几个、几点来、去哪个厂、谁去接。

第一屏不做"线索列表"，做**今日待办**（打开就是今天，不需要选日期）：

```
┌ 今天要接 6 人 · 已到 2 · 待核实 3 · 新线索 11 ──────────┐
│ 09:00  张三    番禺立信  普工   [已到] [改期] [不来]      │
│ 待定   李四    番禺立信  普工   ⚠钟点未定  [已到] …       │
│ 13:30  王五    增城捷普  包装   [已到] [改期] [不来]      │
├ 待核实（约的时间已过，未确认）──────────────────────────┤
│ 昨天 09:00  赵六  立信  → [到了] [没来] [改到__]          │
├ 该催一句（booked/intent 超 24h 无消息）──────────────────┤
│ 孙七  昨天问过工价，再没回  → [发话术] [放弃]             │
└──────────────────────────────────────────────────────────┘
```

- **谁看**：当班顾问（手机），默认只看自己名下的；老板切"全部"。
- **看什么**：按 **约面时间排序的、今天要发生的事**，不是按 `updated_at`。时间未定的排最前（最需要打电话）。
- **点什么**：每行三个按钮，一屏内解决，不跳详情页。
- 列表页（全部线索、按 stage 筛）保留，但它是**第二屏**，查账用，不是干活用。

## 二、人工确认：一屏点名

到面 / 爽约 / 入职 / 改期这四件事客户不会在微信里说，必须人工。但"必须人工"不等于"必须填表单"。

**主交互 = 早上点名（roll call）**：
顾问在厂门口，打开"今早到厂名单"，一屏列出今天所有约面的人，**默认全部勾选"到"，点掉没来的，一次提交**。

为什么这样最省力：
1. 业务分布是"到的人多、没来的人少"，默认选中符合多数，操作量 = 没来的人数；
2. 顾问此刻**就在现场**，有事实依据，不是猜；
3. 一屏 8–10 人，10 秒点完，没有弹窗、没有下拉、没有备注必填；
4. 提交动作本身就是"我确认过了"，责任清晰。

配套三条（省力但不能省真相）：
- **不点就不算**：没提交的人保持"待核实"，**绝不默认算到面**，第二天进"该补的账"。
- **客户自带证据**：客户发"我到了"/定位 → 卡片自动浮到顶部，一键确认；客户说"今天来不了" → 一键"改期/放弃"。
- **入职单独一个按钮**，且在"到面"之后才出现（入职常有延迟 1–3 天，别逼顾问当天点）。

## 三、自动推断怎么才不误伤

误伤有两个方向，都比"漏记"贵：

**① 把没来的人判成爽约（冤枉人）**——文档里已改成 `pending`，方向对，但要再加两条：
- **先问再判**：到了宽限期，系统只做一件事——**自动发一句"今天还过来吗？需要我帮你改时间吗"**，同时卡片变"待核实"。
  客户的回复是最强证据，一句"明天吧"就能自动救回成 `booked`。
- **不允许自动写终态**：`no_show` 只能由人点。定时任务永远只能产出"疑问"，不能产出"结论"。

**② 把没约上的人算成约面（虚高，老板据此加投放会亏钱）**——比 ① 更隐蔽：
- 现在 prompt 规定"只有日期没钟点就填 09:00"，这会让 `09:00` 变成假事实，顾问 9 点没见到人就以为客户爽约。
  **产品要求区分"日期已定"和"钟点已定"**：钟点未定的显示"待定"，不显示 09:00，也不按 09:00 触发核实（改为当天 18:00 才进待核实）。
- 每条自动变更必须能**一键看依据**：卡片上直接带判定理由 + 触发它的那两句原话。顾问 3 秒内能判真假，比任何模型调参都有效。

**统计口径必须分账**：`待核实` 单独一列，不并进到面也不并进爽约。
到面率 = 已确认到面 ÷（已确认到面 + 已确认爽约），否则 pending 会把分母搞脏，日报天天变。

## 四、字段：现在缺的（按"缺了就干不了活"排序）

| 优先级 | 字段 | 缺了的后果 |
|---|---|---|
| P0 | `owner_user_id` 归属顾问 | 3 个人谁跟谁说不清，撞单、漏跟 |
| P0 | `source` 渠道（抖音/58/老乡介绍/地推/自然） | **投放效果无法归因，老板唯一的决策依据没了** |
| P0 | `phone` 手机号 | 企微 ID 打不了电话，客户不看到厂就联系不上 |
| P0 | `real_name` 真实姓名 | 昵称多是"青冥""随缘"，到厂点名对不上人 |
| P1 | `job_id`（关联知识库岗位） | `job_title` 是自由文本，"立信电子厂"能有 5 种写法，按厂统计全废 |
| P1 | `shift_ok` 能否两班倒 / `has_id` 证件是否齐 / `need_dorm` 是否住宿 | 这三条是**白跑的头号原因**，现场才发现最伤客户 |
| P1 | `deposit_state` 押金/体检费（未提/已告知/已收/免） | 劳务纠纷源头，出事时没有任何记录 |
| P1 | `next_follow_at` + `next_action` | 顾问真正需要的是"下一步做什么"，不是"现在什么状态" |
| P2 | `pickup` 接人方式（自到厂/集合点） | 早上不知道该去哪等 |
| P2 | `lost_reason` 结构化流失原因 | "太远/工价低/找到别的厂"没法反哺话术和选品 |

原则：**这 10 个字段顾问一个都不用手动填**。能抽的让 LLM 抽；抽不到的（渠道、归属、手机号）在加微信那一步一次性带上。

## 五、日报：老板看 4 个数 + 3 个率 + 1 笔账

每天 9:00 一条（企业微信推给老板，不邮件、不打开后台）：

1. **4 个数**：新线索 / 今日约面 / 今日到面 / 今日入职
2. **3 个率**（都按**渠道**和**顾问**各拆一列，这是判断"投放"和"话术"的唯一办法）：
   - 约面率 = 约面 ÷ 有效咨询（聊过工价的）
   - 到面率 = 到面 ÷（到面 + 爽约）
   - 爽约率
3. **1 笔账**：`昨日还有 N 单未核实`——逼着把数据补齐，否则所有率都是假的。
4. **对照组**：昨日 / 上周同一天，一行带过。绝对数没有比较就没意义。
5. **AI 可信度**：`自动判定被人工推翻 X 次 / 共 Y 次`。没有它，没人知道该不该信这张表，也没法判断 prompt 改动是变好还是变坏。

老板的真正问题只有两个：**钱投在哪个渠道划算**（分渠道约面率+到面率）、**哪套话术/哪个顾问更能把人约到厂**（分顾问约面率）。日报只回答这两个就够。

## 六、我不建议做的事

- **不做自动爽约判定 / 自动改终态**：一次冤枉就是一次投诉，且会污染整月统计。
- **不做全字段 CRM 表单**：顾问在手机上不会填 12 个框。字段靠抽，人手只点 3 个按钮。
- **不做 AI 意向度排行榜**：`intent 1–5` 现在不可校准，排出来的顺序会引导顾问跟错人，比没有更糟。
- **不做自动催问机器人**（除"到点确认"那一句）：高频追问在企微里容易引起反感甚至投诉，人工一句更贵但更有效。
- **不做线索公海/自动分配规则**：1–3 个人，口头分比规则快，规则只会制造扯皮。
- **不做第二个 IM 后台**：聊天已经在企微，这里只做"待办 + 确认"，别做成聊天工具。
- **不做漏斗大屏和复杂 BI**：没人每天看大屏，日报一条消息就够。
- **不把 `dormant` / `unsuitable` 做成自动终态**：沉默 7 天不代表放弃，客户可能下周才回来。
- **不做自动建"入职"**：涉及工资结算，错一条赔一笔。

## 七、和技术实现最容易冲突的三处

1. **stage 该不该存"推测"**：技术上最省事是定时任务直接写 `no_show`，状态机干净、查询简单。
   产品上要求 **stage 只存事实，推测放 `pending_confirm` + 理由字段**，代价是列表要联合判断两处。
2. **`interview_at` 用 09:00 兜底**：对 LLM 和对存储都方便（一个字段搞定非空），
   产品上必须拆出"钟点是否确定"，否则会制造假时间并触发假核实。
3. **字段来源**：技术倾向全部交给 LLM 抽取（省一个录入入口），
   但渠道、归属、手机号**对话里根本不存在**，必须有一条人工/系统写入路径——这是绕不开的额外入口。
