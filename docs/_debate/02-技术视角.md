# 谈单线索闭环 · 技术视角

> 只谈怎么落地，不写代码。依据 `docs/谈单状态机与面试记录设计.md`、`backend/app/{models_lead,api_lead,main,settings}.py`、
> `services/lead_extract.py`、`workers/{outbox,wecom_sync}.py`、`docs/_debate/01-产品视角.md`。

## 一句话结论

定时推断做成 `workers/lead_sweep.py` 里的第三个 asyncio 任务，只改 `pending_confirm` 和入队一句询问、**永不写 stage 终态**；
`interview_at` 拆成「锚点 + 精度」两列消灭 09:00 假时间；看板用后端直出的单页 HTML；所有 lead 写入走 `version` 条件更新，优先级 manual > sweep > llm。

## 一、定时推断落在哪

复用 `main.py:35-61` 的写法：lifespan 里第三个 `asyncio.create_task`，和 outbox、sync 并列，同一个 try/finally 里 cancel。

| 项 | 取值 |
|---|---|
| 文件 | `backend/app/workers/lead_sweep.py` |
| 函数 | `run_once(now=None)`（now 可注入，测试用）/ `run_forever(interval)` |
| 开关 | `APP_LEAD_WORKER`（默认 True）、`APP_LEAD_INTERVAL`（默认 300 秒） |
| 扫描条件 | `stage='booked' AND pending_confirm=0 AND check_at<=now`，`check_at` 建索引 |
| 间隔理由 | 业务时间精度是「分钟级」，5 分钟与 outbox 同量级；单轮命中通常不到 10 行 |

**不会抢锁，但必须守三条**：①每轮一个短 session，处理完立即 commit，绝不在事务里发 HTTP、调 LLM；②sweep 内零 LLM 调用，
判断全落在本表字段上；③建议在 `db.py` 的 connect 事件上加 `PRAGMA journal_mode=WAL` + `busy_timeout=5000`（aiosqlite 原生支持，不加依赖）。
现在没设，默认 rollback journal 下读事务会挡写——而 `observe()` 恰好是「读 lead → await LLM → 写」，这是**当前就该先修的锁风险**，比新加 worker 更要紧。

**多进程不靠「只起一个」**：sweep 每一步都是条件更新（`UPDATE ... WHERE id=? AND pending_confirm=0` 看 rowcount）或幂等入队
（`create_delivery` 的 `(conversation_id, idempotency_key)` 唯一约束），重复执行是 no-op。`APP_LEAD_WORKER` 只是运维开关，不承担正确性。
`dormant` 同理不自动落 stage，只在列表里算「最后消息距今 N 天」。

## 二、到面核实：完整链路

核心思路：booked 那一刻就把「什么时候该问」算成绝对时刻存下来（`check_at`），sweep 只做比较——不在 SQL 里做日期运算，SQLite 没有 interval。

1. **谁算**：LLM 判 booked（`normalize`）或人工标记 booked（`manual_update`）时调 `compute_check_at(interview_at, precision)` 写入 `check_at`。
   钟点已定 = `interview_at + 3h`，落在 22:00–08:00 的顺延到次日 09:00；钟点未定（`precision='day'`）= **当天 18:00**，不按 09:00 触发。
2. **谁触发**：`run_once()` 扫到后先抢占：`UPDATE leads SET pending_confirm=1, nudged_at=now WHERE id=? AND pending_confirm=0 AND stage='booked'`，
   rowcount=1 才继续；同时写 `LeadEvent(event_type='check_pending', source='system')`。
3. **发什么**：`create_delivery(conversation_id, key=f"lead-nudge:{lead_id}:{check_at}", content=模板, source="system")`，固定模板不过 LLM
   （「今天还过来吗？需要我帮你改个时间吗？」），不写厂名和时间，避免模型编错；文案走 `APP_LEAD_NUDGE_TEXT`。
4. **谁真正发**：后端只写 `deliveries`，**不碰企微**。agent 的 `GET /api/v1/agent/commands` 领走（`api_agent._pull_one` 已按 device_id +
   `channel_type='wxwork_local'` 过滤），凭证只在 agent 手里。这条线不能破，也不需要在后端加任何企微配置。
5. **客户回了**：「我到了」→ 抽取推 `interviewed`；「明天吧」→ 抽取产出 booked + 新 `interview_at`，`pending_confirm` 清 0、`check_at` 重算，
   天然救回；回别的 → 保持 pending，进待核实队列。
6. **客户不回**：**不做任何终态**。pending 保留，`nudged_at` 后 24h 在待办标「已问未回 N 小时」，48h 进日报「待补账」。`no_show` 只能人工点。
7. **两个兜底**：入队前校验会话的 `ChannelAccount.device_id` 非空且设备未 disabled，否则只写事件「无法送达」，不制造永远 queued 的僵尸投递；
   每轮把 key 前缀 `lead-nudge:` 且 `created_at < now-6h` 仍 queued 的投递 `mark(..., 'blocked', reason='过期未发出')`，防止 agent 隔夜上线半夜补发。

## 三、字段方案：`interview_at` 不再造假

| 字段 | 类型 | 含义与写法 |
|---|---|---|
| `interview_at` | DateTime（不变） | **锚点**。钟点确定=真实时刻；只有日期=当天本地 00:00，不再填 09:00 |
| `interview_precision` | String(8)，新增 | `minute` / `day`，默认 `day`（宁可保守） |
| `check_at` | DateTime，新增，索引 | 核实时点，booked 时一次算定，见 §二 |
| `nudged_at` | DateTime，新增 | 首次发问时刻，用于「只问一次」与 SLA |
| `version` | Integer，新增，默认 0 | 乐观锁，见 §五 |

- 写者只有三处：`lead_extract.normalize()`（LLM）、`api_lead.manual_update()`（人工）、`lead_sweep`（只碰 pending/nudged，不碰 stage 和时间）。
- `normalize()` 改两处：删掉「知道日期填 09:00」，改为输出 `interview_precision`；booked 的校验从「有 interview_at」变成「有 interview_at 且有 precision」。
- `build_messages()` 的输出契约加 `interview_precision`，并写明「只知道日期就填 day，不要自己编钟点」。
- 展示：`precision='day'` 只显示 `11-05 钟点未定`；排序仍按 `interview_at`（00:00），同一天 day 精度自然排前，正好符合「最该打电话的排最前」。
- 迁移：SQLite `ALTER TABLE leads ADD COLUMN ...`（带常量默认值合法，不用重建表）；存量行 precision 回填 `day`、`check_at` 回填 `interview_at+3h`，
  但**不补发任何消息**，历史数据不追溯。

## 四、看板放哪

| | A 后端单页 HTML | B React 管理台加页 | C 只出 API |
|---|---|---|---|
| 交付成本 | 低：一个 `HTMLResponse`，内联 CSS/JS，无构建 | 高：跨后端 + 构建 + 发版 | 最低 |
| 鉴权 | 同源，页面内 fetch 带 Bearer | 两套用户体系（8090 是 JWT，8080 是旧 Node） | 无 |
| 数据一致性 | 直连本库 | **不连本库**：`frontend/` 走 `VITE_LEGACY_ORIGIN` 指 8080，是另一套数据 | 直连 |
| 上线方式 | 重启生效 | `npm run build` + 静态托管，而 8090 不托管前端 | 无 |
| 手机可用 | 能（自己写响应式） | 能 | 不能 |

推荐 **A**。8090 是纯 API 这个前提不该为一块看板破掉；A 不是「托管前端工程」，只是后端自己的一个只读页，零构建、零跨域、零第二套鉴权。
B 的真正风险不是工时，是**它会把两套后端的数据混进一个界面**——顾问看到的数字和 8090 库对不上，比没有看板更糟；真要做 B，前提是管理台整体迁到 8090，那是另一个项目。
边界：P2 只做三件事——今日待办（按 `check_at` / `interview_at` 排）、待核实队列、三个按钮（到了 / 改期 / 不来）。不做漏斗大屏、不做聊天。
挂 `GET /api/v1/leads/board`，token 从 localStorage 读，没有就让人贴一次（登录接口给的就是 JWT），不新开一套鉴权。

## 五、幂等与并发

1. **`leads.version` 乐观锁**：所有写入 `UPDATE ... WHERE id=? AND version=?`，rowcount=0 重读一次再试，连输两次放弃并记日志。SQLite 单条 UPDATE 原子，
   够用，也不需要 `SELECT FOR UPDATE`（SQLite 没有）。
2. **LLM 期间不持事务**：`observe()` 现在是「读 lead → await extract → 写」，模型那几十秒一直占着读事务。改成三段：短事务取快照（stage/version/interview_at）
   → 无事务调模型 → 短事务条件写。这是并发正确性的前提，不是性能优化。
3. **优先级 manual > sweep > llm**：sweep 永不写 stage，天然不打架。LLM 落库前若 `updated_by='manual'` 且 `updated_at` 在 10 分钟内，直接丢弃本次结果，
   防止顾问刚点「到面」就被模型拉回 booked。
4. **事件去重**：`lead_events` 给 `(conversation_id, message_id)` 建 partial unique index（`WHERE message_id <> ''`）。SQLAlchemy 同时给 `sqlite_where=` 和
   `postgresql_where=` 即可，两边都支持，不用 `ON CONFLICT`。
5. **现有两条幂等路径**：observe 靠 `last_message_id` 短路，sweep 靠 `create_delivery` 的唯一约束。agent 上报只写 messages/conversations（`agent_ingest`），
   不写 leads——真正的并发面只有 observe / manual / sweep 三方，被第 1、3 条覆盖。

## 六、我不同意的产品主张

**先正面回应 01 第七节的三个冲突点**：①stage 存不存推测——同意产品，stage 只存事实，列表多读两个字段的代价我认；②09:00 兜底——同意，
且比他要求的更彻底，连「日期」都不塞进时刻字段（§三）；③字段来源——只同意一半，见下面第 2 条。

1. **「定时任务只产出疑问，不产出结论」——他自己也产出了结论。** `pending_confirm=1` 就是一句判断：这人现在不该算到面。它比 `no_show` 便宜，不等于中立。
   我会照做，但 UI 上写成「超时未确认」而不是「待核实」，并给 pending 加 48 小时强制结账，否则 pending 会变黑洞，到面率永远算不出来。
2. **「这 10 个字段顾问一个都不用手动填」——`source`、`owner`、`phone` 抽不出来也带不进来。** 渠道和归属不在对话里，手机号只在客户主动发时才有；
   「加微信那一步一次性带上」在系统里没有落点：加好友发生在客户自己的微信里，后端没有通讯录权限，agent 的 `wecom_io_core` 也不许加任何动作。
   所以这三个字段 P2 只能是空的，日报不许拿它分组；要填只能加一个三字段小表单——那是新入口，需要产品签字。
3. **「到面率 = 到面 ÷（到面 + 爽约）」在小样本下会骗人。** 一天 6 单，分母 4 还是 6 差 50%，而且把 pending 排除在分母外，等于专挑「已核实清楚的人」算比例。
   日报只报绝对数 + 未核实数；率放月度，且分母 < 30 时不展示。
4. **「一屏点名、默认全部勾选到」和第 47 行「不点就不算」自相矛盾。** 默认勾选等于批量写事实，漏点一个人就是一次误判到面，方向恰好是他最担心的
   「把没来的人算成到面」。改成默认全不勾，顶部放一个「全选到」，提交时若有人未操作，弹一次「3 人未标记，按未核实提交？」。
5. **「不做自动催问，只发到点那一句」——技术上保证不了「只发一句」就够了。** 问了不回、或回了「明天吧」但抽取置信度 <0.65 没落库，这条线索就停在 pending
   里没人管。所以除了发给客户的那一句，必须有一条**只给顾问、不发给客户**的待办推送（页面徽标 + 日报「待补账」），否则「先问再判」只会问、不会判。
