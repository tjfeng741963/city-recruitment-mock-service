# 遗留问题：换账号断线与扫码后的二次验证

记录日期：2026-11-15。本文记录两个**已定位根因、尚未修复**的运维阻塞，都发生在云端企微设备上。

前一个问题有完整的代码复现证据；后一个只确认了「缺口存在」，具体窗口形态还需要在真机上抓一次。

---

## 一、云端换企微账号 → 网页版断线、消息不同步

### 1.1 现象

在云端那台机器上把企微换成另一个账号后：

- 企微本身正常收发消息；
- 后台网页版显示设备掉线；
- 网页收不到新消息，也无法下发。

客户端日志只有一行软失败，容易被忽略：

```
[桥接] 失败（忽略，不影响主心跳）：HTTP 409 Device is bound to a different account
```

### 1.2 根因

`bridge_devices.account_id` 记的是设备**第一次心跳时登录的企微账号**，之后账号一变就拒绝。

[device-bridge.ts:92](../src/modules/messaging/device-bridge.ts#L92)：

```js
if (accountId && device.account_id && accountId !== device.account_id)
  throw new BridgeError("Device is bound to a different account");
```

`BridgeError` 默认 `statusCode = 409`。而抛错发生在 UPDATE 之前，所以**心跳时间戳完全不更新**。

### 1.3 完整故障链（已用内存库实测复现）

探针脚本：`过程文件/probe-account-switch.ts`（未提交）

```
1. 换账号前：旧账号 A 心跳 online
   OK    -> account_id=account-A  state=online  heartbeat_at=1700000000000

2. 云端换成账号 B 后：新账号 B 心跳 online
   抛错  -> Device is bound to a different account (409)
   库内  -> account_id=account-A  state=online  heartbeat_at=1700000000000  ← 冻住

3. 70 秒后（超过 60s 掉线阈值）
   生效状态=offline                                    ← 自动折算掉线

4. 上报入站消息前的 online 门禁
   抛错  -> Device must be online

--- 补救尝试 1：重新 pair 换发 token ---
   pair 后 account_id=account-A  state=offline  ← 账号没被清掉！
   用新 token + 新账号 B 心跳
   抛错  -> Device is bound to a different account (409)   ← 换 token 无效

--- 补救尝试 2：手工清空 account_id ---
   清空后用账号 B 心跳
   OK    -> account_id=account-B  state=online             ← 恢复
```

**要点**：`pair()`（[device-bridge.ts:31](../src/modules/messaging/device-bridge.ts#L31)）只更新 `token_hash / state / heartbeat_at`，**不重置 `account_id`**。所以「重新注册」「重新配对」这个常规自救手段在这里失效。

### 1.4 为什么现场看不出来

[autopilot.py](../agent/autopilot.py) 的心跳是软失败：

```python
except Exception as exc:
    log(f"[桥接] 失败（忽略，不影响主心跳）：{describe_error(exc)}")
```

进程照常跑、企微照常收发、日志只有一行「失败（忽略）」。所以表现为「云端一切正常，只有网页掉线」。

### 1.5 立即恢复

清空 `account_id` 即可，客户端下一轮心跳（≤30 秒）会用新账号重新绑定：

```sql
UPDATE bridge_devices SET account_id='' WHERE device_code='<设备码>';
```

### 1.6 这条守卫是有意的

它防的是**设备令牌泄露后被别的企微账号冒用**，把指令发到错误的号上。测试 [device-bridge.test.ts:70](../tests/device-bridge.test.ts#L70) 明确断言了 409，用例名写着「enforces per-device credentials and rejects switching the bound account」。

问题在于**没有给「合法换账号」留出口**——设计时假设一台设备永远一个号。

### 1.7 修复选项

| 方案 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| **A. 管理员解绑接口** | `POST /api/v1/bridge/devices/:code/unbind-account`，admin 权限，清空 `account_id` | 小：1 个路由 + 1 个测试 | 需要人工点一下，不能自愈 |
| **B. 换账号自动解绑** | 客户端带上新旧账号，服务端放行并记审计 | 中：客户端 + 服务端 | 削弱了守卫原本要防的事 |
| **C. pair 时清空** | `pair()` 顺带 `account_id=''` | 最小：1 行 | 能重新 pair 就能解绑；但 pair 需要 register key 或 admin，风险可控 |

**建议：先 A（可用逃生口），再做 C（让重新配对能自愈）。B 不建议。**

### 1.8 待决策

**换账号是偶发还是常态？**

- 偶发（几个月一次）：A 够用；
- 常态（按班次切换）：C 必须做，并且要重新评估「设备绑定账号」这个设计前提是否还成立。

## 二、扫完二维码还要输验证码，这个环节完全没有覆盖

### 2.1 现象

云端企微掉登录后，网页上出现二维码，用户扫码成功，**但登录并没有完成**——企微接着弹出验证码（短信/邮件确认），而这一步没有任何远程通道。

结果是：用户扫了码，网页仍显示等待，自动回复继续停摆。

### 2.2 现有实现只覆盖到「显示二维码」

[login_qr.py](../agent/login_qr.py) 的全部能力：

```
只找登录窗（WeChatLogin 类名）
  → PrintWindow 截图（近空图降级全屏 BitBlt）
  → PNG → base64 → 上传
  → 恢复登录后清掉服务端旧图
```

`_tick()` 的逻辑是**二元的**：`state != "login_required"` 就认为恢复了，否则继续推二维码。中间没有「已扫码、待验证」这个状态。

### 2.3 判定层也识别不了验证码

[autopilot.py:238](../agent/autopilot.py#L238) 的 `detect_wecom_state()`：

```python
if any(cls == "WeChatLogin" for cls, _visible in windows):  return "login_required"
if any(cls == "WeWorkWindow" and visible ...):              return "online"
```

判定表写在 [docs/_contract/设备心跳与看板契约.md](_contract/设备心跳与看板契约.md)，只有 `online / login_required / not_running / hidden / unknown` 五个状态，**没有验证码这一态**。

关键后果：**扫码成功后若弹出验证码窗口而登录窗仍未关闭，状态会一直停在 `login_required`**——和「还没扫码」完全无法区分。

### 2.4 缺口清单

| 缺什么 | 说明 |
| --- | --- |
| 状态 | `detect_wecom_state()` 没有「已扫码、待验证」这一态 |
| 截图 | 验证码窗口的窗口类名未知，`find_login_window()` 只认 `WeChatLogin` |
| 输入 | 没有任何把验证码回填到云端机器的通道 |
| 反馈 | 网页只有「有码 / 没码」，没有「扫码成功，请输入验证码」 |

### 2.5 已知的未知

**验证码窗口的窗口类名，我没有抓到过。** 这需要真机触发一次才能确定，不能凭猜写死——猜错的结果是截图抓到主界面，把聊天列表发到网页上。

同样不确定的还有：

- 验证码是短信、邮件，还是企微内确认？
- 验证码窗口是独立窗口还是嵌在 `WeChatLogin` 里？
- 有没有「无需验证」的账号白名单（常见于固定 IP / 可信设备）？

这三个答案决定实现方式完全不同。

### 2.6 可能的实现方向（未定）

**若验证码窗口是独立窗口**：

```
客户端额外抓验证码窗口 → 上传第二张图
  → 网页同时显示「二维码已扫」+ 验证码输入框
  → 用户输入 → 服务端下发指令 → 客户端粘贴到验证码框并回车
```

**若只是嵌在登录窗里的输入框**：

```
同一个截图里就有，网页显示整窗；
用户在网页输入验证码 → 下发 → 客户端键入
```

后一种更简单，但要先确认真实窗口结构。

无论哪种，都会用到键鼠注入——而 [AGENTS.md](../AGENTS.md) 明确规定 `agent/` 的动作层只能改三处（`autopilot.py` / `reply_store.py` / `brain.py`），`wecom_io_core/` 一个字节都不能动。**向验证码框输入属于新的动作，必须先证明「不加失败、加了成功」并走确认流程**，不能直接叠补丁。

### 2.7 与此前文档的关系

[扫码登录-实现范围与边界-20261115.md](扫码登录-实现范围与边界-20261115.md) 第 4.4 节写了「真实扫码登入未验证」，但**没有提到扫码后还有验证码**——当时的假设是「扫完就登上了」。本文补上这个缺口。

---

## 三、两件事的共同点

两个问题都源自同一个盲区：**只在「理想路径」上验证过**。

- 换账号：假设一台设备永远一个号 → 换号即死锁；
- 扫码：假设扫完就完成 → 二次验证即死锁。

两者都不是偶发 bug，是**状态机少了一个分支**。修复时应该先把状态补全，再谈怎么实现输入。
