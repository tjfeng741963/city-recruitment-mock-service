# 自动化运行方式与前台独占问题

> 日期：2026-11-07
> 起因：实机测试发现键鼠发送必须抢前台，导致「这台电脑只能给机器用，不能给人用」。
> 结论：现在的实现是**独占式自动化**；要真正无人值守，只有三条路，见第四节。

---

## 一、为什么必须抢前台

`agent/wecom_io_core/send.py` 的发送方式是**全局键盘事件**：

```
Ctrl+F 搜索会话名 → Ctrl+A/Ctrl+V 粘贴 → Enter 进会话
→ Ctrl+A/Delete 清空 → Ctrl+V 粘贴正文 → Ctrl+A/Ctrl+C 回读校验 → Enter 发送
```

Windows 的 `keybd_event` / `SendInput` 只会把按键送到**当前拥有焦点的窗口**。企业微信的聊天输入框是内嵌 Chromium 控件，用后台消息（`PostMessage`）灌不进去——这一点项目文档里已经付过代价：

> `docs/实施规划-Windows单机交付.md:20`
> 这条序列是上游逐条调过的（剪贴板占用、焦点丢失、窗口隐藏、首次按键被吞，四类问题各对应一处处理）。换任何"更简洁"的写法都会退回原状——本项目已经为此付出过两次代价。

所以：**抢前台不是实现偷懒，是这个技术路线的硬约束。**

### 后果

- 企业微信窗口必须可见、不能被最小化
- 运行期间不能锁屏
- 人在这台机器上工作时会被抢焦点

## 二、坐标与 DPI：两个必须分清的东西

实机排查时踩过一次坑，记下来避免后人重犯。

| 场景 | 是否需要坐标 | DPI 是否影响 |
|---|---|---|
| **产品发送路径**（`send.py`） | ❌ 全程键盘，零点击 | ❌ 不受影响 |
| **诊断/补丁脚本**（算点击点） | ✅ 需要 | ✅ **必须 `set_dpi_aware()`** |

实测数据（本机 200% 缩放）：

```
GetSystemMetrics(SM_CXSCREEN) = 1440 x 900     ← 逻辑像素
DwmGetWindowAttribute 窗口    = 2910 x 1300    ← 物理像素
截屏结果                      = 1455 x 650     ← 逻辑像素
```

`2910 ÷ 2 = 1455`，`1300 ÷ 2 = 650`。

**如果不声明 DPI 感知**，算出的物理坐标（如 y=1194）会被 `SetCursorPos` 当成逻辑坐标，实际落到屏幕外（屏幕只有 900 高），点击全部落空。

规则：
- 进程启动第一件事调用 `win.set_dpi_aware()`
- 所有坐标统一用**物理像素**（`find_window()` 经 DWM 返回的就是物理像素）
- 点击点用**窗口相对比例**表达，不用绝对坐标

## 三、本次修复：焦点没进输入框

### 现象

```
步骤1 已回车进入会话
步骤2 已清空输入框残留
本轮失败：输入框校验：焦点未落在输入框（Ctrl+C 未生效，剪贴板仍是哨兵）
```

### 原因

上游动作序列假设「回车进入会话后，焦点自动落在输入框」。**这个版本的企业微信不成立**——回车后焦点仍在搜索结果/消息列表，导致后续的 `Ctrl+V` 粘贴无处可去。

### 修法

在「进入会话」之后、粘贴之前，**显式点击聊天输入框**，并对候选点做重试：

```
候选点（窗口相对比例，按命中率排序）
  (0.52, 0.70)  (0.52, 0.66)  (0.52, 0.74)  (0.40, 0.70)
每个候选点：点击 → 粘贴 → 回读校验
  校验通过 → 继续发送
  校验失败 → 清空 → 换下一个点
```

回读校验沿用原有的哨兵法（`verify_input_box`），不新增键位。

## 四、要真正「后台无人值守」，只有三条路

### 方案 A：官方微信客服 API（唯一真·无人值守）

**已实现，未启用。** 代码是现成的：

```
src/modules/wecom/wecom-channel.ts:57    kf/send_msg     官方发送
src/modules/wecom/wecom-client.ts        token 刷新重试（40014/42001）
src/modules/wecom/wecom-store.ts         发件箱幂等 + 窗口校验
```

需要的环境变量（`src/modules/wecom/wecom-config.ts:10-11`）：

```
REA_WECOM_ENABLED=true
REA_WECOM_CORP_ID              企业ID
REA_WECOM_APP_SECRET           应用Secret
REA_WECOM_CALLBACK_TOKEN       回调Token
REA_WECOM_ENCODING_AES_KEY     回调加密Key
REA_WECOM_OPEN_KFID            客服账号ID
```

**硬限制**（代码里已实现）：

| 限制 | 代码位置 |
|---|---|
| 48 小时回复窗口 | `wecom-channel.ts` → `WeCom 48-hour reply window expired` |
| 单个窗口最多 5 条 | `WeCom five-message reply allowance exhausted` |
| 会话状态校验 | `kf/service_state/get` |
| 人工接管时禁止自动回复 | `Human takeover before WeCom send` |

**适用边界**：只适用于**微信客服入口**（客户从客服链接/二维码进来）。

> 微信客服和招聘员外部联系人私聊不是同一个通道。不要用 `kf/send_msg` 向已有招聘员好友会话发送消息。 —— `docs/企业微信API接入断点分析与实施方案.md`

### 方案 B：把机器和人分开（零代码改动）

| 做法 | 说明 |
|---|---|
| 专用电脑 / NUC | 一台小主机专跑企微 + 客户端 |
| 虚拟机 | VMware/Hyper-V 里跑 Windows，宿主机照常用 |
| 独立 Windows 会话 | 远程桌面连进去跑，前台互不干扰 |

自动化独占一台机器，人用另一台。今天就能用，不改代码。

### 方案 C：会话存档 + 侧边栏半自动

```
求职者私聊 → 会话内容存档 SDK（读）
           → 服务器解密、生成 AI 建议
           → 企微侧边栏 H5 展示
           → 招聘员点发送（ww.sendChatMessage）
```

AI 帮人写，人点发送。不抢前台、无风控风险，但需要人参与。

## 五、选型建议

| 业务入口 | 推荐方案 | 是否需要人 |
|---|---|---|
| 微信客服（客服链接/二维码） | **A** | 否 |
| 招聘员好友私聊，允许专用机器 | **B** + 现有键鼠自动化 | 否（机器上无人） |
| 招聘员好友私聊，要求同一台机器工作 | **C** | 是（人点发送） |

## 六、运维要点

- `autopilot.py --watch` 常驻；进程崩了不会自愈，需要 watchdog
- 企业微信窗口必须保持可见，最小化后发送会中止（`_wait_visible` 会拦住）
- 锁屏期间同样中止
- 发送失败会标记 `failed`，下一轮自动重试（最多 2 次整段重试）
- 失败原因在日志和网页的历史记录里都能看到
