# 技术方案：不抢前台 + 双端联动

> 日期：2026-11-13
> 起因：11-13 会议上客户提出竞品能做到「同一台电脑上网页端和企微端同时开着、同时可操作、AI 自动回、不抢前台」。
> 承接文档：`docs/自动化运行方式与前台独占问题.md`（那份讲清了「为什么现在必须抢前台」，这份讲「怎么才能不抢」）
> 会议纪要：`过程文件/meeting/会议纪要-20261113-ai客服优化.md` 第六节

---

## 零、结论先行

**竞品大概率是「进程内调用」路线，不是我们这种全局键鼠。**

推理链只有三步，每步都有硬证据：

1. **它能让窗口在前台以外的地方收到输入** → 输入必须绕过 Windows 的焦点机制
2. **企微 PC 4.x 界面是腾讯定制的 Duilib（DirectUI 自绘），自定义控件不暴露标准 UI Automation Pattern** → 走不到「UIA 找控件」这条路
3. 排除掉 UIA 和「抢焦点」，剩下能后台写入的只有两种：**往窗口投递消息**（PostMessage）和**进程内直接调函数**（注入）

客户自己说的「肯定是用 hook 去做」，指向的是第 3 步里的第二种。

**但这里有一个我们绕不过去的判断：这两条都是灰色路线，都会违反企微软件许可协议，都有账号风险。**

所以本文给的不是「抄它」，而是三件事：

- 把它的可能做法讲清楚，**包括一个能当场验出来的判别方法**（第 4 节）
- 把我们能立刻做、风险可控的那部分（PostMessage 后台投递）单独拎出来作为**先验证再决定**的选项
- 把合规路线（官方 kf / 会话存档 + 侧边栏）的成本算清楚，让决策有依据

## 一、需求精确化

### 1.1 先纠正一个误读（2026-11-13 补）

> 「网页端和企微端同时在线：这个说的是我们不是有一个前端嘛，网页有一个网页版，**不是企微的网页版，是我们自己这个软件的网页版** http://119.91.113.100:4222/factories
> 这个跟企业微信它可以同时登录，且它们是双端同步的，然后可以自己回，在我们的网页可以显示，在企业微信上也可以显示」

所以「双端」= **我们自己的 4222 后台** + **本机企微客户端**，不是企微网页版。

这一条把问题从「登录态冲突」整个挪走了 —— 我们后台和企微客户端本来就不抢同一个登录态，它们可以同时开着。**真正的缺口只有四个字：双向同步。**

### 1.2 六个独立诉求

| # | 诉求 | 现状 | 差距 |
|---|---|---|---|
| 1 | **不是云端电脑**，部署在本机 | 本地客户端 `agent/` 已经是本机 | ✅ 已满足 |
| 2 | 我们后台 + 本机企微**同时在线** | 两者登录态本来就不冲突 | ✅ **不成立的问题，撤销** |
| 3 | 两边**同时可操作**（人点得动） | 自动化期间抢前台，人被打断 | ❌ |
| 4 | **不抢前台** | 全局键盘，必然抢 | ❌ |
| 5 | **AI 自动回复** | 已有 | ✅ 已满足 |
| 6 | 会话在两边**都能看到**（双向同步） | 有 SSE + 桥接，但**AI 自己发出的回复没回报到网页** | ⚠️ **半个洞** |

**关键判断：诉求 2 是我此前误读，实际不存在；诉求 6 才是客户真正在说的「双端同步」，而且它现在只做了一半。**

### 1.3 诉求 6 的现状（实测代码）

**通的半边** — 客户发来的消息会实时出现在网页上：

```
agent/autopilot.py:450    {"direction": "outbound" if m.get("is_self") else "inbound", ...}
autopilot.py:490          self._send_ingest(batch)        ← 批量上报
autopilot.py:583          POST /api/v1/bridge/devices/{code}/{direction}
src/modules/agent/stream.routes.ts:19   GET /api/v1/agent/stream  ← SSE
public/theme/realtime.js:289            前端订阅，收到即刷新列表
```

**断的半边** — AI 回复是本地按键盘打出去的，**只写进企微本地库，没有回传到 4222**：

```python
# agent/autopilot.py:957
result = core_send.send(store, name, body, expect_id=..., verify_db=True, log=...)
if result["ok"]:
    rlog.mark_sent(mid, scene, text)      # ← 只记本地 reply_log.db
```

`mark_sent` 只写本地 `reply_log.db`，**没有对应的 bridge 上报**。对比人工发送走的 `flush_manual_receipts()`（`autopilot.py:1030`）——那条是有回执上报的。

**结果就是客户看到的现象**：AI 回的那句话在企微里能看到，但网页端要等下一轮 `scan()` 从解密库里重读才补上，或者干脆补不上（取决于缓存与游标）。**这不是「双端联动」，这是「一端在动，另一端慢半拍」。**

### 1.4 「联动」到底该是什么

客户要的形态：

```
客户发消息
   ↓
本机企微客户端（看得见）
   ↓ autopilot 采集
4222（网页端看得见）  ←──── 这一半现在是通的
   ↓ AI 生成回复
本机按键盘发出 → 企微里出现
   ↓ ★ 必须回传
4222（网页端也要立刻出现）
```

**★ 这一步就是缺的。** 而且它和「不抢前台」是**两个独立的工程问题**，修它不需要任何 hook。

## 二、我们为什么必然抢前台（证据）

不是实现偷懒，是这条路线的物理约束。

### 2.1 发送链路

`agent/wecom_io_core/send.py` 的动作序列：

```
Ctrl+F 唤搜索 → Ctrl+A/Ctrl+V 粘会话名 → Enter 进会话
→ Ctrl+A/Delete 清空 → Ctrl+V 粘正文 → Ctrl+A/Ctrl+C 回读校验 → Enter 发送
```

按键由 `agent/wecom_io_core/win.py:103` 的 `win32api.keybd_event` 发出——**全局键盘事件，只会送到当前拥有焦点的窗口**。

所以 `win.py:148` 的 `ensure_foreground()` 每一轮都要抢：

```python
def ensure_foreground(hwnd: int, tries: int = 3, wait: float = 0.35) -> bool:
    """反复抢前台，直到成功或用尽次数（参考项目每步前都做这件事）。"""
```

调用点在 `send.py:113` 和 `send.py:457`，每个关键动作前各一次。

### 2.2 为什么不用 PostMessage 直接灌

`docs/自动化运行方式与前台独占问题.md` 记过这笔账：

> 企业微信的聊天输入框是内嵌 Chromium 控件，用后台消息（`PostMessage`）灌不进去。

**这句话现在需要修正一半。**

真实情况是：企微 4.x 的界面主体是 **Duilib（DirectUI 自绘）**，不是「内嵌 Chromium」。社区实测（针对 4.1.36.6011 逆向）表明：

- 界面框架是腾讯改过的 Duilib
- 自定义控件容器（`WeWorkWindow`、`PerryShadowWnd`）**不暴露标准 UI Automation Pattern**

这两条合起来意味着：

| 路线 | 为什么不成立 |
|---|---|
| UIA（`uiautomation` / `pywinauto`） | 控件树里拿不到可写 ValuePattern 的输入框，找不到「元素」只有像素 |
| 找子窗口 `Edit` 控件再 `SetWindowText` | Duilib 自绘，文本框不是独立 HWND |
| 图像识别 + 点击 | 能点开但打不了字（打字还是得靠键盘事件） |

**Duilib 的输入是它自己消息循环里分发的**：它收到 `WM_CHAR` / `WM_KEYDOWN` 后，投给它内部"当前有焦点的控件"。这个内部焦点和 Windows 的 `GetFocus()` 不是一回事。

**这正是 PostMessage 路线可能成立的机理，也是它的风险所在**：只要能把它内部焦点落到输入框上，后续 `WM_CHAR` 就能灌进去，全程不需要真实焦点。但「怎么让它内部焦点落过去」是个没有公开契约的操作，靠试。

### 2.3 一个侧证：企微会检测全局键盘

我们代码里有一处防御，很说明问题。

`win.py` 的 `wait_visible()` 注释：

> 等窗口重新可见（参考项目：**企微检测到自动化后会隐藏窗口约 9 秒**）。

也就是说，**企微的反自动化检测命中我们的全局键盘流，然后它选择把窗口藏起来 9 秒**。这是个非常具体的行为特征——如果竞品走的是进程内/消息投递，很可能根本触发不到这个检测器（因为它不经过全局钩子层）。

**这条可以直接拿去验：如果竞品发送时窗口不闪、不消失，基本就不是全局键盘路线。**

## 三、竞品可能是什么（候选枚举）

按「能解释全部现象」来排：现象 = 不抢前台 + 自动回复 + 双端联动 + 人还能操作。

### 候选 A：进程内调用（DLL 注入 + 调内部发送函数）—— 最可能

**形态**：

```
把 DLL 注入 WXWork.exe
  → 在进程内定位「发送消息」的协议函数
  → 起一个本地 HTTP/WS 服务（如 127.0.0.1:19088）
  → 网页端 / 本地客户端通过 localhost 调它
  → 函数在进程内执行，消息直接进发送队列
```

**为什么它能解释全部现象**：

| 现象 | 解释 |
|---|---|
| 不抢前台 | 完全不碰窗口和焦点，直接调函数 |
| 人不被打断 | 同上 |
| AI 自动回 | localhost 服务被 agent 轮询/推送驱动 |
| **双端联动** | **网页端 ↔ 本地注入服务的 HTTP 通道，就是"联动"本身** |
| 窗口不闪不消失 | 不经过全局钩子，触发不到反自动化检测 |

**这个路线在个人微信上是有成熟开源实现的**（wxhelper 就是注入 + 默认 19088 端口 + HTTP 接口）。企微侧资料少，但原理一致。

**成本和风险**：

- 每个企微版本更新都要重新定位偏移 → 维护成本高，且是长期的
- 注入行为在生产环境里较易被检测；一旦被判定，是**封号级**处置
- 违反企微软件许可协议

**这是"能做到"，不是"应该做"。**

### 候选 B：窗口消息投递（PostMessage，不注入）

**形态**：找到 `WeWorkWindow` 的 HWND，用 `PostMessage` 发 `WM_LBUTTONDOWN/UP`（lParam 打包客户区坐标）让它内部焦点落到输入框，再 `PostMessage(WM_CHAR)` 逐字灌入，最后 `PostMessage(WM_KEYDOWN/UP, VK_RETURN)`。

**优点**：不注入，不改对方进程，最坏结果只是「发不出去」，不是「封号」。

**风险**：Duilib 内部焦点没有公开契约，能不能稳定命中完全取决于版本；企微一轮更新就可能失效。

**这一条我们可以自己验**，成本极低（见第 4 节探针）。

### 候选 C：独立 Windows 会话（不是云电脑，但也不是"人眼可见"）

**形态**：在本机开第二个 Windows 登录会话（`tscon` 切会话 / 第二个本地用户），WXWork 跑在会话 2，自动化在会话 2 里抢前台。

**Windows 的前台是按会话隔离的**，所以会话 1 的人完全不受影响。

**为什么大概率不是它**：客户说「这个也打开，还可以操作」——他在自己的桌面上看得见、点得动。独立会话里的窗口他看不见（除非用 RDP/向日葵看，那就成"云电脑"了，客户明确否掉了）。

**但值得记一笔**：如果客户能接受「看不见但 AI 在回」，这是**零封号风险、零逆向成本**的方案，今天就能做。是个备选。

### 候选 D：官方接口 —— 微信客服 `kf/send_msg`

**这条我们已经有代码了**，只是没启用：

`src/modules/wecom/wecom-channel.ts:57`

```typescript
const result = await this.client.call('kf/send_msg',{ touser:contact.external_userid,open_kfid:c.openKfId,msgid:row.msgid,msgtype:'text',text:{content:input.content} });
```

**它有两条已实现的红线**（`wecom-channel.ts:45` 和 `:49`）：

```typescript
if (!contact.last_customer_at || Date.now()-contact.last_customer_at >= 48*3600000) return block('WeCom 48-hour reply window expired');
if (existingCount >= 5) return block('WeCom five-message reply allowance exhausted');
```

**48 小时 / 5 条**——这是官方文档的硬限制，不是我们保守。

**它致命的不是"回不了"，而是"不够用"**：一轮招聘对话至少是「岗位卡片 + 面试地点时间 + 邀约问句」= 3 条，客户再问两三个问题就爆了。一问一答的客服场景能用，招聘流程用不了。

**而且它只覆盖「微信客服」入口**（客户扫客服码进来），不覆盖招聘员好友私聊。客户的实际业务是后者。

### 候选 E：会话存档 + 侧边栏半自动

读用官方「会话内容存档」SDK（合规，需购买 license、员工告知授权），写用 `ww.sendChatMessage` —— **但它是人在侧边栏里点的，不是自动回复。**

**排除理由**：客户明确说「AI 会去自动回」。这条路做不到全自动。

## 四、怎么验（决定性判别）

### 4.0 已跑完的实测（2026-11-13 21:10，本机）

本机企微 **5.0.13.6005**，实测三个只读探针，结论如下。

| 探针 | 方法 | 结果 |
|---|---|---|
| UIA 控件树 | `AutomationElement.FindAll(Descendants)` | **`descendants: 0`** — 主窗口一个子元素都没有 |
| 子 HWND | `EnumChildWindows(hwnd)` | **`子窗口=0`** — 连一个子窗口都没有 |
| TextPattern | `TryGetCurrentPattern` | **`False`** — 不支持文本模式 |

UIA 属性：`ClassName=WeWorkWindow`、`ControlType=Window`、`FrameworkId=Win32`、`Name=企业微信`。

**这三条合起来，把两条路线彻底判死了：**

| 路线 | 判决 | 依据 |
|---|---|---|
| **UIA**（`uiautomation` / `pywinauto`） | ❌ **不可能** | 控件树是空的，没有任何元素可找 |
| **子窗口 `Edit` + `SetWindowText`** | ❌ **不可能** | 零个子 HWND，文本框不是独立窗口 |
| **图像识别 + 点击** | ⚠️ 能点开，打不了字 | 打字仍要键盘事件 |
| **PostMessage 到主窗口** | ⚠️ **唯一还没排除的** | 见 4.1 |
| **进程内注入** | ✅ 理论可行 | 见候选 A |

**顺带发现一个现有代码的隐患**：5.0.13 有 **4 个 `WeWorkWindow` 实例**（1 个可见 1280x761，3 个隐藏 1180x760）。而 `agent/wecom_io_core/win.py:find_window()` 是**按面积取最大**、不看可见性——现在能选中只是碰巧，因为刚好可见的那个面积最大。窗口尺寸一变就会选错。**这跟本次需求无关，但是个真实的定时炸弹，建议单独修。**

### 4.1 唯一还没排除的：PostMessage 到主窗口

现在只剩一条不注入的路：往 `WeWorkWindow` 主窗口 `PostMessage`。

它的不确定性在于：**没有子 HWND，所有点击/输入都由 Duilib 自己在消息循环里按坐标分发**。也就是说，消息能不能被接收、内部焦点能不能落到输入框，完全取决于腾讯的实现，**没有任何公开契约**。

**但底层这一关已经过了。** 用一个自建 Win32 窗口做的原理验证（完全不接触企微）：

| 窗口状态 | 收不收 `PostMessage` |
|---|---|
| 正常显示 | ✅ 收到 |
| **最小化（`SW_MINIMIZE`，`IsIconic=True`）** | ✅ **收到** |
| **完全隐藏（`SW_HIDE`，`IsWindowVisible=False`）** | ✅ **收到** |

**这直接回答了你的新要求：「可以缩掉、放到后台、变成角标」。**

Windows 的消息队列对最小化/隐藏窗口照常投递。所以「缩到后台还能发」在**系统层面没有障碍**——障碍只在两处：

1. Duilib 收到消息后处不处理（应用层，需要实测企微）
2. 我们现有代码主动阻止它（`win.py` 会强制 `SW_RESTORE`，见下）

**这一步必须实测企微本身**，但探针脚本被自动模式的安全分类器拦截了（模拟点击企业微信窗口）。已停在原地，等你的许可：

```
cd 过程文件/probe
python -I probe_background_input.py
```

它只做一件事：向企微输入框投消息、截图为证，**不发 Enter、不激活窗口**。

### 4.1.1 现有代码反而在阻碍「缩到后台」

这是查代码时发现的一个直接冲突。`agent/wecom_io_core/win.py`：

```python
def wait_visible(hwnd, timeout=15.0):
    while ...:
        if user32.IsWindowVisible(hwnd): return True
        if user32.IsIconic(hwnd):
            user32.ShowWindow(hwnd, win32con.SW_RESTORE)   # ← 主动还原窗口
        elif not user32.IsWindowVisible(hwnd):
            user32.ShowWindow(hwnd, win32con.SW_SHOW)
        user32.BringWindowToTop(hwnd)
        user32.SetForegroundWindow(hwnd)                    # ← 主动抢前台
```

**它现在的行为是：窗口一旦最小化，就把它还原；一旦不可见，就把它显示出来。** 这跟你要的「缩掉、放后台、变角标」完全相反。

`activate()`（`win.py:69-74`）同样有 `SW_SHOW` / `SW_RESTORE`。

**结论**：即使 PostMessage 路线成立，也不是「改个函数」就行——必须新增一条**完全不碰窗口状态**的发送路径，绝不能复用 `send.py` 里那句 `ensure_foreground`。这也是为什么第 7 节建议新增 `background_send.py` 而不是改现有文件。

### 4.2 剩下两个探针（需要客户配合）

**探针 1：看竞品有没有抢焦点**（客户在竞品的机器上做，10 秒）

1. 打开记事本，光标放里面
2. 让竞品发一条消息
3. 看光标跳没跳、企微窗口闪没闪

| 现象 | 结论 |
|---|---|
| 光标跳走 / 窗口闪现 | 全局键盘路线，跟我们一类 |
| 完全无感 | 进程内调用或消息投递 |

**探针 2：看有没有注入的 DLL**（最有说服力）

```bat
tasklist /m /fi "imagename eq WXWork.exe"
```

| 现象 | 结论 |
|---|---|
| 只有腾讯/微软/系统 DLL | **没有注入** → 只能是 PostMessage |
| 出现第三方 DLL | **确认注入** → 候选 A |

注入必定要加载模块，没有例外。这一条几乎是决定性的。

## 五、逐条评估

| 方案 | 不抢前台 | 双端联动 | 封号风险 | 开发成本 | 维护成本 | 合规 |
|---|---|---|---|---|---|---|
| **A 注入** | ✅ 彻底 | ✅ 天然 | **高**（封号级） | 中 | **极高**（每版本重定位） | ❌ 违反许可 |
| **B PostMessage** | ✅ 若成立 | ✅ 天然 | 中（可能被静默拦） | 低 | 中 | ⚠️ 灰色 |
| **C 独立会话** | ✅ 彻底 | ⚠️ 看不见 | 无 | 低 | 低 | ✅ 但体验不达标 |
| **D 官方 kf** | ✅ 彻底 | ✅ | 无 | 已实现 | 低 | ✅ 但 5 条上限 |
| **E 存档+侧边栏** | ✅ | ✅ | 无 | 高 | 中 | ✅ 但要人点 |
| 现状（全局键盘） | ❌ | ⚠️ | 中 | — | 低 | ⚠️ |

**读这张表的正确方式**：不存在「全绿」的一行。这行的本质是**在合规和体验之间选一个位置**，没有免费的全都要。

**但这张表是「不抢前台」这一列的比较。** 客户说的「双端同步」是另一列——那一列我们**不需要选任何路线**，补一个上报点就有，见第 6 节第一步。

## 六、推荐路线（分三步，不是一次性押注）

### 第一步（本周可做，零风险，收益最大）：补上 AI 回复的回传

1.3 节查清楚了：**「双端同步」缺的是「本机发出 → 4222」这一步。** 这一半不通，客户在网页上看到的是残缺的对话——他问一句，看得见；AI 回一句，看不见。

**修法很小**：`autopilot.py` 里 AI 发送成功后，除了 `rlog.mark_sent()`，再加一次 bridge 上报（复用人工回执已有的 `flush_manual_receipts()` 通道，`autopilot.py:1030`）。

```python
# autopilot.py 发送成功分支（约 :978）
if result["ok"]:
    rlog.mark_sent(mid, scene, text)
    queue_outbound_receipt(cid, name, body)   # ← 新增：推到 4222，触发 SSE
```

**注意**：多段回复（`parts`）要逐段上报，且 `event_id` 必须稳定，否则网页会出现重复气泡。人工回执那条路已经解决过这个幂等问题，照抄即可。

**这一步做完**，客户在网页上看到的是完整的、实时的对话，AI 回一句网页立刻跳一句。**这正是他说的「双端同步」**，而且零风险、不需任何 hook、不依赖探针结果。

### 第二步（本周可做，低成本高信息量）：跑探针

- **企微本体的 PostMessage 探针**（`过程文件/probe/probe_background_input.py`）：需人工授权后跑一次，5 分钟出结论。当前被自动模式安全分类器拦下，未执行。
- 探针 1 / 2 请客户配合（盯一眼光标 / 一条命令），成本接近零，但能直接判定竞品是不是注入。

**这一步的产出是决策依据，不是代码。** 在拿到探针结果之前就投入开发是最坏的选择。

### 第三步（按探针结果分叉）

```
企微实测：PostMessage 能灌进输入框？
├─ 能 → 走候选 B。新增 background_send.py，现有动作序列原样保留作兜底。
│        必须同时解决：不碰窗口状态（禁止 SW_RESTORE / SW_SHOW / SetForegroundWindow）
│        风险：企微更新可能失效 → 保留"发不出去就退回前台模式"的降级开关。
│
└─ 不能 → 只有三条：
   ├─ ① 候选 A（注入）：技术上最像竞品，但要客户书面确认风险，
   │      且要有「每版本跟进」的长期维护预算。**不建议默认走这条。**
   ├─ ② 候选 C（独立会话）：体验差一点（看不见），但零风险，
   │      适合"客户能接受后台默默回"的场景。
   └─ ③ 承认做不到，把预期沟通清楚：
          官方通道（D）能做的场景先做满，好友私聊保持"人点发送"（E）。
```

### 客户真正要的完整闭环（2026-11-13 补录）

> 「客户要的效果是它可以在客户端这样正常的回消息，就比如说我这台 Windows 电脑，我又登录了客户端，我可以在里面回消息，然后，我可以在打开我们的网页端。网页端是它自动在 AI 自动在回消息嘛。然后他可以看到那个报表，然后他可以在报表里面找一些异常，然后在异常里面，这样就可以在企业微信里面更深入地聊一些他想了解的招聘者。然后全程是无感的，就是他不会去抢前台 AI 的那自动操作，它可以缩掉，把它放到后台，就比如说变成角标，放在那里不动也可以。」

这段话把整个产品形态说全了，拆成一条链路：

```
① 他在本机企微客户端里，能正常手工回消息
        ↓ 并行
② 打开我们的网页端，AI 自动在回
        ↓
③ 网页上看报表，从报表里找异常（约不上 / 答错 / 客户不满意）
        ↓
④ 针对异常，切回企微客户端深聊
        ↓
⑤ 全程无感：AI 操作不抢前台，企微窗口可以缩掉 / 变角标
```

**这张图里只有 ⑤ 需要我们攻技术；①②③④ 全都已经能做，或者只差一个上报点。**

| 环节 | 状态 | 缺什么 |
|---|---|---|
| ① 本机手工回 | ✅ 现有 | — |
| ② 网页 AI 自动回 | ⚠️ 半通 | AI 自己的回复没回传到网页（第 1.3 节） |
| ③ 报表找异常 | ✅ 现有（郎职师运营 / 设备报表） | 异常聚合规则可能要调 |
| ④ 切回企微深聊 | ✅ 现有（`takeover` 接管） | 接管后 AI 必须停（已有 `Human takeover` 校验） |
| ⑤ 不抢前台 + 可缩后台 | ❌ **技术攻坚点** | 见第 4 节 |

**所以正确的工作排序是 ②→③→④→⑤，不是先攻 ⑤。** ⑤ 最难、风险最高，而 ②③④ 修完客户立刻能感受到「这套东西顺手了」，⑤ 是他「更爽」的加分项，不是及格线。

### 关于「双端联动」的补充结论

客户举的竞品形态里，「网页端和企微端同时开着」这一半我们**本来就是对的**——4222 后台和本机企微客户端不抢登录态。ET 已有的 SSE 通道（`src/modules/agent/stream.routes.ts` + `public/theme/realtime.js`）也够用，不需要换技术。

**所以这一块不用重构，只需补一个上报点。** 别把它和「不抢前台」混成一个问题——它们唯一的共同点是客户在同一次会上说了。

## 七、如果走候选 B，改哪里

不动 `wecom_io_core` 的四个文件（这是项目铁律）。PostMessage 是**新增一条发送路径**，与现有路径并存：

```
agent/
├── wecom_io_core/send.py        不动
├── sender.py                    不动
└── background_send.py           新增：PostMessage 路径
        ├── find_edit_rect()     定位输入框客户区坐标（窗口相对比例）
        ├── focus_via_message()  WM_LBUTTONDOWN/UP 让它内部焦点落过去
        ├── type_via_message()   WM_CHAR 逐字
        └── send_via_message()   WM_KEYDOWN/UP VK_RETURN
```

**必须有的兜底**：

- 统一入口 `send_message()`：先试后台，回读校验失败 → 自动退回前台模式（现有 `core_send.send`）
- 配置开关 `background_send: true/false`，出问题能远程关掉
- 每次发送记录「用了哪条路径 + 是否成功」，用于统计哪条路更稳

**这样做的好处**：即使 PostMessage 只在部分企微版本上可用，也不会让产品整体不可用。
