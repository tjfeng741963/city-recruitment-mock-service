# 后台欢迎语配置与验收

## 功能范围

客户添加企业微信后，Windows 客户端在发现该客户的首次会话记录时，可以请求 `/api/v1/flow/greet`，取得后台配置的固定招聘介绍，逐条发送。介绍可以包含工作内容、工作时间、岗位福利、面试要求等，不限于打招呼。客户不必先问问题，固定文本不调用模型。

用户确认的配置范围是：**每个企微号各配一套**。同一工厂多个基地时，先发该号的共通招聘信息，再让客户选择基地。不能把某个基地的差异信息默认当作全厂通用口径。

**触发边界**：沿用现有客户端扫描会话记录的方式，不是新增企业微信官方“添加客户”事件监听。如果加好友没有产生客户端能够读取的首次记录，当前链路不会仅凭通讯录新增主动触发。因此“加好友、不发任何消息”必须实机验收，不能以 HTTP 或模拟测试代替。

后台配置功能不改发送动作。后续链路核查已确认真实自动好友提示能够触发，且定位到“抢不到前台”和发送前提前记已打招呼的问题；经用户确认，新增客户端投递记录和只读桌面检查，详见[首句失败恢复说明](欢迎语失败恢复与桌面条件-20261116.md)。冻结发送底层、键鼠动作、发送时序及底层重试保持原样；不自动给老客户补发，不在生产环境自动创建或启用测试文案。

## 后台怎么配置

管理员登录后，打开侧栏“坐席设备”（`/agent-devices`）：

1. 在列表上方选择企微对应的坐席设备，核对名称、设备码和绑定工厂。
2. 点击“加好友招聘介绍”，填写标题和正文，启用后保存。
3. 一套介绍可有多条消息，用单独一行 `---` 分隔。可以新增、删除和修改任意文本段落，支持分条预览和“填入测试文案”。
4. 再次打开会读取本号内容和启用状态；修改本号不会修改其他号。该入口目前配置文本，未新增设备级图片/视频发送能力。

设备入口对应当前登录的企微号，不是自动识别个人身份的账号目录；若 Windows 客户端换了企微账号，需先核对设备、绑定工厂和招聘介绍，不要直接沿用上个号的业务内容。

“岗位 / 工作”（`/service-positions`）另保留通用欢迎语和岗位专属首句，作为**没有配置本号介绍时**的回退：

1. 点击列表上方“通用欢迎语”。不需要先新增岗位。
2. 写标题和正文，勾选“启用”后保存。标题仅供后台识别，不发给客户。
3. 正文中单独一行 `---` 表示下一条消息；普通换行仍在同一条消息里。
4. 编辑时可以看到每条消息的文本预览；“插入分条”插入分隔符。
5. “填入测试文案”只填充编辑框，仍需点击保存才会生效，不会直接发送。
6. 再次打开会读取已保存的正文和启用状态，重复保存更新同一条记录。

前期测试文案：

```text
你好，欢迎咨询招聘岗位。
---
我先帮你了解一下。
---
请问你现在在哪个城市？
```

这会形成三条独立消息。空白分段会被忽略；只有分隔符的启用内容会被接口拒绝。

实际开场顺序是：本企微号的启用招聘介绍 → 当前岗位的启用首句 → 启用的通用欢迎语 → 原来的默认开场。本号介绍优先，不会被旧岗位首句覆盖。通用欢迎语面向所有设备，不适合放某一家工厂独有的招聘事实。

设备没有板块、地铁设备尚未配置城市，或者暂无可用岗位时，仍可使用通用欢迎语询问城市。没有岗位事实时，不应在通用文案中写工资、待遇或面试地点等承诺。岗位专属模板仍支持原有占位符；分条发生在占位符展开前，岗位字段里的 `---` 不会变成额外消息。

“停用”仅停用这一条配置；可能继续采用岗位专属首句或原有默认开场，**并不等于关闭整个自动回复系统**。停用的原文保留，可以重新编辑并启用。

## 发完招聘介绍后，知识库如何继续工作

- 本号只对应一个可用岗位时，保存该岗位的身份和事实快照，后续追问直接按该岗位处理，不重新发整套招聘介绍。
- 多个基地时，只保存同一工厂所有可见岗位一致的事实和雇主身份，不默认选第一个基地。各基地工资、地址、要求有差异时，不拿第一条岗位的数据冒充通用事实。
- 客户选基地前问共通福利，可直接答共通岗位字段；问其他问题仍按该雇主范围查知识库。差异信息尚未确定时请客户选基地，不借用别家/别基地的信息。
- 客户明确选择基地后，保存对应岗位和地点，继续面试咨询。再次问工资等按所选岗位回答；不会重发本号招聘介绍。
- 招聘介绍是人工配置的固定文案，**修改它不会自动改写岗位字段或知识库**。正式内容应与已确认的岗位 Excel、后台岗位资料和知识库保持一致；若福利/面试要求变更，需同步维护对应事实来源。
- 原有会话没有 `device_intro_sent` 标记时，继续使用原有问答路径；本次不更改知识库内容、索引或防串厂规则。

## 配置生效与历史会话

- 保存后无需重启 Windows 客户端；Python 回复服务的设备配置有约 60 秒缓存，验收前至少等一分钟。
- 已经打过招呼的客户，不会因为编辑文案再次收到欢迎语。不要删除 `.greeted.json`、清空真实会话或回复历史来测试。
- 新生成的介绍先保存在客户端 `welcome_deliveries`，只有各段的目标会话新消息确认后，才标记该介绍完成，并补写 `.greeted.json`。未完成介绍优先于该会话后来的普通问题，不会被合并覆盖。
- 明确未发出的段落沿现有队列恢复，不重新调用服务端取另一版文案；中断或结果未知会暂停，不能直接整套重发。修改后台文案不替换已经保存的待发介绍。
- 这里不保证断电、网络中断或并发下严格“恰好一次”；结果未知需核对。客户端没有改变底层发送动作、时序或整段重试次数。
- 升级不会重置旧 `.greeted.json`，也不会自动修复或给历史失败客户补发；原文和实际消息需先核对。
- 若岗位配置了专属首句，修改通用文案不会覆盖它；测试前先核对这项优先级。

## 开发实现

| 位置 | 改动 |
| --- | --- |
| `src/modules/agent/position-scripts.routes.ts` | 允许显式 `position_id=0` 保存和筛选通用首句；仍限管理员；通用条目仅允许 `greet`；启用内容不能为空 |
| `src/modules/agent/agent.routes.ts` | `device_scripts` 增加 `greet`，按设备码各存一套，仅管理员配置；校验设备、空内容和长度；保留更新和停用原文 |
| `public/theme/position-scripts.js` | 坐席设备页增加本号招聘介绍入口；复用抽屉、分条预览、测试文案、启用编辑与回填；原岗位页入口保留 |
| `backend/app/services/device_scripts.py` | 先分隔模板，再按真实岗位字段和面试时段渲染每条正文 |
| `backend/app/api_flow.py` | 优先本号招聘介绍，返回有序 `parts`，记录介绍和共通/已选岗位上下文；问答按实际雇主和所选岗位接续，不伪造客户消息 |
| `backend/app/services/flow_engine.py` | 多基地介绍后的追问、基地选择和选定后事实问答衔接；不替客户选首个基地 |
| `agent/autopilot.py`、`agent/reply_store.py` | 后续修复：独立首句投递记录、分段确认、失败保留原文与提问、未知结果暂停、只读桌面条件检查；不修改冻结发送底层 |
| `scripts/kb-publication-smoke.py` | 增加后台保存 → 配置下发 → 真实回复 API → 停用的隔离 HTTP 场景 |

复用已有 `device_scripts` 和 `position_scripts` 表及配置下发逻辑，没有数据库迁移。主入口使用 `device_scripts(device_code, stage='greet', city='')`，同键更新不重复创建；通用回退仍是 `position_scripts(position_id=0, stage='greet')`。原有接口和默认开场保留。`/bridge/devices/:code/config.scripts` 原有下发已按设备隔离，无需更改客户端发送代码。

## 自动验证及限制

- Node 回归覆盖通用首句创建、筛选读回、更新不重复、停用后不下发、权限和参数校验。
- Node 增加本号介绍的两设备隔离、修改停用回填、启用空内容/不存在设备/城市和长度校验，以及管理员权限回归。
- Python API 回归覆盖没有客户问题时返回三条文本、板块/城市/岗位缺失、岗位优先、不借用其他岗位、普通换行、分隔与占位符顺序、真实岗位面试时段。
- 客户端编排测试将所有桌面输入 API 替换为 mock：空正文系统记录可以触发首句、发送顺序正确、正常重启不重复，未登录和干跑不发送。新增发送失败/分段恢复、客户新问题不吞介绍、崩溃未知结果、账号切换及桌面不可用的回归。这不是服务器真实企微验收。
- 两个临时服务仅监听本机回环地址，使用临时数据库与合成数据；测试不连接 Windows 客户端，不给真实客户发消息。
- Python 增加本号介绍优先级、没有客户提问时分条返回、多基地仅存共通事实、选基地后工资一致、真实雇主 FAQ 仍可回答且不借别家厂、缺配置时固定介绍可发的回归。
- 此轮浏览器访问本地测试页被自动权限检查拒绝，未完成页面点击与视觉验收。保存读回和实际回复服务已经有 HTTP 联调；页面验收仍需补齐。

## 集中验收步骤

1. 确认部署中的 Node 与实际 Python 回复服务均包含本次改动，客户端在线并使用 flow 模式；核对当前企微账号与设备/工厂的映射，桌面会话须连接且解锁。心跳 online 不等于桌面一定可发送。
2. 在“坐席设备”选择测试企微号，打开“加好友招聘介绍”，填测试文案，核对分条预览；保存，关闭重开、刷新页面，检查内容与启用状态保留。
3. 再选择另一企微设备，确认本号内容没有出现在另一号的配置里；本号介绍优先于岗位/通用首句。正式启用前核对绑定工厂与内容口径。
4. 保存后等至少一分钟。用从未与该企微聊过的测试微信添加好友，完成企微端接受，**不发任何消息**，观察是否收到配置的各条招聘介绍及其顺序。
5. 如果没有收到，先查客户端是否读取到首次会话记录、是否调用 `/flow/greet`、接口是否返回 `parts`、桌面是否可用、`--list` 中首句状态及发送回读是否成功；不要先修改发送动作。明确未发送可恢复；held/unknown 先核对，不要求换一个新微信掩盖失败。
6. 多基地时先问共通福利，再回复“广州”，确认系统不默认选首个基地；明确选“陈村”或“竹料”后再问工资，核对对应岗位且不重复整套介绍。
7. 正常重启客户端，确认同一联系人不重复介绍；停用后重开后台确认停用状态保留，新联系人不再使用这份本号介绍。停用可能回退其他首句/默认开场。

如果没有新的测试微信，已有客户继续发“工资多少”不能证明加好友触发成功。可先完成后台和 HTTP 验收，待有真正新联系人再验收第 4 步；不要删除真实历史制造新客户。
