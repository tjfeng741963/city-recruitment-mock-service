# 后台欢迎语配置与验收

## 功能范围

客户添加企业微信后，Windows 客户端在发现该客户的首次会话记录时，可以请求 `/api/v1/flow/greet`，取得后台配置的固定欢迎语，逐条发送。客户不必先问问题，固定文本不调用模型。

**触发边界**：沿用现有客户端扫描会话记录的方式，不是新增企业微信官方“添加客户”事件监听。如果加好友没有产生客户端能够读取的首次记录，当前链路不会仅凭通讯录新增主动触发。因此“加好友、不发任何消息”必须实机验收，不能以 HTTP 或模拟测试代替。

本次不改 `agent/` 文件，不改键盘动作、发送时序、重试策略，不自动给老客户补发，也不在生产环境自动创建或启用测试文案。

## 后台怎么配置

管理员登录后，打开侧栏“岗位 / 工作”（`/service-positions`）：

1. 点击列表上方“通用欢迎语”。不需要先新增岗位。
2. 写标题和正文，勾选“启用”后保存。标题仅供后台识别，不发给客户。
3. 正文中单独一行 `---` 表示下一条消息；普通换行仍在同一条消息里。
4. 编辑时可以看到每条消息的文本预览；“插入分条”插入分隔符。
5. “填入测试文案”只填充编辑框，仍需点击保存才会生效，不会直接发送。
6. 再次打开会读取已保存的正文和启用状态，重复保存更新同一条记录。

前期测试文案：

```text
你好，欢迎咨询招聘岗位。
---
我先帮你了解一下。
---
请问你现在在哪个城市？
```

这会形成三条独立消息。空白分段会被忽略；只有分隔符的启用内容会被接口拒绝。

通用欢迎语面向所有设备；需要区分岗位时，点击具体岗位行里的“话术”，在“加好友首句”中配置专属内容。实际顺序是：当前选中岗位的启用首句 → 启用的通用欢迎语 → 原来的默认开场。不会借用其他岗位的首句话术。

设备没有板块、地铁设备尚未配置城市，或者暂无可用岗位时，仍可使用通用欢迎语询问城市。没有岗位事实时，不应在通用文案中写工资、待遇或面试地点等承诺。岗位专属模板仍支持原有占位符；分条发生在占位符展开前，岗位字段里的 `---` 不会变成额外消息。

“停用”仅停用这一条配置；可能继续采用岗位专属首句或原有默认开场，**并不等于关闭整个自动回复系统**。停用的原文保留，可以重新编辑并启用。

## 配置生效与历史会话

- 保存后无需重启 Windows 客户端；Python 回复服务的设备配置有约 60 秒缓存，验收前至少等一分钟。
- 已经打过招呼的客户，不会因为编辑文案再次收到欢迎语。不要删除 `.greeted.json`、清空真实会话或回复历史来测试。
- 正常发送成功后的重启去重沿用现有 `.greeted.json` 和回复记录。
- 这里不保证分条发送中途失败、网络中断或并发重复请求下的严格“恰好一次”。本次没有更改客户端失败重试策略。
- 若岗位配置了专属首句，修改通用文案不会覆盖它；测试前先核对这项优先级。

## 开发实现

| 位置 | 改动 |
| --- | --- |
| `src/modules/agent/position-scripts.routes.ts` | 允许显式 `position_id=0` 保存和筛选通用首句；仍限管理员；通用条目仅允许 `greet`；启用内容不能为空 |
| `public/theme/position-scripts.js` | 通用入口、测试文案填充、分条插入、文本预览、启用状态编辑与回填 |
| `backend/app/services/device_scripts.py` | 先分隔模板，再按真实岗位字段和面试时段渲染每条正文 |
| `backend/app/api_flow.py` | 在岗位配置不足时支持通用首句；返回有序 `parts`；记录 `scripted_sent.greet`，不伪造客户消息 |
| `scripts/kb-publication-smoke.py` | 增加后台保存 → 配置下发 → 真实回复 API → 停用的隔离 HTTP 场景 |

复用已有 `position_scripts` 表的 `(position_id, stage)` 唯一约束和配置下发逻辑，没有数据库迁移。新配置使用 `position_id=0, stage=greet`；原有正数岗位 ID 的接口和默认开场保留。

## 自动验证及限制

- Node 回归覆盖通用首句创建、筛选读回、更新不重复、停用后不下发、权限和参数校验。
- Python API 回归覆盖没有客户问题时返回三条文本、板块/城市/岗位缺失、岗位优先、不借用其他岗位、普通换行、分隔与占位符顺序、真实岗位面试时段。
- 客户端编排测试将所有桌面输入 API 替换为 mock：空正文系统记录可以触发首句、发送顺序正确、正常重启不重复，未登录和干跑不发送。这不是服务器真实企微验收。
- 两个临时服务仅监听本机回环地址，使用临时数据库与合成数据；测试不连接 Windows 客户端，不给真实客户发消息。
- 此轮浏览器访问本地测试页被自动权限检查拒绝，未完成页面点击与视觉验收。保存读回和实际回复服务已经有 HTTP 联调；页面验收仍需补齐。

## 集中验收步骤

1. 确认部署中的 Node 与实际 Python 回复服务均包含本次改动，客户端在线并使用 flow 模式。
2. 后台打开通用欢迎语，填测试文案，确认三条预览；保存，关闭重开、刷新页面，检查内容与启用状态保留。
3. 核对岗位专属首句，避免其覆盖本次通用测试文案。通用启用会作用于所有设备，生产测试应选合适时段。
4. 保存后等至少一分钟。用从未与该企微聊过的测试微信添加好友，完成企微端接受，**不发任何消息**，观察是否收到三条欢迎语及其顺序。
5. 如果没有收到，先查客户端是否读取到首次会话记录、是否调用 `/flow/greet`、接口是否返回 `parts`、发送回执是否成功；不要先修改发送动作。
6. 收到后回复“广州”，确认后续正常进入城市/基地及岗位流程；普通交流不再次发送欢迎语。
7. 正常重启客户端，确认同一联系人不重复欢迎；停用后重开后台确认停用状态保留，新联系人不再使用这份通用文案。

如果没有新的测试微信，已有客户继续发“工资多少”不能证明加好友触发成功。可先完成后台和 HTTP 验收，待有真正新联系人再验收第 4 步；不要删除真实历史制造新客户。
