# 还缺什么：基础会话 + 人工回复

日期：2026-11-01　对照代码：`backend/`（160 个测试全绿）

---

## 一、直接回答

**「获取会话 → 人工输入回复」这条链路，代码已经完整，逻辑上能跑通。但真实环境现在还发不出去，卡在 3 件事上。**

今天新补了 3 个原先会导致"看起来能跑、其实不会动"的死结：

| 死结 | 后果 | 状态 |
|---|---|---|
| 没有手动同步接口 | 回调没配好时，一条消息都拉不到，也没法验证凭证 | ✅ 已补 `POST /channels/{id}/sync` |
| 没有定时兜底同步 | 回调丢一次就永久漏消息 | ✅ 已补 15s 轮询 worker |
| `APP_OUTBOX_WORKER` 默认关 | 人工点了发送，消息永远停在 `queued` | ✅ 已改为默认开 |

所以现在的状态是：**代码侧已经没有阻断项**，剩下的是配置、部署和体验。

## 三、还缺的

### P0 · 不补就在真实环境走不通

| # | 缺什么 | 影响 | 怎么补 |
|---|---|---|---|
| 1 | **真实企微凭证** | 一条消息都收不到 | 后台建自建应用 → 授权「微信客服-可调用接口的应用」→ 勾选客服账号 → 填企业可信 IP → 5 个环境变量 |
| 2 | **公网回调地址** | 客户发消息不会触发同步 | 域名 + HTTPS，或临时用 80 端口反代到 8090；地址填 `/webhooks/wecom` |
| 3 | **前端还没接新 API** | 只能 curl，没有界面 | 现有 React 接待台改调 `/api/v1/conversations*`；字段：`unread`/`takeover`/`delivery_status` |

> 第 3 条是"能不能用"的分水岭：后端已经能收发，但顾问没有界面点。旧前端连的是 TS 服务（8080），字段名和路由都不一样，必须改造。

### P1 · 能跑，但用起来别扭

| # | 缺什么 | 影响 | 补法 |
|---|---|---|---|
| 4 | **图片/语音/文件消息只有占位** | 客户发图，顾问只看到 `[image]`，点不开 | `sync.py` 落 `media_id`，加 `GET /messages/{id}/media` 代理下载 |
| 5 | **客户昵称头像为空** | 会话列表全是空白客户，分不清谁是谁 | `client.customer_batchget()` 已封装，建客户后异步回填 |
| 6 | **没有权限隔离** | 任何登录用户能看全部会话 | 按 `devices`/`assigned_user_id` 过滤；`deps.py` 加 scope 校验 |
| 7 | **撤回消息未处理** | 客户撤回后，服务端仍显示原文 | 处理 `msgtype=event` 的 `msg_recall` |
| 8 | **只能挂一个客服账号** | 多业务线无法分流 | `channel_accounts` 已支持多行，但配置读取的是单例 `open_kfid`，需改成按通道取凭证 |
| 9 | **没有消息搜索** | 找历史对话只能翻页 | `messages` 加全文索引或 `ILIKE` 查询 |

## 四、上线执行顺序（每步都有明确验收）

| 步 | 动作 | 验收标准 |
|---|---|---|
| 1 | 填 7 个 `APP_WECOM_*` 环境变量 | 启动日志出现「企微同步 worker 已启动」 |
| 2 | `POST /api/v1/channels/{id}/sync` | 返回 `{"pages":1,...}` 而不是 502；报 60020 就是可信 IP 没配 |
| 3 | 配公网回调（`/webhooks/wecom`） | 后台保存 URL 成功；`GET` 验证返回 echostr 明文 |
| 4 | 手机发一句话 | `GET /conversations` 出现该客户，`unread=1` |
| 5 | `POST /conversations/{id}/messages` | 202，5 秒内 `delivery_status` 变 `accepted`，手机上真收到 |
| 6 | 前端接上这三个接口 | 顾问能在界面上看到消息并回复 |

第 2 步是**最有价值的一步**：它能在没有前端、没有回调的情况下，单点验证凭证、可信 IP、客服账号授权三件事是否都对。

## 五、企微的硬限制（不是 bug，要提前告诉运营）

| 限制 | 具体 | 影响 |
|---|---|---|
| 48 小时窗口 | 客户最后一条消息起 48 小时内才能回 | 隔天想追客户，发不出去 |
| 每条消息 5 条上限 | 同一窗口内最多回 5 条 | 长对话会被截断，需人工换渠道 |
| 单条 2048 字节 | UTF-8 计数，中文约 680 字 | 长回复要拆分或精简 |
| 不能主动营销 | 窗口外只能走模板消息，本项目未实现 | 不能当群发工具用 |
| 会话状态 0/1 才可发 | 待接入池、人工接待中都不能 API 发 | 客服账号要设成「智能助手接待」 |

这四条决定了产品形态：**它是"客户来找你时的高效应答工具"，不是"主动触达工具"**。谁的预期不对，上线后一定扯皮。

---

## 六、一句话总结

> 后端已经能"收消息 + 发消息"，缺的是**凭证、公网地址、前端界面**这三样外部条件；再往上是图片消息、客户资料、权限这些体验项；最后才是迁移、监控这些生产化项。

按第四节的顺序做，1→2 当天就能验证通不通；3→5 是一次完整的真机闭环；第 6 步才是真正让人能用起来。
