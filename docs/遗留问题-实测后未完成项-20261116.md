## 一、需要产品决策的

### 1.1 地点消息发不出去（客户端能力缺口）

**现象**：运营话术里写「到了打这个电话」「地址在XX路」，客户收得到文字；但企业微信的**地图位置气泡**发不出来。

**证据**：`agent/wecom_io_core/send.py` 的全部发送函数只有两类：

```
send()        # 文字：Ctrl+F 搜会话 → 输入 → 回车
paste_media() # 图片/视频：剪贴板放文件 → Ctrl+V
```

全文搜 `location` / `位置` / 坐标，`send.py` 与 `autopilot.py` 均无任何匹配。`MEDIA_EXTS = (".jpg", ".jpeg", ".png", ".mp4")` 里也没有任何位置相关的扩展或标记。

**为什么不建议做**：企微发位置要在 UI 里「+ → 位置 → 搜点/选点 → 发送」，五步都依赖弹窗层级。键鼠自动化在任何一步窗口状态不对时，可能把内容发到错误的会话——这比不发更糟。

**当前替代方案**：面试地点作为文字出现在岗位卡和面试通知里（`interview_place` / `interview_notice`）。

**如果一定要做，前置条件**：先在目标机器上抓一次位置弹窗的控件结构，确认版本稳定后再评估。

### 1.2 「不符合」原因没有记录（`disqualified_reason` 全库无写入方）

**现象**：候选人页有「不符合」这个状态，但没有「为什么不符合」的来源。

**证据**：`disqualified_reason` 在三个文件里被 **SELECT** 出来：

- [agent.routes.ts:303](../src/modules/agent/agent.routes.ts#L303) — 候选人列表的列
- [activation.jobs.ts:24](../src/modules/activation/activation.jobs.ts#L24)、[activation.routes.ts:90](../src/modules/activation/activation.routes.ts#L90) — 激活策略的输入
- [response-serializers.ts:49](../src/shared/response-serializers.ts#L49) — 序列化白名单

**没有任何一处 INSERT 或 UPDATE 写它**。整个仓库 grep `insert|update` 与 `disqualified_reason` 的组合，零命中。

**影响**：激活复聊时读到的永远是空串，无法按「因为年龄超了」和「因为嫌工价低」分流。

**要做的话**：Python 侧放弃时已经有 `slots["recruit_status"] = "disqualified"`，但没带原因；需要先把放弃原因归类（年龄/工价/远/已有工作/其他），再由 `profile_push.build_profile()` 下发。

## 二、数据与展示不实

### 2.1 看板 9 个区块有 8 个是写死的

**现象**：`/dashboard` 上大部分图表是空的或恒为 0。

**证据**：[agent.routes.ts:479](../src/modules/agent/agent.routes.ts#L479) 一行返回：

```js
return serializeStatusDashboard({
  devices: { total: devices, active_today: 0 },      // active_today 写死 0
  messages: { total: messages, hourly },             // hourly 是 24 个全 0
  queue: { pending },
  errors: { failed_today: failed, ai_abnormal: 0 },  // ai_abnormal 写死 0
  state_distribution: {},                            // 空对象
  device_ranking: [],                                // 空数组
  dify_health: [],                                   // 空数组
  degraded: [],                                      // 空数组
  daily_trend: [],                                   // 空数组
});
```

真正有数据源的只有 3 个：`devices.total`、`messages.total`、`queue.pending`。

**另一处**：`hourly` 是 `Array.from({length:24}, (_,hour) => ({hour, count: 0}))` —— 恒为 0，不是「今天这个点没消息」，是根本没查。

### 2.2 `failed_today` 其实是「历史全部失败」

**证据**：同一行上方

```js
const failed = db.prepare(`SELECT COUNT(*) AS total FROM agent_messages WHERE status='failed'${failedScope.sql}`).get(...).total;
```

**没有日期条件**。字段名叫 `failed_today`，实际连三个月前的失败也算进去。运营看到这个数字会以为是今天出事了。

**修法**：加 `AND date(created_at)=date('now')`，同时把「历史累计」单独出一个字段。

## 三、静默失败（出错没人知道）

### 3.1 档案推送失败完全静默

**证据**：[api_flow.py:554](../backend/app/api_flow.py#L554)

```python
if (profile_records or result.action) and profile_push.has_content(out_profile):
    try:
        await profile_push.push(device_code, payload.session_key, out_profile)
    except Exception:  # noqa: BLE001  推送是附加动作，不许影响客户收到话
        pass
```

注释说得对——推送失败不能影响客户收消息。但 `pass` 之外没有任何记录：4222 挂了、token 过期、超时，全部无声无息。结果就是**客户在微信里聊得好好的，网页候选人页永远是空的**，而且没人知道为什么。

**建议**：至少把失败写进类同 `unknown_questions` 的台账表，或打一条带 device/session 的 ERROR 日志。

### 3.2 发送失败在网页上看不到

**证据**：客户端发送结果只写本地 `reply_log.db`：

```
mark_sent / mark_failed / mark_skipped / mark_held
```

[reply_store.py:113-148](../agent/reply_store.py#L113) 全是本地 SQLite。

上报 4222 的走的是另一条路——`_queue_bridge_messages()` 扫的是**企微解密库里的实际消息**。所以：

- 发送成功 → 企微库里有一条 → 上报 → 网页有记录
- **发送失败 → 企微库里没有 → 网页一条都没有**

运营在会话页看到的是「这条消息不存在」，而不是「这条消息发送失败」，两者含义完全不同。

**这一条和已修的媒体上报是同一类问题**（本地有真相、网页没体现），但失败态更难：需要在 `mark_failed` 时额外走一次桥接上报。

### 3.3 SSE 只有三种事件

**证据**：[stream-events.ts:100-103](../src/modules/messaging/stream-events.ts#L100)

```
messageCreated(deviceCode, customerId, sourceEventId)
commandUpdated(deviceCode, command)
deviceUpdated(deviceCode, state, reason)
```

**没有候选人/档案事件**。所以候选人页和「沟通中」状态只能靠前端轮询刷新。之前修的红点反复出现，根因也是这个（数据落库了，但没有推送通道，前端只能靠轮询，轮询时机和读库时机错开就闪）。

## 四、运维与清理

### 4.1 客户端改动不会随 Docker 部署生效

**事实**：`Dockerfile` 只 COPY `src/`、`public/`、`frontend/`，**不含 `agent/`**。

客户端跑的是目标机器上的 `C:\agent` 副本。所以这轮的 `agent/autopilot.py` 修复（媒体消息上报）必须手动同步：

```
python sync_from_github.py --target C:/agent --ref main --dry-run
python sync_from_github.py --target C:/agent --ref main --apply --restart
```

脚本只覆盖 `agent/**.py`，不碰 `config.json` / `reply_log.db` / `media/` / `logs/`。

**长期风险**：这条链完全靠人记得跑，忘了就是「服务器修好了、机器上还是旧代码」。建议把「agent/ 有变更」做成部署后的一次性提醒（比对 `git diff --name-only HEAD~1 -- agent/`）。

### 4.2 废弃 worktree 里有一个 0 字节的源文件

**位置**：`C:\tmp\wt-of\backend\app\services\flow_engine.py`

**事实**：0 字节，`git status` 显示 `M`。原因是上一轮修 bug 时脚本先以 `"w"` 模式打开、后抛异常，把文件截断了。

**不影响线上**：该 worktree 已废弃，正式代码在 `C:\tmp\wt-seg` 与主仓。但如果有人误进去跑 `pytest`，会得到一堆 ImportError。

**建议**：删除该 worktree（`git worktree remove C:/tmp/wt-of --force`），或至少 `git -C C:/tmp/wt-of restore backend/app/services/flow_engine.py`。
