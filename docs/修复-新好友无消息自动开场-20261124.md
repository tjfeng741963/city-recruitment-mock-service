# 新好友无消息自动开场

## 根因与范围

基于 main `4d2ed04` 排查：`scan_added_contacts()` 在 target=all 时直接返回，
指定联系人模式虽有补充扫描，主循环的变化签名仍只覆盖 message/session，未覆盖 user.db。
因此只有通讯录变化、客户没发消息时可能一直读到旧通讯录。

原有测试没有覆盖「target=all、只有通讯录变化、客户不发消息」的完整链路，
因此指定目标的补充扫描和已有开场配置并不能证明生产默认范围下会主动触发。
本次新增从通讯录变化到发送器的隔离回归，避免只验证配置保存或消息回复。

本次用户已明确要求修复主动欢迎触发。只修改 autopilot 的检测与调度、reply_store 的本地记录，
沿用已有岗位开场/节点配置和发送函数；不修改 `wecom_io_core/`、不增加键鼠动作或改动作时序。
系统 Agent 使用已有固定内容和顺序；Dify 的工作流配置不由本次重写。

## 实现约束

- user.db 及 WAL 纳入变化签名；刷新失败必须重试，不接受失败刷新为已同步。
- 全联系人扫描使用普通微信联系人表 `wechat_contactV1`，不把企业通讯录 `user_table` 的新增同事当候选人。
  表不可读时报告扫描不可用，不用混合通讯录猜测，也不建立空的错误基线。
- 基线按企微账号和数据目录隔离，保存在 reply_log.db 内，与既有备份一起保留。
- 首次成功读取只建立基线，不给历史联系人批量发；之后新增入队，不依赖客户发消息。
- 名称暂缺时保留新增状态；名称补齐后再发；改名、删除后再出现、重启均不构成第二次新增。
- 新增状态确认和欢迎触发入账须在同一个 SQLite 事务内完成，失败回滚后可重试。
- 继续尊重接待范围、已欢迎/已发送账本、人工接管、流程状态和发送就绪闸门。
- Dify 模式仍不执行 Agent 固定开场；此时记录看到的联系人，避免切换回 Agent 后补发历史欢迎。
- 启动时回复来源尚未同步则保留观察状态，待来源明确后再决定是否登记 Agent 触发。

## 内容与顺序的配置入口

沿用「AI 接待 → 话术流程 → 岗位 → 岗位配置 → 编辑开场」的已有内容、排序和延迟。
岗位已启用节点流程时以节点内容、连线顺序和等待设置为准，旧开场编辑不会覆盖已保存节点。
本次修复触发条件，不新增另一份欢迎语配置，也不代替企业微信本身的好友自动通过设置。

## 验证与回滚

使用隔离 SQLite、模拟通讯录与发送器验证：首次基线、新增无消息、多条自定义顺序、
user.db/WAL 变化、扫描失败恢复、空名字、账号隔离、反序会话 ID、重启幂等、内部员工排除、
模式切换和事务失败回滚。运行相关 Python 回归、前端构建及仓库检查。

本地测试不等于云 Windows 实装或企微送达。上线须安装对应客户端包，并用授权新联系人实测。
回滚恢复旧客户端程序，保留 reply_log.db、流程状态和新增基线表；不清库、不重置已发送记录。

## 实机验收边界

外部联系人来源沿用冻结 Store 已支持的 `wechat_contactV1(wxid,name)`。
本轮未读取云 Windows 的实际通讯录结构，仍需客户端升级后核对该来源是否可读，
以及新增记录是否确实对应已通过的联系人；不可读会暂停全量扫描并提示，不降级为企业通讯录。

客户端升级后先确认日志出现「已建立普通微信联系人基线」，再使用获得授权的测试联系人添加并通过。
测试联系人不发送任何文字，核对指定开场/首节点是否按顺序执行，最后在接收端确认收到。
建立首次基线以前已经添加的人不会自动补发；不能通过删除账本或基线来做验收。
