> 基线：`e129384`（feat(invite-group): 名单直发企微群，按真实群会话 id 落点）
> 采集时间：2026-11-16 15:30–16:05（只读分析，未改动任何代码）
> 线上事实来源：服务端 `119.91.113.100` 的 4222 / 8090 只读接口 + 客户端 `134.175.40.31` 的 `C:\agent\logs\run.log` 与 `C:\agent\config.json`

## 0. 先给结论

这套系统**不是一个后端 + 一个客户端**，而是**两条并行链路、四套状态机**：

| 链路 | 谁发指令 | 谁执行 | 当前是否生效 |
|---|---|---|---|
| 自动回复 | 客户端本地 `drain()` 调 8090 flow 取话术 | 客户端键鼠 | ✅ 生效（真正的回复来源） |
| 人工发送 | 控制台 → **Node 4222** `bridge_commands` | 客户端键鼠 | ✅ 生效 |
| 人工发送（新） | 控制台 → **Python 8090** `deliveries` | 客户端 `main.py`（**生产没跑**） | ❌ 只入队，无人领取 |
| 服务端直发 | Python 8090 outbox worker | 企微客服 API（KF） | ⚠️ 代码在，与键鼠链路互斥 |

所以「项目写好了为什么发不出去」的答案是：**同一条业务在 4222 和 8090 各有一套实现，客户端只接了 4222 那套。**

## 2. 端的定义与责任边界

| 端 | 物理形态 | 唯一职责 | 绝不该做的事 |
|---|---|---|---|
| 客户端 agent | Windows + pythonw | 采集、决策编排、**唯一能操作键鼠的执行者** | 不直连企微 API，不猜业务规则 |
| Node 4222 | 容器/进程 + SQLite | 控制台、人工指令队列、设备桥接、自动化旁路 | 不碰键鼠、不持企微登录态 |
| Python 8090 | uvicorn + PostgreSQL | 话术大脑（flow/KB）、线索、服务端直发通道 | 不碰窗口 |
| 前端 SPA | 由 4222 托管 | 运营界面 | 不决定发送结果 |

**红线（AGENTS.md）**：`agent/wecom_io_core/` 四个文件禁改；禁止新增键鼠动作。所有「怎么点、怎么粘贴」只能由 core 决定。

## 3. 客户端 agent（最复杂的一端）

### 3.1 进程模型

| 项 | 现状 |
|---|---|
| 启动方式 | 计划任务 `\wecom-agent`（LogonTrigger，Administrator，InteractiveToken）→ `pythonw.exe C:\agent\autopilot.py --watch` |
| 为什么是 pythonw | `run.cmd`（`:loop` 5 秒保活）会被 Windows Terminal 托管，终端窗口抢前台；改成 pythonw 后无窗口 |
| 副作用 | pythonw 无控制台 → `sys.stdout is None`（已用文件日志兜底）；**子进程各自新开控制台 → 屏幕闪黑窗** |
| 日志 | 自写 `C:\agent\logs\run.log`（不走 print） |
| 单实例 | 文件锁 `acquire_single_instance()`；`--list/--reset/--retry-held/--flush-receipts` 例外（不碰键鼠） |
| 遗留任务 | `\WinAgentKeepAlive`：每天 03:00 `net start WinAgent`（SYSTEM/session 0，镜像自带，与本项目无关） |

### 3.2 一轮循环（`--watch` 真实执行顺序）

```
loop:
  state = detect_wecom_state()          # tasklist 查 WXWork 进程 + 枚举窗口（只读，不激活）
  login_watch.alert_login_required()    # 掉登录才动作，120s 冷却
  qr_pusher.tick()                      # 掉登录时截图上传二维码，约 30s 一次
  reporter.tick(state, pending_count()) # 心跳 + 上报（内部有节流）
  sleep(cfg.interval)                   # 线上实测约 41s
  if wal_signature 变化: store.refresh()# message.db 变了才重新打开
  scan()                                # 新消息入 reply_log
  drain()                               # 自动回复（唯一话术决策点）
  pump_safely()                         # 人工指令（4222 claim）
```

### 3.3 本地账本（发送真相在客户端）

`reply_log.db` 三张表：

| 表 | 作用 | 状态 |
|---|---|---|
| `reply_log` | 每条入站消息的处置结果 | `pending / sent / failed / skipped` |
| `manual_receipts` | 人工指令回执补传队列 | `unknown / succeeded / failed` × `pending / acked / rejected` |
| `greeted`（文件） | 首句「加好友问候」只发一次 | `.greeted.json` |

> 设计要点：**服务端不是发送真相源**。客户端断网/重启后靠 `pending+failed` 自动补发，靠 `message_id` 去重；`skipped` 保留 message_id 就是为了「永远不再发第二次」。

### 3.4 回复决策（`drain()`）

按顺序过 8 道闸门：

1. `wecom_state != online` → 一条都不发（11-02 被强退的教训），只记一条 60s 冷却的日志
2. 同会话多条未回 → 只回**最新且有文本**那条，其余标 `merged`
   （加好友/撤回会插入 type=1011 空文本，纯按时间取最新会拿到空串，KB 直接拒答）
3. `is_system_conv()` → 系统/官方会话不回复
4. 冷却 `cfg.cooldown`（与人工指令共享 `_last_reply_at`，避免抢键鼠）
5. 首句判断：首次接触走 `/flow/greet`，失败回落 `/flow/answer`
6. 大脑 `brain=flow`：`POST 8090 /api/v1/flow/answer`，`session_key` = 企微会话 id（状态存服务端）
7. 媒体：`split_media_marks` 拆文本+媒体，先预取素材（`C:\agent\media`）
8. 发送：core `Ctrl+F` 搜会话 → `Enter` → `Ctrl+A/Delete` → 剪贴板 `Ctrl+V` → 哨兵回读 → `Enter`

### 3.5 盲发护栏（11-05 事故后加）

键鼠发送靠「搜索会话名」，搜不到时焦点会留在上一个会话 → **消息发给错误的人**。因此 `pump_commands` 在发送前必须：

- `contact_id/name` 不是系统会话
- `name` 必须存在于当前企微会话列表（`_session_names`）
- 租约未过期（`lease_until > now`）
- `begin_manual_command` 写盘成功（同一条指令不重复执行）
- 发送完成后**回读解密库**，落点不是该 `contact_id` → 回执 `unknown` 而不是成功

### 3.6 双通道上报

| 通道 | 内容 | 失败影响 |
|---|---|---|
| 8090 | `POST /api/v1/agent/ingest`（会话+消息镜像）、`/devices/{code}/heartbeat`（queue_size） | 看板/会话页看不到新消息，不影响发送 |
| 4222 | `/bridge/devices/{code}/heartbeat`(online/offline/scanning)、`/messages`(inbound 事件)、`/config`(远端话术) | 控制台看不到设备在线、人工指令无法下发 |

`_bridge_pending` 落盘：4222 暂时不可达时先存本地，下一轮补发（单条失败不堵队）。

### 3.7 人工指令（`pump_commands`）

```
bridge.claim()              # 4222 原子 claim，租约 60s，返回 {id, lease_token, content, nickname}
  ├─ 本地已有执行记录 → 跳过（防重复执行）
  ├─ 校验：内容/昵称非空、非系统会话、昵称在会话列表
  ├─ sender 发送（与自动回复同一把键鼠锁、同一冷却）
  └─ receipt(succeeded|failed|unknown) + 补传队列 flush
CLAIM_INTERVAL = 10s（两次领取的最小间隔，避免空转）
```

### 3.8 已知失败模式

| 现象 | 根因 | 当前处置 |
|---|---|---|
| 「抢不到前台」 | RDP 断开/锁屏/窗口最小化 | 判失败，不重试到下一轮 |
| 「输入框校验：焦点未落」 | 窗口 1096×663 > 屏幕 1076×643，输入框被挤出 | 环境问题，需调窗口/分辨率 |
| 企业微信黑屏不渲染 | 同上（DWM/合成器在断开 RDP 后停止绘制） | 需真实交互会话 |
| 一眼看到黑窗闪烁 | pythonw 无控制台，`tasklist`/解密子进程各自新开控制台 | 见 §9.8 |

## 4. Node 4222（控制台 + 桥接台）

### 4.1 定位

一个 Fastify 进程同时承担三件事：

1. **前端静态托管**：`GET /` 返回 SPA（实测 200 + text/html）
2. **业务 API**：171 条 `/api/v1/*`（agent / messaging / wecom / dify / activation / admin / permissions / relations / resources / scheduler / files / generic / core）
3. **设备桥接台**：`/api/v1/bridge/devices/:code/*`（heartbeat / claim / receipts / inbound / outbound / config / login-qr）

### 4.2 关键数据表与状态机

`bridge_commands`（人工/自动下发的唯一执行单元）：

```
queued ──claim──► claimed(lease 60s) ──receipt──► succeeded
   ▲                  │                     └──► failed
   │                  └──租约超时──────────────► unknown（可能已发出，要求人工核对）
   └── 同幂等键且上次 failed 时允许重新入队
```

- `succeeded` 必须带 `message_id`；同一指令的重复回执必须完全一致，否则 409
- 设备在线判定：`heartbeat_at` 超过 60s → 视为 offline，claim 直接返回空
- 幂等键：`manual-reply:sha256(device_code\0customer_id\0idempotency_key)`

`message_deliveries`：`sending / succeeded / failed`（Node 自动化用）。
`agent_conversations`：`customer_id`（700016/700017 这套）+ `nickname` + `unread` + `takeover`。
`invite_group_sends`：邀约群幂等键 `invite-group:<device>:<eventId>:<date>`。

### 4.3 消息自动化（`handleInbound`）的 7 道闸门

```
1 INSERT OR IGNORE agent_messages   → 事件级去重（同 eventId 不重复处理）
2 takeover=1                        → 人工接管，不自动回
3 设备 enabled                       → 否则 failed
4 observe_only=true                 → 只记录，绝不生成回复（防双引擎）
5 old_friend 未放行                 → 只记录
6 Dify 生成回复（deviceData.dify_url/dify_key）→ 空则 failed
7 二次检查 takeover → channel.sendMessage → 打回复规则标签
```

> **线上实况**：`pc-win-01` 的 `dify_url=""`，所以第 6 步必然失败 → Node 这条路实际**不产生任何回复**。真正回客户的是客户端 `drain()`。这属于「靠空配置侥幸不冲突」，不是设计上的互斥。

### 4.4 邀约群（本版本新功能）

`profile.routes.ts` 侧：`invited && registrationText` → 组装工厂/岗位/时段/地点 → `sendInviteGroupLine()`：

- 发送前查 `invite_group_sends` 是否已 `sent`（幂等）
- 通道优先级：`convId`（真实群会话 `R:1970325309996590`）直发 > webhook
- 群会话登记：`contact_id = convId`、`nickname = 群名`

### 4.5 扫码登录中转

设备把登录窗截图传到 `/bridge/devices/:code/login-qr`（设备令牌鉴权），前端用用户 JWT 读取展示。因为机器在云端，**没有这条路就永远没人能扫码**。

## 5. Python 8090（话术大脑 + 新投递体系）

### 5.1 接口面（43 条 path）

| 分组 | 典型路由 | 消费者 |
|---|---|---|
| auth | `/auth/login`、`/auth/me` | 客户端 brain、看板 |
| flow | `/flow/answer`、`/flow/greet`、`/flow/state`、`/flow/reset` | **客户端 drain** |
| kb | `/kb/answer`、`/kb/entries`、`/kb/search` | 客户端、4222、前端（经 4222 代理） |
| agent | `/agent/ingest`、`/agent/commands`、`/agent/commands/{id}/ack` | 客户端（**仅 ingest 在用**） |
| conversations | `/conversations`、`/conversations/{cid}/messages`、`/takeover` | 前端（若直连）/ 我本次实验 |
| devices | `/devices/{code}/heartbeat` | 客户端 |
| leads | `/leads/{id}/manual`、`/leads/board` | 前端（经 nginx/4222） |

### 5.2 flow 引擎：状态是事件投影

- `session_key` = 企微会话 id
- 每轮返回 `{reply, stage, collected, done}`，槽位（城市/工厂/岗位/姓名/电话/面试时段）逐轮补齐
- `POST /flow/reset?session_key=` 不是删行，而是**重放/清空事件**让投影回到初始（这轮「都当全新用户」就是靠它）
- 客户端只负责「把 reply 发出去」，不参与任何判断 → 话术改配置即可上线

### 5.3 投递 + outbox（服务端直发那条路）

```
POST /conversations/{cid}/messages  → Delivery(status=queued)  → 202
GET  /agent/commands?wait=N         → 条件更新抢占 queued→sending，一次给一条
POST /agent/commands/{id}/ack       → 只接受 sent / failed
outbox worker                       → 把 queued 交给 channels/wecom_kf/sender（企微客服 API）
```

**关键事实**：`GET /agent/commands` 的消费方只写在 `agent/main.py`，而生产跑的是 `autopilot.py`。我实测 `POST /conversations/22/messages` 返回 `202 {"delivery_id":1,"status":"queued"}`，客户端日志里**从未出现任何 claim 记录**。→ 这条队列是死的。

### 5.4 双后端

同一份 Python 代码跑了两份（宿主机 systemd `recruit-backend` + 容器 `city-recruitment-api`），连同一个 PostgreSQL，靠「宿主机管 outbox / 容器管 sync」分工避免重复执行。这是历史遗留，`双后端与参数下发现状.md` 有完整说明；已知代价：日志两处、内存翻倍、宿主那份曾落后 61 个提交（现已由 CI 统一）。

## 6. 前端

- 单页 SPA，**由 4222 托管**；所有请求走相对路径 `/api/...`，即全部打到 4222
- 涉及 8090 的能力（知识库、flow 编排、线索看板）由 4222 的路由**服务间转发**（`X-Profile-Token`），前端不直连
- 结果是：**4222 挂了，控制台整体不可用**（哪怕 8090 健康）

能反向影响客户端的只有 4 个面：

| 面 | 通道 | 生效方式 |
|---|---|---|
| 设备配置/话术 | 4222 `/bridge/devices/:code/config` | 客户端每轮 `remote.sync()` 拉取并合并 |
| 会话页人工发送 | 4222 `/agent/conversations/:id/send` | 入 `bridge_commands`，客户端 claim |
| 邀约群配置 | 4222 `PUT /agent/invite-group` | 服务端直接发群，不经客户端 |
| 扫码登录 | 4222 `/bridge/devices/:code/login-qr` | 前端展示二维码 |

## 7. 端到端时序

### 7.1 自动回复（主链路）

```
客户发消息 → 企微落库 message.db
  → 客户端 scan 解密/读取 → reply_log(pending)
  → drain: 合并/过滤/冷却 → POST 8090 /flow/answer（带历史 6 条）
  → 8090 返回 reply+stage
  → sender 键鼠发送（搜会话→粘贴→回读确认）
  → reply_log 标 sent；同时 Reporter 把该消息 ingest 到 8090、inbound 到 4222
  → 4222 记消息、算未读、尝试 Dify（当前失败）→ 不回
```

### 7.2 人工发送（当前唯一可用的人机通道）

```
控制台发送 → POST 4222 /agent/conversations/:id/send
  → 写 message_events / message_deliveries / bridge_commands(queued) + agent_messages(queued)
  → 客户端 pump_commands（≤10s 一次）claim（lease 60s）
  → 校验昵称/系统会话/租约 → 键鼠发送 → 回读落点
  → receipts(succeeded + message_id) → bridge_commands.succeeded → 控制台气泡转「已发送」
```

实测：`15:42:53` 入队 → `15:43:18` 回执 `succeeded`，全程约 25 秒（含 41 秒轮询的运气）。

### 7.3 邀约成功 → 名单进群

```
客户资料齐 → 8090 flow 判 invited → profile_push 回写 4222
  → Node 侧 invited && registrationText 命中
  → 组装单行名单（工厂/岗位/时段/地点）
  → 幂等查询 invite_group_sends
  → convId 直发（R:1970325309996590）或 webhook
```

### 7.4 掉登录 → 扫码

```
客户端 detect_wecom_state=login_required
  → login_watch 拉前台提示 + qr_pusher 截图
  → POST 4222 /bridge/devices/:code/login-qr（设备令牌）
  → 前端展示 → 手机扫码 → 客户端下一轮恢复 online
```

## 8. 一致性检查：真相到底在谁手里

| 事实 | 真相源 | 副本/镜像 | 冲突风险 |
|---|---|---|---|
| 会话身份 | 客户端 `message.db`（conv_id） | 4222 `customer_id`(700xxx) / 8090 `conversation_id`(19/22) | **两套 id 不通用**，无法直接互发 |
| 回复该说什么 | 8090 flow（session 状态） | 客户端不缓存话术 | 低 |
| 这条消息发没发出去 | 客户端 `reply_log` | 4222 `bridge_commands`（仅人工）、8090 `deliveries`（无人领） | **三本账，口径不同** |
| 设备是否在线 | 客户端心跳 | 4222 `agent_devices`(60s)、8090 `devices` | 双心跳可能不一致 |
| 人工指令 | 4222 `bridge_commands` | 8090 `deliveries`（死队列） | 同一条业务两个入口 |
| 邀约群发没发 | 4222 `invite_group_sends` | — | 低（幂等键兜住） |

## 9. 当前版本的结构性问题（按影响排序）

1. **人工发送双入口，新入口是死队列**
   8090 `/conversations/{cid}/messages` 入队即返回 202，没有任何消费方；前端若打到它，看起来「成功」实际永远发不出去。

2. **两套会话 id 空间**
   4222 用 `customer_id=700017`，8090 用 `conversation_id=22`，没有映射表 → 想切到 8090 发送，先得补这层映射。

3. **自动回复双引擎，靠空配置「侥幸」不冲突**
   Node 侧 Dify 未配置所以不产回复；一旦有人填了 `dify_url`，就会和客户端本地 drain 双回。真正的互斥开关是设备 `observe_only`，当前**没开**。

4. **发送真相三本账**
   `reply_log`（客户端）/ `bridge_commands`（人工）/ `deliveries`（未用）。排查「到底发了没」要查三处，且时间口径不同。

5. **前端单点依赖 4222**
   控制台与业务 API 同进程，4222 挂 = 控制台全挂，8090 再健康也没用。

6. **无卡单告警**
   两条队列都只有「入队/领取/回执」，没有队列深度、超时堆积的监控；死队列能躺一整天没人发现（本次就是）。

7. **环境强耦合**
   键鼠链路要求：交互式会话、窗口完整可见、尺寸 ≤ 屏幕、能抢到前台。RDP 断开/黑屏/窗口 1096×663 都会直接让发送失败。

8. **客户端子进程弹控制台窗口**
   pythonw 无控制台 + `tasklist`/`python.exe` 未加 `CREATE_NO_WINDOW` → 每轮自检闪一次黑窗（源码 6 处 `subprocess.run`：`autopilot`/`collector`/`sender`/`login_qr`/`login_watch`/`register`）。
   *注：本次分析期间工作区这 6 个文件已有未提交修改（加 `creationflags=_CREATE_NO_WINDOW`），不属于 `e129384` 基线。*
