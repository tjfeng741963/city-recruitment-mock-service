## 二、判死的两条，为什么彻底没救

### 2.1 不是配置问题，是架构决定的

企微 5.0.13 的输入框用的是 **`CreateTextServices`（TOM 无窗口 RichEdit）**。
`DuiLib.dll` 里 `RICHEDIT50W` / `MSFTEDIT_CLASS` **一次都没有**。

这是一条设计决策，不是 bug：

```
没有子 HWND  → EnumChildWindows 返回 0
             → 没有窗口能接收 WM_CHAR
             → PostMessage 投进主窗口后被丢弃
             → UIA / MSAA 也拿不到元素（不产生可访问性节点）
```

**所以"换个工具库试试"这条路彻底堵死。** 换什么库都是在 Win32 消息层打转，
而这一层被设计成不接受合成输入。

### 2.2 实测数据（可复核）

| 探针 | 结果 |
|---|---|
| `UIA FindAll(Descendants)` | `0` |
| `MSAA get_accChildCount` | `0` |
| `EnumChildWindows` | `0` |
| `WM_NCHITTEST` | 返回 1（**说明 WndProc 活着**） |
| `WM_LBUTTONDOWN` / `WM_CHAR` | UI **零变化** |
| 两种抓帧法交叉验证 | `PrintWindow` 与屏幕 `BitBlt` 一致（排除缓存图） |
| DPI 已声明 | 窗口 1280x761 → 2560x1522（排除坐标错） |

**关键点**：`WM_NCHITTEST` 有回执但鼠标键盘无效，
说明消息**进了窗口、被主动丢弃**——不是"发错了地方"。

## 三、剩下的三条，逐条说清楚

### 路线 ①：进程内注入

**这是唯一能完全满足客户要求的路线。**

**已验证的技术基础（静态分析，非猜测）：**

| 发现 | 值 | 意义 |
|---|---|---|
| `DuiLib.dll` | 独立 DLL，4.7 MB，带完整导出表 | 可 LoadLibrary 后直接调 |
| 管理器挂载方式 | **`GetPropW(hwnd, L"Duilib")`** | **零偏移拿到管理器指针** |
| `FindControl` | 已导出 | 按名字找 `input_edit` |
| `SetText` / `AppendText` / `GetText` | 已导出 | 可直接写文本 |
| **`GetTextServices()`** | 已导出 | **拿到 TOM 接口，绕过消息循环打字** |
| `SendChatMessage` | **138 处符号** | 业务层发送函数在进程内 |
| `SendMessageToConversation` | 22 处 | 同上 |

**理论实现链路（未实机验证）：**

```c
CPaintManagerUI* pm = GetPropW(hwnd, L"Duilib");   // 零偏移
CControlUI* edit   = pm->FindControl(L"input_edit");
ITextServices* ts  = ((CRichEditUI*)edit)->GetTextServices();
ts->TxSendMessage(WM_CHAR, ch, 1, NULL);           // 或 SetText
// 最后一步：触发发送（找发送按钮回调或业务函数）
```

**为什么这条能满足「不抢前台 + 可缩角标」**：
全程在进程内调用，不碰窗口焦点、不需要窗口可见。

**硬约束：**

| 约束 | 现状 |
|---|---|
| 需要 **32 位 DLL**（`WXWork.exe` 是 x86） | ❌ **本机无任何 C++ 编译器** |
| 需要 **32 位注入器** | ❌ Python 是 64 位，无 32 位 Python |
| `OpenProcess` 权限 | ❓ 探测被安全策略拦截，未验证 |
| 版本维护 | ⚠️ 每个企微版本都要重新确认偏移 |
| 封号风险 | ⚠️ **高**（注入是明确的违约行为） |

**真正的工作量在哪**：不是"注入进去"（那有开源模板），而是
**最后一步——找到并正确调用业务层发送函数**。它依赖登录态、会话上下文、
可能的参数校验。这是逆向工作量。

---

### 路线 ②：独立 Windows 会话

**做法**：在本机开第二个 Windows 登录会话，企微跑在会话 2，自动化在会话 2 里抢前台。
Windows 的前台是**按会话隔离**的，所以会话 1 的人完全不受影响。

| 维度 | 评价 |
|---|---|
| 不抢前台 | ✅ 彻底（根本不在同一个会话） |
| 可缩角标 | ✅ 会话 2 里怎么样都行 |
| 封号风险 | ✅ **无**（不注入、不改客户端） |
| 实现成本 | ✅ 低（`tscon` / 第二个本地用户） |
| **客户看得见窗口** | ❌ **看不见** |

**这条的唯一问题就是最后一行。** 客户明确说「这个也打开，这个也打开，还可以操作」——
他要看得见。独立会话里他看不见（除非远程连进去，那就成云电脑了，他明确否掉了）。

**但如果客户能接受"后台默默回、网页上看结果"**，这是**零风险、今天就能做**的方案。

---

### 路线 ③：官方微信客服 API

**已实现但不够用**（`src/modules/wecom/wecom-channel.ts`）。

**硬限制（官方文档，非我们保守）：**

| 限制 | 值 |
|---|---|
| 时间窗口 | 客户发消息后 **48 小时** |
| 条数 | 每个窗口最多 **5 条** |
| 入口 | **只覆盖"微信客服"**（扫客服码进来），**不覆盖招聘员好友私聊** |

**为什么不够用**：一轮招聘对话至少是「岗位卡片 + 面试地点时间 + 邀约问句」= 3 条，
客户再问两三个问题就爆了。而且客户的实际业务是**好友私聊**，不是客服入口。

## 五、我的建议：分两步，不要一次押注

### 第一步（今天就能做，零成本）：先确认客户到底要哪个

客户描述的形态（看得见 + 可操作 + AI 自动回 + 不抢前台）在技术上**必然指向注入**。

但客户可能没意识到"看不见窗口"和"零风险"之间可以选。给他两个选项：

| 选项 | 代价 | 效果 |
|---|---|---|
| A. 要看得见 | 注入，有封号风险，每版本维护 | 完全符合他描述的竞品 |
| B. 能接受看不见 | 零风险，今天就能做 | 后台默默回，网页上看结果和报表 |

**这个问题不确认，就直接投入注入，是在替客户做风险决策。**

### 第二步（若选 A）：先解决工具链，再做最小验证

不要在工具链没解决时写代码。顺序应该是：

```
1. 装 32 位编译环境（VS Build Tools）        ← 当前卡点
2. 写最小 32 位 DLL：只做一件事
     GetPropW(hwnd, L"Duilib") → FindControl(L"input_edit") → 打印结果
   不改文本、不发消息
3. 若第 2 步成功 → 验证"写文本"
4. 若写文本成功 → 攻"发送"这一步（最难）
5. 全部通过 → 才谈产品化
```

**第 2 步是关键决策点**：它能同时回答"能不能注入"和"能不能拿到控件指针"。
这两个问题一有答案，整条路线的可行性就定了。

## 六、必须让客户知道的四件事

1. **不能保证不封号。** 注入是明确的违约行为，企微的反制规则不公开且会变。
2. **封的是客户的业务账号**，损失是正在进行的客户关系，不是软件钱。
3. **每个企微版本更新都可能失效**，这是持续的维护成本，不是一次性的。
4. **技术通了之后，瓶颈会变成"AI 回得对不对"。** 后台发送解决"能不能发"，
   不解决"该不该这么回"——后者要靠固定流程节点和发送前校验。
