# 可行性分析：后台静默自动回复（不抢前台 + 可缩角标）

> 日期：2026-11-13
> 分支：`feat/background-send`
> 性质：**只做技术可行性分析，不写实现**
> 前置：`docs/技术方案-不抢前台与双端联动-20261113.md`（已有实测与路线枚举）
> 本机实测环境：企业微信 PC **5.0.13.6005**，Windows 11

---

## 零、结论

**技术上可行，但不是「不抢前台」这一个问题，是三个叠加的问题。三个都能解，代价不同。**

| 问题 | 可行性 | 难度 | 风险 |
|---|---|---|---|
| ① 不抢前台把消息发出去 | ❌ **实测不成立**（PostMessage 被企微过滤） | — | — |
| ② 窗口缩后台 / 变角标时还能发 | ⚠️ **系统层可行，但企微不给机会** | — | — |
| ③ 规避风控封号 | **有办法，但做不到「零风险」** | 中 | **中（这是真正的风险点）** |

> **2026-11-13 22:30 更新：①② 已实测判死。**
> 企微 5.0.13 的 Duilib 会过滤掉 `PostMessage` 投递的合成输入，
> 详见 §2.2–2.3。原本"不用注入就能后台发送"的最优路线不存在了。
> 剩下的只有**注入**或**独立 Windows 会话**，两者的代价都在下面重算。

**最重要的一句判断：** 原以为 ①② 是低风险工程问题、③ 才是风险点。
实测后反转了：**① 根本做不到（除非注入），所以"低风险后台发送"这条路本身就是不存在的。**

关于商业价值，我的判断是**成立但要打折**：一个机器人同时跟多个客户聊、效率提升接近一倍是真的；但这个价值的前提是「客户不封号」，而这恰恰是唯一不能完全保证的一环。**现在还要再加一条前提：得先解决技术路线。**

## 一、问题拆解

客户要的完整形态（2026-11-13 原话）：

> 「在不抢前台的情况下，他可以在我们 Windows 底部也可以是一个角标。然后他要自己回东西」

拆成四条硬约束：

| # | 约束 | 含义 |
|---|---|---|
| C1 | **不抢前台** | 人在用别的软件时，键盘焦点不许被抢 |
| C2 | **可最小化 / 可隐藏 / 可缩角标** | 企微窗口不必可见，能缩进托盘 |
| C3 | **AI 自动回复真实发出** | 不是草稿，是客户手机上真收到 |
| C4 | **不被风控封号** | 这是商业化的前提，封了号产品就废了 |

**C1 和 C2 是同一类（窗口与焦点），C3 是输入机制，C4 是行为特征。三者技术上可以分开解决。**

## 二、C1 + C2：不抢前台 + 可缩后台

### 2.1 已经验证的部分（本机实测，2026-11-13 21:10）

**企微 5.0.13.6005 的窗口结构，三个只读探针：**

| 探针 | 结果 |
|---|---|
| UIA 控件树 `FindAll(Descendants)` | **`descendants: 0`** |
| 子 HWND `EnumChildWindows` | **`子窗口=0`** |
| `TextPattern` 支持 | **`False`** |

**这判死了两条路：**

- ❌ UIA（`uiautomation` / `pywinauto`）：控件树是空的，没有元素可操作
- ❌ 子窗口 `Edit` + `SetWindowText`：零个子 HWND，文本框不是独立窗口

**Windows 消息投递对最小化/隐藏窗口是否有效（自建窗口验证，不碰企微）：**

| 窗口状态 | 收到 `PostMessage` |
|---|---|
| 正常显示 | ✅ |
| 最小化（`IsIconic=True`） | ✅ **收到** |
| 完全隐藏（`IsWindowVisible=False`） | ✅ **收到** |

**结论：C2 在操作系统层面没有障碍。** 消息队列不管窗口可不可见，照常投递。

### 2.2 已经验证的部分（第二轮，2026-11-13 22:30，决定性）

**上一节验证的是「Windows 会不会投递」，这一节验证的是「企微会不会处理」。结论：不会。**

本机实测，企微 5.0.13.6005，窗口被 VS Code 遮挡、不在前台（正是客户要的场景）：

| 探针 | 做法 | 结果 |
|---|---|---|
| 步骤 1 | 最小化态 `PostMessage` 点击会话 | UI 无变化 |
| 步骤 2 | 未声明 DPI 的点击 | 像素差 **0.0000**（坐标本身是错的，不计入结论） |
| 步骤 3 | DPI 对照 + 真实鼠标点击 | 真实点击也无效 → 发现被 VS Code 遮挡，对照组设计错误 |
| 步骤 4 | 只读几何诊断 | 屏幕 2880x1800（200% 缩放）；窗口在 (160,92) 2560x1522；`WindowFromPoint` 返回遮挡方 |
| **步骤 5** | **DPI 正确 + 被遮挡 + 点击导航** | **像素差 0.0043**（印刷/采样噪声级别，肉眼看 before/after 完全一致） |
| **步骤 6** | **两种独立抓帧法交叉验证** | `PrintWindow` 与屏幕 DC `BitBlt` 互相一致（差 0.0000），说明抓帧可信；点击后两法都是 **0.0000** |
| **步骤 7** | **三种变体穷尽** | `WM_MOUSEMOVE`+点击 = 0.0002；直接 `WM_CHAR` = 0.0000；**`WM_NCHITTEST` 返回 1** |
| 步骤 8 | `SendMessageTimeout` 回执 | 被自动模式拦截，未执行（非必需，前七步已互相印证） |

### 2.3 结论：PostMessage 路线不可行

**关键证据链：**

1. **`WM_NCHITTEST` 返回 1（HTCLIENT）** —— 说明企微的 WndProc 活着、在处理消息、消息确实进了窗口
2. **但 `WM_LBUTTONDOWN` / `WM_CHAR` 完全不产生任何视觉变化** —— 消息收到了，被丢弃
3. **两种独立抓帧法结果一致** —— 排除「PrintWindow 返回缓存图」这个干扰项
4. **DPI 已正确声明** —— 排除「坐标算错」这个干扰项

**这意味着：企微的 Duilib 层会过滤掉非硬件产生的合成输入。**

这其实是个合理的设计——现代 IM 客户端普遍这么做，用来挡自动化。它不分辨"谁发的"，
而是分辨"这条消息有没有对应的真实硬件输入事件"。`PostMessage` 天生没有。

**因此：**

| 路线 | 判定 |
|---|---|
| UIA / pywinauto | ❌ 控件树为空 |
| 子窗口 `SetWindowText` | ❌ 无子 HWND |
| **`PostMessage` 投递** | ❌ **消息被过滤（本轮实测）** |
| 进程内注入（直接调内部函数） | ⚠️ 未验证，但这是理论上唯一剩下的不抢前台路线 |
| 抢前台全局键盘 | ✅ 可行（现有实现），但违反 C1 |

**剩下的选项只有两个，都很重：**

- **注入**：绕过消息层，直接在进程内调发送函数。能解决 C1/C2，但封号风险最高、每个企微版本都要重新逆向。
- **独立 Windows 会话**（前面候选 C）：零风险，但客户看不见窗口，体验不达标。

### 2.4 上一轮留下的推测需要更正

本节旧版（22:00 前）写过：

> 「原理上说：Duilib 在自己消息循环里按坐标分发点击……就全程不需要真实焦点」

**这条推测现在被证伪了。** Duilib 确实按坐标分发，但它分发的是**硬件输入队列里的**消息，
不是投递进消息队列的。两者在 Win32 层面都算"消息"，但对 Duilib 来说可区分。

### 2.5 还有一个没排除的细节

`WM_NCHITTEST` 能通说明 WndProc 在处理**系统消息**。
但"系统消息能处理、鼠标键盘消息被丢弃"也可能是**钩子级别的过滤**，而不是 Duilib 层过滤。

这个区别对方案选择很重要：

- 如果是 Duilib 层过滤 → 注入仍然可能成功（绕过 UI 层直接调业务函数）
- 如果是全局钩子过滤 → 注入也可能被拦（但注入在进程内，通常能绕过用户态钩子）

**要区分需要更多逆向工作，不在本次可行性分析范围内。** 记录下来，等真要投入时再查。

**这是整个方案唯一的技术未知数。** 必须实测，不能推理。

### 2.3 现有代码正好反着来（必须新开路径）

`agent/wecom_io_core/win.py:wait_visible()`：

```python
if user32.IsIconic(hwnd):
    user32.ShowWindow(hwnd, win32con.SW_RESTORE)   # 主动还原窗口
elif not user32.IsWindowVisible(hwnd):
    user32.ShowWindow(hwnd, win32con.SW_SHOW)      # 主动显示
user32.BringWindowToTop(hwnd)
user32.SetForegroundWindow(hwnd)                    # 主动抢前台
```

`activate()`（`win.py:69-74`）同样有 `SW_SHOW` / `SW_RESTORE`。

**这个行为跟 C1/C2 完全相反。** 所以不是改函数，是必须新增一条「零窗口操作」的路径，一行 `SW_RESTORE` 都不能有。

### 2.4 C1+C2 小结

| 项 | 状态 |
|---|---|
| 理论可行性 | ✅ 成立（无子窗口 + 消息投递可达） |
| 系统层验证 | ✅ 已完成（最小化/隐藏都收到消息） |
| 应用层验证 | ❌ **未做**（需要向企微投递消息，待授权） |
| 工程代价 | 中：新增 `background_send.py`，不动 `wecom_io_core` |

**判定：C1+C2 值得投入，因为失败成本极低——最坏情况是「发不出去」，不会封号。**

## 三、C4：风控封号（真正的风险点）

### 3.1 先分清两种「封」

| 类型 | 触发原因 | 后果 | 我们会不会碰到 |
|---|---|---|---|
| **账号封禁** | 协议逆向 / 注入 / 异常登录 | 账号停用，客户业务中断 | 走 PostMessage **大概率不会**；走注入 **会** |
| **功能限制 / 静默拦截** | 检测到自动化行为 | 消息发不出、窗口被隐藏 | **可能碰到**（我们已经被碰到过） |

**证据：企微已经在检测我们了。**

`agent/wecom_io_core/win.py` 的注释里记着：

> 企微检测到自动化后会隐藏窗口约 9 秒

这是**基于全局钩子的检测**（`keybd_event` 会有 `WH_KEYBOARD_LL` 回调可被监控）。而 `PostMessage` 不经过全局钩子，**理论上检测不到**。这是选择 PostMessage 而非全局键盘的第二个理由（第一个是不抢前台）。

但对结论要谨慎：**「检测不到」是推理，不是验证。** 企微也可能有别的检测维度（窗口消息频率、输入速度、点击坐标分布等）。

### 3.2 能做的规避手段（按有效性排序）

| # | 手段 | 有效性 | 成本 |
|---|---|---|---|
| 1 | **不用注入**，只用 `PostMessage` | 高（去掉最大风险源） | 零（本来就是设计） |
| 2 | **人类化节奏**：打字间隔随机、句间停顿、不秒回 | 高（我们已有 `_jitter`） | 低 |
| 3 | **限速**：同一会话每分钟不超过 N 条，全设备每小时不超过 M 条 | 高 | 低 |
| 4 | **不群发**：只回主动来消息的人，绝不主动触达陌生人 | **极高**（群发是封号第一诱因） | 零（业务本来就不需要） |
| 5 | **保持窗口正常状态**：允许用户随时接管，不长期独占 | 中 | 低 |
| 6 | **降级开关**：远程可一键关掉后台发送，退回前台模式 | 高（出问题能救命） | 低 |
| 7 | **灰度**：先 1 台设备跑一周，观察有无异常再铺开 | 高 | 中 |

**第 4 条最重要**：招聘业务本身是「客户主动来问」，不是主动群发，这天然规避了最大的风控雷区。**这是我们这个场景相对其他 RPA 场景的结构性优势。**

### 3.3 绕不过去的残余风险

**必须诚实说清楚三件事：**

1. **没有任何方案能保证零封号。** 企微的检测规则不公开且会变，任何「零封号」的说法都是营销口径（搜到的 FlowBot 等厂商就是这么宣传的，无独立验证）。
2. **PostMessage 属于「未经许可的操作第三方软件」**，即使不被检测，也违反企微软件许可协议。风险是「被发现」，不是「一定被发现」。
3. **封的是客户的账号，不是我们的。** 一旦封了，客户损失的是**正在进行的业务和客户关系**，不是软件钱。这是商业上最需要提前讲清楚的一点。

### 3.4 C4 小结

**判定：风险可控，但不能承诺零风险。** 关键是把「不用注入 + 不群发 + 人类化节奏 + 可远程降级」这四件事做成硬约束，而不是可选项。

## 四、C3：消息真的发出去（与风控的交集）

如果走 PostMessage，有一个跟风控直接相关的细节：

**发送成功与否，只能靠回读确认。** 现有代码已经有这套机制（`send.py` 发完回读解密库，`_find_new_sent` 确认落点）。走后台路径必须保留它——否则「以为发了其实没发」，客户投诉时无法举证。

但回读依赖**解密本地数据库**，这部分现有代码是成熟的（`store.py`），跟抢不抢前台无关。**可以完整复用。**

## 五、商业价值评估

### 5.1 客户说的价值（成立）

> 「一个人的工作效率可以提升近一倍，因为有一个机器人在跟他回企业微信，然后他可以做自己的工作，然后时不时可以打开企业微信去看」

**这个账算得通，但成立有条件：**

| 前提 | 是否成立 |
|---|---|
| AI 回复质量够好，不需要人频繁纠正 | ⚠️ **当前不够**（11-13 会上客户明确说「已读乱回」「邀约率没那么好」） |
| 人只需要「时不时看一眼」 | ⚠️ 取决于异常率 |
| 不封号 | ⚠️ 见第三节 |

**换句话说：后台发送把「AI 能不能自动回」的瓶颈，从技术问题变成了质量问题。** 技术一旦通了，客户会立刻发现下一个瓶颈是「它回得对不对」——而这正是 11-13 会上另三个议题（固定流程节点、发送前校验、知识库审批）在解决的事。

### 5.2 真正的商业价值点

**不是「提升一倍效率」，是「一个人能同时盯 N 个账号」。**

一台机器 + 后台静默发送 = 一个人可以同时挂多个企微账号（客户在 11-13 会上提过「同一台电脑控制多一个账号」）。这个价值比「效率翻倍」更实在，因为它直接改变了**人力成本结构**，而不是让一个人舒服一点。

**但这也放大了风控风险**：多账号同机、同 IP、同时段高频发消息，是典型的自动化特征。**一机多号是风控的高危场景，必须提前设计**（错开时段、不同设备指纹、限速）。

### 5.3 竞品的定价参考

搜到的商业 RPA（影刀等）报价约「一年几万块」。我们能提供的是**行业内特定场景的深度定制**（懂招聘流程、懂知识库、懂邀约），不是通用 RPA。**这个差异化是真实的，不靠后台发送也能卖；后台发送是加分项，不是卖点本身。**

## 六、可行性结论（2026-11-13 22:30 修订）

| 约束 | 可行性 | 判定依据 |
|---|---|---|
| **C1 不抢前台** | ❌ **实测不成立** | PostMessage 被企微过滤（§2.2–2.3），只剩注入路线 |
| **C2 可缩后台/角标** | ⚠️ 系统层可行，企微不给机会 | 最小化/隐藏都收 PostMessage，但收了不处理 |
| **C3 消息真发出** | ✅ 抢前台路线可行 | 回读确认机制现成可复用 |
| **C4 不封号** | ⚠️ **可控但不能保证** | 不用注入 + 不群发 + 人类化 + 可降级；残余风险必须告知客户 |

**总判定（修订）：原方案「不注入 + 不抢前台」这条路不存在。**

这不是"暂时没验证成功"，是**技术前提被证伪**：企微的 Duilib 层过滤非硬件输入。
要继续走「不抢前台」，只剩**注入**；不接受注入，就只能回到**抢前台**或**独立会话**。

**所以现在真正要决策的，不是"怎么做"，而是"愿不愿意为不抢前台付出注入的代价"。**

## 六·补、三条可行路线与代价重算

| 路线 | 不抢前台 | 可缩角标 | 封号风险 | 版本维护 | 客户能看见窗口 |
|---|---|---|---|---|---|
| **A 注入** | ✅ | ✅ | **高** | **每版本重逆向** | ✅ |
| **D 独立 Windows 会话** | ✅ | ✅ | 无 | 无 | ❌ 看不见 |
| **E 现状（抢前台）** | ❌ | ❌ | 中 | 低 | ✅ |

**三条没有一条能同时满足"不抢前台 + 客户看得见 + 零风险"。**

- 要客户体验（看得见）：只能选 A 或 E
- 要零风险：只能选 D（但客户看不见，体验不达标）
- 要真实客户要的那个效果：**只能选 A**，并接受它的代价

**这是本次可行性分析最重要的一句话。**
客户描述的竞品形态（网页端+企微端同时可见可操作、AI 自动回、不抢前台），
在技术上必然指向注入——这不是我们的实现选择，是这个需求的唯一解。

## 七、建议的验证阶梯（修订）

### L0：已完成 ← 结论：不通过

| 项 | 结果 |
|---|---|
| 窗口结构探针 | ✅ UIA 全空、无子 HWND |
| 消息投递可达性（自建窗口） | ✅ 最小化/隐藏都收 |
| **企微本体 PostMessage** | ❌ **被过滤，路线判死** |

**L0 不通过。** 按原计划应该"止损、转注入或放弃"——这正是现在要决策的点。

### L1′：注入可行性评估（新，未开始）

如果决定走 A，需要先做的是**成本和风险评估**，不是写代码：

| 要查清 | 为什么 |
|---|---|
| 企微 5.0.13 的发送函数定位难度 | 决定每版本维护工作量 |
| 是否有现成开源注入框架可用 | 决定起步成本 |
| 注入后的封号实际概率 | 决定能不能卖给客户 |
| 腾讯的检测手段更新频率 | 决定这个方案能活多久 |

**这一层的产出应该是"值不值得做"，不是"做出来了"。**

### L2：单机灰度（若 L1′ 通过）

- 只对**一个测试账号**开启，只回**主动来消息**的客户
- 记录每一次发送：用了哪条路径、成功与否、耗时
- 观察指标：发送成功率、企微有无异常（窗口消失、掉线、限流提示）

### L2：双路径并存（2 周）

- 后台优先，失败自动退回前台模式
- 远程开关 `background_send: true/false`
- 人类化节奏 + 全设备限速

### L3：一机多号（谨慎）

- **这一步风险最高**，必须单独评估
- 需要先有 L2 至少 2 周无异常的数据

---

## 八、必须让客户知道的三件事

在投入开发前，这三句必须说清楚，否则后面一定扯皮：

1. **不能保证不封号。** 我们能做到的是「不注入、不群发、像真人一样发」，但企微规则不公开，任何承诺都是假的。
2. **封的是你的账号和客户关系，不是软件。** 风险归属要提前约定。
3. **技术通了之后，瓶颈会变成「AI 回得对不对」。** 后台发送解决的是「能不能发」，不解决「该不该这么回」——后者要靠 11-13 会上说的固定流程节点和发送前校验。
