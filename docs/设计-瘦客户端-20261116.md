## 0. 一句话

客户端从「半个后端」退化为「执行器」：只做 **读消息 → 领任务 → 键鼠执行 → 回执 → 审计**。

「回什么、发给谁、什么时候发、是否接管」全部由服务端决定：任务队列在 4222，话术决策在 8090。

## 2. 目标与非目标

### 目标（可验收）

1. 客户端代码 ≤ **1500 行**（不含 `wecom_io_core`），代码里不出现「回什么」的业务分支。
2. 全系统只有 **一条任务队列、一条回执通道、一份审计日志**；客户端只出站访问 4222，不再直连 8090。
3. 每次发送都能用 `task_id` 追到：谁建的、什么时候领的、执行到哪一步、结果如何。
4. 三类故障不产生重复发送：进程被杀、服务端宕机、租约过期。
5. 保留：发送动作序列、单实例、交互式会话、扫码登录、媒体发送。

### 非目标

- 不改 `wecom_io_core` 的任何一行，不新增键鼠动作。
- 不做 Windows 服务（Session 0 碰不到桌面）。
- 不做公网回调（客户端只出站）。
- 不做多账号调度、本地 LLM、本地知识库。
- 不重写语言/框架；继续 Python，因为 `wecom_io_core` 是 Python。

## 3. 目标架构

```
┌──────────────────────── 4222（Node + SQLite）────────────────────────┐
│  任务队列 bridge_commands（唯一）                                     │
│    queued → claimed →（started_at 写入）→ succeeded / failed / unknown  │
│  入站事件 → 调 8090 flow 决策 → 生成任务 → 同一次响应带回              │
│  控制台：任务时间线、回执、人工重试                                     │
└───────────────▲──────────────────────────────┬───────────────────────┘
        回执 / 入站 / 心跳                 claim / 任务
┌───────────────┴──────────────────────────────▼───────────────────────┐
│  小型客户端（交互会话，单进程，1 执行线程 + 1 IO 线程）                 │
│    扫描本机库 → 入站 outbox → 上传                                     │
│    领任务 → 校验 → 键鼠执行 → 回读 → 回执                               │
│    本地：audit.jsonl + ledger.db（任务/发件箱） + 127.0.0.1 诊断口      │
└───────────────▲──────────────────────────────┬───────────────────────┘
        只读解密副本                       键鼠
┌───────────────┴──────────────────────────────▼───────────────────────┐
│  企业微信 PC（窗口 + 登录态 + message.db）                             │
└──────────────────────────────────────────────────────────────────────┘

        4222 ──内网服务调用──► 8090（flow / KB / leads）
        客户端不再直接访问 8090
```

### 3.1 边界

| 能力 | 客户端 | 4222 | 8090 |
|---|---|---|---|
| 读本机消息 | ✅ | | |
| 键鼠发送 | ✅ | | |
| 任务队列 / 租约 / 幂等 | | ✅ | |
| 决定回什么 | | 转发 | ✅ |
| 会话/消息镜像、看板 | | ✅ | 兼容期由 4222 转发 |
| 扫码二维码中转 | 截图上传 | ✅ 存储 | |
| 设备在线判定 | 心跳 | ✅ | 兼容期由 4222 转发 |

### 3.2 自动回复时序（目标）

```
客户发消息 → 企微 message.db
  → 客户端扫描到新消息，写 outbox
  → POST 4222 /bridge/devices/:code/inbound
       4222 落 agent_messages（幂等）
       4222 调 8090 /flow/decide（内部接口，带 session_key + 最近对话）
       8090 返回 parts（可多段，含媒体）
       4222 按段建任务（同一 group_id，seq 1..N），幂等键带 seq
       响应体直接带回 tasks（最多等 8s；超时返回 202，任务走 claim 长轮询）
  → 客户端逐条执行：一条任务 = 一条气泡 = 一个 message_id
  → POST /receipts（succeeded/failed/unknown + message_id + steps）
  → 4222 推进任务状态、写 outbound 消息、通知控制台
```

### 3.3 人工发送时序（目标）

```
控制台发送 → 4222 入队 bridge_commands（source=manual）
  → 客户端 claim（长轮询 25s）
  → 同一执行器发送
  → 回执推进状态，控制台气泡转「已发送」
```

自动与人工**共用一条队列和同一个执行器**，不再有两套冷却、两套校验。

### 3.4 为什么队列放 4222

- `bridge_commands` 已经具备完整状态机、租约、幂等唯一键、回执冲突检测、控制台和在线判定（`src/modules/messaging/device-bridge.ts`）。
- 4222 是控制台宿主，人工发送的入口本来就在这里；放 8090 会让前端多一次跨服务转发。
- 8090 继续做「大脑」，不持有设备连接和任务租约，职责更干净。

> 备选：队列放 8090。代价是控制台、设备在线、人工回执都要改道；不推荐。

## 4. 任务契约

### 4.1 端点

| 方法 | 路径 | 方向 | 说明 |
|---|---|---|---|
| POST | `/api/v1/bridge/devices/:code/inbound` | 客户端 → 4222 | 入站消息；响应新增 `tasks` |
| POST | `/api/v1/bridge/devices/:code/claim` | 客户端 → 4222 | 领任务；现有接口，新增 `content/media/kind/group_id/seq/trace_id` |
| POST | `/api/v1/bridge/devices/:code/started` | 客户端 → 4222 | **新增**：第一次按键前上报，标记 `started_at` |
| POST | `/api/v1/bridge/devices/:code/receipts` | 客户端 → 4222 | 回执；新增 `steps/duration_ms` |
| POST | `/api/v1/bridge/devices/:code/heartbeat` | 客户端 → 4222 | 保留 |
| POST/DELETE | `/api/v1/bridge/devices/:code/login-qr` | 客户端 → 4222 | 保留 |
| POST | `/api/v1/flow/decide` | 4222 → 8090 | **新增**内部接口；不在公网暴露 |

### 4.2 任务结构

```json
{
  "id": "9f1c...",
  "group_id": "grp_7d2a...",
  "seq": 1,
  "total": 2,
  "device_code": "pc-win-01",
  "customer_id": 700017,
  "contact_id": "S:1688...",
  "nickname": "张三",
  "kind": "media",
  "source": "auto",
  "trace_id": "tr_20261116_223000_001",
  "content": "[图片]",
  "media": [
    {"type": "image", "name": "佛山-安检员.png", "url": "/api/v1/media/...", "sha256": "…", "size": 183402}
  ],
  "lease_token": "…",
  "lease_until": 1763300000000,
  "expires_at": 1763300600000,
  "attempts": 0
}
```

- **一条任务 = 一条气泡 = 一个 `message_id`**，与现有 `bridge_commands.content` / 回执模型一一对应，不破坏回读校验。
- 多段回复由 4222 拆成多条任务，共享 `group_id`，用 `seq/total` 排序；不把 `parts` 塞进一条任务。
- **文字和媒体必须拆成两条任务**：`wecom_io_core` 的发送序列是「文字回车发送」和「媒体粘贴回车发送」两次动作，天然是两条气泡，不能放进同一条任务。
- `kind` 只有 `text` / `media` 两种；纯媒体任务 `content` 写稳定占位（`[图片]` / `[视频]`），`media` 带 URL、`sha256`、`size`；**一条媒体任务只带一个文件**（`paste_media` 一次粘贴一个）。
- 任务里**不带**「为什么发」的理由，执行器不需要理解业务。

### 4.3 状态机

```
queued ──claim──► claimed ──/started（写 started_at）──► claimed(已开始)
   ▲                  │                                      │
   │                  │                                      ├──receipt──► succeeded
   │                  │                                      ├──receipt──► failed
   │                  │                                      └──receipt──► unknown
   │                  ├──租约过期且 started_at 为空──► queued
   │                  └──租约过期且 started_at 非空──► unknown
   └── 同幂等键且上次 failed（人工触发 requeue）
```

关键改动：**区分「领到」与「已开始」**。

- 不新增 `status='started'`：现有 `bridge_commands` 的 CHECK 约束只允许 `queued/claimed/succeeded/failed/unknown`，加状态值要重建表，风险不划算。用 `started_at IS NOT NULL` 表达「已开始」，状态仍是 `claimed`。
- `claimed` 且 `started_at` 为空：没按键，租约过期可安全重排。
- `claimed` 且 `started_at` 非空：可能已按键，租约过期一律 `unknown`，等人工核对。

这解决了现在 `expireClaims` 把「领了但没发」也标 `unknown`、人工要逐条核对的问题。

### 4.4 幂等键

| 来源 | 键 |
|---|---|
| 自动回复 | `auto:<device>:<conv_id>:<inbound_msg_id>:<seq>` |
| 人工发送 | `manual:<device>:<command_id>`（沿用现有） |

4222 已有 `UNIQUE(device_code, idempotency_key)`；重复入队返回原任务，不新建。

### 4.5 `unknown` 语义

只有三种情况记 `unknown`：

1. 已按回车但解密库回读不到落点；
2. `started_at` 非空之后进程崩溃 / 租约过期；
3. 发送过程抛异常且无法判断是否已发出。

`unknown` **永不自动重发**，只能在控制台人工核对后显式重试。宁可少发一条，不可重复发。

### 4.6 分段规则（`group_id`）

- 一次决策返回 N 段 → 4222 在同一事务里建 N 条任务，`seq=1..N`，`created_at` 相同，靠 `rowid` 保证出队顺序。
- 客户端一条一条领、一条一条发，不在任务内循环多段。
- 某段 `failed` 或 `unknown` → 同组后续仍是 `queued` 的任务全部标 `failed`（`error=previous segment failed`），避免隔几分钟又补发后半句。
- 人工重试只重排该段，不整组重放。
- 组内所有任务都 `succeeded` 才算这次回复完成；控制台按 `group_id` 聚合展示。

### 4.7 时效

队列会带来延迟，必须给任务设有效期，避免设备恢复后把半小时前的话术发给客户：

- 自动任务默认 **10 分钟**内有效，人工任务默认 **60 分钟**；`expires_at` 随任务下发。
- `claim` 前先清扫过期 `queued` → `failed`（`error=expired`），不发送。
- 设备离线超过有效期时，入站消息仍落库，但不再补发自动回复，只提示人工跟进。

### 4.8 优先级（已拍板）

- **人工 > 自动**。`claim` 排序：`CASE source WHEN 'manual' THEN 0 ELSE 1 END, created_at, rowid`。
- 同一优先级 FIFO；人工任务不打断正在执行的任务，只排在下一个。
- 同一会话内，如果存在未完成的 `group_id`（还有更小 `seq` 未结束），只允许领该组的下一个 `seq`，不允许插入其他任务，保证多段话术不被拆散。
- 人工量大时自动任务会被推迟，但自动任务有 10 分钟 `expires_at`，过期即作废，不会把旧话术发出去。这是接受的取舍。

## 5. 客户端设计

### 5.1 目录与行数预算

```
agent-lite/
  main.py          装配、单实例、信号、退出          ~80
  config.py        配置加载与校验                    ~100
  runtime.py       主循环、状态探测、线程模型         ~200
  transport.py     heartbeat/inbound/claim/started/receipt  ~250
  executor.py      wecom_io_core 调用、媒体、护栏      ~250
  ledger.py        SQLite：tasks / outbox            ~200
  audit.py         JSONL、轮转、脱敏                  ~120
  api.py           127.0.0.1 诊断口                   ~150
  wecom_io_core/   原样冻结，零改动
```

目标 ≤ 1500 行。删除 `brain.py`、`remote_config.py`、`echo_guard.py`、`reply_store.py` 的决策部分。

### 5.2 线程模型

- **执行线程**：唯一允许调用 `wecom_io_core.send()` 的线程，串行执行任务。
- **IO 线程**：心跳、inbound、claim 长轮询、receipt 补传、媒体下载；不碰键鼠。
- 两线程通过 `queue.Queue` 传递任务；队列长度 1，避免堆积。
- 禁止 asyncio 并发发送，禁止两个线程同时抢前台。

### 5.3 主循环

```
每轮（1~2s）：
  state = probe_wecom()                  # 只读，缓存 5s
  io_tick()                              # 心跳到期就发；补传 outbox
  new = scan_local_db()                  # 只在 WAL 签名变化时 refresh
  for msg in new: outbox.add(inbound)    # 立即交给 IO 线程上传
  if state == online and executor.idle:
      task = claim(wait=25)              # 长轮询，有任务立即返回
      if task: executor.submit(task)
```

相比现在 40 秒一轮，长轮询把新任务延迟压到秒级，同时不需要高频空转。

### 5.4 执行器

任务执行的固定顺序（一条任务只发一条气泡）：

1. 校验会话名存在、不是系统会话；读不到会话列表 → `failed`，不盲发。
2. `media` 任务先下载文件并校验 `sha256/size`；缺失或不匹配 → 该任务 `failed`，不发送（同组文字任务不受影响）。
3. 等剪贴板可写（15s），失败 → `failed`（尚未按键）。
4. 写本地 `tasks.started_at`，调 `/started`（1s 超时，失败也继续，服务端有租约兜底）。
5. 按 `kind` 分两条路径：
   - `text`：`core_send.send(content, expect_id=contact_id, verify_db=True)`，回读得到 `message_id`。
   - `media`：`core_send.paste_media(name)`（内部就是写剪贴板 → `Ctrl+V` → 回车）；媒体无法哨兵回读，粘贴后 2 秒刷新本机库，取目标会话在发送时间窗内新增的 outbound 媒体消息作为 `message_id`。
6. 文字任务回读不到落点 → `unknown`；媒体任务 2 秒内找不到新消息 ID → `unknown`，不重试。
7. 回执：
   - 拿到 `message_id` → `succeeded`
   - 明确未发出（抢不到前台、剪贴板失败、找不到素材） → `failed`
   - 已回车但回读未确认 / 异常中断 → `unknown`
8. 记录每一步到 `audit.jsonl` 和回执 `steps`。

**冷却**：只保留一个「距上次键鼠操作」的最小间隔（默认 8s），失败也计入；不再做客户端侧指数退避，因为失败不会自动重试。

**二次领取保护**：`claim` 到的 `task_id` 如果本地 `tasks` 里已有 `started_at`，说明这条任务本机已经开始执行过（`/started` 或回执可能丢了），**不再发送**，直接回执 `unknown`。这条规则防止服务端租约重排后同一台机器把同一条消息发两遍。

### 5.5 本地账本

只保留两张表，服务端才是任务真相：

```sql
CREATE TABLE tasks (
  task_id TEXT PRIMARY KEY,
  state TEXT NOT NULL,              -- claimed / started / finished
  claimed_at REAL NOT NULL,
  started_at REAL,
  finished_at REAL,
  result TEXT,                      -- succeeded / failed / unknown
  error TEXT
);

CREATE TABLE outbox (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,               -- inbound / receipt
  payload TEXT NOT NULL,
  state TEXT NOT NULL DEFAULT 'pending',
  attempts INTEGER NOT NULL DEFAULT 0,
  next_at REAL NOT NULL,
  created_at REAL NOT NULL
);
```

启动时：`tasks` 里 `started_at` 非空但没有回执的，补发 `unknown`；`outbox` 里 pending 的全部重传（服务端幂等）。

### 5.7 媒体路线（已拍板）

| 视频 mp4 | `CF_HDROP`（文件路径） | 以文件形式粘贴上传 |

约束：

- 任务里的 `url` 由客户端用设备令牌下载到 `media_dir`，文件名 `<sha8>-<原名>.<ext>`；只接受白名单扩展名，拒绝路径分隔符和 `..`。
- 下载后校验 `sha256` 与 `size`，不匹配即 `failed`，不发送。
- 单文件上限 50MB（可配），超出不下载。
- 媒体任务与文字任务分开排队（见 4.2），媒体失败不影响已发出的文字。
- 缓存按 LRU 清理（7 天 / 1GB），避免磁盘涨满。
- 媒体无法哨兵回读，成功判定依赖「发送后本机库出现新的 outbound 媒体消息」；找不到记 `unknown`。

### 6.2 JSONL 格式


### 6.3 脱敏与保留

- 手机号、身份证、微信号在写日志前打码；正文只存 `text_hash` + 前 20 字，不存全文。
- 媒体只存文件名和 hash，不存二进制。
- 按天轮转，保留 30 天或 200MB，先到为准。
- `audit.jsonl` 与 `ledger.db` 属于客户隐私，**不入库、不外传**（沿用 `agent/README.md` 的红线）。

|---|---|---|

## 7. 服务端改动

### 7.1 4222

1. **扩展 `bridge_commands`**：

```sql
ALTER TABLE bridge_commands ADD COLUMN kind TEXT NOT NULL DEFAULT 'text';
ALTER TABLE bridge_commands ADD COLUMN group_id TEXT NOT NULL DEFAULT '';
ALTER TABLE bridge_commands ADD COLUMN seq INTEGER NOT NULL DEFAULT 1;
ALTER TABLE bridge_commands ADD COLUMN total INTEGER NOT NULL DEFAULT 1;
ALTER TABLE bridge_commands ADD COLUMN media_json TEXT NOT NULL DEFAULT '[]';
ALTER TABLE bridge_commands ADD COLUMN source TEXT NOT NULL DEFAULT 'manual';
ALTER TABLE bridge_commands ADD COLUMN trace_id TEXT NOT NULL DEFAULT '';
ALTER TABLE bridge_commands ADD COLUMN started_at INTEGER;
ALTER TABLE bridge_commands ADD COLUMN expires_at INTEGER NOT NULL DEFAULT 0;
```

> 字段含义：`kind` 是内容形态（`text` / `media`），`source` 是来源（`auto` / `manual`），两者不要混用。
>
> 两个约束：`customer_id` 是 NOT NULL，自动任务必须先由 inbound 建立或查到会话；纯媒体任务的 `content` 写稳定占位（如 `[图片]`），否则回执对账时空串与观察到的占位文本会冲突。
>
> 迁移注意：存量 `queued/claimed` 行的 `expires_at` 回填 `now + 3600s`，`0` 在 claim 时按「不过期」兼容；存量 `claimed` 行把 `started_at` 设为迁移时间，避免上线瞬间被当成「未开始」重排而导致重复发送。

2. **`/inbound`**：落消息后调 8090 决策，把 `parts` 里的文本段和媒体标记拆成 `text` / `media` 任务（同 `group_id`，`seq=1..N`），响应体加 `tasks`；同一 `event_id` 重复上报返回空任务。
3. **`/claim`**：返回 `content/media/kind/group_id/seq/trace_id/expires_at`；先清扫过期任务，只领 `queued` 且未过期的，租约 60s。排序按 4.8：人工优先、同优先级 FIFO、同会话未完成组优先。`?shadow=1` 为只读联调模式，不改变任务状态。
4. **`/started`**：校验 `lease_token`，写 `started_at`；重复调用幂等。
5. **`/receipts`**：新增 `steps/duration_ms`，落 `task_events` 表供控制台画时间线；某段失败时把同组后续 `queued` 任务标 `failed`。
6. **租约清扫**：`claimed` 且 `started_at IS NULL` → 重排 `queued`；`started_at` 非空 → `unknown`。
7. **控制台**：按 `group_id` 聚合展示一次回复的多个气泡；`unknown` 单独筛选、人工核对后重试。
8. **停用旧 Dify 自动回复**：显式拒绝 `observe_only=false` 的设备走 `handleInbound` 生成回复，不能继续靠 `dify_url` 为空。

### 7.2 8090

1. 新增 `POST /api/v1/flow/decide`（沿用现有 `X-Profile-Token` 服务间鉴权）：入参 `session_key, device_code, text, history, is_first_contact`，出参 `{parts, stage, finished, skip, dedupe_key}`。
   - 首句判断放在这里：`stage=start` 且无历史 → 返回 greet parts。
   - 现有 `/flow/answer`、`/flow/greet` 保留一个版本做兼容，客户端切换后下线公网访问。
2. 线索判定：在收到 4222 的决策请求时顺带记录入站；回执后再由 4222 调 `/leads/observe`（或 8090 自己消费事件）。不放在客户端。
3. **设备心跳（已拍板）**：客户端只向 4222 发心跳；4222 每次收到后**服务端转发一次**到 8090 新增的 `/api/v1/internal/devices/{code}/heartbeat`（服务间 token，不伪造设备令牌），保证线索看板不断流。客户端不再双发，也不再持有 8090 凭据。

## 10. 测试与验收

| 层 | 用例 |
|---|---|
| 契约 | inbound 重复 event_id 不重复建任务；claim 只领 queued；started 幂等；receipt 重复一致返回 200，冲突返回 409；同组 seq 顺序正确 |
| 状态机 | `claimed` 且 `started_at` 为空，租约过期 → 重排；`started_at` 非空，租约过期 → unknown；`unknown` 不被自动重试；同组前段失败后续段被标 failed |
| 客户端 | outbox 断网重传；启动补发 unknown；媒体缺失 → 该媒体任务 failed、文字任务不受影响；剪贴板占用 → failed 且不按键；重复 claim 同一 task_id 不重发 |
| 媒体 | 图片 DIB+PNG、视频 CF_HDROP；粘贴后 2 秒内回读到新 outbound 消息 → succeeded，读不到 → unknown；sha256 不匹配不发送 |
| 审计 | 每个事件字段齐全；手机号被打码；日志轮转和保留生效 |
| 端到端 | 假执行器 + 真服务端跑 100 条任务，0 重复；三段回复按 seq 发成三条气泡；真机 dry-run 10 条 |
| 故障 | kill -9 执行中；服务端宕机 10 分钟；企微掉登录；RDP 断开 |

验收线：

- 客户端 ≤ 1500 行（不含 core）。
- 一次发送在 `/tasks/{id}` 能看到 ≥ 5 个步骤和耗时。
- 100 条任务重放，重复发送 0 条。
- `unknown` 任务全部出现在控制台待核对列表。
- 服务端恢复后 60s 内 outbox 清空。

## 11. 风险与取舍

| 风险 | 影响 | 处置 |
|---|---|---|
| 服务端改造比客户端大 | 工期不可控 | 先做阶段 0/1，客户端瘦身与审计先落地 |
| 4222 成为唯一队列 | 4222 挂 = 自动回复停 | 已有单点，先加队列深度/积压告警 |
| 决策同步链路变长 | 首响变慢 | inbound 等待 8s；超时走 claim，不让客户等 |
| 分段任务数量变多 | 队列压力、顺序问题 | 一条任务一条气泡；同组 `seq` 排序，前段失败即取消后段 |
| 队列延迟导致话术过期 | 客户收到过时回复 | `expires_at` + claim 前清扫；离线超时不补发 |
| 人工持续插队 | 自动任务饥饿 | 人工量低；自动任务 10 分钟过期，过期即作废，不发旧话术 |
| 媒体文件大或损坏 | 发送失败、占用磁盘 | 50MB 上限 + sha256 校验 + 独立任务 + LRU 清理 |
| 日志含个人信息 | 合规风险 | 脱敏 + 30 天 + 本地保存，不上传全文 |
| PyInstaller 误报 | 安装失败 | 用 onedir、签名、加白名单；保留 uv 运行方式 |
| `wecom_io_core` 不可观测 | 只能看外层步骤 | 在 executor 包一层 step 日志，不改 core |
| 交互桌面依赖 | RDP 断开就发不出 | 沿用现状；心跳暴露状态，运维及时处理 |

## 12. 决策记录（2026-11-16 已拍板）

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 任务队列归属 | **4222**（复用 `bridge_commands`） | 状态机/租约/幂等/控制台/在线判定都已存在；8090 只做大脑，不持设备连接 |
| 2 | 8090 心跳 | 客户端只发 4222；**4222 服务端转发**到 8090 | 客户端只保留一条出站通道，不再保存 8090 管理员密码；线索看板不断流 |
| 3 | 决策延迟 | inbound **同步等 8s**；超时返回 202，任务走 claim 长轮询 | 8s 覆盖绝大多数 flow 决策；不让客户等 25s |
| 4 | 媒体路线 | 任务带 URL；客户端下载成本地文件，**写剪贴板 → `Ctrl+V` → 回车** | 复用 core 的 `paste_media`，不新增键鼠动作；图片 DIB+PNG、视频 CF_HDROP |
| 5 | 人工 / 自动优先级 | **人工优先**，同优先级 FIFO；同会话未完成组不插队 | 人工消息时效性更强；自动任务有 10 分钟过期兜底，不会发旧话术 |

以上作为阶段 0 的实施输入；除非出现阻塞性事实（例如 4222 无法在入站链路里调 8090），不再回头讨论。
