# 部署手册：架构与安装

> 覆盖三套环境：生产服务端、Windows 键鼠客户端、本地开发。
> 最后更新：2026-11-25（对应 commit `aa9147a` 前后）

---

## 一、这套系统在做什么

企业微信**个人号**招聘自动化。没有企微官方 API，所有消息靠 Windows 客户端在企微窗口里**模拟键鼠**发出。

```
客户在企微发消息
   ↓
[企微客户端] 本地加密 SQLite（message.db / session.db / user.db）
   ↓ wecomcracker 解密读取（只读）
[autopilot.py] 扫描新消息 → 本地队列 reply_log.db
   ↓ HTTP（设备令牌）
[服务端 4222] /api/v1/agent/chat → 生成回复（Agent 模型 或 Dify）
   ↓ 返回待发文本/媒体
[autopilot.py] 串行发送：Ctrl+F 搜会话 → 回车 → 粘贴 → 回车
   ↓
客户收到消息
```

**关键约束**：发送是**单线程串行**的，一条一条来（间隔 8 秒，失败退避 16/24/32 秒）。所以吞吐上限约 7 条/分钟，这是键鼠方案的物理限制。

## 三、服务端安装

### 首次部署

```bash
# 1. 取源码
cd /srv/apps/city-recruitment-mock-service/source

# 2. 环境变量（首次从模板复制，然后填密钥）
cp .env.production.example .env.production

# 3. 构建并启动
sudo docker compose -f docker-compose.production.yml up -d --build

# 4. 健康检查
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4222/
sudo docker ps --filter name=city-recruitment-app
```

### 日常更新

```bash
cd /srv/apps/city-recruitment-mock-service/source
git pull --ff-only                       # ⚠️ 见下方「已知问题」
sudo docker compose -f docker-compose.production.yml build app
sudo docker compose -f docker-compose.production.yml up -d app
```

**前端在镜像里**，不在宿主机挂载。`REA_FRONTEND_DIR=/app/frontend-vue/dist`，所以改前端也必须 `build app` 重建镜像，不能只替换文件。

### 验证前端是否真的更新

```bash
sudo docker exec city-recruitment-app sh -lc 'ls -l /app/frontend-vue/dist/assets/ | tail -3'
# 产物 hash 文件名应该变化；也可 grep 新代码里的关键字
```

> 如果 `COPY frontend-vue/dist` 在构建日志里显示 **CACHED**，说明源码没变——先确认 `git pull` 真的成功了。

### 数据备份 / 恢复

```bash
DB=/srv/apps/city-recruitment-mock-service/source/data/app.sqlite

# 备份（先停容器避免写冲突）
sudo docker stop city-recruitment-app
sudo cp $DB $DB.bak-$(date +%Y%m%d-%H%M%S)
sudo docker start city-recruitment-app

# 恢复
sudo docker stop city-recruitment-app
sudo cp $DB.bak-20261124-231038 $DB
sudo docker start city-recruitment-app
```

## 四、Windows 客户端安装

### 首次安装

1. 装 Python 3.11（`C:\Program Files\Python311`）
2. 装企业微信并登录**指定的招聘号**
3. 把客户端包解压到 `C:\agent`（包来自 GitHub Release，见下节）
4. 确认 `C:\agent\config.json` 里的 `device_code` / `bridge_token` 与后台设备一致
5. 用 `client_manager.py` 的界面点「启动自动回复」

### 一键更新（GUI）

`client_manager.py` 提供：

| 按钮 | 作用 |
|---|---|
| **检查更新** | 拉 GitHub 最新 `win-client-*` Release，显示版本与更新说明 |
| **安装更新** | 下载 zip → 校验 → 替换文件（失败自动回滚） |
| **导入更新包** | 离线场景：手动选本地 zip |
| **启动 / 停止自动回复** | 控制 `autopilot.py --watch` 进程 |

更新逻辑在 `agent/client_updater.py`：

- 数据源：`https://api.github.com/repos/tfjeng741963/city-recruitment-mock-service/releases`，只认 tag 前缀 `win-client-`
- 安全校验（任何一项不过就拒绝安装）：
  - zip 整体 sha256（`windows-client.sha256`）
  - 文件白名单（24 个客户端文件，多一个少一个都不行）
  - **冻结核心 hash**：`wecom_io_core/{win,send,store,crypto}.py` 必须与 `deploy/client/frozen-core-sha256.json` 一致
  - 依赖基线：`agent/pyproject.toml`、`agent/uv.lock` 不许变
- 全局互斥锁 `Global\CityRecruitClientUpdater`，防止两个更新同时跑
- 替换失败会恢复替换前的文件

> ⚠️ **改过 `wecom_io_core/` 就必须同步更新白名单**，否则打包和客户端更新都会失败。白名单有两处，必须同时改：
> - `deploy/client/frozen-core-sha256.json`
> - `scripts/package_windows_client.py` 里的 `APPROVED_CORE_HASHES`
>
> 注意用的是**归一化 hash**（`\r\n`/`\r` 先转成 `\n` 再 sha256），不是文件原始 hash。算错了会一直报 `frozen core hash mismatch`。

### 发版流程（服务端 → 客户端）

```
改代码 → push 到 main
   ↓
GitHub Actions (.github/workflows/deploy.yml)
   ├─ 构建 + 测试
   ├─ scripts/package_windows_client.py 打包 windows-client.zip
   ├─ 打 tag win-client-<commit-sha>
   └─ 创建 Release（先 draft，两个产物校验通过才发布）
   ↓
客户端 GUI 点「检查更新」→ 安装
```

手工打包验证：

```bash
python scripts/package_windows_client.py --commit HEAD --base HEAD~1 --output dist/windows-client
```

## 六、关键配置

### 服务端 `.env.production`

| 变量 | 说明 |
|---|---|
| `REA_DATABASE_PATH` | SQLite 路径，容器内默认 `/data/app.sqlite` |
| `REA_FRONTEND_DIR` | 前端产物目录，默认 `/app/frontend-vue/dist` |
| `REA_MESSAGE_CHANNEL_PROVIDER` | 不设或 `bridge`：走设备键鼠发送 |
| `REA_DIFY_API_KEY` / `REA_DIFY_BASE_URL` | Dify 模式才需要 |

### 客户端 `config.json`

| 字段 | 说明 |
|---|---|
| `device_code` | 设备标识，必须与后台设备一致（如 `pc-win-01`） |
| `bridge_server` | `http://119.91.113.100:4222` — **chat 和桥接都走这个** |
| `bridge_token` | 设备令牌，服务端签发 |
| `interval_seconds` | 扫描间隔，生产 20 |
| `cooldown` | 两条消息最小间隔，默认 8 秒 |
| `target` | `all` 表示监听全部会话 |
| `dry_run` | `true` 时只走流程不真发（**重置基线时用**） |

> `server`（8090）是历史遗留字段，`Brain` 实际用的是 `bridge_server`（4222）。

## 七、回复链路（谁决定发什么）

```
前端「话术流程」下拉 ──→ 只选「编辑哪个岗位的话术」，不影响发送
前端「设备管理 → 接待设置」──→ 决定该设备按哪个岗位回复（唯一生效入口）
   ↓
服务端 positionOfDevice(device_code) 解析岗位
   ↓
GET /api/v1/agent/opening   → 开场清单（按 position_opening.seq 排序）
POST /api/v1/agent/chat     → 单条回复（Agent 或 Dify）
   ↓
客户端按返回顺序逐条发送；开场清单有 1 分钟缓存
```

切换接待岗位时，前端会弹确认框并调用 `clear-unread` 清空全部未读；服务端在写回 `agent_session` 时若发现 `position_id` 变化，会**清空该会话上下文**，避免用旧岗位话术回答。

## 八、已知问题与排障

| 现象 | 原因 | 处理 |
|---|---|---|
| `reply_ready=false, reason=desktop_unavailable` | 会话不是 Active（RDP 断开） | `tscon 2 /dest:console` 把会话交接到控制台；已注册 `\KeepDesktopActive` 计划任务每 2 分钟自愈 |
| `reason=window_hidden` / `window_unavailable` | 企微主窗口被最小化，或切换账号留下**可见但全黑**的残留窗口 | `win.find_window()` 已优先选可见且非全黑的窗口；仍失败就手动把企微窗口点出来 |
| `reply_ready=false, reason=auto_send_failed` | 连续发送失败累计 | 落点类错误已不再累加；其余情况重启客户端清零 |
| 开场判 `unknown` 导致会话被锁 | 视频回读超时（旧逻辑） | 已修：文本确认即算开场成功，媒体失败只记日志 |
| 消息发到别的会话 | Ctrl+F 搜索命中歧义（同名/相似名会话） | 未根治。短期靠会话名唯一化；长期需改定位方式 |
| `git pull` 报 `Could not resolve hostname github-city-recruitment` | 生产 remote 指向不存在的 SSH 别名 | 未修。临时用 sftp 传文件 + `sudo cp` 再 build |
| 打包报 `frozen core hash mismatch` | 改了 `wecom_io_core/` 没更新白名单 | 同步改两处白名单，注意用归一化 hash |
| 客户端日志"不动" | 看错了文件 | 真日志是 `logs/run.log`；`pilot.log` 是旧 cmd 重定向残留，重启后不再更新 |

### 常用排障命令

```bash
# 客户端进程
tasklist /FI "IMAGENAME eq pythonw.exe"

# 客户端日志尾部
powershell -NoProfile -Command "Get-Content C:\agent\logs\run.log -Tail 30"

# 服务端会话数
curl -s "http://119.91.113.100:4222/api/v1/agent/conversations?device_code=pc-win-01" -H "authorization: Bearer <token>"
```

## 九、重置基线（清空历史，重新开始）

清空后不能让客户端把历史消息当新消息回复，否则会给一批老客户群发。

```bash
# 1. 停客户端
# 2. 备份并清空 C:\agent\reply_log.db 的 reply_log 表、清空 .greeted.json
# 3. config.json 临时设 backfill_hours=0、dry_run=true
# 4. 启动，跑两轮（历史消息被标为"历史消息（初始化跳过）"，不真发）
# 5. 把残留 pending 改成 error='重置基线（不补发）'
#    原因：record_unread() 会把 error 以「历史消息」开头的 skipped 重新入队
# 6. 恢复 dry_run=false，重启
```

服务端同步清空（保留配置）：

```
agent_conversations / agent_messages / agent_archive / agent_session
opening_log / bridge_commands / bridge_inbound / bridge_outbound
message_events / message_deliveries / dify_* / device_events / unknown_questions
```

**不要清**：`agent_devices`、`service_positions`、`position_opening`、`factories`、`users`、`reply_mode_transition`。
