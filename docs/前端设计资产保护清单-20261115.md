## 一、结论

**`public/theme/` 与 `public/admin-enhancements.js` 是用户亲自设计的视觉层，全部是手写源码。任何重构、升级、换框架，都必须在保留这套视觉的前提下进行，不得替换或丢弃。**

## 三、可以用，但不许换的两层

必须分清「页面骨架」和「视觉层」：

| 层 | 归属 | 能否替换 | 说明 |
|---|---|---|---|
| **页面骨架 / 路由 / 业务逻辑** | 竞品编译产物（`public/assets/`，56 个 chunk） | ✅ 可以替换 | 这是要补的「骨架」 |
| **视觉层**（上表文件） | **用户设计** | ❌ **绝对不换** | 这套视觉是产品差异化的核心 |

### 具体含义

**如果将来把页面骨架换成 React 或还原成 Vue 源码：**

1. 上表 12 个文件**原样保留**，不删、不重写、不"优化"
2. 新页面骨架必须**复用这套 CSS 类名**，让视觉完全一致
3. 如果类名对不上，**改新骨架去迁就 CSS**，不是改 CSS 去迁就新骨架
4. 迁移完成后，`public/theme/*.css` 仍然是从唯一真实来源

**允许的改动：**

- 在现有 CSS 里**增加**新样式（追加，不覆盖）
- 修 CSS 里的 bug（不影响整体视觉）
- 按用户明确要求调整配色、圆角、动效参数

**禁止的改动：**

- 用另一个 UI 框架的样式替换（Element Plus / Ant Design / Tailwind 等）
- "为了统一"重写这套 CSS
- 迁移到 React 时丢掉或重做这套视觉
- 删掉 `theme/` 目录或其中任何文件

## 四、给后续开发者的检查清单

改前端之前自查：

- [ ] 我改的是 `public/assets/`（骨架）还是 `public/theme/`（视觉）？
- [ ] 如果动了 `theme/`，是不是用户明确要求的？
- [ ] 新页面有没有复用 `theme/*.css` 的类名？
- [ ] 有没有引入第二套 UI 框架的样式？
- [ ] 改动后，玻璃质感 / 大圆角 / 渐变背景 / 动效是否还和原来一致？

**任何一项答不上来，先停手确认。**

---

## 五、为什么要有这份清单

2026-11-15 讨论「补前端骨架」时，用户明确强调：

> 「就是我自己写的这个玻璃前端不会被换掉吧？这个就是最新版本，你不能换掉我的这个玻璃前端，要记住这个事情。」

补骨架的目的是让**页面结构**可维护，不是换视觉。两者混淆会导致：

- 用户几个月的设计成果被"技术升级"顺手丢掉
- 产品失去差异化（这套玻璃质感是和竞品拉开差距的地方）
- 已经验收过的界面重新变成未验收

**记在这里，是因为对话会结束，仓库不会。**
