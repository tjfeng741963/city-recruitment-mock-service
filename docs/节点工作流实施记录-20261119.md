# 节点工作流实施记录与接手清单（2026-11-19）

基线：main `9cf5dc7`。开发分支：`feat/node-workflow-followup`。依据仓库《方案-节点工作流与复聊-20261119.md》，本轮完成 P1 实现及部分对账护栏。**本记录不是线上发布证明，也不代表真实企微验收通过。**

## 1. 目标与边界

原链路首次接触先发完整旧开场，再把同一条消息提交 chat，导致重复介绍。旧开场没有等待闸门，greeted 布尔也无法描述发送进度。

本轮把流程介绍和自由答疑分为互斥出口，增加节点、等待、一次性复聊、本地游标和逐条发件箱。没有承诺添加好友瞬间触发，也没有缩短冻结发送器的耗时。好友发现仍依赖现有采集链路，配置的条间等待不等于客户看到消息的实际间隔。

## 2. 后端已实现

- 迁移 `046_agent_flow.sql` 新增流程、节点、边、会话状态镜像及预留服务端发件箱表。旧 position_opening 不删除、不覆盖。
- 六个接口：GET/PUT `/api/v1/agent-flow`、POST `/api/v1/agent-flow/migrate`、GET `/api/v1/agent/flow`、GET/POST `/api/v1/agent/state`。接口清单与守卫同步更新。
- 整图事务保存，version 递增；前端携带旧版本时冲突返回 409。旧开场迁移幂等，每条先变成等待节点，保存为停用草稿，由运营重新分组。
- 类型只接受 text/image/video/followup/branch/end，没有 await 类型。等待用 await_reply 布尔。每组 1–6 条，文本最多 2000 字；复聊只允许一条文本且 max_times 固定 1。
- 校验入口、孤儿、循环、停用节点、边起终点、等待出口、分支兜底；timeout 必须指向 followup，复聊后只能结束。
- 媒体必须启用且属于本岗位或通用池，名称不允许路径穿越。流程启用时，文本数字必须出现在本岗位事实字段。**数字集合校验不能识别同一数字用错单位或语境，仍需审核工资口径。**停用草稿允许保存待核对的历史数字。
- 运行接口使用现有 DeviceBridgeStore 绑定设备令牌与 device_code。状态按 `(device_code,session_key)` 隔离，只接受更大的 revision，避免旧镜像覆盖新游标。
- chat 新增 sent_summary，显式传入（包括空数组）时不再注入完整旧开场；省略时保持旧客户端行为。模型仍可简短回答客户主动追问的字段，约束的是整段重复介绍。
- `/agent/opening` 默认保持旧列表；仅显式 `mode=flow` 才展开首个等待闸门前的节点消息。

## 3. Windows 客户端已实现

新增纯标准库 `agent/flow_state.py`，只负责 SQLite 状态，不产生键鼠事件。修改 autopilot.py 的编排与 brain.py 的 HTTP 来源，`agent/wecom_io_core/` 四个冻结核心文件无改动。

### 单轮单出口

- 新客户只运行流程到第一个等待闸门，同轮不调 chat。
- 等待时客户文本优先匹配 keyword，其次 any_reply；空系统事件不推进。branch 支持关键词与 default 兜底。
- 旧联系人继续自由答疑，不因启用流程补播介绍。流程结束后不再落回旧开场。
- 按入站消息 ID 去重，防重启再次消费已推进过的消息；同一秒的新回复仍能处理。
- running 中断先续发；新的客户问题保留 pending，下一轮消费。即使没有新消息，tick 也能恢复 running。
- 旧列表兼容路径也取消了开场后同轮 chat，但等待闸门只在节点流程启用后生效，未启用岗位仍用原列表。

### 发送与故障

- 每条发送前 claim outbox，成功后立即落 sent 和游标。重复 claim 只有原状态 sent 才能跳过；sending/failed/unknown/skipped 都不能冒充成功继续走。
- 文本 ok=true 仍须回读确认 conversation_id。回读缺失或异常按 unknown；失败/未知均进入 held，不自动重发。流程发送失败立即停止当前批次，避免扩大到下一个联系人。
- 图片/视频先补本地素材，只有本轮先有文本成功且确认目标会话，才调用原 paste_media。重启直接续到纯媒体时 held，不能凭旧游标猜桌面焦点。
- 所有发送仍用原 core_send。没有新增定位键鼠动作，没有调整核心步骤 sleep、重试或焦点行为。
- paste_media 的成功表示原发送器执行成功，**不代表已获得数据库媒体送达证明**；真实送达、格式和焦点稳定性仍需实机测试。

### 复聊与持久化

- 按等待节点自己的 wait_minutes 计时；没有 timeout 边则到期 expired，有 timeout 边只发一次复聊，不继续后面的介绍。复聊后 30 分钟未回复进入 expired。
- 设备每 60 秒最多启动一次复聊，限速落 SQLite，失败和重启同样消耗配额。北京时间 21:00–09:00 不复聊。dry-run、非 online、人工接管、已流失时不主动发送。
- 每个会话保存开始时的完整流程快照，新版本只影响新会话；运营停用流程阻止新启动，在途会话继续自己的快照。
- 新配置每分钟刷新，独立缓存 `agent/state/flow.remote.json`，避免与 RemoteConfig 的 config.remote.json 两个写入者互相覆盖。缓存绑定服务器地址及设备编码；设备明确被拒绝鉴权时暂停发送。
- 启动及恢复 online 时对账。中断的发送记录进入 held；超过 10 分钟的 sending 在对账时转 unknown。服务端 revision 比本地新也先 held，不按节点序号推断分支进度。
- 仅服务端镜像、没有本地发件箱时，活动会话恢复为 held，终态可恢复。换机应完整复制状态文件，不能只凭服务端游标自动续发。
- 每日以北京时间 03:00 为日期分界，在线循环首次扫到时用 SQLite backup 生成快照，保留 7 份；不是独立系统计划任务。
- state 运行目录整体忽略提交；没有清理 greeted、没有移动或清空 reply_log.db，没有制造新联系人测试状态。

phase 只用 idle/running/awaiting/followup_due/followup_sent/replied/expired/held。outbox 单条状态是 sending/sent/failed/unknown/skipped，不能混用。

## 4. 后台 P1 编辑器

岗位 Agent 抽屉新增“流程”Tab，保留人设和旧开场。支持：从旧开场生成停用草稿、创建空白草稿、编辑标题和文本、选择媒体、增删组内消息、配置间隔、增删文本节点、设置等待和分钟数、添加一次性复聊、编辑删除出口与关键词、选择入口和启停、整图保存和未保存提示。

**目前是列表式过渡界面，不能描述成无限画布已经完成。**接口拒绝非法图，新增节点后必须把它接到入口可达路径再保存。媒体前应安排本轮可验证落点的文本。

## 5. 与方案的明确差异和剩余工作

1. 在途会话用自己的快照，不跟随最新版本重置节点；比“只缓存一份最新版”的草案更保守。
2. 流程缓存独立文件，不混写 config.remote.json。
3. 没有统一 `--state-dir`，没有移动旧 reply_log，也没有用导入 greeted=idle 的办法重播老客户。
4. 服务端 agent_flow_outbox 是预留表，本轮真实明细仍在本地，没有投递明细上报和网页轨迹。
5. 尚无网页解除流程 held 的入口。旧 `--retry-held` 只针对 reply_log，不能解除 flow_state 的 held；后续需有审计、逐条确认的恢复工具，不能直接清库批量补发。
6. P2 无限画布、拖拽连线、自动布局、微信气泡预览与导出未做；P3 会话状态徽标与轨迹页未做。
7. giveup 边暂为预留，没有客户端专用语义，列表编辑器不提供；拒绝场景先用关键词边到结束节点。
8. 没有迁移或启用正式岗位流程，没有改写线上深圳 9 条内容，也没有更新 Windows 运行程序。内容编排与代码部署须分别验收。

## 7. 同事发布与集中验收清单

用户没有多余普通微信，不要继续让用户消耗新联系人。先用模拟测试及专用测试设备，真实加好友由同事提供测试微信。

1. 审查开发分支和 CI。合并 main 会自动发布后台，但不能证明 Windows 已经升级；不要未经安排合并。
2. 备份后台数据库、Windows 程序配置、greeted、reply_log.db 和 state。停止唯一 sender 后做一致备份或 SQLite backup，保留 WAL；不要运行两个 sender。
3. 先部署后端迁移和接口，流程保持 disabled。Windows 同步 autopilot.py、brain.py、flow_state.py，确认设备令牌、岗位绑定、企微登录、桌面未锁定。
4. 测试岗位配置“要求→等待→薪资→等待→结束”，薪资挂 timeout 一次性复聊；测试 wait_minutes 可先设 1–2，正式设 15。数字必须来自该岗位事实，不随便写测试工价。
5. 首次触发只收要求，不应同时收到模型长答；空系统事件不推进；客户回复后只发薪资，不重发要求；流程结束后新问题正常答疑。
6. 到期只收到一条复聊，再等不重复。复聊发送失败必须 held，不能显示已发。测试避开北京时间静默时段。
7. 测试发送成功后重启和发送结果未知后重启。未知时停住是预期；禁止删除账本。纯媒体恢复缺少本轮文本验证时 held 也是预期。
8. 执行中改流程版本：旧客户按快照，新客户用新版本；停用不启动新流程、不重播旧介绍。
9. 人工接管、流失、掉登录、dry-run 不主动复聊；原正常工资、地址问答仍能使用。
10. 记录好友通过、首次发现、每条发送开始/回读、客户实际收到的时间，区分采集延迟、冻结发送器耗时及条间等待，不能把 delay_ms=1000 当成 1 秒送达保证。

实机通过前不能宣布“秒级连发已解决”“不会串人”“媒体已送达”或“方案全部完成”。

## 8. 回滚与下一开发顺序

后台回滚用 git revert 走 main 发布。Windows 恢复备份程序，保留新旧账本与快照。已有活动流程时，回滚旧客户端前先暂停 sender 并核对会话；旧客户端不认识新游标，不能直接恢复自动发送。

后续优先：实机验证 P1 → 有审计的 held 恢复及投递明细展示 → P2 无限画布/预览 → P3 状态徽标和轨迹。不得通过修改冻结动作层或清空状态绕过失败。
