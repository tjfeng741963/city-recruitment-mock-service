# Windows 发送异常与取证

11 月 22 日 08:15–08:18（北京时间），Dify 返回了回复，Windows 日志随后记录抢前台失败、输入校验失败、回车和未确认回读。事故现场发现有回复正文落入 PowerShell，旧客户端账本仍有一条记为已发送。事后检查只看到一个自动回复进程，焦点切换来源仍待确认。

新版要求从企微库的目标会话回读到唯一的新文本消息才记为发送成功。回读缺失、落入另一会话、多段只发了一部分或发送途中进程退出时，保留「待核对」记录，停止当前批次或流程，原记录不自动重发。人工指令通过正文核验后才继续发附带媒体。旧开场接口目前只有失败回执可用于未确认结果，回执附有核对原因，Windows 账本保留真实状态。

## 下次发生时收集什么

在运行 Windows 客户端的机器上，从安装目录执行以下只读命令。从旧到新查看轮转日志，保留故障时间前后的发送事件。

```powershell
Get-ChildItem -LiteralPath .\logs -Filter 'run.log*' -File |
  Sort-Object LastWriteTime |
  Select-String -SimpleMatch ' wecom_send ', ' wecom_send_hold ' |
  ForEach-Object { $_.Line }
```

- 记录客户端版本、设备标识及故障时间和时区。按 `attempt_id` 合并事件，用 `trace_id`、消息编号或人工指令编号与对应账本核对。
- `start`、`core_0`、`core_3`、`core_4` 和 `result` 分别对应发送入口、前台就位后的采样、输入校验通过后的采样、回车后的采样和最终结果。对照 `sender_pid`、`foreground_pid` 和 `window_class`，确认采样时前台是否发生变化。`start` 后缺少 `result` 时，同时检查进程退出或日志轮转。
- 统计 `phase=result` 的 `outcome` 和 `reason_code`，结合 `wecom_send_hold` 的已完成段数核对企微出站。优先检查 `wrong_conversation`、`target_conversation_missing`、`target_message_missing` 和 `sender_exception`。采样事件只记录窗口类和进程 ID，以及关联所需的编号，省略窗口标题、聊天正文和剪贴板内容。

## 验收与回退

隔离验收覆盖无回读、错会话、第二段失败、异常退出与人工附件顺序。真人验收用专用测试会话，核对企微出站、客户端账本和网页人工回执。窗口日志是事后采样，发送中途切换焦点仍可能影响按键落点。媒体是否到达也需要单独核对，现有媒体动作回执只表示客户端执行了发送操作。

回退时先备份回复账本和轮转日志，再通过客户端发布流程回退代码。已记录为「待核对」的条目保留原状态。逐条核对企微后再决定如何处理，整批重新入队可能重复已确认的段落。
