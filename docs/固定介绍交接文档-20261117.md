# 固定介绍连续发送交接文档

> 更新日期：2026-11-17（北京时间）  
> 适用版本：`main` `e52969774a81448ea2d0b4489383df31e89e611a`  
> 交接对象：下一位负责 Windows 企微客户端实测、日志诊断和后续开发的同事

这份文档只记录本轮“加好友后自动发送固定招聘介绍”的真实修改、发布和验收结果。它不包含任何密码、token、客户姓名、真实会话 ID 或客户资料。接手时先看本文，再看仓库根目录的 `AGENTS.md`；客户端动作层的限制优先级最高。

## 1. 需求和最终目标

业务要求是两个有先后关系的环节：

1. 普通微信添加当前企业微信，企业微信自动通过后，客户端主动发送后台配置的多条固定招聘介绍。
2. 固定介绍全部发送完成后，客户之后提出的问题才进入知识库问答。

固定介绍期间客户可能已经发来问题。这个问题必须保留，不能打断固定介绍，也不能先回答问题导致介绍缺段。正确顺序是：

```text
加好友提示入库
  → 取固定介绍分段
  → 按顺序发完全部分段
  → 确认固定介绍完成
  → 读取并回答期间积压的问题
```

本方案继续使用现有 Windows 客户端读取企业微信本地解密库和既有键鼠发送链路，没有接入企业微信官方客户联系 API，也没有使用企业微信原生欢迎语。

## 2. 当前真实链路

```text
普通微信加企微并被通过
  → WXWork 本地库出现自动好友提示记录（常见 type=1011/type=2）
  → agent/autopilot.py 的 scan() 发现并登记 reply_log
  → drain() 按会话判断是否首次接触
  → agent/brain.py 请求 8090 的 /api/v1/flow/greet
  → 服务端返回 reply + parts
  → autopilot 逐段调用现有发送函数
  → 每段确认落到当前会话
  → 整组完成后才把会话记入 greeted
  → 下一轮 drain 才处理客户期间发来的问题
```

这里的“自动发送”依赖企业微信本地库先出现可读的自动好友提示记录。它不是官方好友事件回调，因此企业微信自身没有写入提示、客户端未运行、客户端掉线或 Windows 桌面会话不可用时，客户端不会凭空发送。

主要本地状态如下：

| 状态 | 位置 | 用途 |
| --- | --- | --- |
| 固定介绍投递记录 | `agent/reply_log.db` | 保存介绍原文、分段、当前段、成功/失败/未知状态 |
| 已完整打过招呼的会话 | `agent/.greeted.json` | 防止客户端重启后重复发送整组介绍 |
| 运行参数缓存 | `agent/config.remote.json` | 缓存设备远端配置和话术版本 |
| 运行日志 | Windows `C:\agent\logs\run.log` | 观察轮询、远端配置、桌面状态和发送结果 |

## 3. PR #54：固定介绍与普通问答分阶段

PR #54 已合并到 `main`，合并提交为 `ca5f597`，主题是“加好友固定介绍连续发送并阻断问答抢占”。主要改动只在 `agent/autopilot.py` 和客户端测试文件，未修改 `agent/wecom_io_core/`。

### 3.1 固定介绍按 parts 分段发送

服务端返回的固定介绍包含完整文本和 `parts`。客户端逐段发送：

- `WELCOME_PART_DELAY = 1.1`：代码目标是相邻介绍段之间约 1.1 秒；
- 第一段使用原有完整发送流程，负责搜索并确认目标会话；
- 第一段成功后设置 `welcome_fast_ready = True`；
- 后续段使用 `_send_welcome_part_fast()`，复用已经打开的同一会话，不再每段重新 `Ctrl+F` 搜索；
- 后续段仍使用原有的清空输入框、粘贴、哨兵回读、回车发送等动作，不新增鼠标点击、Alt、Tab 或 SendInput；
- 每段发送后刷新本地库，并记录该段已确认。

关键代码位置：

- 常量：`agent/autopilot.py:153-154`
- 分段循环：`agent/autopilot.py:1364-1436`
- 同一会话快速续发：`agent/autopilot.py:1507`

### 3.2 普通问题不会抢占固定介绍

`drain()` 会先找当前会话尚未完成的 welcome delivery。只要该记录仍在 `ready` 或待续发状态，当前会话就由固定介绍拥有；同一会话后续收到的“工资多少”等问题继续留在 `reply_log.db` 的 pending 队列，不会在本轮被知识库处理。

固定介绍所有分段确认完成后，客户端才把会话加入 `.greeted.json`。下一轮才会读取积压的问题并调用 `Brain.reply()`。这就是本轮真实测试中“发送工资多少没有打断固定介绍”的原因，也是预期行为。

### 3.3 失败和重启不会直接丢掉介绍

固定介绍的“取文案”和“确认已发送”分开处理：

- `/flow/greet` 成功只代表拿到了文案，不代表客户已经收到；
- 首段或后续段发送失败时，原文和当前分段进度保留；
- 发送结果未知时不自动重放整组，避免重复发送；
- 重启后可以从已确认的分段继续，但必须先检查日志和真实聊天窗口；
- 只有整组完成才记为已打招呼。

## 4. e529697：修复首条介绍延迟二三十秒

本次真实验收发现：自动通过好友后前十秒没有发送，二三十秒后才出现第一条。通过 Windows 日志确认了原因。

### 4.1 原因

设备远端配置的通用 `interval_seconds` 默认是 20 秒。PR #54 只在客户端启动时把 flow 模式的轮询压到 3 秒，但每次心跳都会执行 `RemoteConfig.sync()`，它又把通用 20 秒配置写回 `cfg["interval"]`。

因此客户端实际表现是：

```text
启动时 3 秒
  → 心跳刷新远端配置
  → interval 被恢复成 20 秒
  → 主循环下一轮 sleep 20 秒
  → 自动好友提示要等到下一轮才被 scan() 发现
```

部署前 Windows 日志中的心跳间隔约 42 秒，能够印证客户端正在按通用配置运行，而不是按欢迎语目标运行。

### 4.2 修复内容

提交 `e529697` 增加 `_enforce_flow_welcome_interval(cfg)`：

- flow 模式且当前 interval 大于 3 秒时，强制收紧为 3 秒；
- 启动时调用一次，覆盖有桥和无桥两种配置；
- 每次远端配置热刷新后再次调用，防止后台默认值把它恢复成 20 秒；
- 非 flow 模式不受影响；
- 只改变轮询调度，不改变任何企微键鼠动作。

关键代码位置：

- `agent/autopilot.py:157`：`_enforce_flow_welcome_interval()`
- `agent/autopilot.py:606`：心跳远端配置刷新后的保护
- `agent/autopilot.py:2185`：启动阶段的保护

部署后的 Windows 日志已经出现：

```text
[远端配置] ... 热更 interval
[首句] flow 触发轮询已收紧为 3s
```

这解决的是“第一条介绍启动太晚”。它把目标恢复到“本地好友提示出现后最多等一个约 3 秒轮询周期”，不等同于保证好友通过动作本身一定在固定毫秒数内完成。

## 9. 已知限制与后续开发方向

### 9.1 不能承诺每秒发送的原因

代码中目标间隔是 1.1 秒，但 Windows 企微发送不是普通 HTTP 接口。现有发送链路要求窗口可见、输入框哨兵回读和发送后回读。企业微信检测到自动化后可能把窗口隐藏约 9 秒，客户端必须等待窗口恢复，否则继续发送可能触发风控。

因此后续开发只能在 `agent/autopilot.py` 的编排层做：

- 增加每段开始/结束时间的日志；
- 区分“代码主动等待”和“窗口隐藏等待”；
- 统计每段发送结果和恢复原因；
- 优化调度和失败状态；
- 继续保持问题排队和介绍优先。

不得为了追求 1 秒直接修改 `wecom_io_core`、增加点击、绕过 `_wait_visible()` 或快速重试。

### 9.2 建议的后续开发顺序

1. 由同事完成一次新版本真实速度验收，拿到逐段时间戳和日志；
2. 如果第一条仍超过 3 秒，检查 flow 模式、远端配置热更和本地 `.greeted.json`，不要先改发送动作；
3. 如果第一条及时但后续间隔变长，确认是否命中窗口隐藏或输入框校验失败；
4. 根据证据补充测试，重点覆盖“分段中断后恢复”和“提问积压后按顺序处理”；
5. 只有确认根因属于编排逻辑时，才继续修改 `autopilot.py`，并按 `AGENTS.md` 先写诊断、测试和回滚方案；
6. 每次客户端修改都要同步到 `C:\agent`，不能只推 `main` 就认为 Windows 已更新。

### 9.3 不要做的操作

- 不要删除 `.greeted.json` 来反复制造首次联系人；
- 不要清空 `reply_log.db`；
- 不要运行 `--reset` 作为测试准备；
- 不要对真实客户发送测试文本；
- 不要在固定介绍未完成时手动插入同一会话回复；
- 不要启动第二个 autopilot 实例；
- 不要把后台保存成功当作 Windows 已发送成功；
- 不要把 CI 通过当作真实企微送达证据。

## 10. 回滚方式

如果新版本导致客户端无法启动或企微状态异常，先保留日志和当前数据库状态，再执行回滚：

1. 停止 `wecom-agent`；
2. 备份当前 `C:\agent\autopilot.py`；
3. 将已核对的备份文件恢复为 `C:\agent\autopilot.py`；
4. 启动 `wecom-agent`；
5. 核对企业微信 online、待发队列和日志；
6. 不删除 `.greeted.json`、`reply_log.db` 或聊天历史。

代码仓库回滚使用普通 `git revert`，不要 force push `main`。如果只需要回滚 Windows 客户端，先回滚客户端文件并保留服务器版本，避免把已经发布的知识库修复一起回退。
