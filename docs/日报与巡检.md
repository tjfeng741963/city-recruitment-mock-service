# 日报与数据巡检

两个只读脚本，解决两件不同的事：

| 脚本 | 给谁看 | 回答的问题 | 会不会改库 |
|---|---|---|---|
| `scripts/daily_report.py` | 老板 / 顾问 | 今天约了几个、到面率多少、有没有人等着回 | 不改 |
| `scripts/inspect.py` | 运维 / 开发 | 库里有没有脏数据、采集端还活着吗 | 默认不改；`--fix-safe` 只改被判为安全的项（当前没有） |

都在 `backend/` 下用 `uv run` 执行。两个脚本都只读库，跑在线上不会打断业务。

## 一、日报 daily_report

### 用法

```bash
cd backend

uv run python -m scripts.daily_report              # 今天（东八区）
uv run python -m scripts.daily_report --date 2026-11-04
uv run python -m scripts.daily_report --days 7     # 近 7 天：逐日表 + 合计
uv run python -m scripts.daily_report --json       # 机器可读
```

`--date` 与 `--days` 可组合：`--days 7 --date 2026-11-04` 表示以 11-04 为最后一天
往前数 7 天。`--date` 的格式是 `YYYY-MM-DD`，格式错会直接报参数错误（退出码 2），
不会静默退回今天——日期猜错比报错更麻烦。

### 真实输出（2026-11-04，`data/app.db`）

```
===== 城市招聘日报 2026-11-04 =====
【线索】
  今日新线索        3
  今日约面          2
  今日到面          0
  今日爽约          0
  待核实            0
【漏斗（累计）】
  已约面 2   已到面 0   爽约 0
  到面率 0.0%   爽约率 0.0%
【会话】
  总会话 73   今日有消息 6   今日入站消息 14
  未回复（最后一条是客户） 13
【采集端】
  pc-office-01   online / online   最后心跳 13 秒前
【开关】
  线索抽取：开启   扫描：开启
```

`--days 7` 会多一段逐日表：

```
===== 城市招聘日报 2026-10-29 ~ 2026-11-04（7 天）=====
【逐日】
  日期            新线索  约面  到面  爽约  入站
  2026-10-29           0     0     0     0     6
  ...
  2026-11-04           3     2     0     0    14
  合计                 3     2     0     0    26
```

逐日表之后仍是同一套漏斗/会话/采集端/开关，其中「期内有消息 / 期内入站消息」
是 N 天的和，「总会话 / 未回复 / 待核实」是当前快照（这几个量按天相加没有意义）。

### 指标口径

**切日**：全部按东八区（UTC+8）切天，库里是 naive UTC。查询边界在 Python 里
换算成 naive UTC 后再进 SQL，例如本地 `2026-11-04 00:00` = UTC `2026-11-03 16:00`。
直接按 UTC 切，本地 0–8 点发生的单会被算到前一天，早班时段全错。

| 指标 | 怎么算 | 为什么这么算 |
|---|---|---|
| 今日新线索 | `leads.created_at` 落在当天 | `created_at` 是这条线索第一次被抽出来的时间，等于「今天新进来多少人」 |
| 今日约面 | `lead_events` 中 `event_type='scheduled'` 且 `at` 落在当天 | 用流水不用 `stage`：今天约了 3 个、其中 1 个明天改期，看 `stage` 只能看到最后状态，会少算 |
| 今日到面 | `lead_events.to_stage='interviewed'` 且 `at` 落在当天 | 人工标记才会产生这条流水，是唯一可信的「人真的来了」 |
| 今日爽约 | `lead_events.to_stage='no_show'` 且 `at` 落在当天 | 同上，只能人工判定 |
| 待核实 | `leads.pending_confirm=1` 的当前条数 | 是「此刻还挂着多少」，不是某天的流水，所以不带日期条件 |
| 已约面（累计） | `lead_events` 中 `event_type='scheduled'` 的总条数 | 与 `GET /api/v1/leads/stats` 的 `funnel.booked` 完全一致 |
| 已到面（累计） | `lead_events.to_stage='interviewed'` 总条数 | 同上，与 `funnel.interviewed` 一致 |
| 爽约（累计） | `lead_events.to_stage='no_show'` 总条数 | 同上 |
| 到面率 | 已到面 ÷ 已约面 | 分母必须是「约过面的人」。用线索总数做分母，会把还在咨询的人算成没到面，数字永远偏低 |
| 爽约率 | 爽约 ÷ 已约面 | 同上 |
| 总会话 | `conversations` 总条数 | — |
| 今日有消息 | 当天有消息的**会话去重数** | 一个客户连发 10 条只算 1 个活跃会话 |
| 今日入站消息 | 当天 `direction='inbound'` 的消息条数 | 入站才是客户主动，出站里混着自动回复，混在一起看不出热度 |
| 未回复 | 最后一条消息是 `inbound` 的会话数 | 「客户说了话、我们还没接」才是要人处理的事。按 `max(id)` 取最后一条：`messages` 只追加，同一秒内的多条也不会并列 |
| 采集端 | 第一条设备的 `status / wecom_state / 最后心跳` | 单机阶段只认第一台设备，与 `api_lead_board` 同一取法。心跳秒数只做展示，离线判定由 `workers/device_watch` 负责，日报不重复下结论 |
| 开关 | `lead_guard` 的 `LEAD_EXTRACT_OFF` / `LEAD_SWEEP_OFF` 文件是否存在 | 文件存在即关闭，每次调用重新 stat，不缓存 |

**分母为 0 时输出 `-`，不输出 `0.0%`。** 「一个都没约」和「约了都没来」是两件事，
后者才是问题；混成同一个 0% 会让老板在没什么可看的时候以为出了事故。
JSON 里对应 `null`，不是 `0`。

`--json` 的顶层结构与终端板块一一对应：

```json
{
  "date": "2026-11-04",
  "leads": {
    "new": 3, "scheduled": 2, "interviewed": 0, "no_show": 0,
    "pending_confirm": 0,
    "funnel": {"booked": 2, "interviewed": 0, "no_show": 0,
               "interview_rate": 0.0, "no_show_rate": 0.0}
  },
  "sessions": {"total": 73, "active_today": 6, "inbound_today": 14, "unreplied": 13},
  "device": {"device_code": "pc-office-01", "status": "online", "wecom_state": "online",
             "last_heartbeat_at": "2026-11-04T20:59:30+08:00", "age_seconds": 27},
  "switches": {"extract": {"enabled": true, "reason": ""},
               "sweep":   {"enabled": true, "reason": ""}}
}
```

`--days N` 时顶层多出 `mode: "range"`、`start`、`end`、`days`（逐日数组），
`leads` 里是 N 天的合计 + 当前待核实 + 累计漏斗；`sessions.active_today` 与
`inbound_today` 是 N 天的和。

## 二、巡检 inspect

### 用法

```bash
cd backend

uv run python -m scripts.inspect              # 全部检查
uv run python -m scripts.inspect --fix-safe   # 只自动修「安全」的问题（当前没有）
```

### 真实输出（2026-11-04，`data/app.db`）

```
===== 数据巡检 2026-11-04 20:59 =====
[WARN] 岗位缺城市    145/218 个岗位没有 city（66.5%，阈值 50%）
[OK] 线索置信度低  0 条线索 confidence < 0.65
[OK] 长期待核实    0 条待核实超过 48 小时
[OK] 会话孤岛      0 条消息的 conversation_id 找不到所属会话
[OK] 重复线索      0 个会话有多条线索记录（同一会话只应有一条）
[OK] 设备从未心跳  0/1 台设备从未上报心跳
[OK] 卡片错误      0 个会话 external_id 为空（回执对不上，卡片发不出去）
[OK] 库体积        1.1 MB（data\app.db，阈值 500 MB）
------------------------------------------------------------
共 8 项：OK 7 / WARN 1 / FAIL 0
```

### 检查项与判定

| 检查 | 判定 | 级别 | `--fix-safe` |
|---|---|---|---|
| 岗位缺城市 | `kind='job'` 且 `city is null` 的条数，占岗位总数 > 50% 报警 | WARN | 否 |
| 线索置信度低 | `leads.confidence < 0.65` 的条数，> 0 报警 | WARN | 否 |
| 长期待核实 | `pending_confirm=1` 且 `coalesce(check_at, updated_at)` 早于 48 小时前 | WARN | 否 |
| 会话孤岛 | `messages.conversation_id` 找不到对应 `conversations` 的条数 | **FAIL** | 否 |
| 重复线索 | `leads.conversation_id` 出现多次的会话数 | WARN | 否 |
| 设备从未心跳 | `devices.last_heartbeat_at is null` 的台数 | WARN | 否 |
| 卡片错误 | `conversations.external_id` 为 NULL 或空串的条数 | WARN | 否 |
| 库体积 | SQLite 主库文件 > 500 MB | WARN | 否 |

三点说明：

- **级别**：`OK` 正常；`WARN` 需要人看一眼，但不阻断；`FAIL` 是数据完整性问题
  （消息读不出来 / 统计口径被污染），必须当天处理。
- **只有「会话孤岛」是 FAIL**。其余项是常态噪音——缺城市、置信度低每个库都会有几条，
  一报警就让人重视，结果就是整条巡检被忽略。
- **单项执行失败记 WARN 并继续**，不中断整轮。表还没建、字段临时缺失都会走到这里，
  这是工具/环境问题，不应该伪装成数据问题，也不该让一轮巡检整体罢工。

### 为什么 `--fix-safe` 现在什么都不改

框架是留好的：每个检查项都可以挂一个 `fixer`，`--fix-safe` 只跑挂了 `fixer` 的项。
但目前 8 项全部 `fixer=None`，原因写在各检查项的 `manual_reason` 里：

| 检查 | 不能自动修的原因 |
|---|---|
| 岗位缺城市 | 城市要从岗位原文里抽，误判会改坏知识库原文（这是给客户回答工价的依据） |
| 线索置信度低 | 置信度低说明模型判不准，改状态得人看对话，自动改等于乱猜 |
| 长期待核实 | 到面/爽约只能人确认，工具无权替客户下结论 |
| 会话孤岛 | 补会话还是删消息会影响历史，得判断哪边是对的 |
| 重复线索 | 合并两条线索要先决定保留哪个 `stage`，自动合并会丢进度 |
| 设备从未心跳 | 心跳为空说明采集端没跑起来，删设备记录不解决任何问题 |
| 卡片错误 | 缺 `external_id` 通常是采集端上报丢了，要重新同步而不是清空 |
| 库体积 | 压缩/归档库要停机窗口和备份，脚本里做太危险 |

一句话：**这个库里"能自动修"的脏数据，修错的代价都比留着的代价大。**
等真出现安全的场景（比如给存量数据回填一个确定无歧义的默认值），
给对应 `Check` 挂 `fixer` 即可，`fix_safe` 的执行/提交/回滚逻辑已经就位。

### 退出码

| 结果 | 退出码 | cron/CI 行为 |
|---|---|---|
| 全部 OK / 只有 WARN | 0 | 继续，日志里留痕 |
| 出现 FAIL | 1 | 触发告警，人工介入 |

`WARN` 不返回 1 是刻意的：每天都有 WARN 的检查一旦阻断流水线，人就会关掉它。

## 三、放进定时任务

### Linux（cron）

```bash
# 每天 08:30 出当天日报（含昨天为止的数据），追加到日志
30 8 * * * cd /opt/city-recruitment-mock-service/backend && /usr/local/bin/uv run python -m scripts.daily_report >> /var/log/recruit/daily.log 2>&1
# 每天 09:00 巡检；退出码非 0 才发告警
0 9 * * * cd /opt/city-recruitment-mock-service/backend && /usr/local/bin/uv run python -m scripts.inspect >> /var/log/recruit/inspect.log 2>&1; [ $? -ne 0 ] && echo "巡检发现 FAIL，见 /var/log/recruit/inspect.log" | mail -s "数据巡检告警" ops@example.com
```

两个注意点：

- `cd` 到 `backend/` 再跑。`app.settings` 会读当前目录的 `.env`，库路径也是相对
  `data/app.db` 的，cwd 不对会连到空库。
- `uv` 用绝对路径。cron 的 `PATH` 只有 `/usr/bin:/bin`，直接写 `uv` 会 command not found。

### Windows（计划任务）

```powershell
schtasks /Create /SC DAILY /ST 08:30 /TN "recruit-daily-report" /TR "cmd /c cd /d C:\city-recruitment-mock-service\backend && C:\Users\me\.local\bin\uv.exe run python -m scripts.daily_report >> C:\city-recruitment-mock-service\backend\data\logs\daily.log 2>&1" /F
schtasks /Create /SC DAILY /ST 09:00 /TN "recruit-inspect" /TR "cmd /c cd /d C:\city-recruitment-mock-service\backend && C:\Users\me\.local\bin\uv.exe run python -m scripts.inspect >> C:\city-recruitment-mock-service\backend\data\logs\inspect.log 2>&1" /F
```

- 先把 `uv.exe` 换成 `where uv` 的实际路径（WinGet 装的一般在
  `%USERPROFILE%\.local\bin\uv.exe`），日志目录先手动建好。
- 路径含空格时 `/TR` 的引号会被 cmd 吃掉，改为写一个 `.bat` 再用 `/TR "C:\path\run.bat"`。
- 想在 FAIL 时弹窗/发邮件，用「任务计划程序」里给该任务挂一个「事件触发」，
  或直接改成运行 `inspect.bat`（内容 `uv run python -m scripts.inspect || exit /b 1`）。

### 指向别的库

两个脚本都走 `app.db.SessionLocal()`，库地址由 `APP_DATABASE_URL` 决定，
默认 `sqlite+aiosqlite:///./data/app.db`：

```bash
APP_DATABASE_URL="sqlite+aiosqlite:///./data/backup-20261101.db" uv run python -m scripts.daily_report --date 2026-11-01
```

测试用同一个开关隔离：`APP_DATABASE_URL="sqlite+aiosqlite:///./data/test_report.db"`。

## 四、巡检结果怎么读

### 看到 WARN

按这个顺序看，**不是每条都要当天处理**：

1. **长期待核实**：有人约了面，到点了没人确认来没来。这是直接丢单的地方，
   先看 `/leads/board` 的「待核实」分组，逐个打电话确认。超过 48 小时基本等于流失。
2. **卡片错误**（`external_id` 为空）：这些会话的消息发不出去，客户看到的是没人回。
   先看是不是采集端重启后没回填会话标识，重新同步一次；不要删会话。
3. **重复线索**：一个会话两条线索，看板和统计会翻倍。查是哪次抽取并发写进去的。
4. **设备从未心跳**：采集端装了但没连上。看设备端日志和 `data/instance.json`，
   不是数据库问题。
5. **岗位缺城市**：占比高说明岗位抽取没覆盖「城市」这一列。影响的是「XX 有什么岗位」
   这类检索——`kb_search` 的第一层就是 `city`，缺了只能退化成全文扫。当前真实库
   是 145/218（66.5%），属于**已知欠账**，按批补，不需要每天看。
6. **线索置信度低**：抽样看几条对话，判断是模型判错还是客户真的没说清楚。
   用来调抽取 prompt，不是逐条改数据。
7. **库体积**：接近 500 MB 时规划一次归档（历史消息按年切表），提前做，别等到写不进去。

### 看到 FAIL

只有一种：**会话孤岛**。处理顺序：

1. 先备份：`cp data/app.db data/app.db.bak-$(date +%F)`
2. 看规模：`[FAIL] 会话孤岛 12 条消息的 conversation_id 找不到所属会话`
3. 少量（个位数）：大概率是手工删过会话或写消息时拿错 id，按 `conversation_id`
   查这几条消息，人工判断是补会话还是删消息。
4. 大量（成百上千）：先停采集端，再查是不是同步逻辑在会话落库前就写了消息。

**不要**在没备份的情况下跑任何 `DELETE`。巡检只负责报告，不负责清理。

### 必须人工、工具永远不该碰的

- 到面 / 爽约 / 入职的判定（`manual` 接口）
- 岗位的城市、工价、年龄这些事实字段
- 删除任何会话或消息
- 合并重复线索
