# 企微风控后重新扫码登录——预案设计（暂不实现）

> 2026-11-11。场景：企业微信触发风控，桌面端被登出，需要人工重新扫码。
> 本文只做设计，不动代码。实现时机：客户专用机（134.175.40.31）跑起真实账号后。

## 一、场景还原

```
正常：autopilot 轮询本地解密库 → 生成回复 → 键鼠发送
风控：企微被强制登出 → 桌面弹出扫码登录窗
      ├── 解密库不再更新（收不到新消息）
      ├── 发送必然失败（会话窗口不存在）
      └── autopilot 还在跑 → 盲发 → 更高的风控风险
```

**核心原则：宁可掉线停摆，绝不盲发。**

## 二、检测（怎么知道被风控了）

三层信号，任一命中即判定"会话不可用"：

| 层 | 信号 | 检测方式 |
|---|---|---|
| 窗口 | 出现企微登录窗（标题含「登录」「扫码」） | win32 枚举顶层窗口标题 |
| 收件 | 解密库 N 分钟无新消息（且历史平均有） | collector 增量为 0 计时器 |
| 发件 | 连续 3 次 send 失败且失败原因一致（找不到会话/窗口） | reply_log 失败连击计数 |

三者同时/相继成立才触发，避免误判（客户长时间不回消息≠掉线）。

## 三、处置（触发后自动做什么）

```
① 立即停发：autopilot 主循环挂起，reply_log 记 skipped(reason="风控离线")
② 心跳降级：向 4222 报 state=offline —— 网页设备列表立刻显示掉线
③ 队列保护：bridge_commands 里未执行的发送指令标记挂起（claim 后不执行），
   防止恢复登录后突然把积压消息连环轰炸出去
④ 通知：4222 reminder-tasks 加一条「设备 X 需要人工扫码」，
   前端设备页红标（现有 online 字段已支持展示）
```

## 四、恢复（人工扫码之后）

```
人工扫码登录成功
   → client 检测到主窗口恢复（登录窗消失 + 会话列表可见）
   → 心跳恢复 state=online
   → 挂起的发送指令【丢弃】而不是补发（时过境迁，补发必尴尬）
   → reply_log 记一条恢复事件，主循环自动继续，无需重启进程
```

## 五、运营侧配合（降低风控概率）

| 措施 | 现状 |
