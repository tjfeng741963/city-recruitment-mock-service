## 一、客户答应面试后，前端会看到什么（现有链路实测）

```
客户："可以"（答应面试）
  ├─ 8090 flow：stage → collect（开始要姓名电话）
  ├─ ⚠️ 4222 此时【没有任何变化】——前端无感知（缺口，见下）
  ▼
客户："张三 13812345678"（姓名+电话齐了）
  ├─ 8090：stage → done，action=book_interview
  ├─ 档案推送 4222：
  │    agent_conversations：name/phone/recruit_status=invited/state=pending_invite/
  │                         factory_name/interview_date/interview_time/province
  │    candidate_events：新建一条「报名成功」事件
  ▼
前端三处同时变化（刷新即见）：
  ① 对话管理列表：姓名/电话副行出现、工厂+城市行出现、📅 面试日期徽标点亮
     （徽标条件：interview_date 且 recruit_status=invited）
  ② 候选人员页：「报名成功」tab 出现一行：
     设备 | 昵称 | 姓名 | 电话 | 事件时间 | 面试日期 | 面试工厂 | 城市/区县 | 提醒次数
  ③ 待提醒任务：面试日过后自动进入，供跟进
```

### 现有真空档（答应面试的"瞬间"）

`collect` 阶段（答应了、姓名电话还没拿到）前端**完全看不见**——运营不知道
"这个客户已经答应面试、正在留联系方式"。如果客户给到一半走人，运营无从跟进。

**补法（待实装，约半天）**：`collect` 阶段也推一次档案（只带 stage，不带姓名电话），
React 候选页加「沟通中」状态显示；拿到姓名电话后自动升级为「报名成功」。

## 三、城市-工厂-岗位-知识库统一逻辑（设计）

### 数据模型（现状已具备，缺的是"用起来"的规则）

```
4222 资源库（运营管理页维护）
  cities（province, city_name）
    └─ factories（factory_name, place 在 data_json）
         └─ service_positions（wage/hours/age/welfare 在 data_json）

4222 话术层
  device_scripts（device_code + stage + city 唯一）      ← 给哪台机、哪个阶段、哪个城市
  unknown_questions（question, occurrence_count）        ← 答不上的问题沉淀

8090 知识层
  kb_entry（kind=script, city, factory_name, title, body）← 插问话术，字段天然带城市
```

### 统一取数规则（一条消息进来后的查找顺序）

```
定位三要素：device_code（哪台机）→ city（客户城市）→ stage（对话阶段）

① 发岗位信息（send_info）
   device_scripts(device, send_info, city) 命中
      → 渲染 {{factory}} {{wage}} {{place}} {{window}} 占位符（数据=该城市 service_positions）
      → 整段直发，模型不碰数字
   未命中 → 4222 jobs(city) 代码拼多段 → 再无 → DEMO_JOBS 兜底

② 插问（体检/住宿/社保/地点…）
   kb_entry(kind=script) 打分匹配：
      基础分 = 命中关键词总长
      【城市加权】entry.city == 客户城市 → +3 分；entry.city 为空 → +0；
                 entry.city != 客户城市 → 排除（深圳的住宿话术不发给东莞客户）
      取最高分，低于阈值 → 兜底「我确认一下」+ 记 unknown_questions

③ 换岗位
   纯代码列该城市 service_positions（模型看不见岗位列表，永远不让它答）

④ 未命中沉淀
   unknown_questions → 运营照清单补录 kb_entry
   （标题=问题主题含关键词，正文=话术，city 选填，立即可用无需重启）
```

### 这个设计的关键点

1. **城市是贯穿所有层的索引**：资源（岗位）、话术（device_scripts）、知识（kb_entry）
   都带 city 维度，查找时城市不一致直接排除——杜绝"广州话术发给东莞客户"类事故
2. **事实与话术分离**：岗位数字（工价/年龄）永远来自 service_positions，话术只是模板；
   模型只负责理解意图，不产出任何事实
3. **闭环运营**：对话答不上 → unknown_questions 沉淀 → 运营补录 → 立即生效，
   知识库越用越准，不需要开发介入
