## 1. 本轮修了什么

### 1.1 问题

企业微信的 `message_id` 是**按登录账号自增**的，不是全局唯一。同一个数字在 A 号表示 A 号会话的某条消息，在 B 号表示完全不同的一条。`reply_log` 旧表把 `message_id` 设成全局 `UNIQUE`，于是换账号后新消息被 `INSERT OR IGNORE` **静默吞掉**——既不报错，也不进队列，客户永远等不到回复。

实测在客户端库中确认到这类被吞的消息（`Evans_峰`、`🦄Garbo_C🦄` 等会话的重复 ID 段），加上账号切换场景频繁（退出登录、重新扫码都会触发），属于必须修的阻塞项。

### 1.2 改动

| 文件 | 改动 |
| --- | --- |
| `agent/reply_store.py` | `reply_log` 唯一键改为 `UNIQUE(conv_id, message_id)`；`init()` 检测旧表若存在 `message_id` 单列唯一索引，则重建表并原样搬移历史行 |
| `agent/reply_store.py` | `mark_sent/mark_failed/mark_unknown/mark_skipped/mark_held` 增加 `conv_id` 参数，UPDATE 收窄为 `WHERE conv_id=? AND message_id=?` |
| `agent/reply_store.py` | 欢迎语记账（`save_welcome`/`fail_welcome`/`confirm_welcome_part`/`resolve_welcome`）对 `reply_log` 的更新同样按 `conv_id` 收窄 |
| `agent/autopilot.py` | 全部 16 处调用点补上 `cid`；`--reset` 路径用行内 `conv_id` |
| `backend/tests/test_reply_log_conv_message_key.py` | 新增：跨账号同 ID 可共存、同会话幂等、`mark_sent` 不串会话、旧库迁移保留数据 |

迁移是**幂等**的：第二次 `init()` 检测不到单列唯一索引就直接跳过，不会重复重建。

## 3. 当前阻塞：企微窗口渲染失效

### 3.1 现象

客户端能收消息（`1688855894882096` 的 `message.db` 在 12:05 仍在写入），队列也在动，但**每一条发送都在输入框校验失败**：

```text
步骤0 前台就位、窗口可见
步骤1 已回车进入会话
步骤2 已清空输入框残留
发送失败：输入框校验：焦点未落在输入框（Ctrl+C 未生效，剪贴板仍是哨兵）
```

同样的三段序列每约 30 秒重复一次，`抢不到前台` 计数为 0，`企微窗口持续隐藏` 计数为 0——说明**不是** `ensure_foreground` 失败，也**不是** `_wait_visible` 判定隐藏。

### 3.2 定位过程与已排除项

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| RDP 断开导致桌面不可用 | 排除 | `qwinsta` 显示 console / Administrator / ID 2 / **运行中** |
| 企微窗口被隐藏 | 排除 | `IsWindowVisible=True`，`IsIconic=False` |
| 窗口在屏幕外 | 排除 | rect `(1,1)-(1023,719)`，在 1024×768 内 |
| 窗口在别的虚拟桌面 | 排除 | `IsWindowOnCurrentVirtualDesktop=True`，三窗口 desktopId 相同 |
| 多开窗口互相遮挡 | 排除 | 逐个 `SetWindowPos` + `SetForegroundWindow` 后仍失败 |
| **渲染面失效** | **确认** | 桌面截图和 `PrintWindow` 拿到的都是**空白/纯黑**，任务栏也没有企微图标 |

三个 `WeWorkWindow`：

```text

hwnd=2163514 pid=4780 visible=True  rect=(1,1)-(1023,719)
hwnd=9896916 pid=6636 visible=False
```

企微进程树：`6636`（11/16 16:35，带 `/relogin_param=…设备环境异常，需要通过手机企业微信扫码进行安全验证`）→ `604`（`--broker`）→ `6544` / `4780`（`--switch-account`）。

也就是说：窗口对象存在、样式是可见的、焦点能抢到，但会话内的 Chromium 绘制表面已经不再输出内容。键鼠事件打进去，输入框并不存在，`Ctrl+C` 自然复制不到东西，剪贴板停在哨兵值——这与 `verify_input_box` 的报错完全吻合。

### 3.3 结论：渲染面在窗口重绘后自行恢复，真正的拦路问题是回读 bug

在会话 2 里对该窗口做了一次「最小化 → 还原 → SetWindowPos → RedrawWindow」之后，窗口重新开始渲染，`verify_input_box` 随之通过。**渲染失效只是当时的表象，不是根因**；真正的持续失败来自 §3.4 的回读缺陷。

用户 2026-11-17 决定：先不重启企微（避免 `/relogin_param` 触发扫码），只把代码修完推完。

### 3.4 真正的根因：`_find_new_sent` 按列名取 `rowid`

发送流程按下回车之后，`send()` 会用 `_find_new_sent()` 回读解密库确认落点。这段代码写的是：

```python
"select rowid, conversation_id, content from message_table ..."
...
if r["rowid"] in before:
```

但 `message_table` 的 `message_id` 是 `INTEGER PRIMARY KEY`，也就是 **rowid 的别名**。SQLite 因此把 `select rowid` 的返回列命名为 `message_id`，`r["rowid"]` 对**每一行**都抛 `IndexError: No item with that key`。

后果链条：

```text
按键成功、消息确实发出
  → _find_new_sent 抛 IndexError
  → send() 捕获后返回 {ok: True, detail: "已发送但回读失败：No item with that key"}
  → autopilot 判为「回读未确认」，记 unknown
  → unknown 不参与自动补发，只等 --retry-held 人工核对
  → 客户侧可能已经收到，但后台账本永远停在 unknown
```

`_sent_snapshot` 一直用位置下标 `r[0]`，所以它从不受影响——这也解释了为什么"发送前的快照正常，发送后的确认永远失败"。

修复：改为 `r[0]`，与 `_sent_snapshot` 一致。这是**只读回读**，不触碰任何键鼠动作。
