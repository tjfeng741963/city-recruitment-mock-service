## 4. 本轮做了什么：云端扫码登录

### 4.1 要解决的问题

账号跑在云端专用机，**用户和运营都碰不到那块屏幕**。企微被风控登出后桌面弹出扫码窗，原先的处理只是"把窗口拉到前台 + 响一声"——对云端机器等于没处理，自动回复无限期停摆。

### 4.2 链路

```
login_required → 只找登录窗(WeChatLogin)截图 → PNG → base64
  → POST /bridge/devices/:code/login-qr（设备令牌）
  → device_login_qr 表，每设备只留最新一张
  → GET /agent/devices/:code/login-qr（用户 JWT + 设备范围）
  → 网页设备页每 5 秒轮询 → 用户用手机扫
```

### 4.3 关键取舍

| 决定 | 原因 |
| --- | --- |
| 每设备只留最新一张 | 二维码约 2 分钟刷新，历史帧无用；一张 PNG base64 几十 KB，留着撑爆 SQLite |
| 上传认设备令牌、读取要用户 JWT | 二维码等同登录凭证，拿到就能顶替账号登录 |
| 上传 30 秒一次、错误 60 秒记一次 | 不刷屏，也不影响主循环 |
| 恢复登录后清掉服务端旧图 | 否则网页一直显示失效二维码，用户扫了没反应 |
| 截图/编码/上传失败全部吞掉 | 一个截图错误不能把自动回复进程搞停 |
| 近空图（<4KB）改用全屏 BitBlt | PrintWindow 抓硬件加速窗口常返回全黑图 |
| 手写 PNG 编码 | 客户端依赖只有 httpx / pywin32 / pycryptodomex，没有 Pillow |

### 4.4 验证到什么程度

已覆盖（自动化）：上传后读回、只留最新一帧、无令牌被拒、空图/超大图被拒、恢复后清除、匿名读取被拒；客户端侧"在线不传、找不到窗口不崩、异常不外泄、恢复清图、30 秒节流"。

**没覆盖**：真实扫码登入。要触发只能让企微真的退出登录，会中断自动回复，时段需业务侧决定。

## 5. 本轮做错了什么（和怎么发现的）

### 5.1 迁移编号撞车，三次

| 时间 | 撞车的两份 | 后果 |
| --- | --- | --- |
| 11-14 | `029_city_links_unique` / `029_flow_nodes` | 流程节点表不存在，配置台 500 |
| 11-14 | `031_media_assets` / `031_old_friend_status` | 老友状态表未建 |
| 11-15 | `033_old_friend_status` / `033_device_login_qr` | 二者之一被静默跳过 |

另有一份邀约群迁移 `035` 与 `035_device_login_qr` 撞车，已由 `ea67e10` 改号 036（尚未合入 main）。

根因：`migrate.ts` 用**数字前缀**做 `schema_migrations` 去重，同号的后一个整段跳过，而且**没有任何报错**；CI 从空库跑同样通过，所以测试全绿也发现不了。

当前状态：main 上最大编号 035，无重复。但这仍靠人肉检查，**没有 CI 守卫**（见遗留）。

### 5.2 补丁差点毁掉整页

侧栏补丁初版把标题容器（`.main-scroll`）直接喂给文本替换函数，而该函数用 `textContent` 整体赋值——会把容器里所有子节点抹掉。自查时发现，改成只处理"无子元素的叶子标题节点"。

### 5.3 微信登录态判定沿用旧逻辑

`detect_wecom_state()` 靠窗口类名枚举，没有引入新的风控信号。这是有意为之（不动动作层），但也意味着：企微卡在非登录窗的异常界面时，不会上传任何图，网页显示"还没收到二维码"。
