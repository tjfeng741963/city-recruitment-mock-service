# 加好友欢迎语链路核查

核查时间：2026-11-16 21:20～21:25（北京时间）。只读检查 Windows 服务器运行配置、客户端源码、本地回复账本、现有解密消息快照及日志；没有发送消息、清历史、刷新解密快照或修改生产配置。

## 结论

现有 Windows 客户端确实能在真实加好友后的自动提示到达时，主动向服务端取招聘介绍，不要求客户先输入问题。本次查到三次以自动好友提示触发的真实尝试。不能再把这条链路描述为只有接口模拟、必须新增官方接口才能触发。

但这三次尝试都因“抢不到前台，已中止”失败；消息快照内也未发现对应招聘介绍在客户主动提问前发出。已触发不等于已送达。本次证据不能证明企微管理端另外配置了原生欢迎语，也不能排除其他账号或更早历史存在该配置。

## 当前实际链路

普通微信与企微建立好友关系 → 企微本地库出现自动好友提示 → `autopilot.scan()` 扫描并登记 → `drain()` 判断首次会话 → `Brain.greet()` 请求实际 8090 回复服务的 `/api/v1/flow/greet` → 返回招聘介绍及分段 → Windows 客户端调用现有发送动作 → 回读并更新回复记录。

本次实例的触发记录含 type=1011 系统提示及 type=2 的“我已经添加了你，现在我们可以开始聊天了。”。扫描同一会话最新消息时实际选到了 type=2 自动提示。这不是客户提出业务问题。不能由此把所有 type=1011 统一认定为新增好友事件。

客户端当前为 flow 模式，非 dry-run，设备仍为 `pc-win-01`。本次读取的当前登录账号与早先联调账号不同，不能沿用历史账号与设备的身份对应结论；账号身份详情未写入公共仓库。

## 已定位的问题

1. **发送失败提前登记首句**：当前 `drain()` 在 `_brain.greet()` 返回成功后立即更新 `.greeted.json`，发生在真实键盘发送及数据库回读之前。HTTP 成功只代表内容生成成功，不能作为发给客户成功的依据。
2. **业务状态与投递不同步**：服务端已生成介绍并推进流程，桌面发送失败后的下一轮可能进入后续邀约，未保留原介绍作为待发送任务。
3. **首句被普通消息合并覆盖**：同会话合并机制可能把失败首句原记录跳过，之后普通回复成功也不会补齐原介绍。
4. **桌面发送前台不可用**：日志确认了失败点。21:25 查询时 RDP 的 Administrator 会话为 `Disc`（断开），客户端和企微进程都在该会话内。系统事件 25 显示当天 16:34:31 重连，该批会话首条实际发出的回复在 16:34:55；与之前连续“抢不到前台”的失败存在明确时间关联。没有取得失败当刻的完整桌面状态或锁定事件，不能把当前断开状态反推为当时唯一原因，也不能直接改键鼠动作或叠加抢焦点补丁。

## 建议后续修复（尚未实施）

先沿用已存在的自动好友提示触发，官方客户联系 API 保留为可选替代路线，不作为当前必需前置条件。后台按号配置招聘介绍的草稿 PR 可继续使用，但不能宣称已发布或已经解决投递问题。

分两步处理：

1. 只读诊断发送失败时的桌面会话、锁定状态与窗口情况，确认“抢不到前台”的环境原因。不通过发送测试消息诊断，不新增键鼠动作。
2. 针对 `agent/autopilot.py`、`agent/reply_store.py` 及实际服务端首句状态，设计独立的介绍投递记录：取文案与发送成功分开；只有确认完成发送后才记已打招呼；普通消息合并不删除待发介绍。分段发送要记录进度，结果未知不能盲目整套重放，避免重复或错发。

第二步需要先定清普通问题与待发介绍的顺序、部分失败及未知结果处理，再实施。不能只移动一行 `.greeted.json` 写入就声称修复完成。

### 动作影响、验证与回滚

- 只修投递编排和状态，不改冻结的 `wecom_io_core/{win,send,store,crypto}.py`，不新增键鼠动作，不调发送时序或整段重试。
- 先用临时库和 mock 发送覆盖：自动提示触发、成功后记已发、失败/重启保留原文、普通问题不吞介绍、分段中断、未知结果、无名字/接管/离线不发、正常知识库问答。
- 实机先确认环境、映射及唯一发送来源，再约真实加好友验收；对方不输入问题，核对触发、发送回读及客户实际收到三项。模拟重放不能代替真实添加。
- 按仓库 `AGENTS.md` 的客户端改动流程，具体诊断与方案经用户确认后才改客户端。当前线上代码与本地检出的客户端版本存在差异，实施前需逐文件核对，不能直接覆盖同事修改。
- 回滚前先检查未决介绍任务，避免旧版把任务当普通消息重发；备份状态并回退经过核对的版本。不删除真实 `.greeted.json`、聊天历史或回复账本。

## 尚不能确定的事项

- 用户所见的某一条历史欢迎语是否由企微原生配置发送：缺少该条历史消息与当前企业管理端配置的对应证据，本次不能武断归因。
- 删除后重加同一个普通微信是否能重复走新添加链路：当前仍按会话去重，不能保证。
- 所有加好友方式及企微版本是否都会生成相同可读提示：本次仅确认实际观察到的实例，不作全覆盖保证。
