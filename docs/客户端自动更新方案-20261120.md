# 客户端自动更新方案（2026-11-20）

> 目标：合并到 `main` 之后，服务端和 Windows 客户端**一起更新**，不再靠人工拷文件。
> 状态：**方案已定，尚未实施**。本文只写设计、实测依据和落地步骤。

---

## 1. 为什么需要这个

客户端 `C:\agent` 一直是**手工拷文件**更新的，与 `origin/main` 长期漂移。已经发生过的事故：

- **2026-11-18**：部署只拷了 17 个 `.py`，唯独漏了 `register.py`。`autopilot.py:85` 的
  `import register` 在**模块导入期**崩溃，守护进程每 5 秒拉起一次、每次死在同一行，
  `run.log` 涨到 5.3 MB，客户端完全停止回复。
  （详见 `docs/故障记录-20261118-客户端崩溃循环与输入框焦点.md`）
- **2026-11-19**：`agent/login_code.py` 和 `agent/client.py` 都推上去了，但 `autopilot.py`
  是旧版本、从来没调用过 `LoginCodeFetcher`——验证码提交后永远存在服务端内存里没人取走。
  网页上那句「设备几秒内自动输入」在客户端升级前是空头承诺。

两次的共同点：**推上去的文件和该跑的文件不是同一份，而且没人知道**。

仓库里其实早就有 `deploy/client/sync_from_github.py`（按 ref 取 tar 包、逐文件备份、
不动运行期文件），但**从未在部署流程里使用过**。

## 2. 现状实测（2026-11-20）

| 项 | 事实 |
| --- | --- |
| 客户端 | `134.175.40.31`，用户 `Administrator`，目录 `C:\agent` |
| Python | `C:\PROGRA~1\Python311\python.exe`（3.11.9） |
| 启动链 | 计划任务 `CloudPilot` → `pilot-hidden.vbs` → `start-pilot.cmd` → `python.exe autopilot.py --watch` |
| 单实例 | 命名互斥体 `Global\CityRecruitAutopilot`，第二个实例会自己退出 |
| `git` | **未安装**（`Get-Command git` 无结果） |
| `sshd` | Running（管理员账号走 `C:\ProgramData\ssh\administrators_authorized_keys`） |
| GitHub 仓库 | **公开**（`private: false`）→ codeload 可匿名下载 |
| 客户端出网 | `gitee.com` 200/468ms，`codeload.github.com` 200/1082ms，`api.github.com` 200/273ms |

**结论：客户端不需要装 git**——`sync_from_github.py` 走的是 tarball，不依赖 git。
仓库公开意味着**不需要在客户端保存任何 token**。

### 现有 `sync_from_github.py` 已经做到的

- 从 `codeload.github.com/{repo}/tar.gz/{ref}` 取包（优先用系统 `curl`，避开客户端 Python
  缺 CA 证书导致的 `SSLCertVerificationError`）
- **只覆盖 `agent/` 下的 `.py`**（含 `wecom_io_core/` 子目录），其余一律不碰
- 覆盖前逐文件备份为 `xxx.py.bak-YYYYmmdd-HHMMSS`
- 比较时忽略 CRLF/LF 差异（客户端文件长期是 CRLF，不代表内容不同）
- 默认 dry-run，必须显式 `--apply` 才写盘

**不碰的运行期文件**：`config.json`、`.greeted.json`、`reply_log.db`、`media/`、`logs/`、`_decrypted/`。

### 缺的是什么

1. 没有人调用它——不在任何自动化路径上
2. 没有「变了才更新」的判断，得有人记得跑
3. **没有自检**——坏提交会被原样写进去，下次重启就是崩溃循环
4. 没有更新后重启动作

## 3. 两个方案

### A. 流水线推（GitHub Actions → SSH 到 Windows）

`deploy` job 在 Linux 部署成功后，多一步 SSH 到 Windows，跑同步脚本。

| | |
| --- | --- |
| 优点 | 真正「合并即更新」；日志留在 CI；失败可见 |
| 缺点 1 | **客户端那一刻离线 / 重启 / 没人登录，这次更新就永久丢失，不会重试** |
| 缺点 2 | 需要给 `Administrator` 配 SSH key，且必须写到 `administrators_authorized_keys` 并设严格 ACL（历史上「所有 key 都 Permission denied」大概率就是踩了这个坑） |
| 缺点 3 | 客户端要对外暴露 SSH，增加一个攻击面 |

缺点 1 是致命的。以这台机器的历史——崩溃循环、半夜重启、RDP 断开后无人登录——
「合并那一刻客户端正好不在线」不是小概率事件。

### B. 客户端拉（计划任务定期比对 sha）★ 推荐

客户端自己每 N 分钟检查一次 `main` 的 sha，变了才下载更新。

| | |
| --- | --- |
| 优点 | **自愈**：离线错过一次，下次检查补上；重启后继续 |
| 优点 | 不依赖 autopilot 活着——它挂了照样能更新，正好覆盖最需要更新的场景 |
| 优点 | 不需要任何入站凭据、不开放新端口、CI 不用改 |
| 优点 | 仓库公开 → 客户端不用存 token |
| 缺点 | 延迟（默认 5 分钟），不是「合并那一刻」 |

延迟 5 分钟在业务上无意义——服务端部署本身也要 2~3 分钟。

**选 B。** 真正的诉求是「合并后两端最终一致」，不是「同一毫秒」。

## 4. 方案 B 的实现设计

### 4.1 新增文件

| 文件 | 作用 |
| --- | --- |
| `deploy/client/update_agent.py` | 入口：比对 sha → 需要时调用 sync → 自检 → 重启 |
| `deploy/client/install-updater.bat` | 注册计划任务 `AgentUpdater`（每 5 分钟） |

复用现成的 `sync_from_github.py`（作为模块 import），不重写下载/备份逻辑。

### 4.2 流程

```
每 5 分钟触发
  │
  ├─ 读 C:\agent\.deployed_sha          没有 → 当作全新，需要更新
  ├─ 取远端 main 的 sha                  api.github.com/repos/{repo}/commits/main
  │                                      失败/超时 → 直接退出，下一轮再来（不报错刷屏）
  ├─ 相同 → 退出
  │
  ├─ 下载 tar 包到临时目录
  ├─ 解出 agent/*.py 到 临时目录（不直接写 C:\agent）
  ├─ 自检：
  │    · 所有 .py 能被 compile()（语法关）
  │    · 在临时目录里跑 `python -c "import autopilot"` 的导入自检（导入关）
  │      失败 → 丢弃本次更新，记录日志，不写任何文件
  ├─ 自检通过 → 逐文件备份 .bak-<stamp> → 覆盖
  ├─ 写 .deployed_sha = 新 sha
  └─ 重启 autopilot（见 4.3）
```

**自检这一步是为了防 2026-11-18 那种事故复发**：那次是 `import register` 缺失导致导入期崩溃。
有了导入自检，这种包根本落不了地，旧代码继续服务。

### 4.3 重启方式

最稳的是「结束进程，等 `start-pilot.cmd` 的循环自己拉起」：

```
taskkill /F /IM python.exe        （只杀 C:\agent 目录下的那个更精确）
```

`start-pilot.cmd` 的循环会在 5 秒内重新拉起，自然加载新代码。
比另外调 `schtasks /Run` 安全——避免撞上单实例互斥体后新实例直接退出。

**注意**：更新时机撞上正在发送的消息，会让那条消息停在中间态。
`reply_log` / WAL 有恢复机制，但不是零成本。可选优化：只在 `pending_count()==0` 时重启。

### 4.4 计划任务

```
schtasks /Create /TN AgentUpdater /SC MINUTE /MO 5 /RU Administrator /IT /F ^
  /TR "C:\PROGRA~1\Python311\pythonw.exe C:\agent\update_agent.py --apply"
```

`/RU Administrator /IT` 与现有 `CloudPilot` 保持一致。
用 `pythonw.exe` 避免弹黑窗。

### 4.5 日志

`C:\agent\logs\update.log`，每行带时间戳，记录：
sha 旧→新、更新/新增/未变的文件数、自检结果、重启动作、异常。
只在**有变化时**写，避免 5 分钟一条把日志刷爆。

## 5. 边界与已知风险

| 风险 | 处理 |
| --- | --- |
| 坏提交把客户端搞挂 | 自检不通过则整体丢弃，不写任何文件 |
| 更新时正在发送 | 接受中间态，靠 `reply_log` 恢复；可选加「空闲才重启」 |
| 目录里堆积临时脚本（`_wq2.py`、`shot-*.py`、`restore-v3.py` 等） | 本方案不清理。可选：把清单外的文件挪到 `_archive/` |
| `wecom_io_core/` 是冻结区 | `sync_from_github.py` 只按字节覆盖，不做任何「优化」，符合冻结区要求 |
| 客户端离线 | 下一轮自动补上 |
| GitHub 不可达 | 记录后退出，不影响 autopilot 运行 |

### 关于仓库可见性

GitHub 仓库当前是**公开**的。已扫描已跟踪文件：

- Windows 服务器密码：**0 命中**
- 私钥（`BEGIN ... PRIVATE KEY`）：**0 命中**
- 只有服务器 IP（`134.175.40.31` / `119.91.113.100`）出现在注释和 docs 里

IP 单独泄露风险低。**若改为私有仓库，方案 B 需要在客户端保存一个只读 token**
（Gitee 的 access_token 或 GitHub fine-grained token，放在 `C:\agent\updater.json`，
ACL 限定 Administrator）。这是改私有前必须先决定的事。

## 6. 落地步骤

1. 写 `deploy/client/update_agent.py`（比对 sha + 自检 + 重启），复用 `sync_from_github.py`
2. 写 `deploy/client/install-updater.bat`（注册计划任务）
3. 上传到客户端 `C:\agent\`，手工跑一次 `--dry-run` 验证
4. 手工跑一次 `--apply`，确认：文件更新、自检通过、autopilot 被重启并重新上线
5. 合并一个无害的小改动到 main，观察 5 分钟内客户端自动跟上
6. 观察一周，确认没有把日志刷爆、没有误杀发送中的消息

## 7. 待决问题

1. **仓库要不要转私有？** 转私有 → 客户端要存 token（见 §5）。不转 → 保持现状。
2. **Gitee 镜像怎么同步？** 目前是手工推了一次（`stray-awakening/city-recruitment-mock-service`，
   `main` 停在 `eafad933`）。要么在 CI 里加一步 `git push gitee`，要么接受它只做冷备份。
   注意 Gitee 的 WAF 会拦标准 API 调用，需要用 `--data-urlencode` + 浏览器 UA（2026-11-20 实测）。
3. **要不要顺手清理 `C:\agent` 的临时脚本？** 现在有一堆 `_wq2.py`、`shot-*.py`、
   `restore-v3.py`、`switch-pilot-log.py` 之类的手工调试脚本，跟仓库无关。

## 8. 附：与服务端部署的对比

|  | 服务端（Linux） | 客户端（Windows） |
| --- | --- | --- |
| 触发 | CI `deploy` job，合并 main 即触发 | 计划任务每 5 分钟比对 sha |
| 取代码 | `git fetch` + `git checkout --detach $GITHUB_SHA` | codeload tarball（无 git） |
| 落盘范围 | 整个仓库（`git reset --hard` + `clean -fdx`） | 只 `agent/*.py` |
| 保护 | `-e '.env*' -e data -e node_modules` 保住运行配置 | 逐文件 `.bak`，运行期文件不碰 |
| 生效 | 重建容器 | 杀进程，`start-pilot.cmd` 5 秒内拉起 |
| 可重试 | 否（失败要重新合并或重跑） | **是（天然自愈）** |
