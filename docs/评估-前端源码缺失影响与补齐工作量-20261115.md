# 前端源码缺失：影响评估与补齐工作量

> 日期：2026-11-15
> 性质：**现状盘点 + 影响评估 + 方案与工作量估算**
> 数据来源：本机仓库实测（`public/assets/`、`frontend/src/`、`src/modules/`）
> 触发：2026-11-15 讨论「没有源码重要吗、影响多大、补齐要多久」

---

## 零、一句话结论

**重要，但不是致命。**

现在线上跑的前端（`public/`）是竞品打包后的黑盒，**没有源码**。这让你能改的样子和不能改的样子被死死框住。但补源码有三条路，最划算的那条**不是反编译，而是把已有的 React 那一套补完**——它已经写好了 45 个页面、8726 行。

---

## 一、现状：两套前端，一套有源码一套没有

| | Vue 版（`public/`，线上在跑） | React 版（`frontend/`，没上线） |
|---|---|---|
| 源码 | ❌ **无**（只有压缩产物） | ✅ **有**（56 个 `.tsx`，8726 行） |
| 页面 | 37 个 View | 56 个 tsx（45 个超 100 行） |
| 路由 | 39 条 | 7 个模块 + 若干具名路由 |
| 调用的接口 | 64 个 | 75 个（`frontend/src/api/`） |
| 能否改页面结构 | ❌ 只能 DOM 注入 | ✅ 随便改 |
| 上游来路 | 竞品打包产物（第一个 commit `3f6555d` 就在） | 同事自己写的 |

### Vue 版到底是什么

**不是「你搭的界面」，是「竞品的打包产物 + 你的设计层」。** 三层要分清：

| 层 | 归谁 | 源码 | 例子 |
|---|---|---|---|
| **页面骨架/路由/业务逻辑** | 竞品编译产物 | ❌ 56 个 chunk，最长单行 279,848 字符 | 城市列表、设备页、会话页 |
| **视觉样式** | **你设计的** | ✅ 完整 | `theme/theme.css` 986 行、`glass.css` 506 行 |
| **交互增强** | 我们加的 | ✅ 完整 | `kb-console.js` 35KB、`city-factories.js` 14KB |

**好消息**：`theme/` 那四个 CSS（986 + 506 + 146 + 324 行）**最长行 224 字符、带 14-17 处注释**，是手写源码，随时可改。你设计的液态玻璃、渐变、大圆角全在这里。

**坏消息**：页面结构（哪个页面有哪些表格列、什么字段、什么交互顺序）全在那 56 个压缩 chunk 里。

### 意外的好消息：这个 bundle 其实很好还原

我抽了 `CityLinkView` 实测，它**没有做变量名混淆**：

```javascript
const B = {
  options(){ return S.get("/api/v1/city-links/options") },
  list(){    return S.get("/api/v1/city-links") },
  save(d){   return S.post("/api/v1/city-links/batch", d) }
}
te = { __name:"CityLinkView", setup(d){ ... } }
```

组件名、API 端点、模板结构、变量顺序全保留。CSS 更彻底——**完全没压缩**，带 scoped 哈希：

```css
.city-link-page[data-v-f84850b0]{width:100%}
```

所以「还原」不是从零猜，是照着读。

## 二、没有源码，影响到底有多大

分四个场景看，严重程度递增：

### 2.1 改样式 / 加面板 —— **没影响** ✅

`theme/*.css` 和 `theme/*.js` 都是完整源码。改配色、改圆角、加一个覆盖式面板（像知识库配置台那样）完全自由。

**这是你目前 90% 的日常需求。**

### 2.2 改页面结构 / 加路由 —— **受限，但能绕** ⚠️

不能改 Vue 的页面结构，只能 DOM 注入。项目里已有成功先例：

- `city-factories.js`：319 行，把「厂区管理」一级入口藏掉、在城市每行加「厂区 N」按钮 —— **绕过了路由限制**
- `kb-console.js`：35KB，完全独立的知识库配置台 —— **绕过了页面限制**

代价是**脆弱**：靠 `MutationObserver` 盯着 Vue 重新渲染就行续挂，Vue 改一次 DOM 结构就可能失效。

### 2.3 框架升级 / 修深层 bug —— **做不到** ❌

- Vue 版本、Element Plus 版本**锁死在编译产物里**，升不了
- 打包产物里如果有 bug（比如某个组件在特定数据下渲染错），**只能从外面绕，改不了根因**
- 没有 sourcemap，线上报错**只有压缩后的行号**，排查极难

### 2.4 最要命的一条：**这套东西没法重建** ❌

如果哪天 `public/assets/` 被误删、被覆盖、或者需要重新构建（比如换个 CDN、加个构建优化），**没有任何办法重新生成**。它只有一份，且是别人给的二进制。

**这才是「依赖另外一个东西」的真正风险**——不是改不动，是**一旦丢就没了**。

好在这份产物**在 git 里**（第一个 commit 就进来了），有完整历史，不会丢。风险降了一档。

## 三、另一个独立问题：两套知识库数据割裂

这个跟前端源码**无关**，但影响更大，单列出来。

| 入口 | API | 表 | 谁在读 |
|---|---|---|---|
| 侧栏「知识管理」（Vue 原生） | `/api/v1/knowledge` | `knowledge_items` | Node 的 `kb-match` |
| 侧栏「知识库配置台」（我们注入的） | `/api/v1/kb-faqs` 等 | `kb_faq` | **Python 的 AI 回复** |

证据：

```python
# backend/app/services/kb_faq.py 开头
- 本文件是新路径：扫 kb_faq，按 vertical + scope **硬过滤**，不做模糊打分。
```

```typescript
// src/modules/agent/profile.routes.ts:310
SELECT id, title, content, data_json FROM knowledge_items WHERE status='enabled'
```

**后果**：在「知识管理」里改一条答案，AI 可能不用（它走 `kb_faq`）；在配置台里配的，旧界面列表看不见。

**这是数据层冲突，不是接口层冲突。** 两个 API 各跑各的，都不会报错，用户只会发现「改了没生效」。

**行业背景**：`docs/交接文档.md` 记录存量 `knowledge_items` 有 **534 条**（从易歪歪备份导入）。如果 AI 现在只读 `kb_faq`，那 534 条可能白存了。**这一点需要实测确认**——查两张表各多少行、有没有迁移过。

## 四、18 个接口是占位返回（顺带发现）

`src/modules/generic/generic.routes.ts` 有个兜底：没实现的路由一律返回假内容。

```typescript
if (route.includes("/export") || route.includes("/template"))
  return reply.type("application/octet-stream").send(Buffer.from("local export placeholder"));
```

命中兜底的：

```
/api/v1/import-export/*          导入导出（7 个）
/api/v1/upload/image|video       图片/视频上传
/api/v1/knowledge/batch/import   知识库批量导入
/api/v1/recruiters               招聘员
/api/v1/unknown-questions        未知问题
/api/v1/holiday-schedules        节假日
```

**界面上这些按钮点了没反应，或者导出个空文件。** 这是空缺，不是冲突，但用户点下去会觉得系统坏了。

## 五、补齐源码的三条路

### 方案 A：反编译还原成 Vue 源码

**产物**：`public/` 那套变成可维护的 `.vue` 工程。

| 步骤 | 工作量 |
|---|---|
| 搭 Vue 3 + Vite 工程，接上 39 条路由 | 1-2 天 |
| 提取 API 契约（64 个，已能自动抽取） | 0.5 天 |
| 格式化 56 个 chunk，逐个转 `.vue` | **主要工作量** |
| 搬 `theme/*.css`（本来就是源码） | 0.5 天 |

**页面转换按复杂度分（实测 chunk 大小）：**

| 档 | 数量 | 单页估时 | 小计 |
|---|---|---|---|
| 简单（<8KB，列表/表单） | **26** | 0.5 天 | 13 天 |
| 中等（8-15KB） | **6** | 1.5 天 | 9 天 |
| 复杂（≥15KB，会话/看板/设备） | **5** | 3 天 | 15 天 |
| **合计** | **37** | — | **≈37 人天** |

**一个人约 7-8 周；两个人并行约 4 周。**

**风险**：
- `createElementBlock` 那层要人肉翻译，机械且易错
- 转完必须逐页回归（37 个页面，测试成本另算）
- 转出来的代码风格未必比原来好，可能「还原了但更难维护」

**什么时候选它**：如果 Vue 那套就是产品未来形态，且不想动技术栈。

---

### 方案 B：补完 React 那套（**推荐**）

**这是被低估的一条路。** React 已经写了不少：

| 项 | 实测 |
|---|---|
| `.tsx` 文件 | **56 个** |
| 代码量 | **8726 行** |
| 超过 100 行的真实实现 | **45 个** |
| 已定义的 API | **75 个**（比 Vue 的 64 个还多） |

**已经原生实现的模块**（`App.tsx` 直接渲染，非占位）：

- `reception`（接待）—— `ReceptionPage` + `ChatPane` + `ConversationList` + `CandidateCard` + `triage.ts`
- `devices`（设备）—— `DevicesPage` + `DeviceDetail` + `DeviceDialogs`
- `positions`（岗位）—— `PositionsPage` + `PositionEditPage` + `usePositions`
- `settings`（设置）—— `SettingsPage` + `SettingsLists`

**还是占位的模块**（`LegacyPage`，27 行，只是弹个「打开原页面」的链接）：

- `candidates`（候选人/老友/状态看板/评估）
- `activation`（复聊，7 个页面）
- `knowledge`（知识库/话术/未知问题/规则）
- `extras`（城市周边/节假日）

**要补的**：约 20-25 个页面，按 Vue 对应页面的复杂度估：

| 档 | 数量 | 单页估时 | 小计 |
|---|---|---|---|
| 列表/表单页 | ~15 | 1 天 | 15 天 |
| 中等页 | ~6 | 1.5 天 | 9 天 |
| 复杂页（会话/看板） | ~4 | 3 天 | 12 天 |
| **合计** | **~25** | — | **≈36 人天** |

**和方案 A 几乎一样的工作量，但收益完全不同：**

| | 方案 A（还原 Vue） | 方案 B（补完 React） |
|---|---|---|
| 工作量 | 37 人天 | 36 人天 |
| 终点 | 一套「逆向出来的」Vue | 一套**自己写的** React |
| 后续维护 | 还原代码可能更难维护 | 正常现代工程 |
| 设计复用 | 直接复用 `theme/*.css` | 需要把 `theme/*.css` 的类名对到 React 组件 |
| 回归测试 | 37 页全要测 | 已有 45 页不用重测 |

**方案 B 的额外成本**：要把你设计的 `theme/*.css` 搬到 React 上。但那是 CSS，逻辑通就能搬——**这是唯一需要额外投入的地方，也是最不该省的地方**（不然就丢了你这套视觉）。

---

### 方案 C：维持现状 + 继续 DOM 注入

**工作量：0。** 现在就能用。

**代价**：§2.2/§2.3/§2.4 那三条限制永久存在。每加一个新功能，都要写一段 `MutationObserver` 补丁。

**适用**：只是想短期交付、不打算长期迭代。

## 七、如果你问我怎么选

**选方案 B，但分两步走，别一次性推倒。**

### 第一步（1-2 周）：先解决最疼的两个问题

1. **知识库数据割裂**（§3）——这个比前端源码更急。先查清 `knowledge_items` 534 条有没有进 `kb_faq`，没有就迁，有就隐藏旧入口
2. **18 个占位接口**（§4）——按使用频率补最常用的 3-5 个（`upload`、`import-export` 优先级最高）

这两件事不影响前端架构，做完用户立刻能感知。

### 第二步（4 周起）：React 补齐

按模块优先级排：

```
1. knowledge   ← 知识库是核心，且现在两个界面打架
2. candidates  ← 候选人管理是日常
3. activation  ← 复聊看板，7 个页面但结构类似
4. extras      ← 城市周边/节假日，最简单，放最后
```

每个模块补完就把 `LegacyPage` 换掉，**双轨并行**，随时可回退。

### 关于「源码没有」的最终判断

**重要程度：中高。**

- 不是「系统跑不起来」的致命问题（产物在 git 里，不会丢）
- 是「改不动、升不了、修不了根因」的长期束缚

**但它的解法不是反编译**——你最需要的不是那 56 个 chunk 的源码，而是**一套能自由改的、属于你自己的前端**。React 那套已经走了 60% 的路，补完比逆向更划算。
