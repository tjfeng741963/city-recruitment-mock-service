# 对齐：多智能体自然对话流程设计（v3，2026-11-12）

> 定稿设计契约。实施智能体可直接照做。只改 flow 层（`backend/app/api_flow.py` / `flow_llm.py` / `flow_engine.py`）+ 测试；
> 单进程多角色，不引入新服务；岗位事实/工价护栏/KB/媒体标记/dedup 机制全部不动。
> 依据：客户原话反馈（加好友→问一句城市→整段岗位信息倾倒，像模板机器人）+ 代码现状核实。

## 一、现状问题（代码证据）

| 证据点 | 位置 | 问题 |
|---|---|---|
| 拿到城市即全量倾倒 | `flow_engine.py:424-433`（step 的 ask_city 分支 → `enter_info_result`） | 客户说"广州"后同一轮就发出 厂名/工价/班次/年龄/吃住/地点/时间 三段全量卡 + 邀约问句 |
| `interview_offer_sent` 同轮置位 | `flow_engine.py:373` | 岗位信息和面试邀约捆绑发出，客户还没表达兴趣就被问"能不能来面试" |
| 模型路径同样强制直发 | `flow_llm.py:315-318`（apply_result：有 city 且未 offer → `enter_info_result`） | 模型的自然措辞这轮不被采用，等于固定节奏 |
| config 话术轮同样一轮跳邀约 | `api_flow.py:176-195` | `will_send_info` 命中即发素材并直接 `stage=ask_interview` |
| 只有一个"陈姐"人设 | `flow_llm.py:65-118`（SYSTEM_PROMPT 单一） | 所有阶段同一套指令，模型被鼓励"尽快聊到约面试"，没有节奏约束 |

结论：问题不在模型，在**编排层把"推荐、展开、邀约"三件事压进了一轮**。

## 二、新对话流程（stage 机 v3）

### 2.1 状态机全景

```
greet (新)        接待：寒暄 + 了解需求（城市/想做什么/经验顾虑），不发任何岗位信息
   │  退出：slots.city 已知 → recommend
   │  兜底：累计 3 个客户轮仍无 city → ask_city
   ▼
ask_city (保留)   兜底直问城市（greet 超限 / 老会话兼容）。拿到 city → recommend
   ▼
recommend (新)    匹配：按 city+job_index 发「1 个岗位简短卡」（代码拼）+ 钩子问句
   │  客户感兴趣（agree 类答复 / 想去 / 问细节）→ expand
   │  不感兴趣（disagree / 换一个）→ job_index+1 重发简卡；列表用尽 → 「帮你问问」
   ▼
send_info (语义改造=expand)  客户感兴趣后才展开：全量岗位卡（原 send_info_parts 三段）
   │  发完 → ask_interview（interview_offer_sent=True，语义不变）
   ▼
ask_interview → collect → done / kb   全部保留现状（KB、媒体标记、collect 一次问两个、
                                       done 重激活、gave_up）
```

### 2.2 stage 常量与语义

| stage | 常量 | 变更 | 语义 |
|---|---|---|---|
| `greet` | `STAGE_GREET = "greet"`（新增） | 新 | 接待阶段，禁发岗位事实 |
| `ask_city` | 保留 | 行为微调 | 拿到城市后**不再**直发全量卡，改跳 recommend |
| `recommend` | `STAGE_RECOMMEND = "recommend"`（新增） | 新 | 简短卡推荐 + 试探兴趣 |
| `send_info` | 保留常量名 | 语义收窄为"展开" | 只在客户感兴趣后进入；内容=原三段全量卡 |
| `ask_interview` / `collect` / `done` / `kb` | 保留 | 不动 | 现有能力（KB 插问、媒体标记、一次要两个字段、重激活）不变 |

**兼容关键**：`ask_city` / `send_info` 字符串不改名，老会话事件流（`stage_change to send_info` 等）投影后语义仍然成立，无需迁移（见 §七）。

### 2.3 「还在了解阶段」的识别（greet 的退出判定，代码决定，不信模型表态）

进入 recommend 的**充分条件（任一命中，当轮立即转）**：

1. `extract_city(text)` 命中，或 `slots.city` 已有值（模型在 greet 轮抽到城市写进 slots 也算）——城市是推荐的最小必要条件，有了就推，不等"聊够"；
2. 客户明确要岗位但没说城市：意图词命中（复用/扩充 `_WANTS_MORE` 思路，新增 `有什么工作|招什么|哪个厂|介绍个|找活|找工作|有没有班`）→ 转 `ask_city` 直问城市（不寒暄拖延）。

**硬上限**：greet 阶段累计 3 个客户 turn（用 `state["turns"]` 与 stage 进入时基线差值）仍无 city → 当轮强制转 `ask_city`。防止"了解阶段"变尬聊。

greet 轮内照常 `_absorb(slots, text)`（客户顺口报的姓名/年龄/省区照记）；模型只许问**一件事**（想做什么 → 有没有经验/顾虑 → 城市，按客户已给信息的缺项追问），由 persona 指令约束（§三）。

### 2.4 recommend 的轮转逻辑（代码决定）

`step()` 的 recommend 分支（确定性优先）：

1. **发卡轮**：进入 recommend 时（`slots.get("job_card_sent")` 为假）由代码直发简短卡（§四格式），置 `job_card_sent=True`，stage 保持 recommend。**简卡不过模型**——数字零风险。
2. **回应轮**：客户答复后：
   - `is_agree(text)` / 含「感兴趣|想去|可以|干|做」且非提问 → 进 expand（= send_info 语义）：代码发全量三段卡（复用 `send_info_parts`），`interview_offer_sent=True`，stage → ask_interview；
   - `is_disagree(text)` 或「不想干|换一个|别的厂|太远|不合适」→ `job_index += 1`：还有岗位 → 重发新简短卡（代码拼）；列表用尽 → 「这边暂时就这几个，你想要什么条件我帮你留意，有了马上回你」（复用 `_list_other_jobs` 的用尽话术）；
   - 插问（`looks_like_question`）→ 走 KB（§六 `_KB_STAGES` 扩容），答完留在 recommend；
   - 含糊（「嗯」「哦」）→ 重发钩子问句。
3. 模型在 recommend 阶段的作用：客户答复千奇百怪时帮忙判断意向并自然措辞——但**发卡动作仍由代码做**（`apply_result` 里：stage=recommend 且 agree 信号 → 直接 `expand_info_result`，模型措辞不采用，同 v2 对 enter_info_result 的处理）。

### 2.5 done / 重激活语义（保留 + 一处小改）

- done 后静默、`booked` 后 KB 命中即答（`a_step` 头部分支）——全部保留；
- `api_flow.py:88-95` 重激活：`stage_before=="done"` 时，
  - `slots.interview_offer_sent` 为真 → 回 `ask_interview`（现状）；
  - 为假（老客户没展开过）→ 回 `recommend`（`job_card_sent` 重置为假，重新发卡）。

## 三、多智能体角色注入（单进程，按 stage 切人设）

### 3.1 机制

`flow_llm.py` 的 `SYSTEM_PROMPT` 增加 `{persona}` 占位符；`build_messages` 按 `state["stage"]` 从 `PERSONAS` 取对应段拼入。同一进程、同一模型，只换"此刻你是谁、该说什么、不该说什么"。确定性回退路径（`fallback_step`）的话术天然与各阶段人设对齐（问候/问城市/简卡/邀约/登记各归其位），无需额外改动。

### 3.2 人设表（`PERSONAS: dict[str, str]`，key=stage）

| stage | 角色 | 此刻该说 | 绝不该说 |
|---|---|---|---|
| `greet` | **接待**（陈姐本人，刚加上好友） | 自然回应寒暄；了解需求：想做什么工种、有没有经验、有没有顾虑（吃住/距离）；**一次只问一件事**；语气热络像熟人 | 任何厂名、工价、班次、面试、地点、发岗位信息；催促 |
| `ask_city` | **接待** | 直接、客气地问城市（可带上已知城市列表：「广州深圳东莞都有厂」= 现 `_city_ask`） | 岗位细节 |
| `recommend` | **匹配顾问** | 围绕当前推荐岗位：一句话点出亮点、回应客户顾虑；引导兴趣 | 报新的数字（简卡外的工价）；要姓名电话；同时讲多个厂 |
| `send_info` | **匹配顾问（展开）** | 确认细节（班次/吃住/地点），配合全量卡做口语化铺垫 | 改任何数字 |
| `ask_interview` | **邀约顾问** | 问这两天能否来面试；答插问后自然接回邀约 | 报新岗位、新工价 |
| `collect` | **登记专员** | 只登记姓名+手机号（一次要两个）；顺口确认面试时间地点 | 聊别的岗位、新话题 |
| `done` | 不调模型（现状保留） | — | — |

### 3.3 persona 文本示例（实施时照抄进 PERSONAS）

```python
_PERSONA_GREET = """你现在处于接待阶段，刚加上客户好友。你的任务只有一个：像真人猎头一样聊起来，
搞清楚三件事：他想做什么工种、有没有经验、有什么顾虑（吃住、距离都算）。
一次只问一件事，客户答了哪个就顺着接。这个阶段你手里没有任何岗位可以介绍——
禁止出现任何厂名、工价数字、班次、面试安排。客户催你要岗位时，回「你想找哪边的？我看看手上有啥合适的」并记下城市。"""
```

（recommend/其余 persona 实施时按 §3.2 表格逐条落成同格式文本。）

### 3.4 JSON 输出契约扩展

`SYSTEM_PROMPT` 的 stage 枚举改为 `greet|ask_city|recommend|send_info|ask_interview|collect|done`；`slots` 示例增加 `"job_card_sent": false` 说明（模型只读不写，代码负责置位）。`ALLOWED_STAGES` / `_STAGE_ORDER` / `_QUESTION` / `_ASKED_HINTS` 同步扩充（见 §六）。

## 四、岗位推荐卡格式（recommend 简短卡，纯代码拼）

### 4.1 数据源与护栏

- 数据来自 `jobs_for_city(city)`（4222 远端，`ContextVar` 注入机制不动）；
- 工价护栏不变：简卡由**代码从岗位字段拼**（与 `send_info_parts` 同级保护），`_money_guard` 继续覆盖模型输出的 expand 轮；
- 无岗位（`jobs_for_city` 空）→ 复用 `_no_job_parts`「已记下，帮你问问」+ unknown_question，stage 回 ask_city（现状语义）。

### 4.2 卡片结构（新增 `recommend_parts(slots) -> list[str]`，放 flow_engine）

```python
def recommend_parts(slots, when=None) -> list[str]:
    job = _job_of(slots)
    if not job:
        return _no_job_parts(str(slots.get("city") or ""))
    factory = _factory(job)
    kind = str(job.get("job_title") or "").split(" ")[-1]
    highlight = _job_highlight(job)   # 见 4.3
    return [
        f"你{city}的话，这边正好有个{factory}的{kind}在招，{job.get('wage_text','')}，{highlight}。",
        f"地址在{job.get('place','')}那边。这个你感兴趣吗？感兴趣我把班次和面试安排详细发你。",
    ]
```

要点：**两段式**——段1 = 工厂+工种+工价+一句亮点；段2 = 地点短语 + 钩子问句「这个你感兴趣吗？」。字段全部照抄岗位数据，不出现班次明细/年龄/吃住全量（留给 expand）。

### 4.3 亮点提取（新增 `_job_highlight(job) -> str`）

优先级：`welfare_text` 第一个顿号/逗号前的片段（如「包吃包住」）→ `hours_text` 第一个片段（如「两班倒」）→ 空串则省略亮点子句。取第一个片段而非全文，保证一句话。

### 4.4 config 运营话术（`device_scripts`）在新流程中的位置

- `pick_script(..., STAGE_SEND_INFO, city)` 的 stage 参数不变；触发时机从"拿到城市那轮"改为**expand 轮**（客户对简卡表示兴趣后），仍走"素材交给模型组织 + 工价护栏"路径（`api_flow.py` 的 script 分支保留，改 `will_send_info` 条件，见 §六）；
- 运营配的话术建议后续调整为钩子式开头（文档告知运营即可，代码不强校验）。

## 六、风险与灰度

### 6.1 灰度机制（核心：开关只控制新会话起点，老会话零迁移）

- 环境变量 `FLOW_DIALOG_V3`（默认 `0`=v2 行为）：
  - `new_state()` 在开关关时初始 stage 仍为 `ask_city`（v2），开时为 `greet`；
  - `step()` / `apply_result()` 中 greet/recommend 分支只在开时可达（老会话 stage 不可能是新字符串，天然走老分支）；
  - 开时老会话（stage=ask_city）拿到城市 → recommend 简卡：行为变化但是**收窄**（少发信息），比全量更安全，可接受；
- **回滚**：开关关掉即回 v2，事件流无需迁移（投影纯函数，新旧 stage 字符串都合法）。

### 6.2 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 模型 JSON 里乱回新 stage 字符串 | 低 | `ALLOWED_STAGES` 白名单 + clamp 已有机制兜住 |
| greet 阶段模型泄岗位（抢跑） | 中 | persona 硬禁令 + `greet_guard` 代码兜底：greet 轮 reply 里若出现「元/小时|厂名命中 `jobs_for_city` 任一 factory_name」→ 丢弃模型输出回退 `_city_ask`（复用回声防护同款覆盖手法） |
| recommend 意向误判（客户随口「可以」被当感兴趣） | 中 | expand 判定沿用 `is_agree` 的短句约束 + `looks_like_question` 排除；误展开的代价低（多发一次全量卡），不误约 |
| greet 3 轮上限把慢热客户推入直问 | 低 | 直问城市本就是 v2 行为，客户无感 |
| 换岗轮 `job_index` 越界 | 低 | `_job_of` 已有 `min(index, len-1)` 钳制；列表用尽有专用话术 |
| 4222 前端「offered」提前出现（recommend 即推 offered） | 低 | 与 v2「发全量即 offered」相比是提前一轮，业务可接受；如不可接受改为 recommend→"asking"，一行配置 |
| config 运营话术与简卡节奏不匹配（话术是全量式） | 中 | 话术只在 expand 轮注入（客户已要细节），节奏天然吻合；运营侧建议改钩子式开头 |
| 测试面扩大 | — | 见 §5.5 清单；开关关时旧用例必须全绿（回归线） |

### 6.3 验收口径（新增）

1. 新会话首轮只寒暄+问一件事，reply 不含任何 `wage_text`/`factory_name`；
2. 报城市后收到**两段**简卡（≤60 字/段），含钩子问句；此时 stage=recommend、`interview_offer_sent` 为假；
3. 答「感兴趣」→ 收到原三段全量卡 + 邀约，`interview_offer_sent=True`；
4. 答「不想干/换一个」→ 收到下一个岗位简卡，`job_index=1`；
5. 开关关闭时，v2 全流程用例全绿（行为逐字节不变）。
