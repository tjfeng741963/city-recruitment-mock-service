# 知识库方案 v3：品类可扩展的流程驱动知识库

> 2026-11-13。基于 69 张真实生产截图、两份话术 docx、两份岗位 xlsx。
> 前提：这套东西要卖给同行，一个客户可能管几百个厂、数个招聘品类。**结构错了，后面每接一个客户都要返工。**
>
> **v3 相对 v2 的修正**：v2 用「一个厂既有工厂岗又有地铁岗」论证不该拆库——**这个论据是错的**。工厂和地铁是两个不同的**招聘品类**，不是同一个厂的两种岗。
> 真正的扩展轴是品类（工厂 / 地铁 / 白领 / 保姆 / 船员），而不同品类的**实体语义完全不同**：工厂招工的对象是厂，保姆的对象是家庭，船员的对象是船东。
> 结论：**核心共享 + 品类插件**——不是「一套加个字段」，也不是「每种品类建一套库」。

---

## 零、三个先决判断

### 判断 1：一套知识库还是两套？——**一套核心，品类做插件**

先说清一个事实：**工厂和地铁是两个不同的招聘品类，不是同一个厂的两种岗。**

这家公司今天是做劳务派遣的，工厂和地铁都是它下面的品类。未来做白领、保姆、船员，那是**新品类**，而且实体语义完全不同：

| 品类 | 招工对象的称谓 | 岗位关键属性 |
|---|---|---|
| 工厂 | 工厂 | 工价 / 班次 / 包吃住 / 体检 / 纹身 |
| 地铁安检 | 线路、城市 | 身高 / 纹身 / 线路 / 班次计薪 / 转正 |
| 白领 | 公司 | 学历 / 年限 / 技能 / 薪资结构 / 五险一金 |
| 保姆 | 家庭、雇主 | 住家与否 / 带孩子 / 做饭 / 老人护理 / 体检 |
| 船员 | 船东、船名 | 船型 / 航线 / 证书 / 合同期 / 上下船港 |

**这不是「同一张表的几个字段」，是「同一套流程框架下的不同数据模型」。**

所以两头都不能走：

| 错误做法 | 后果 |
|---|---|
| 每种品类建一套库 | 设备、会话、消息、候选人档案、FAQ 引擎全部复制 N 份；客户扩品类时数据打不通 |
| 一张万能表加字段 | `employer` 里塞 `factory_name` / `household_name` / `vessel_name`，加一个品类加三个字段 |

**正解：核心共享，品类做插件。**

```
共享核心（所有品类同一份）
  tenant / user / device / conversation / message /
  candidate / profile / flow_session / faq_engine / template

品类定义（一行一个品类，可增删，带 schema）
  vertical(id, code, name, config_json)

统一契约（跨品类同构的部分）
  employer（招工方抽象） / position（岗位） / location（地点）

扩展承接
  position.data_json + vertical.config_json（JSON Schema）
```

**判断的关键：品类差异不是靠"多建表"承接，是靠"动态字段 + schema"承接。**
这个项目已经有一半答案了——前端岗位表单里的「岗位模板」本来就是任意 Key/Value 的语义字段（页面原文：`配置岗位的动态字段。Key 为语义名称，Value 为格式化好的文本内容`）。

```
工厂岗： wage_text / hours_text / welfare_text / age_text / tattoo_policy
保姆岗： live_in / cooking / childcare / eldercare / trial_days
船员岗： vessel_type / route / certificate / contract_months / port
```

**同一张 `position` 表，`data_json` 存不同键**；品类表里声明该品类该有哪些键，前端按 schema 动态渲染表单。

> 一句话：**逻辑隔离靠 `vertical_id`，结构共享靠动态字段，物理存储绝不拆。**


### 判断 2：工厂多了怎么分清？——**位置建通用树，招工方有稳定编码和别名**

你说的场景是真实的：**一个工业区十几个厂**。现在的结构顶不住：

| 现状 | 问题 |
|---|---|
| `cities` 有 `city_name` UNIQUE，无区县级表 | 「广州」下面的番禺/白云/黄埔只能塞 `data_json`，无法按区检索 |
| `factories` 只有 `factory_name` + `city_id`，**无唯一约束** | 同一个区两家「精密五金」直接分不开 |
| 无「工业区/园区」概念 | 客户说「我在钟村工业区」，系统不知道那是哪几个厂 |
| 无别名机制 | 客户说「松下」，库里是「松下万宝电子（广州）有限公司」——**对不上** |

工厂多了以后，**"分不清厂"的根因不是检索算法，是工厂本身没有唯一身份。**

而且这个「招工方」在不同品类里根本不是同一种东西：

| 品类 | 招工方是什么 | 需要额外记什么 |
|---|---|---|
| 工厂 | 工厂 | 工商信息、园区、厂房 |
| 保姆 | 家庭 | 家庭成员、住址、有没有宠物 |
| 船员 | 船东 / 船 | IMO 号、船型、航线 |

所以不能建 `factory` 表，要建 **`employer`（招工方）** 抽象表 + **`location`（地点）** 通用树：

```
location（开放层级）
  工厂：省 → 市 → 区 → 园区 → 面试点
  保姆：省 → 市 → 区 → 雇主家
  船员：省 → 市 → 港口
```

**同一张表，不同品类用不同深度。**

### 判断 3：15 组问答怎么做包？——**按品类一份，带占位符，可升级**

不能做成"一份固定数据"，因为不同客户工价地址全不一样；也不该一个品类一份硬编码。要做成：

```
模板包（平台维护，每个品类一份：faq-factory-v1 / faq-subway-v1 / faq-domestic-v1）
   ↓ 导入到某个租户
租户实例（可改，可删，可增；记录来源 template_item_id）
   ↓ 与岗位动态字段合并渲染
最终回复（数字来自 position.data_json，话术来自模板）
```

模板里的动态部分用占位符：`{wage}` `{age}` `{address}` `{employer}`，导入后由岗位事实填充。

**升级能力**：模板发新版本时，只更新「没被租户手工改过」的条目（靠 `template_item_id` 判断），改过的不动。

## 一、从截图读出来的真实流程（未变）

### 1.1 工厂线（一账号一厂）

```
加好友 → 发招聘卡 → 【可选】确认工种 → 问答 → 约面试 → 收姓名电话 → 发面试须知

### 1.2 地铁线（一账号多城市）

```
加好友 → 问城市 → 发城市岗位卡 → 问答 → 约面试（发面试点图+步行指引）→ 收资料 → 发面试通知

证据：`地铁-郑__佛山百花-宗锐.jpg`（开场「佛山 邀约快」）、`地铁-阎__南宁实招1.jpg`（「发个位置」→ 地图 + 文字指引）

### 1.3 差异（决定了「品类」为什么必须是一等实体）

| 维度 | 工厂 | 地铁 |
|---|---|---|
| 账号 ↔ 地点 | 一账号一厂 | 一账号多城市 |
| 第二句 | 问工种 | 问城市 |
| 岗位卡字段 | 分月工价、住宿水电、体检 | 身高纹身、线路、班次计薪 |
| 面试点 | 厂门口 | 总部，需转乘，要文字指引 |

## 三、数据模型（v3 的核心）

### 3.0 品类表：一切扩展的入口

```sql
CREATE TABLE vertical (
  id INTEGER PRIMARY KEY,
  tenant_id INTEGER NOT NULL DEFAULT 1,
  code TEXT NOT NULL,             -- factory | subway | white_collar | domestic | maritime
  name TEXT NOT NULL,             -- 工厂 | 地铁安检 | 白领 | 保姆 | 船员
  config_json TEXT NOT NULL DEFAULT '{}',
  sort_order INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'enabled',
  created_at TEXT, updated_at TEXT,
  UNIQUE(tenant_id, code)
);
```

`config_json` 决定这个品类长什么样：

```json
{
  "employer_label": "工厂",
  "location_levels": ["province", "city", "district", "park", "point"],
  "position_schema": [
    {"key": "wage_text",     "label": "工价",     "type": "text", "required": true},
    {"key": "hours_text",    "label": "班次",     "type": "text"},
    {"key": "welfare_text",  "label": "吃住",     "type": "text"},
    {"key": "age_text",      "label": "年龄",     "type": "text"},
    {"key": "tattoo_policy", "label": "纹身要求", "type": "text"}
  ],
  "faq_pack": "faq-factory-v1",
  "flow_template": "flow-factory-v1"
}
```

加「保姆」品类时，`employer_label` 变「雇主」，`location_levels` 去掉 `park`，`position_schema` 换成 `live_in` / `cooking` / `childcare` / `eldercare` / `trial_days`。

**不动一行代码。**

### 3.1 位置：开放层级树

```
工厂：省 → 市 → 区 → 园区 → 面试点
保姆：省 → 市 → 区 → 雇主家
船员：省 → 市 → 港口
```

```sql
CREATE TABLE location (
  id INTEGER PRIMARY KEY,
  parent_id INTEGER REFERENCES location(id),
  level TEXT NOT NULL,        -- province | city | district | park | point（开放字符串，非枚举）
  name TEXT NOT NULL,
  code TEXT NOT NULL DEFAULT '',         -- 国标码，便于未来对接
  lat REAL, lng REAL,
  address TEXT NOT NULL DEFAULT '',
  walk_guide TEXT NOT NULL DEFAULT '',   -- 「地铁2号线C出口，电梯上7楼A7-A8室」
  image_key TEXT NOT NULL DEFAULT '',    -- 客户端 C:\agent\media\xxx.jpg
  status TEXT NOT NULL DEFAULT 'enabled',
  data_json TEXT NOT NULL DEFAULT '{}',
  UNIQUE(parent_id, level, name)
);
CREATE INDEX ix_location_level ON location(level, status);
```

**一张表搞定所有品类的层级**，深度由品类决定。`park` 这一级专门用来解决你说的「一个工业区十几个厂」——客户说「我在钟村工业区」，先按 `park` 缩小范围。

`point` 这一级承载面试点/试工点/港口，`walk_guide` + `image_key` 直接对应"发地址"能力。

**迁移策略**：现有 `cities` 表**不删不改**，作为视图兼容层；回填时 `cities.city_name` → `location(level='city')`，`cities.province` → `location(level='province')`。前端先不动，等新表稳定后再切。

### 3.2 招工方：`employer` 通用表 + 稳定编码 + 别名

```sql
CREATE TABLE employer (
  id INTEGER PRIMARY KEY,
  tenant_id INTEGER NOT NULL DEFAULT 1,
  vertical_id INTEGER NOT NULL REFERENCES vertical(id),
  employer_code TEXT NOT NULL,          -- 稳定编码：GZ-PY-001 / BJ-CY-H01 / SH-V-007
  display_name TEXT NOT NULL,           -- 松下万宝电子（广州）有限公司 / 朝阳区王女士家
  short_name TEXT NOT NULL DEFAULT '',  -- 松下万宝 / 王女士
  location_id INTEGER REFERENCES location(id),
  status TEXT NOT NULL DEFAULT 'enabled',
  data_json TEXT NOT NULL DEFAULT '{}', -- 品类特有字段
  created_at TEXT, updated_at TEXT,
  UNIQUE(tenant_id, employer_code)
);
CREATE INDEX ix_employer_loc ON employer(tenant_id, location_id, status);

CREATE TABLE employer_alias (
  id INTEGER PRIMARY KEY,
  employer_id INTEGER NOT NULL REFERENCES employer(id) ON DELETE CASCADE,
  alias TEXT NOT NULL,              -- 松下 / 万宝 / 狄原 / 荻原（错别字也收）
  weight INTEGER NOT NULL DEFAULT 0,
  UNIQUE(employer_id, alias)
);
CREATE INDEX ix_alias_text ON employer_alias(alias);
```

`data_json` 按品类存：

| 品类 | 存什么 |
|---|---|
| 工厂 | 工商信息、厂房层数、是否有夜班食堂 |
| 保姆 | 家庭成员、住址楼层、有无宠物、是否住家 |
| 船员 | IMO 号、船型、建造年份、航线 |

**为什么必须 `employer_code`**：厂名会改（改制、并购），编码不会。设备绑定、问答、档案全引用 `employer_id`，改名不影响历史数据。

**为什么必须 `employer_alias`**：真实对话里客户说「松下」「荻原」（还写成「狄原」）。没有别名表，"分不清厂"永远无解——系统根本不知道这两个词指谁。

### 3.3 岗位：一岗多地点

```sql
CREATE TABLE position (
  id INTEGER PRIMARY KEY,
  tenant_id INTEGER NOT NULL DEFAULT 1,
  employer_id INTEGER NOT NULL REFERENCES employer(id),
  vertical_id INTEGER NOT NULL REFERENCES vertical(id),
  position_name TEXT NOT NULL,       -- 普工 / 叉车工 / 焊工 / 安检员 / 保姆 / 水手（工种即岗位名）
  status TEXT NOT NULL DEFAULT 'enabled',
  featured INTEGER NOT NULL DEFAULT 0,
  data_json TEXT NOT NULL DEFAULT '{}',  -- 按 vertical.position_schema 存
  created_at TEXT, updated_at TEXT,
  UNIQUE(tenant_id, employer_id, position_name)
);
CREATE INDEX ix_position_vertical ON position(tenant_id, vertical_id, status);

-- 一岗多地点：地铁一岗覆盖 4 城、船员一岗多港口、工厂一岗多面试点
CREATE TABLE position_location (
  position_id INTEGER NOT NULL REFERENCES position(id) ON DELETE CASCADE,
  location_id INTEGER NOT NULL REFERENCES location(id),
  PRIMARY KEY(position_id, location_id)
);
```

地铁「一岗覆盖广州/佛山/深圳」再也不用复制三条岗位。

### 3.4 岗位事实：占位符的取值来源

`data_json` 按 `vertical.position_schema` 存（沿用现有前端"岗位模板"的动态字段机制）：

| 占位符 | data_json 键 | 例（工厂） | 例（保姆） |
|---|---|---|---|
| `{wage}` | `wage_text` | 第一个月25元/小时，第二个月26元/小时 | 月薪 7000-9000 |
| `{welfare}` | `welfare_text` | 包吃包住，不扣水电 | 包吃住，月休四天 |
| `{shift}` | `hours_text` | 早班8-20，夜班20-8，自由选择 | 住家，无休或单休 |
| `{work}` | `work_text` | 汽车配件分拣打包贴标签 | 带 2 岁男宝，做饭打扫 |
| `{dorm}` | `dorm_text` | 4-6人间，空调热水电梯公寓 | 雇主家单独房间 |
| `{age}` | `age_text` | 18-40岁 | 45-55岁优先 |
| `{address}` | 由 `location(level='point')` 取，不存 data_json | — | — |

**占位符没填就整句降级**：`{dorm}` 为空 → 该 FAQ 退回通用措辞，绝不输出 `{dorm}` 字面量。


### 3.5 场景问答：按 ID 绑定，不按名字

```sql
-- 023_kb_faq.sql
CREATE TABLE kb_faq (
  id INTEGER PRIMARY KEY,
  tenant_id INTEGER NOT NULL DEFAULT 1,
  vertical_id INTEGER REFERENCES vertical(id),  -- NULL = 所有品类通用
  scope_level TEXT NOT NULL DEFAULT 'global',   -- global | vertical | city | employer
  scope_location_id INTEGER REFERENCES location(id),
  scope_employer_id INTEGER REFERENCES employer(id),
  question TEXT NOT NULL,
  keywords TEXT NOT NULL DEFAULT '[]',
  answer TEXT NOT NULL,             -- 可含 {占位符}
  media TEXT NOT NULL DEFAULT '[]', -- 【图片:x】【视频:y】
  priority INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'enabled',
  template_item_id INTEGER,         -- 来自哪个模板项，便于统计和升级
  created_at TEXT, updated_at TEXT
);
CREATE INDEX ix_faq_scope ON kb_faq(tenant_id, vertical_id, scope_level, status);
```

**为什么按 ID 不按名字**：厂名改了、园区改名了，按名字绑定的问答全部失效。按 ID 绑定，改名字不影响。

**检索顺序（写死，不打分）**：

```
1. vertical_id 匹配（NULL 视为通用）
2. 按 scope_level 从窄到宽：
   employer(当前设备绑定的招工方) → city → vertical → global
3. 同一层内 keywords 命中，命中多条取 priority 最大
4. 都不命中 → 写 unknown_questions，回兜底话术
```

**这一步就是「分不清厂」的解**：客户问"包吃住吗"，系统先拿到**当前设备绑定的 `employer_id`**，只在「该招工方 + 该城市 + 该品类 + 全局」里找，别家的话术**根本不进候选集**。


### 3.6 模板包与流程模板

```sql
-- 024_kb_template.sql
CREATE TABLE kb_template (
  id INTEGER PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,        -- faq-factory-v1 / faq-subway-v1 / faq-domestic-v1
  name TEXT NOT NULL,               -- 工厂通用问答包
  vertical_code TEXT NOT NULL,      -- 绑到品类 code
  industry TEXT NOT NULL DEFAULT 'labor-dispatch',
  version INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'published'
);

CREATE TABLE kb_template_item (
  id INTEGER PRIMARY KEY,
  template_id INTEGER NOT NULL REFERENCES kb_template(id) ON DELETE CASCADE,
  question TEXT NOT NULL,
  keywords TEXT NOT NULL DEFAULT '[]',
  answer TEXT NOT NULL,
  media TEXT NOT NULL DEFAULT '[]',
  priority INTEGER NOT NULL DEFAULT 0,
  sort_order INTEGER NOT NULL DEFAULT 0
);

-- 流程也是模板，不是写死在代码里
CREATE TABLE flow_template (
  id INTEGER PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,        -- flow-factory-v1
  vertical_code TEXT NOT NULL,
  steps_json TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'published'
);
```

`steps_json` 示例（工厂）：

```json
[
  {"stage": "ask_job_type", "ask": "你应聘普工还是叉车？", "skip_if": "only_one_position"},
  {"stage": "send_info",    "action": "render_position_card"},
  {"stage": "ask_interview","ask": "这两天能过来面试吗？"},
  {"stage": "collect",      "ask": "名字和电话发我，给你先报名"},
  {"stage": "done",         "action": "send_interview_notice"}
]
```

导入时：`kb_template_item` → `kb_faq`，`vertical_code` 映射到该租户的 `vertical.id`，记录 `template_item_id`。**升级模板时只更新没被手工改过的项**（靠 `template_item_id` 是否为空判断）。

**加新品类 = 插一行 `vertical` + 一份 `faq_pack` + 一份 `flow_template`，不动代码。**

### 3.7 设备绑定

`agent_devices.data_json` 增加：

```json
{
  "vertical_id": 1,
  "employer_id": 12,        // 工厂/保姆：绑定一个招工方
  "location_ids": [3, 5]    // 地铁/船员：绑定城市或线路组
}
```

心跳时把 `vertical_id` / `employer_id` 一起上报，服务端据此确定 FAQ 检索的 scope。

## 四、检索流程（重写后的完整链路）

```
客户消息进来
   ↓
[1] 取设备上下文：device_code → vertical_id / employer_id / location_ids
   ↓
[2] 读当前流程 stage（flow_template 解释器）
   ↓
[3] FAQ 匹配（vertical → employer → city → global，命中即返回）
   ├─ 命中 → 用岗位动态字段填充占位符 → 回复 → 保持原 stage
   └─ 未命中 → 继续
   ↓
[4] 流程推进（stage 的固定话术，代码拼，模型不改数字）
   ↓
[5] 都不匹配 → unknown_questions + 兜底话术
```

**LLM 的位置**：只在第 3 步和第 4 步之间做「措辞润色」，**输入是已经确定好的事实块**，数字校验照旧（`kb_reply.verify_reply`）。

## 八、这套结构为什么能撑住"做大"

| 未来场景 | 能否撑住 | 靠什么 |
|---|---|---|
| 一个工业区 15 个厂 | ✅ | `location(park)` + `employer` |
| 同一个区两家同名厂 | ✅ | `employer_code` 唯一，名字可以重 |
| 厂改名/被并购 | ✅ | 编码不变，引用不变 |
| 客户说「松下」（简称） | ✅ | `employer_alias` |
| 客户说「钟村工业区那片」 | ✅ | `location(park)` 作为 scope 一级 |
| 地铁一岗覆盖 4 城 | ✅ | `position_location` 多对多 |
| 一个厂/城市多个面试点 | ✅ | `location(level='point')` |
| **开白领品类** | ✅ | `vertical` 一行 + schema，零迁移 |
| **开保姆品类** | ✅ | 同上，`location_levels` 去掉园区级 |
| **开船员品类** | ✅ | 同上，`employer` 存 IMO/船型，`location` 存港口 |
| 接第 2 个租户 | ✅ | 全表 `tenant_id`，品类/模板/招工方各自独立 |
| 换工价不改话术 | ✅ | 占位符，数字只在 `position.data_json` |
| 模板升级不影响已改内容 | ✅ | `template_item_id` 追踪来源 |
| 流程节点增加 | ✅ | `flow_template.steps_json`，代码是解释器 |

## 九、v3 相对 v2 的修正

| v2 | v3 | 原因 |
|---|---|---|
| `business_line` 表 | `vertical` 表 + `config_json` | 品类不只区分流程，还决定招工方称谓、位置层级、岗位字段 |
| `factory` / `park` / `district` / `province` / `city` 五张表 | `employer` + `location`（通用树） | 保姆的"厂"是家庭、船员的"厂"是船东，`factory` 装不下 |
| `interview_point` 独立表 | `location(level='point')` | 面试点/雇主家/港口是同一种东西 |
| 流程写死在 `flow_engine.py` | `flow_template.steps_json` | 加品类不改代码 |
| 模板包全局一份 | 按品类一份 | 工厂和保姆的问答内容不同 |
