## 发布与启动路径

1. PR / 分支检查运行 Node、Python 测试及客户端打包验证；冻结核心或客户端依赖变更会挡在 Linux 部署之前。
2. main 检查通过后，按该完整 SHA 部署 Linux 的 Compose 和 systemd 两条路径。
3. 两条部署均成功后，发布 `win-client-<完整 SHA>` Release，包含 `windows-client.zip`（内含清单）和 SHA-256 校验文件。先验证 tag 和草稿资产，再公开；重跑仅补全草稿缺失资产，不覆盖既有资产。
4. `CloudPilot` 登录触发 → `C:\agent\client-startup.cmd` → `client_updater.py` → 校验、备份、替换 → 原有 `pilot-hidden.vbs` → `start-pilot.cmd`。

Win 不是 Git 工作区，不需要在机器上存 GitHub token。更新器查询当前 main，只接受同 SHA 的公开 Release。包尚未发布、网络失败、已有发送进程、核心不同、缺少本地 `login_code.py` 或校验失败时均停止，不启动客户端。主分支发布和 Win 应用由同一提交关联；Win 实际应用时间是下一次交互登录。

## 回退与待验收边界

更新失败自动尝试恢复已替换源码，若恢复也失败则明确打印失败文件和备份路径，并停止启动。bootstrap 失败会恢复原文件与导出的任务 XML。人工回退 bootstrap 时恢复上述备份，仍保持任务 Disabled。服务端代码按仓库 revert 流程回退；不要自行恢复生产数据库。

本次未验证 main 上的真实 Release 发布或恢复后的客户发送；PR 不能触发生产发布。合并后的首次流水线仍需核对 Release 与 Linux SHA，恢复任务后再核对 `.client-version.json` 和日志。错会话事故根因、unknown 账本处置及恢复发送是独立事项，本功能不会解决或绕过它们。

更新器互斥锁和应用前的进程复查可以阻止重复更新及已运行客户端；它无法锁住外部人工绕过任务的启动行为。维护窗口中应继续使用唯一的 CloudPilot 入口，不同时手工运行 autopilot。
