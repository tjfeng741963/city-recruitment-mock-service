## 二、位置卡：从「发不了」到「随便发」

### 2.1 问题

企微 PC 没有「发送位置」入口，也没有开放接口。客户问「发个定位」，
过去只能回一段文字 + 高德链接，早期还把中文名 percent-encode 进 URL，
客户看到的是 `%E5%86%A0%E5%AE%87...` 一串乱码。

### 2.2 突破：卡片可以直接「造」

剪贴板里的 `WeWork Message` 格式（353 字节）拆开是：

```
41 字节 Boost 头 "22 serialization::archive 19 0 0 1 0 <len> "
外层 protobuf：field1..7 元数据 | field8 = 位置消息 protobuf | field9.. 签名外壳
```

field8 的内容与 `message_table.content`（content_type=6）**完全一致**，
而位置消息本身只有 5 个字段：

```
09 <lng f64> 11 <lat f64> 1a <len><地址> 22 <len><名称> 29 <8×0> 32 00
```

所以保留一份真实卡片的外壳，替换 field8 就能给**任意坐标**生成卡片。
实现：`agent/location_card.py`（`build_card` + `send_card`）。

发送动作与既有媒体发送完全一致，**不新增任何点击/键盘类别**：

```
抢前台 → 等窗口可见 → 点输入框 → 写剪贴板 → Ctrl+V → 等可见 → 回车
```

### 2.3 落地

| 位置 | 改动 |
|---|---|
| 问答 | 客户问定位 → 返回 `location_card` → 客户端补发一张卡；高德链接降级为兜底（且去掉中文 name 参数） |
| 开场 | 新增 `kind=location`（迁移 062），开场最后一条可以是卡 |
| 前端 | 开场工具栏「+ 位置卡」：下拉选面试点自动带坐标 → 实时地图预览（OSM 瓦片，不需要高德 key） |
| 设备配置 | 下发 `location_cards` 字段 |

### 2.4 实测

| 时间 | 动作 | 结果 |
|---|---|---|
| 15:50 | 合成「冠宇商务中心」(113.39114, 23.117692) 发给青冥 | 客户收到原生地图卡，可点开导航 |
| 18:39 | 用 `location_card.send_card()` 重发 | 成功，截图确认 |

## 三、会话定位：emoji 只是表象，根因是「同一个人存两份」

### 3.1 现象

客户 🦄Garbo_C🦄 发来「工资多少」，客户端报
「联系人名称已变化或不能唯一搜索」直接挂起，客户既收不到回复也不进人工队列。

### 3.2 根因

```sql
user_table             id=7881301055908323   name='🦄Garbo_C🦄'   ← 会话 ID 里用的是这个
wechat_contactV1       wxid=ozynqskONaPvn…   name='🦄Garbo_C🦄'   ← 同一个人的微信身份
```

`store.contacts()` 把两张表**合并**，同一个人出现两次、名字一样。旧守卫要求
「同名集合恰好等于会话对方」——集合永远不可能等于单个 id，所以必然被拦。
**emoji 只是让错误更早暴露，去掉 emoji 一样会被拦。**

### 3.3 修法

按表分别判断（`_same_name_ids`）：

- 对方在企微表里 → 只有**企微侧**同名超过一个才拦（微信侧影子记录不算）
- 对方是纯微信联系人 → 微信侧同名超过一个才拦
- 读不到表 → 退回合并口径（保守）

落点安全仍由发送侧 `expect_id` + 发后回读兜底。

实测：Garbo_C 20:12 正常收到开场（2 条文本），不再被拦。

### 3.4 真同名撞车怎么办

两个不同的人都叫「小王」时，搜索框只给一个列表，程序分不清。
**解法是给客户设一个唯一备注**——设完备注，会话显示名变成备注、搜索唯一命中，
守卫也不再判撞车。代码已支持（备注功能见第六节）。

## 四、媒体：明明发到了却判失败

### 4.1 现象

每次开场都在视频那一步中断：

```
[开场 5] video:安检.mp4 发送失败：未回读到目标会话中唯一的新媒体消息
```

### 4.2 根因

查库发现视频**确实到了**：

```
597 | sender=1688855894882096 | content_type=23 | 383 字节
内容头部 hex: 0A 0B 2F E5AE89E6A380 2E6D7034  →  "\n\x0b/安检.mp4"
```

本版企微把粘贴发送的视频落成 **content_type=23**，图片落成 **14**；
而回读只查 `43/49`，差集永远为空 → 必然判失败。

### 4.3 修法

- 类型改为：图片 `(3,13,14)` / 视频 `(23,43,49)`，兼容新旧版本
- 回读加 4 次 × 0.5s 重试（视频要等转码写库）

实测：新代码能读到 597，`video 快照: ['370','597'] 命中: True`。

## 五、开场与回复逻辑

### 5.1 开场播完即停

原来开场播完会**再补一条**针对首句的回复，连着刷屏。改为：

```
[开场] 青冥 开场已播完，等客户下一条
```

客户下一句才走正常问答。相关 39 项用例同步到新行为。

### 5.2 回复里的事实顺序

客户反馈「问什么岗位、几点上班，回复变成时间→岗位」。
事实卡本身是固定顺序（城市→厂名→**岗位**→**工价**→**班次**→…→面试时间），
问题出在模型重排。已在硬规则里明确：

> 陈述多个事实时，顺序必须与岗位事实一致，不许调换；话术库原文自带顺序的也不许重排。

**注意**：三个岗位实测都没复现用户描述的现象，这条规则是防御性的，
需要用户给出具体原话才能确认。

### 5.3 媒体与文案分离

媒体项不再自带配文：保存时自动拆成两条（文本在前、媒体在后），
发送顺序是「文本 → 图片/视频」，不会粘在一起。

## 七、「黑屏」的真凶：我方的控制台窗口

排查中一度判断为「RDP 断开/会话锁屏」，**这是错的**。枚举窗口后拿到证据：

```
hwnd=853446  pid=4968  1180×694  visible=True  PrintWindow亮度=0.0    ← 僵尸窗口
hwnd=2426148 pid=7552  1044×694  visible=True  PrintWindow亮度=227.6  ← 真窗口（渲染正常）
前台窗口 = CASCADIA_HOSTING_WINDOW_CLASS（python.exe 控制台）覆盖大半个屏幕
```

两层原因：

1. 企微「切换账号」留下一个**可见但整块纯黑**的残留实例窗口（更大，盖在上面）
2. 探测脚本用 `python.exe`，每跑一次就弹一个**黑色控制台**压在企微上

### 修法

- 客户端指令泵每 10 分钟检查：可见 `WeWorkWindow` ≥2 个时，把亮度趋近 0 的隐藏掉（只隐藏不杀进程）
- 探测脚本 `python.exe` → `pythonw.exe`，不再产生控制台
- 所有校验改用 `PrintWindow`（抓窗口自身），不用全屏截图（会被遮挡影响）

# 附录 E：客户备注功能——下次怎么接着做

## E.1 已经确认可用的事实

| 事实 | 证据 |
|---|---|
| 备注存在 `external_user_relation_v3.remarks`（按 `user_id`） | 查库确认字段存在，当前全空 |
| 备注可以在本地库**读** | `remark.read_remark(user_id)` 可用 |
| UI 路线存在 | 通讯录 → 搜索 → 第一条结果 → 资料卡「设置备注和描述」→ 弹窗（截图确认） |
| 指令队列可承载 | `kind=set_remark` 入队/领取/回执全通，5 次实测都有 `command_id` |
| 前台能强抢 | `AttachThreadInput` 后不再报「抢不到前台」 |

## E.2 卡住的那一步

```
点击搜索框 → 焦点到了
Ctrl+A     → 选中（高亮可见）
Delete     → 无效
Ctrl+V     → 无效（剪贴板回读确认内容正确）
```

`keybd_event` 与 `SendInput` 都失败。**下一步按顺序试**：

1. **`WM_SETTEXT` / `EM_REPLACESEL` 直投**：用 `FindWindowEx` 找到搜索框子窗口（企微是 Qt，
   可能是自绘控件，没有标准 Edit 句柄——先用 `EnumChildWindows` 打印类名确认）
2. **输入法注入**：`ImmAssociateContext` + 逐字 `WM_IME_CHAR`（中文必须走输入法或剪贴板）
3. **换入口**：不走搜索框，直接在「我的客户」列表里右键 → 设置备注（需要加右键注入，
   `mouse_event` 的 `0x0008/0x0010`，不涉及新的键鼠类别）
4. **放弃 UI**：`UPDATE external_user_relation_v3 SET remarks=?, remark_time=?` 后重启企微，
   验证是否被云端覆盖。**必须先验证再上生产**——覆盖了就等于没做，还可能造成本地/云端不一致

## E.3 建议的验证顺序

```
先做 3（换入口，改动最小、风险最低）
  → 不行再做 1（直投消息）
  → 都不行才考虑 4（改库，必须先在小号上验证云端是否覆盖）
```

## E.4 这件事的真实价值

- 备注本身不是刚需，**它是「同名撞车」的唯一自动解法**
- 如果不做，遇到真同名客户只能人工回（客户端会安全拦下，不会发错人）
- 所以优先级建议低于「岗位补坐标」和「bridge_contacts 上报失败」两件事
