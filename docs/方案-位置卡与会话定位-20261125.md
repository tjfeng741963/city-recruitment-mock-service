# 位置卡与会话定位：机制、前端形态与改造方案

> 2026-11-25 · 覆盖「客户问定位怎么发原生卡」「前端怎么选卡」「名字带 emoji 为什么回不出去」三件事
>
> 结论先行：
> 1. **位置卡不需要识图、不需要采集、不需要收藏**——坐标+地址+名称直接生成，前端就是下拉选面试点。
> 2. **会话定位现在靠「按名字搜索」，emoji 只是暴露了守卫过严**，不是搜索本身不支持；改法是把「姓名唯一性」校验换成「会话 ID + 回读校验」。
> 3. 截图匹配（OCR）只适合当兜底，不该做主路径。

---

## 一、位置卡是什么，为什么企微发不出来

企微 PC 端**没有「发送位置」入口**，也没有开放接口。位置消息是 `content_type=6` 的结构化消息，
只能在手机端或从已有消息里「复制/转发」。

客户问「发个定位」，过去只能回一段文字 + 高德链接：

```
导航：https://uri.amap.com/marker?position=113.39114,23.117692
```

链接能导航，但不是客户习惯的那种卡片，而且早期版本把中文名 percent-encode 进 URL，
客户看到的是 `%E5%86%A0%E5%AE%87...` 一串乱码（已修：去掉 name 参数）。

### 1.1 剪贴板里的位置卡长什么样

右键任意一条位置消息 →「复制」，剪贴板里会出现 8 种格式，其中关键的是企微私有格式
`WeWork Message`（实测 353 字节）：

```
41 字节 Boost 头："22 serialization::archive 19 0 0 1 0 <payload长度> "
外层 protobuf：
  field1..7   消息元数据（field7 = 0x38 06 表示内容类型 6 = 位置）
  field8      0x42 <len> <位置消息 protobuf>     ← 与 message_table.content 完全一致
  field9..    签名/令牌等外壳字段
```

位置消息 protobuf 本身极简单（从库里 7 条真实位置消息反推）：

```
09 <lng: float64 LE>
11 <lat: float64 LE>
1a <len> <地址 UTF-8>
22 <len> <名称 UTF-8>
29 <8 字节 0>
32 00
```

### 1.2 所以卡片可以「造」出来

保留一份真实卡片的外壳（`_PREFIX` / `_SUFFIX` 两个常量），只替换 field8 的内容，
就能给**任意坐标**生成一张能正常发送的原生卡。实现见 `agent/location_card.py`：

```python
def build_card(lng, lat, address, name) -> bytes:
    inner = (b"\x09" + struct.pack("<d", lng)
             + b"\x11" + struct.pack("<d", lat)
             + b"\x1a" + varint(len(addr)) + addr
             + b"\x22" + varint(len(label)) + label
             + b"\x29" + b"\x00" * 8 + b"\x32\x00")
    payload = _PREFIX + b"\x42" + varint(len(inner)) + inner + _SUFFIX
    return (_HEADER + str(len(payload)) + " ").encode() + payload
```

发送动作与既有媒体发送（`paste_media`）完全一致，**不新增任何点击/键盘类别**：

```
抢前台 → 等窗口可见 → 点输入框 → 写剪贴板(WeWork Message) → Ctrl+V → 等可见 → 回车
```

### 1.3 实测记录（134 生产机）

| 时间 | 动作 | 结果 |
|---|---|---|
| 15:50 | 合成「冠宇商务中心」(113.39114, 23.117692) 发给青冥 | 客户收到原生地图卡，可点开导航 |
| 16:10 | 清空剪贴板，只用落盘的 353 字节写回再粘贴 | 卡片照样出现（证明不依赖 UI 复制） |
| 18:39 | 用 `location_card.send_card()` 重发 | 成功，截图确认 |

> 注意：外壳里的签名来自一条真实消息，长期重复使用是否触发风控**尚未长期验证**。
> 当前约束：一次回复最多一张卡，跟随正常回复节奏，不做批量群发。

## 二、前端怎么让运营选位置卡（不需要识图）

### 2.1 位置卡是结构化数据，不是图片

面试点里已经有 `name / address / lng / lat`（来自企微位置消息或手工录入），
卡片就是这四个字段渲染出来的。所以**选择 = 从下拉列表挑一个面试点**，
不涉及截图匹配、不涉及 OCR、也不涉及「从聊天记录里复制卡片」。

### 2.2 交互路径

```
岗位 → 编辑 → 系统 Agent → 开场（N）→「+ 位置卡」
```

弹窗内：

```
面试点      [冠宇商务中心2楼224室        ▼]  [套用]   ← 选了自动带出坐标/地址
卡片标题    [冠宇商务中心                          ]
卡片地址    [广东省广州市天河区车陂路438号3栋2楼201号 ]
经度/纬度   [113.39114]        [23.117692]
预览        ┌──────────────┐  冠宇商务中心
            │  小地图 + 红点 │  广东省广州市天河区…
            └──────────────┘
```

- 地图预览用 OpenStreetMap 瓦片（`tile.openstreetmap.org/{z}/{x}/{y}.png`），
  **不需要高德 API key**，按经纬度算瓦片坐标，红点钉在正中；瓦片加载失败就退化成
  「地图暂不可用」，地址文字始终可见。
- 组件：`frontend-vue/src/components/agent/LocationCardPreview.vue`，面试点编辑和开场列表共用。
- 保存后，开场列表里那一条直接渲染成同一张地图卡，所见即所发。

### 2.3 数据结构

```sql
-- 迁移 062：开场支持 kind='location'
-- content 存 JSON：
{"lng":113.39114,"lat":23.117692,"address":"广东省广州市天河区车陂路438号3栋2楼201号","name":"冠宇商务中心"}
```

服务端 `serializeOpening` 会把 content 解析成 `location` 字段一起返回，前端不用二次解析。

### 2.4 为什么不做「从聊天记录采集卡片」

走过弯路：一开始设计成「运营在企微里右键卡片→复制，客户端读剪贴板上报，后台绑定到面试点」，
还建了 `location_cards` 表（迁移 061）做兜底。后来发现能直接造卡，采集就多余了。

保留采集通道的理由只有一个：万一企微改了消息格式，造卡失效，还能用真实卡片兜底。

## 三、会话定位：为什么名字带 emoji 就回不出去

### 3.1 现在的定位方式

```
Ctrl+F 打开搜索 → Ctrl+A/Delete 清空 → 粘贴联系人名字 → 回车打开会话
→ 清空输入框 → 粘贴正文 → 哨兵回读 → 回车
→ 回读数据库确认消息落在 expect_id 指定的会话里
```

也就是说：**UI 层靠名字搜索，校验层靠会话 ID**。

### 3.2 为什么不能「直接用会话缓存」

客户端确实有本地 `message.db`（加密，已解密读取），里面有 `conversation_id`、
显示名、全部消息。但那是**数据层**，不是**操作层**：

- 企微 PC 是 Qt 应用，没有对外接口，也没有可用的 UI Automation 树；
- 会话 ID（`S:1688855894882096_7881299918302353`）无法直接喂给界面打开某个会话；
- 唯一能「打开指定会话」的界面入口就是搜索框或点列表行。

所以「命中缓存」只能解决**知道是谁**，解决不了**把界面切过去**。切界面必须靠
搜索（文字）或点行（坐标/图像）。

### 3.3 真正卡住的地方：姓名唯一性守卫

`agent/autopilot.py: _sequence_block_reason()`：

```python
contacts = store.contacts()                       # {联系人ID: 显示名}
matches = {key for key, value in contacts.items()
           if str(value or "").strip().casefold() == name.casefold()}
if matches != {other}:                            # other = 会话ID里解析出的对方ID
    return "联系人名称已变化或不能唯一搜索，停止介绍并待人工核对"
```

它要求「显示名完全相等的联系人集合」**恰好等于**会话 ID 里的对方。

Garbo_C 触发这条的原因：
- 显示名含 emoji（🦄Garbo_C🦄），列表里的名字和联系人表里的名字可能不完全一致
  （空格/emoji 变体/备注名），`casefold` 相等比较过不去；
- 或者同名联系人不止一个，集合大小不等于 1。

这是**守卫过严**，不是搜索失败——搜索本身用剪贴板粘贴，emoji 完全没问题。

### 3.4 三种改法对比

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A. 文字唯一子串 | 去掉 emoji/空格，取剩余部分当搜索词，命中后按会话标题校验 | 改动小，仍然纯文字 | 子串仍可能撞名（如「小王」） |
| **B. 放宽守卫 + ID 回读（推荐）** | 只要 `other` 在联系人表里就允许发送；靠 `expect_id` + 发送后回读数据库确认落点 | 直接消灭 emoji/重名问题；安全由 ID 校验兜底 | 若两个会话显示名完全相同，搜索可能打开错的，但**回读会发现并记 unknown**，不会误发 |
| C. 截图/OCR 匹配 | 截图会话列表，OCR 找名字匹配的行，点它 | 完全绕开搜索框 | 脆弱（缩放/主题/字体/滚动都会变）、慢、要维护 OCR 依赖 |

**推荐 B**。理由：现在已经有 `expect_id` 和「发送后回读 `message_table` 确认落点」两道 ID 级校验，
姓名唯一性守卫是冗余的；保留它只会把 emoji 客户全部挡在门外。

C 只建议作为**兜底**：当回读连续两次发现落点不符时，再截图让人工确认，而不是让 OCR 参与主路径。

### 3.5 落地清单（方案 B）

1. `_sequence_block_reason`：把「姓名集合 == {other}」改成「`other` 存在于 contacts」，
   删除名字相等性要求；保留接管/流失/回复来源三条守卫。
2. 搜索词仍用显示名；若搜索后回读发现落点不符，记 `unknown` 并提示人工（现有行为）。
3. 补测试：同名两个联系人、名字带 emoji、备注名与昵称不一致三种场景。
4. 观察一周：统计 `unknown` 里「落点不符」的比例，再决定要不要上 OCR 兜底。

## 四、开场逻辑（已按 2026-11-25 要求调整）

```
客户加好友并发来第一句
  → 按 seq 逐条播开场（文本 / 图片 / 视频 / 位置卡）
  → 播完即停，不再补一条针对首句的回复
  → 等客户下一条消息，再走正常问答
```

改动点：`agent/autopilot.py` 开场循环结束后，由「reopen_for_reply + 继续回复」
改为 `mark_skipped("开场已播完，等客户下一条") + continue`。

后端 39 项 `test_node_flow.py` 用例已同步到新行为。

位置卡作为开场最后一条时：`kind='location'`，客户端在文本都发出后调用
`location_card.send_card()`，失败只记日志、不重试（防重复）。

## 五、成本实测（deepseek-chat，官方价 输入 ¥2/百万、输出 ¥8/百万）

| 项 | 数值 |
|---|---|
| 总调用 | 65 次 |
| 输入 token | 340,409 |
| 输出 token | 6,711 |
| 总花费 | 约 **¥0.74** |
| 平均每条 | 输入 5,237 / 输出 103 → **¥0.011（1 分钱）** |

按天：11-24 花 ¥0.56（47 次），11-25 花 ¥0.18（18 次）。

**结论**：不是「回复贵」，是账户余额本来见底。成本 98% 在输入侧，构成大致是
岗位事实（约 1588 字）+ 人设 + 知识库命中 + 历史对话。

**没有开思考模式**：`agent-llm.ts` 只传 `temperature + max_tokens(700)`，
不传任何 reasoning 开关，且收到 `reasoning_content` / `<think` / `reasoning_tokens>0`
会直接抛 `provider_reasoning` 错误。

降本优先级：历史只带最近 3 轮 > 精简 facts_json > 知识库限条数。
