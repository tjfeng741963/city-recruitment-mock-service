# 灰度诊断能力：做了什么、还差什么、风险在哪

记录日期：2026-11-16。本文说明为灰度测试搭建的「AI 无黑盒」诊断链路，以及尚未覆盖的部分与已知风险。

**一句话**：现在线上每一条回复都能查到「谁生成的、走了哪一步、命中了哪条知识库、模型发了什么 prompt、返回了什么、用了多久、审核改没改、为什么走了兜底」。

---

## 一、做了什么

### 1.1 每轮回复的完整诊断（`trace`）

写在 `flow_events` 的 `type='reply'` 事件的 `body.trace` 里。字段清单：

| 分类 | 字段 | 说明 |
|---|---|---|
| 归属 | `device_code` | 哪台机器、哪个企微号 |
| 来源 | `source` | `script`/`card`/`fact`/`collect`/`kb`/`closing`/空=模型自由发挥 |
| 流程 | `stage_from` → `stage_to`、`action` | 这一轮走了哪一步 |
| 知识库 | `kb_hit_id`、`kb_tier`、`kb_candidates` | **查到过什么**（不受后续重置影响） |
| 知识库 | `kb_used`、`kb_entry_id`、`kb_repeat`、`kb_markers` | **最后用没用** |
| 业务 | `city`、`position_id`、`booked`、`recruit_status` | 当时的业务状态 |
| 审核 | `review[]` | 每轮 verdict/reason、是否改写、是否被事实护栏拦下、是否强制兜底、是否缺席、是否 bypass |
| 审核 | `draft_before_review` | 审核前的原稿（截断 500 字） |
| 兜底 | `echo_guarded`、`media_appended` | 回声拦截、补回媒体条数 |
| 模型 | `llm[]` | 每次调用的完整明细，见下 |

### 1.2 模型调用全景（`trace.llm[]`）

```
model / temperature / max_tokens / ok / attempts / ms /
prompt / raw / tokens{prompt,completion,total} / error
```

三个关键语义：

- **`llm` 为空数组是信息，不是缺数据**——说明这轮一次模型都没调（代码渲染或确定性兜底），能立刻分清「模型答错了」和「根本没调模型」。
- **`attempts` 记重试次数**，失败时 `error` 带异常类型。
- **`api_key` 绝不入库**（有测试断言）。

实现用 `ContextVar` 而不是给 `complete()` 加参数：它被 A 生成、B 审核、知识库改写三处共用，逐层透传会把签名改得到处都是。

### 1.3 隐私开关

| 配置 | 默认 | 作用 |
|---|---|---|
| `APP_LLM_TRACE_ENABLED` | `true` | 关掉后只记元数据（模型/耗时/token/成败/失败原因），不留 prompt 与返回正文 |
| `APP_LLM_TRACE_MAX_CHARS` | `2000` | prompt 与返回的截断长度 |

**prompt 与模型返回里含客户原话。** 生产环境的数据留存期限应与客户约定一致。

### 1.4 复盘导出工具

```bash
cd backend
python -m scripts.gray_report                    # 最近 24h 会话时间线
python -m scripts.gray_report --suspects         # 只看可疑回复
python -m scripts.gray_report --csv out.csv      # 导出给测试员标注
python -m scripts.gray_report --json             # 给看板
```

可疑判定**刻意分开报**，因为这是不同来源的 bug：

- 业务层：走了兜底话术 / 模型复读被拦截 / 审核两轮未过 / 重写稿编工价被拦下 / 来源为空 / 已标记不合适
- 模型层：本轮未调用模型 / 模型调用失败 N/M 次（带原因）/ 模型响应慢 >10s

CSV 列：`会话 / 时间 / 客户原话 / 我们回的 / 来源 / 阶段变化 / 知识库条目 / 可疑原因 / 模型调用次数 / 模型 / 耗时ms / token / 模型失败原因 / 人工判定 / 应为`

## 二、灰度当天怎么用

### 开测前

```sql
SELECT MAX(id) FROM flow_events;   -- 记下起点
```

### 测试中（建议每 2 小时）

```bash
cd backend && python -m scripts.gray_report --since 2026-11-16T09:00 --json
```

重点看四个数：

| 信号 | 说明什么 |
|---|---|
| `sources` 里 `(空)` 占比高 | 模型自由发挥多，输出不可控 |
| `llm` 失败次数 | 中转站不稳定或配错 |
| `suspects` 占比 | 需要人工看的比例 |
| `recruit_status=disqualified` 异常增长 | **误判为不合适**，需立即人工核对 |

### 出问题时怎么定位

```
1. 找到那条回复的 trace
2. 看 source
   ├─ script  → 运营话术错了 → 配置问题，不是代码 bug
   ├─ card    → 代码拼卡错 → 代码 bug
   ├─ fact    → 岗位事实取错（串厂/串城市）→ 数据 bug
   ├─ collect → 资料收集逻辑错 → 代码 bug
   ├─ kb      → 命中了错误的 KB 条目 → 看 kb_candidates 里的 picked 那条
   └─ 空      → 看 trace.llm：调了模型就是模型问题，没调就是兜底路径
3. 看 stage_from → stage_to 跳得对不对
4. 看 draft_before_review 与最终文本的差异（审核改了什么）
```

## 三、遗留问题

### 3.1 未做（本次范围外）

| 事项 | 影响 | 建议时机 |
|---|---|---|
| 知识库「未命中」明细 | `unknown_questions` 只记原话与次数，不记「当时试了哪几层、为什么都没命中」 | 灰度跑一轮后按需补 |
| 多轮会话的整体评分 | 只能逐条看，看不出「这个客户最后有没有约上」的链路质量 | 先用 `recruit_status` 近似 |
| `flow_events` 无清理策略 | 每轮对话写十几条事件，长期会涨 | 灰度结束后定保留期 |
| `disqualified_reason` 仍无写入方 | 分手原因无法归类（其他窗口也记录了同一问题） | 需产品先定分类口径 |

### 3.2 依赖外部才能验证

| 事项 | 卡在哪 |
|---|---|
| 真实模型调用记录 | 本地/测试环境没有真模型，只用桩验证过字段落位；线上需实际跑一轮确认 |
| `gray_report` 在 PostgreSQL 上的表现 | 本地是 SQLite，查询走 SQLAlchemy 应该没问题，但未在 PG 实测 |

## 四、风险

### 4.1 高：数据里存了客户原话

`trace.llm[].prompt` 与 `raw` 含客户消息原文。**这是完整版的代价**，也是必要的——没有 prompt 和返回就查不出模型为什么这么答。

- 开关 `APP_LLM_TRACE_ENABLED=false` 可随时关掉正文，只留元数据
- **上线前应确认**：这些数据的留存期限、谁能查库、是否需要脱敏
- 截断 2000 字，但仍足以包含完整对话片段

### 4.2 中：`flow_events` 体积增长

每条回复的 trace 含 prompt + raw，最坏约 4KB。一天 500 条回复 ≈ 2MB，一个月 60MB。可接受，但要定清理策略。

### 4.3 中：埋点是「尽力而为」，静默失败

`_record()` 在收集器不存在时直接返回，`collect_llm_trace()` 取走即清空。如果某个调用点漏了 `begin_llm_trace()`，那一轮的 `llm` 就是空数组——**和「没调模型」长得一样**。

目前 `flow_answer` 里已覆盖，但 `/flow/greet` 等其他入口**没有加**。走 greet 的回复其 `llm` 会是空，容易被误读。

### 4.4 低：`_trace_options()` 读配置失败时静默降级为「不记正文」

设计上是安全优先（宁可少记也不误记），但意味着配置异常时你只能看到元数据，不会收到任何告警。

### 4.5 低：可疑判定是启发式

命中只代表「值得人工看一眼」，不是结论。阈值（如响应慢 >10s）是拍的，灰度后应按实际分布调整。
