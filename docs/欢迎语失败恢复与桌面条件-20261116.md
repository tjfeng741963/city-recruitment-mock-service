# 欢迎语失败恢复与桌面条件

本说明对应用户在 2026-11-16 确认的修复范围。代码开发与隔离测试不等于生产发布，也不等于真实加好友验收。

## 保留现有触发链路

继续扫描真实加好友后企微本地库产生的自动提示，向实际 Python 回复服务请求 `/api/v1/flow/greet`。招聘介绍继续按设备在后台配置。本轮不接官方客户联系 API，不改 `wecom_io_core/{win,send,store,crypto}.py`，不新增键鼠动作，不调整底层发送时序或重试次数。

哪些加好友方式会生成可读提示，仍由实际企微版本与添加方式决定；本轮已核实实例，未承诺覆盖所有方式。所有 type=1011 也不都代表加好友。

## 修复后的行为

| 情况 | 新行为 |
| --- | --- |
| RDP 会话断开、锁屏或桌面状态不可确认 | 自动队列暂停；不请求首句，不尝试发送，保留待处理消息；错误随现有心跳上报 |
| 服务端返回介绍 | 只保存原文、分段与触发记录，不立即记“已打招呼” |
| 发送前明确失败，例如抢不到前台或剪贴板超时 | 保留原文和已确认进度，后续沿现有队列处理剩余部分，不取另一套介绍 |
| 客户在失败期间继续提问 | 未完成介绍优先，后来的提问保留；介绍完成后下一轮正常回答 |
| 客户的第一个真实问题触发介绍 | 发介绍后仍保留该问题，下一轮回答，不把问题当好友提示消费掉 |
| 某段已确认发送 | 持久化该段进度；恢复时不会再次发送已经确认的段落 |
| 回读不确定、发错会话、进程在生成/发送阶段中断 | 暂停为 held；不盲目重发，不改用普通问答绕过介绍 |
| 全部文字发送且逐段确认目标会话新消息 | 原子记投递完成，再补写 `.greeted.json`；旧标记写盘失败也可由投递记录去重 |
| 更换登录账号、监听对象或退出 flow 模式 | 原介绍不自动跨账号/范围发送，保留记录待核对 |
| 编辑后台文案 | 新介绍使用新配置；已经生成的待发任务保留原文，避免同一套介绍半途换口径 |

这里的“确认”是目标会话中出现唯一匹配的新消息 ID，不是客户已读。底层 `send()` 在回读异常时也可能返回 `ok=True`，因此客户端额外核对发送前后的稳定消息 ID，不能只看 `ok`。

## 本地记录与兼容

在现有 `reply_log.db` 内追加 `welcome_deliveries` 表，初始化幂等，不更改旧表结构，不清真实数据。每个会话保留触发消息、原文/分段、连续确认段数、状态、错误与更新时间。

状态为：preparing（取文案）、ready（有原文待发）、sending（当前段结果未决）、held（暂停核对）、sent（完成）、cancelled（明确取消）。新版本不把历史 `.greeted.json` 当作需要重置的数据，不自动迁移历史失败客户为新任务。

服务端现有 `scripted_sent.greet`、`device_intro_sent` 等字段继续作为流程兼容标记；它们仍可能早于实际发送出现，不能用于宣称客户收到。实际投递结果看客户端记录；本轮未新增后台投递看板。

## 桌面条件与运维边界

客户端只读查询自身 Windows 会话连接状态，以及当前输入桌面是否是可读的 Default 桌面。不会自动连接 RDP、切换控制台、解锁、登录或抢焦点；也不会因为检查失败增加键鼠动作。

**这项修复防止桌面不可用时误推进状态，不会使键鼠程序突然获得锁屏/断开桌面的发送能力。** 上线前必须准备可用的交互桌面。生产核查时发现 RDP 断开；当天重连之后才出现实际回复，与之前“抢不到前台”失败时间相关，但未取得失败当刻的完整窗口状态，不能断言唯一根因。

若运营要求断开 RDP 后仍持续运行，需要单独确认服务器控制台/会话运行方案，并在该状态下实测。不要未经验证加入抢前台补丁、改锁屏策略或直接执行会话切换命令。

## 查看与处理未知结果

在 Windows 客户端目录执行 `python autopilot.py --list`，会显示首句会话 ID、状态、连续确认段数/总段数、会话名和错误。`--retry-held` 不会把未知首句重新放入自动发送。

结果未知时先核对实际聊天，再停止客户端，以避免修改投递记录期间继续发送。以下只是命令说明，不应对未核对的真实会话直接执行：

```powershell
python autopilot.py --resolve-welcome "S:已核实的会话ID" --confirmed-parts 1
```

`--confirmed-parts` 表示人工核实客户已收到的连续完整段数。只能保留已有确认数量，或确认当前未决的一段，不能跳过任意多段。命令仅修改本地记录并退出，不初始化企微、不发送；重新启动客户端后才处理剩余段落。该命令也受单实例锁保护，常驻客户端未停止时不会处理。

如果当前段包含媒体且文字已发、媒体失败，先人工补齐/核对该段，再确认完整段，不重新发送文字。纯媒体首句因无法预先确认目标会话而暂停，本轮后台设备介绍入口本身仍只配置文字。

生成阶段网络/进程中断且没有保存原文时，不能用此命令重新生成。需人工核对服务端与真实聊天后另作处理，不能保证过期或丢失结果可自动补齐。

`--reset` 会取消尚未完成的介绍，避免其在普通回复队列清理后又重新出现。不要用它把真实老客户伪装为新客户。

## 发布与回滚注意

1. 先完成隔离回归，所有发送接口为 mock，数据库为一次性库，不发真实消息。
2. 当前生产客户端源码与本地版本不同；发布前必须备份并核对同事修改，不能用本地整文件盲目覆盖。冻结底层不部署改动。
3. 后台、实际 8090 回复服务与 Windows 客户端是不同发布对象；main 的服务器流水线不等于 Windows 客户端已更新。
4. 发布前备份客户端源码、`reply_log.db` 和 `.greeted.json`，停单实例后更新；升级不会自动补发历史失败会话。
5. 回滚前先查看未完成任务，尤其 next_part>0 或 held/sending。不能直接退回旧版：旧版不认识独立任务，可能把失败源记录当普通回复处理。先停止自动发送，核对并保留任务快照，再按需取消旧队列对应源记录后回退；保留完整原库及备份，不删除真实聊天或覆盖整库。
