# Dify 第二回复路线

2026-11-21：用户确认保留现有 C:\agent 收发，在 4222 按设备选择 Dify。此路线只替换回复生成，不使用系统岗位人设或原开场，不更换发送动作。

```text
企微消息 → 云 Windows C:\agent → 4222 /agent/chat
                                      ↓ 按设备选择
                                Dify Chatflow API
                                      ↓ reply.messages
企微发送回读 ← 原客户端发送与回执 ← 4222 返回文本
```

## 已实现

- 新入口 `/dify-connection`：管理员选择设备来源、检查传入岗位事实、隔离模拟对话；网页测试不向企微发送。
- 来源默认 `agent`。Dify 应用密钥仅存服务端 `REA_DIFY_API_KEY` 或 `REA_DIFY_API_KEY_FILE`，页面不展示密钥。
- Dify 通过 `inputs.position_data` 读取系统绑定岗位的中性信息：名称、城市、工资、工作内容、班次、食宿、面试时间与地址。不传岗位人设、民族/健康等资格筛选条件。
- Dify 会话按设备、当前企微账号、联系人、岗位、应用配置分隔；同一会话串行调用。
- 人工接管、停用、账号/岗位/事实变更在返回前再次核对，变化就暂停。
- Dify 失败、空回复、内部标记、客户端媒体指令、无法从当前资料支持的数字工资会暂停；不回落 Agent。
- Dify 设备不获取旧开场及新节点流程。`bridge/inbound` 保持只落库，避免双回。

## 切换步骤

1. 准备专用测试企微设备，先绑定要咨询的岗位。
2. 停止该设备客户端，等待心跳离线。在线切来源返回 409，防止已缓存旧开场仍继续发送。
3. 在配置页保存 Dify 来源，再启动客户端。必须重新启动才能清除开场/流程内存缓存。
4. 对存在节点流程镜像的老设备，服务端拒绝直接切 Dify。客户端持久化快照可能继续独立续发，不能靠返回空流程消除。需另行诊断和备份本地状态，确认切换方式；本期优先全新设备和独立、干净的客户端状态目录，不删除老会话状态。仅换设备码仍可能读取以联系人为主键的旧本地快照，不能作为隔离证明。保存 Dify 来源需 fresh_client_state_confirmed=true；该确认是人工检查声明，服务端无法证明本地目录干净。
5. 管理员先在网页新建测试会话，核对事实与多轮回复。只有用户指定的测试联系人参与真实收发验收；不向其他客户试发。

## 服务端部署

- `REA_DIFY_BASE_URL`：应用服务 API 前缀，例如同机受保护回环 `http://127.0.0.1:8080/v1`（仅宿主/host 网络中有效）。生产 bridge 网络应使用已验证的私网宿主地址或服务 DNS；不能填容器自己的 127.0.0.1。
- `REA_DIFY_API_KEY_FILE`：只读挂载文件，例如 `/run/dify/app-key`；或使用现有受限 `.env.production` 的 `REA_DIFY_API_KEY`。
- 本次集成应用：`a5c7be0e-3543-4de9-8efc-d3abd87587e1`，名称“系统岗位咨询 · Dify第二路线”。只开放 API；未启用公共聊天网站。原逆向测试应用保持独立。
- 迁移 `047_dify_reply.sql`；046 已由线上节点流程占用，禁止复用。
- 生成日志存 `dify_reply_calls`，只含设备、岗位、错误码、耗时，不记录密钥/聊天原文；Dify 会话和运行日志由 Dify 持有。

## 已测证据与边界

隔离联调服务仅监听服务器 `127.0.0.1:4233`，独立数据库，复制当前 pc-win-01 绑定岗位的中性资料。四轮真实 API 测试已返回工资、班次、面试安排与下一步说明，保持一条 Dify 会话，未生成企微发送命令。本地自动测试覆盖默认路线不变、鉴权、输入更新、会话隔离、接管竞态、停用/换岗、金额和媒体协议。

当前是岗位咨询/面试意向路线，正式报名登记、候选人结构化档案、OA 和群通知尚未接入，不得把“已生成回复”说成“已送达/已报名”。金额校验只覆盖数字金额及常用单位，不等同于完整事实证明；中文大写金额、时间一致性仍依赖应用约束和人工验收。尚未对任何真实企微联系人发送第二路线测试消息。

回滚：停止专用客户端，等待离线，切回 agent，重新启动。保留 Dify 会话与调用表，不做数据库回滚或清理老状态。
