# 设备绑定多岗位——逻辑方案分析（2026-11-18）

> 结论先行：推荐「**设备多岗位池 + 会话锁定**」方案。设备可绑多个岗位（一个主岗位 + N 个候选岗位），
> **每个客户会话在其首次对话时锁定一个岗位**，Agent 会话期间所有回复/媒体/登记都走锁定岗位的上下文；
> 客户明确想看别的岗位时由模型请求换绑（服务端校验后切换）。分三阶段实施，第一阶段改动 6 个文件。

---

## 一、现状（为什么现在是一对一）

当前数据与代码是一对一设计：

```
agent_devices.data_json.position_id = 22   ← 设备绑定一个岗位（单值）
        ↓
positionOfDevice(db, device_code)          ← 服务端解析设备→岗位（agent-chat.routes.ts）
        ↓
buildFacts / openingOf / personaOf(22)     ← 事实卡/开场/人设全按这一个岗位组装
        ↓
agent_session.position_id = 22             ← 会话记忆里也存了岗位（chat 路由）
```

- **客户端无感知**：autopilot 只上报 `device_code` + 会话消息，岗位解析全在服务端——多岗位改造客户端零改动
- **媒体绑定**：`media_assets.position_id`（0=通用池，>0=岗位专属）——通用池天然支持多岗位；岗位专属图按岗位取
- **城市状态推导**：`syncCityRecruitmentStatus()`——设备绑定的岗位城市 → active。单值绑定推导也简单

一对一的问题：一台客户端机（一个企微号）只能招一个岗位——同一台机器想同时接深圳+广州两个岗位的招聘，现在做不到。

## 二、业务场景（什么时候需要多岗位）

| 场景 | 说明 |
|---|---|
| 一号多岗 | 一台设备/一个企微号同时招多个城市的岗位（深圳+广州），客服资源复用 |
| 群聊分线 | 不同微信群对应不同线路岗位（群 A 是深圳群、群 B 是广州群），客户从哪个群来就推哪个岗 |
| 客户换岗 | 客户先问深圳岗觉得远，转问广州岗——同一会话里切换岗位上下文 |
| 人员调度 | 客户端机不止一台，某台临时接手另一台的岗位 |

## 三、四种方案对比

| 方案 | 机制 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| A. 全量投喂 | 设备绑 N 岗，所有岗位事实卡全进 prompt，模型自己判断客户在问哪个 | 实现最简单 | 上下文爆炸（7 岗 × 3KB）；模型答错岗位（串数字）风险高——**多岗位数字串改是招聘大忌** | ✗ 不采 |
| B. 关键词路由 | 服务端按客户消息关键词（城市名/线路名）匹配岗位，每轮动态选岗 | 无需锁定 | 同一会话内客户上下文漂移（上半句深圳下半句广州→事实卡切换，模型记忆混乱）；关键词歧义（"16号线" 深圳广州都有） | ✗ 不采 |
| C. **会话锁定** | 设备绑多岗位（带主岗位）；**客户会话首次对话锁定一个岗位**，之后该会话所有上下文/媒体/登记都用锁定岗位；客户明确表达看别的岗位 → 模型输出换岗意图 → 服务端校验后换锁 | 每个会话上下文单一清晰（数字绝不串）；符合真实客服习惯（一个客户跟一个岗位）；会话记忆机制现成（agent_session.position_id 已存在） | 首次锁定的猜测可能不准（可由模型换岗纠正） | **✓ 采** |
| D. 群聊分流 | 群聊绑定从「群→通知」升级为「群→岗位」，按会话来源定岗 | 最精准（群的归属天然对应线路） | 依赖群聊绑定已配；私聊（非群）没有来源信息，还得兜底 | **✓ 作为 C 的首选定岗依据** |

**采 C + D 组合：设备多岗位池，会话锁定，锁定优先级 = 群聊岗位映射 > 客户显式表达（模型换岗） > 设备主岗位。**

## 四、推荐方案详细设计

### 4.1 数据模型（迁移 046）

```sql
-- 方式：不建中间表，直接扩展 agent_devices.data_json（与现有绑定同范式）
data_json.position_id  = 22            ← 保留：主岗位（兼容旧逻辑/旧前端）
data_json.position_ids = [22, 23, 25]  ← 新增：多岗位池（含主岗位）
```

会话锁定（已有表，无需迁移）：

```sql
agent_session.position_id = 22   ← chat 路由已存；改为「首次锁定后不再跟随设备主岗位」
```

### 4.2 服务端改动点（按文件）

| 文件 | 改动 |
|---|---|
| `agent-chat.routes.ts` `positionOfDevice` | 读 `position_ids` 数组；返回主岗位 + 候选列表 |
| 同 `chat` 路由 | **会话锁定逻辑**：session 已有 position_id → 用锁定的；无 → 按优先级定岗（群聊映射 > 主岗位）并写 session |
| 同 `chat` 路由换岗 | 模型输出新增 `switch_position` 字段（intent）：客户明确问别的岗位 → 服务端校验该岗位在设备池内 → 改写 session.position_id → 提示词告知模型已切换 |
| `buildFacts` | 锁定岗位事实卡照旧；**新增 `other_positions` 字段**：池内其他岗位的一行简表（「广州_地铁安检员：试用期120/班…」，运营在事实卡里配）——模型知道有什么可推荐，但**数字只在锁定岗位的事实卡里**，其他岗位数字只在客户明确换岗后才有 |
| `openingOf` / `personaOf` | 按锁定岗位取（不变） |
| `media_catalog` | 通用池 + **锁定岗位**专属媒体合并 |
| `syncCityRecruitmentStatus` | 任一 `position_ids` 的城市 → active（多岗位多城市同时招聘中） |
| `media_assets.position_id` 绑定校验 | 绑定的岗位必须在某设备的池内才对该设备生效（原逻辑不变，天然兼容） |

### 4.3 前端改动点

| 页面 | 改动 |
|---|---|
| 设备页（坐席设备） | 岗位绑定单选 → 多选（主岗位打星标）；绑定时提示城市状态联动 |
| 面试登记/群聊绑定 | 群聊绑定旁加「该群对应岗位」下拉（选池内岗位）——群聊分流的定岗依据 |
| 会话管理（对话管理） | 会话详情显示「当前锁定岗位」+ 人工换岗按钮（运营兜底） |

### 4.4 客户端改动

**零改动**。autopilot 只报 device_code + 消息；岗位解析/换岗全在服务端。媒体发送按回复里的 medias 名字走（名字来自锁定岗位的媒体目录），现有 paste_media 链路不变。

### 4.5 边界规则（必须明确）

1. **登记归属**：agent_archive 记锁定岗位（登记页可按岗位筛）
2. **媒体串岗防线升级**：可发集合 = 通用池 ∪ **锁定岗位**专属（不再是设备主岗位）——广州客户锁定了广州岗就能收广州地点图
3. **换岗后的媒体**：换锁后按新岗位重算可发集合
4. **开场重播**：开场按锁定岗位——客户首条消息触发开场时用定岗结果；换岗不重播开场（只换上下文）
5. **模型约束**：提示词明确「其他岗位只报名字和一句话简介，具体数字等客户确认换岗后才能说」——防止 A 方案的数字串岗

## 五、分阶段实施路线

| 阶段 | 内容 | 改动量 |
|---|---|---|
| 一（核心） | 迁移 046 + position_ids 读写 + 会话锁定 + 城市推导升级 + 设备页多选 | 后端 3 文件 + 前端 1 文件 |
| 二（体验） | 群聊岗位映射（定岗优先级最高）+ other_positions 简表注入 + 模型换岗意图 | 后端 2 文件 |
| 三（兜底） | 对话管理人工换岗按钮 + 登记按岗位筛选 | 前端 2 文件 |

每阶段独立可用：阶段一上线后即可一设备绑多岗（按主岗位兜底定岗），阶段二/三增强精度。

## 六、风险与约束

1. **数字串岗是最大风险**——C 方案用「会话锁定 + 其他岗位只给一句话简表」硬隔离；模型换岗必须显式（服务端校验岗位在池内才切）
2. **开场序列冲突**——多岗位时客户首条消息定岗后播对应岗位开场；若定岗错了（客户其实是问别的城市），运营在对话管理人工换岗 + 重播开场
3. **群聊映射维护成本**——群聊绑定多了一列岗位，运营每加群要配；阶段二可做「未配映射的群按设备主岗位」兜底
4. **兼容性**——`position_id`（主岗位）保留读写，旧前端/旧脚本不破坏；`position_ids` 缺失时视为单岗位（现状），完全向后兼容

## 七、前置依赖（当前状态）

- ✓ 单岗位链路已全通（生产/测试双端）：设备绑定、事实卡、开场、人设、媒体发送、城市推导
- ✓ agent_session 已存 position_id（会话锁定的落点现成）
