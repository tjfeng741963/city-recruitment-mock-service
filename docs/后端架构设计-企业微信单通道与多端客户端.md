# 后端架构设计：企业微信单通道 + 多端客户端

> 决策文档（先文档后代码）。
> 范围：**只做企业微信**，个人微信桥接（`device-bridge`）不进新架构。
> 形态：**服务端 / 设备（我的电脑）/ 多端客户端** 三层。
> 本文所有结论都可推翻，但推翻前请先看第 13 节的取舍理由。

---

## 0. 一句话方案

**FastAPI + SQLAlchemy 2.0 + PostgreSQL + Redis + WebSocket**，把"微信号"从设备概念里剥出来，设备收敛成"这台电脑"，通道收敛成"企业微信客服账号"，前端退化成纯 API 客户端（Web / 桌面 / 移动同一套接口）。

---

## 1. 目标与非目标

### 要做的

| # | 目标 | 判据 |
|---|---|---|
| 1 | 企业微信客服全链路 | 客户发 → AI 回 → 人工接管 → 人工回，全部走官方接口 |
| 2 | 电脑作为设备接入 | 一条命令注册，服务端能看到在线/心跳/版本 |
| 3 | 多端客户端 | Web、桌面、移动同一套 REST + WS，行为一致 |
| 4 | 消息不丢不重 | 事务性发件箱 + 幂等键 + 状态机可查 |
| 5 | 可替换通道 | 换/加通道不改业务代码，只加适配器 |

### 不做的

- ❌ 个人微信（ADB / 无障碍 / hook），全部下线
- ❌ 企微好友私聊的「会话内容存档」路线（那是另一条产品线，见现有 `docs/企业微信API接入断点分析与实施方案.md` 2.1 节）
- ❌ 多租户 SaaS（先单企业，但预留 `tenant_id` 字段，不实现逻辑）
- ❌ 群发/营销触达（企微侧硬限制，不做）

```
│  Web（React）      桌面（Tauri/Electron）      移动（H5/小程序） │
└───────────────┬──────────────────────────────────────────┘
                │  HTTPS REST + WSS（同一个 JWT）
┌───────────────▼──────────────────────────────────────────┐
│                      服务端（FastAPI）                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐  │
│  │ Auth/RBAC│ │ 业务 API │ │ WS Hub   │ │ Admin/运维 API│  │
│  └──────────┘ └────┬─────┘ └────▲─────┘ └──────────────┘  │
│                    │            │                          │
│  ┌─────────────────▼────────────┴──────────────────────┐  │
│  │           消息核心（Outbox / Delivery / 状态机）      │  │
│  └─────────────────┬───────────────────────────────────┘  │
│  ┌─────────────────▼──────────┐  ┌────────────────────┐  │
│  │  通道适配层 ChannelAdapter  │  │  AI 适配层（Dify）  │  │
│  │  wecom_kf / wecom_audit    │  │  chatflow / http    │  │
│  └─────────────────┬──────────┘  └────────────────────┘  │
└────────────────────┼─────────────────────────────────────┘
                     │ 官方 API（qyapi.weixin.qq.com）
   ┌─────────────────▼──────────────────┐
   │           企业微信                    │
   │  回调 → /webhooks/wecom（服务端收）    │
   └─────────────────▲──────────────────┘
                     │ 心跳 / 任务 / 本地能力
   ┌─────────────────┴──────────────────┐
   │        设备（我的电脑）Device Agent  │
   │  register · heartbeat · execute     │
   └────────────────────────────────────┘
```

**关键取舍：回调永远落在服务端，不落在设备上。**

理由：回调要求公网可达，如果每台设备都要暴露公网，运维成本爆炸。设备只做"执行和本机能力"，通过 WS 长连接领任务，所以设备不需要公网 IP。

## 3. 概念重定义（这是本次最重要的改动）

现有代码里 `agent_devices` 这条记录**既代表微信号、又代表设备、又代表通道**，三合一。新架构必须拆开：

| 层 | 实体 | 含义 | 例子 |
|---|---|---|---|
| 部署层 | **Device** | 一台物理/虚拟主机 | `pc-office-01`（我的电脑） |
| 通道层 | **ChannelAccount** | 一个具体的收发身份 | 企微客服账号 `wkABC...` |
| 消息层 | **Conversation** | 一个客户在某通道上的对话 | `(channel_account_id, external_userid)` |

关系：`Device 1—N ChannelAccount 1—N Conversation 1—N Message`

```
Device: pc-office-01
  └── ChannelAccount: 微信客服A (wecom_kf, open_kfid=wkABC)
        ├── Conversation: 张三 (wm...)
        └── Conversation: 李四 (wm...)
```

这次拆解带来的好处：

1. 换客服账号不用换设备，前端 `device_code` 那个字段终于回到它该有的语义
2. 同一台电脑可以挂多个企微客服账号（现在做不到，`ensureConnection` 是单绑）
3. 以后加「企微会话存档」通道，只是同一设备下多一种 `ChannelAccount`，不动客户端

## 4. 技术选型

### 4.1 Web 框架：**FastAPI**

| 维度 | FastAPI | Litestar | Django Ninja |
|---|---|---|---|
| 生态成熟度 | ★★★★★ | ★★★ | ★★★★（限 Django 内） |
| OpenAPI 自动生成 | ✅ 一等公民 | ✅ | ✅ |
| WebSocket / SSE | ✅ 原生 | ✅ 原生 | 一般 |
| 异步 LLM 流式 | ✅ 最成熟 | ✅ | 弱（Django async 不均） |
| 招人/找资料 | 最多 | 少 | 中 |
| 性能 | 中上 | 更高（msgspec） | 中 |

**选 FastAPI**。理由不是"它最快"——2026 年 Litestar 在冷启动和序列化上确实更快——而是这个项目的瓶颈根本不在框架：卡点在企微 API 限流、Dify 生成耗时、人工响应。这时候拼生态和可维护性更划算。团队里任何人两天能上手。

> 如果后续真有单机 5k+ QPS 的需求（不会），先换 Granian 服务器，再考虑 Litestar，不用重写业务层。

### 4.2 完整技术栈

| 层 | 选择 | 说明 |
|---|---|---|
| 运行时 | **Python 3.13+** | 3.14 可用，注意三方库兼容 |
| 包管理 | **uv** | 比 pip 快一个量级，锁文件可复现 |
| 框架 | **FastAPI** | |
| 校验 | **Pydantic v2** | 天然对接 OpenAPI |
| ORM | **SQLAlchemy 2.0（async）** | 不用 SQLModel，2.0 的 `Mapped[]` 已经够好，SQLModel 抽象层反而挡路 |
| 迁移 | **Alembic** | 必须，现有 SQLite 迁移是手写 SQL，长期会失控 |
| 数据库 | **PostgreSQL 16+**（生产）/ SQLite（本地开发） | 多端并发 + JSONB 查询，SQLite 撑不住 |
| 缓存/队列 | **Redis 7 + arq** | 轻量异步任务队列，比 Celery 简单；已有 Redis 时直接复用 |
| 实时 | **WebSocket（FastAPI 原生）** | 多端推送；SSE 作为降级 |
| 定时 | **APScheduler** | 企微兜底轮询、重试扫描 |
| 观测 | **structlog + OpenTelemetry** | 结构化日志带 `trace_id`/`conversation_id` |
| 测试 | **pytest + pytest-asyncio + httpx** | |
| 代码质量 | **ruff + pyright** | |
| 部署 | **Docker Compose**（单机）/ K8s（以后） | |

### 4.3 为什么不选 Django

有 admin、有 ORM、有权限，看着省事。但这个系统的核心是**长连接 + 异步 IO + 状态机**，Django 的 async 仍是二等公民，企微回调要求 5 秒内响应、AI 生成要等 10~30 秒，这两件事在 Django 里都要绕。后台管理页的问题，用 FastAPI + SQLAdmin（或直接用现有 React 前端）解决，不值得为此绑死整个栈。

## 6. 数据模型

```sql
-- 设备（我的电脑）
CREATE TABLE devices (
  id            BIGSERIAL PRIMARY KEY,
  device_code   TEXT UNIQUE NOT NULL,          -- pc-office-01
  name          TEXT NOT NULL,
  device_token  TEXT NOT NULL,                 -- 设备鉴权，非用户 JWT
  status        TEXT NOT NULL DEFAULT 'offline', -- online/offline/disabled
  agent_version TEXT,
  last_heartbeat_at TIMESTAMPTZ,
  capabilities  JSONB DEFAULT '{}',            -- {"wecom_callback":true,"local_ocr":false}
  tenant_id     BIGINT,                        -- 预留，暂不使用
  created_at    TIMESTAMPTZ DEFAULT now()
);

-- 通道账号（一个企微客服账号）
CREATE TABLE channel_accounts (
  id             BIGSERIAL PRIMARY KEY,
  device_id      BIGINT REFERENCES devices(id),
  channel_type   TEXT NOT NULL,                -- wecom_kf
  name           TEXT NOT NULL,                -- 微信客服A
  external_id    TEXT NOT NULL,                -- open_kfid
  corp_id        TEXT NOT NULL,
  config         JSONB NOT NULL,               -- 不含 secret，secret 走环境/密钥管理
  status         TEXT NOT NULL DEFAULT 'enabled',
  cursor         TEXT DEFAULT '',              -- 企微拉取游标
  last_sync_at   TIMESTAMPTZ,
  UNIQUE(channel_type, external_id)
);

-- 客户
CREATE TABLE customers (
  id            BIGSERIAL PRIMARY KEY,
  channel_account_id BIGINT REFERENCES channel_accounts(id),
  external_userid TEXT NOT NULL,               -- wm...
  nickname      TEXT,
  avatar        TEXT,
  extra         JSONB DEFAULT '{}',
  created_at    TIMESTAMPTZ DEFAULT now(),
  UNIQUE(channel_account_id, external_userid)
);

-- 会话（一个客户在一个通道账号上的对话）
CREATE TABLE conversations (
  id            BIGSERIAL PRIMARY KEY,
  channel_account_id BIGINT REFERENCES channel_accounts(id),
  customer_id   BIGINT REFERENCES customers(id),
  assigned_user_id BIGINT REFERENCES users(id),   -- 分配给的顾问
  state         TEXT NOT NULL DEFAULT 'active',   -- active/closed
  takeover      BOOLEAN NOT NULL DEFAULT false,    -- 人工接管
  last_message_at TIMESTAMPTZ,
  last_message_preview TEXT,
  UNIQUE(channel_account_id, customer_id)
);

-- 消息
CREATE TABLE messages (
  id            BIGSERIAL PRIMARY KEY,
  conversation_id BIGINT REFERENCES conversations(id),
  direction     TEXT NOT NULL,                 -- inbound/outbound
  source        TEXT NOT NULL,                 -- customer/ai/agent/system
  content_type  TEXT DEFAULT 'text',
  content       TEXT NOT NULL,
  external_msgid TEXT,                         -- 企微 msgid，去重用
  delivery_id   BIGINT,
  created_at    TIMESTAMPTZ DEFAULT now()
);

-- 出站投递（事务性发件箱）
CREATE TABLE deliveries (
  id            BIGSERIAL PRIMARY KEY,
  conversation_id BIGINT NOT NULL,
  idempotency_key TEXT NOT NULL,
  content       TEXT NOT NULL,
  status        TEXT NOT NULL,                 -- queued/sending/accepted/unknown/failed/blocked
  blocked_reason TEXT,
  external_msgid TEXT,
  attempts      INT DEFAULT 0,
  next_attempt_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(conversation_id, idempotency_key)
);

-- 每端已读位置（多端必须，否则未读数永远对不上）
CREATE TABLE read_cursors (
  user_id       BIGINT NOT NULL,
  conversation_id BIGINT NOT NULL,
  last_read_message_id BIGINT NOT NULL,
  updated_at    TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (user_id, conversation_id)
);
```

三个关键改进（对应现存的坑）：

1. **`deliveries` 独立成表**，不再让 `agent_messages.status` 承担投递语义 ——"消息存在"和"消息送达"是两件事
2. **`read_cursors` 按用户存**，现在 `conversation.unread` 是单一计数器，多端登录必然错乱
3. **客户昵称头像有地方放**（`customers.nickname/avatar`），解决"所有企微客户都叫微信客服客户"的问题

## 7. 接口契约

### 7.1 REST（统一前缀 `/api/v1`）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/auth/login` | 账号密码 → access + refresh | 公开 |
| POST | `/auth/refresh` | 刷新令牌 | 公开 |
| GET | `/auth/me` | 当前用户 + 权限范围 | 登录 |
| GET | `/devices` | 设备列表（含在线状态） | 登录 |
| POST | `/devices` | 注册设备，返回 `device_token` | admin |
| POST | `/devices/{code}/heartbeat` | 设备心跳（设备 token，非用户 JWT） | 设备 |
| GET | `/channels` | 通道账号列表 | 登录 |
| POST | `/channels/wecom-kf` | 新增企微客服账号 | admin |
| GET | `/channels/{id}/status` | 游标/最近同步/是否可自动回复 | admin |
| POST | `/channels/{id}/sync` | 手动触发拉取 | admin |
| GET | `/conversations` | 会话列表（分页、按通道/接管/未读筛） | 登录 |
| GET | `/conversations/{id}` | 会话详情 | 登录 |
| GET | `/conversations/{id}/messages` | 消息（`after_id` 增量） | 登录 |
| POST | `/conversations/{id}/takeover` | 接管 / 取消接管 | 登录 |
| POST | `/conversations/{id}/messages` | 人工发消息（带 `Idempotency-Key` 头） | 登录 |
| POST | `/conversations/{id}/read` | 上报已读位置 | 登录 |
| GET | `/customers/{id}` | 客户资料 | 登录 |
| POST | `/webhooks/wecom` | 企微回调（公开，验签） | 公开 |

**关键约定**：

- 所有写接口必须支持 `Idempotency-Key` 头，服务端 24h 内同 key 同 body 返回同结果
- 分页统一 `cursor` 而非 offset（消息会持续增长）
- 错误体统一 `{"code": "...", "message": "...", "detail": {...}}`，`code` 与前端文案解耦

### 7.2 WebSocket（`/ws?token=<jwt>`）

客户端连上后先订阅，再收事件：

```jsonc
// 客户端 → 服务端
{"type":"subscribe","topics":["conversation:123","inbox"]}

// 服务端 → 客户端（示例）
{"type":"message.created","conversation_id":123,"message":{...}}
{"type":"conversation.updated","conversation_id":123,"takeover":true,"unread":3}
{"type":"delivery.updated","delivery_id":88,"status":"accepted"}
{"type":"device.status","device_code":"pc-office-01","status":"online"}
{"type":"channel.blocked","channel_id":5,"reason":"48-hour reply window expired"}
```

**多端一致性规则**：

1. 同一条事件推给该会话的所有已订阅端（含同一用户的多台设备）
2. 已读只影响自己的 `read_cursors`，不影响别人的未读数
3. 断线重连用 `?since=<last_event_id>` 补发，服务端保留 5 分钟事件缓冲（Redis Stream）
4. 客户端收到事件后**必须**以服务端 ID 为准，不做本地自增

## 8. 设备代理（我的电脑）

设备不是"手机"，是**一台运行 `device-agent` 的主机**。它只做三件事：

### 8.1 注册

```bash
curl -X POST https://api.example.com/api/v1/devices \
  -H "Authorization: Bearer <admin JWT>" \
  -d '{"device_code":"pc-office-01","name":"办公室主机"}'
# → {"device_code":"pc-office-01","device_token":"dt_xxxxx"}
```

`device_token` 存本机 `~/.recruit/device.env`，只用于设备自身接口，**不是用户身份**。

### 8.2 心跳（30 秒一次）

```json
POST /api/v1/devices/pc-office-01/heartbeat
{
  "agent_version": "0.1.0",
  "capabilities": {"wecom_callback": false, "local_ocr": true},
  "metrics": {"cpu": 0.12, "mem_mb": 380}
}
```

服务端 90 秒没收到心跳 → 标 `offline` → 推 `device.status` 事件给所有客户端。

### 8.3 执行任务（二期再上）

设备通过 WS 领任务（拉模型、跑本地 OCR、导文件）。一期不需要，先留好协议：

```json
{"type":"task.dispatch","task_id":"t_1","kind":"local_ocr","payload":{...}}
{"type":"task.result","task_id":"t_1","ok":true,"data":{...}}
```

> **为什么设备不能自己收企微回调**：回调要公网 URL，设备在家用宽带后面没有固定 IP。除非上内网穿透（frp/cloudflare tunnel），否则必须由服务端统一收。文档里给出的默认形态是服务端收、设备执行。

## 9. 消息可靠性与状态机

### 入站

```
企微回调 → 验签解密 → 入 events 表（幂等，按 msgid）
   → 立即返回 200（<5s，否则企微重试）
   → arq 任务：sync 拉取 → 落 messages → 更新 conversation
   → 若 takeover=false 且通道允许 → 触发 AI 生成
```

### 出站（事务性发件箱）

```
业务写 deliveries(status=queued) + messages  ← 同一个事务
   → worker 取 queued（SELECT ... FOR UPDATE SKIP LOCKED）
   → status=sending
   → 调企微 kf/send_msg
        ├─ errcode=0 且 msgid 匹配 → accepted
        ├─ 明确业务错误 → failed（附原因）
        ├─ 超时/网络不明 → unknown（不重投，等人核对）
        └─ 前置校验不过 → blocked（附原因）
```

**`unknown` 是刻意保留的状态**：网络超时时无法判断对方收没收到，重投可能给客户发两遍。宁可停下让人核对。

### 前置校验（顺序固定，短路返回）

1. 通道账号状态 `enabled`
2. 设备在线（可选，视业务）
3. 客户身份已映射
4. 文本非空且 UTF-8 ≤ 2048 字节
5. 48 小时窗口内（从客户最后一条消息算）
6. 同窗口已发 < 5 条
7. 无人工接管（AI 发送时检查；人工发送跳过）

## 10. 多端策略

| 问题 | 方案 |
|---|---|
| 鉴权 | access token 15 分钟 + refresh token 30 天，refresh 存 `refresh_tokens` 表可吊销 |
| 端识别 | 请求头 `X-Client-Type: web\|desktop\|mobile`，只用于统计和兼容，不影响权限 |
| 离线 | 客户端本地缓存最近 50 条 + 离线队列；重连后按 `last_event_id` 补 |
| 未读 | 服务端算 `count(messages) - read_cursors.last_read_message_id`，不落冗余字段 |
| 冲突 | 会话接管用乐观锁（`version` 字段），两个顾问同时点接管 → 后者 409 |
| 一致性 | 所有时间戳服务端生成（UTC + ISO8601），客户端只负责展示时区 |
| 推送 | 一期只做 WS；二期加企微应用消息 / APNs，通过 `notifications` 抽象 |

## 11. 通道适配层

```python
class ChannelAdapter(Protocol):
    channel_type: str

    async def verify_webhook(self, req: WebhookRequest) -> WebhookResult: ...
    async def fetch_inbound(self, account: ChannelAccount, cursor: str) -> InboundPage: ...
    async def send(self, account: ChannelAccount, target: Customer, msg: OutboundMessage) -> SendResult: ...
    async def health(self, account: ChannelAccount) -> ChannelHealth: ...
```

`wecom_kf` 实现要点（直接对标现有 6 个 TS 文件）：

| 职责 | 现有 TS | 新 Python | 注意 |
|---|---|---|---|
| 回调验签解密 | `wecom-crypto.ts` | `channels/wecom_kf/crypto.py` | AES-256-CBC + SHA1 签名，别用 XML 外部实体解析 |
| token 缓存 | `wecom-client.ts` | `client.py` | 提前 60s 过期，40014/42001 自动重取一次 |
| 增量拉取 | `wecom.routes.ts:47` | `sync.py` | `cursor` + `sync_token` 成对保存，事务内推进 |
| 发送 | `wecom-channel.ts` | `sender.py` | 6 道校验 + 幂等 msgid |
| 客户资料 | ❌ 缺 | `client.customer_batchget()` | **必须补**，否则前端全是"微信客服客户" |
| 线程安全 | `syncRunning` 进程内锁 | Redis 分布式锁 | 多 worker 下进程内锁失效 |

最后一行是重点：现在的 `syncRunning` 只在单进程有效。上 uvicorn 多 worker 后，两个进程会同时拉同一批消息 —— 必须换 Redis 锁（`SET NX PX 30000`）或把 worker 拆成独立进程（推荐后者：`arq worker` 单实例跑同步，API 只读）。

## 13. 迁移路线

不要一次性重写。按这个顺序，每阶段都能独立上线：

| 阶段 | 内容 | 产出 | 风险 |
|---|---|---|---|
| **P0 骨架** | FastAPI 项目 + Alembic + JWT + devices/channels CRUD | 空壳能跑，`/docs` 可看 | 无 |
| **P1 企微打通** | 移植 wecom_kf 四个模块 + 回调 + 同步 + 发送 | 客户发消息能收到、能回 | 中（联调靠真实企微） |
| **P2 消息核心** | deliveries 状态机 + outbox worker + WS 推送 | 多端实时 | 中 |
| **P3 前端切换** | 现有 React 接待台改调新 API（字段名兼容层） | 新老并行 | 低（可回退） |
| **P4 下线旧服务** | 关 TS 服务，数据一次性迁移（SQLite → PG 脚本） | 单一栈 | 低 |

**P1 可以复用现有 TS 服务做「影子通道」**：新服务只读企微、只推 WS，不发消息；等 P1 验收通过再打开发送开关。这样联调期出问题不影响现有业务。

### 迁移时必须一次性做的事

1. `customer_id` 用企微 `external_userid` 重新映射，不要沿用旧的自增 ID（旧 ID 混了个人微信客户）
2. 旧的 `wecom_inbox/outbox` 数据**不要迁**，只迁 `customers/conversations/messages` 的业务内容
3. Secret/Token 全部走环境变量或密钥管理，禁止进数据库明文（现在 `corp_id/open_kfid` 存在 `data_json` 里，可读性差且易泄露）

## 14. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 企微回调必须在 5s 内返回 | 超时会被重试，导致重复 | 回调只落库+入队，绝不在回调里调 Dify |
| 多 worker 抢同一批消息 | 重复回复客户 | worker 单实例 + Redis 锁 + msgid 唯一约束 |
| Dify 生成 10~30s | 客户等太久 | 先发"正在查询"，或异步生成后推送（看产品选择） |
| 48h/5 条限制 | 想追客户追不到 | 产品上明确告知运营，别承诺"随时能发" |
| Postgres 运维成本 | 比 SQLite 重 | 单机 Docker 化，备份脚本每天跑 |
| 重写期间双份代码 | 修 bug 要改两处 | P1 之后冻结 TS 新功能，只修 P0 缺陷 |
