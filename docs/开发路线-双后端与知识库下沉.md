# 开发路线：Windows 单机用户端 + 服务器端管控

> 本版依据 2026-11-04 的决策重写：
> **用户端 = Windows 单机；服务器端通过 IP 管控；LLM Key 界面填写（DeepSeek）；服务器端不存知识库。**
>
> 上一版（Linux + Docker + PostgreSQL 下沉）作废，差异见文末第八节。

---

## 一、目标架构

```
┌──────────────────────────────────────┐
│ 服务器端（我们的 Linux 云主机）          │
│  · 租户/授权/到期                     │
│  · 在线状态（IP、版本、最后心跳）        │
│  · 远程指令队列（改配置/升级/重启）       │
│  · 用量统计（数字，无内容）              │
│  ✗ 不存任何知识库、不存任何会话           │
└───────────────▲──────────────────────┘
                │ 出站 HTTPS 轮询（30s）
                │ 用户端主动上报 + 领取指令
┌───────────────┴──────────────────────┐
│ 用户端（客户那台 Windows）              │
│  ┌──────────┐ ┌──────────┐ ┌────────┐│
│  │ Node 4222│ │Python 8090│ │autopilot││
│  │ 业务+前端 │ │ 知识库+LLM │ │企微采集 ││
│  └────┬─────┘ └────┬─────┘ └───┬────┘│
│       └──────┬─────┘            │      │
│         SQLite（单文件）     本地明文库  │
└──────────────────────────────────────┘
```

三个进程都跑在同一台 Windows 上，由一个启动器统一拉起。

## 二、为什么用户端能是 Windows 单机

关键在于：**Node 侧本来就是 SQLite**，不是 PostgreSQL。

交接文档里的 `node:sqlite`、`VACUUM INTO`、`scripts/backup-sqlite.mjs` 都说明这点。所以 Node 迁到 Windows 几乎零成本。

真正要改的只有 **Python 的知识库层**（`kb_*` 六个模块目前绑 PostgreSQL）。这是本路线唯一的重头戏，见第四节。

Windows 上的组件：

| 进程 | 运行时 | 内存 | 作用 |
|---|---|---|---|
| Node `:4222` | `node.exe`（免安装） | 120MB | 配置 CRUD、前端 38 页、企微回调 |
| Python `:8090` | `python-embed`（免安装） | 150MB | 知识库检索、回复编排、LLM 调用 |
| `autopilot` | 同一 Python | 80MB | 读企微明文库、键鼠发送 |
| 合计 | | **≈350MB** | 客户 8G 内存的机器毫无压力 |

## 三、知识库改用 SQLite（核心改造）

### 现状

`backend/app/` 下六个模块全部基于 PostgreSQL：

| 文件 | 依赖 PG 的地方 |
|---|---|
| `models_kb.py` | `JSONB`、`ARRAY`、`UUID` 类型 |
| `services/kb_search.py` | `ILIKE`、`&&` 数组重叠、`jsonb_path_query` |
| `services/kb_import.py` | `ON CONFLICT DO UPDATE` 批量 upsert |
| `services/kb_extract.py` | 纯 Python，**无 PG 依赖，直接复用** |
| `services/kb_answer.py` | 纯编排逻辑，**基本可复用** |
| `services/kb_reply.py` | 数字校验，纯 Python，**直接复用** |

好消息：**最难的部分（分词、抽取、召回评测）都是纯 Python，不用动。**

### 改造清单

| # | 改造点 | 做法 | 风险 |
|---|---|---|---|
| 1 | 字段类型 | `JSONB` → `TEXT` 存 JSON；`ARRAY` → 逗号分隔或 JSON | 低 |
| 2 | 检索 SQL | `ILIKE` → `LIKE`（SQLite 默认不区分大小写对中文无影响）；数组重叠改 `LIKE '%x%'` 多条件 OR | 中 |
| 3 | 组合筛选 | `tenant_id` 字段去掉（单机单租户） | 低 |
| 4 | upsert | `ON CONFLICT ... DO UPDATE` → SQLite 3.24+ 支持同名语法，可直接用 | 低 |
| 5 | 全文检索 | 二元组 `LIKE` 保留；**可选**升级到 `FTS5` 提速 | 低 |
| 6 | 迁移脚本 | 不复用 Alembic，写一次性建表 SQL | 低 |
| 7 | **召回率回归** | 改完必须跑 `kb_eval`，**低于 70% 不许上线** | **高** |

第 7 项是硬门槛。交接文档记录现在召回率 78%，SQLite 版低于 70% 就说明检索逻辑没对齐（大概率是排序或截断问题——「SQL 层不排序会按主键截断，话术占满 limit」这个坑会以另一种形式重演）。

### 数据迁移

现有 534 条在服务器 PG 里。一次性导出成 JSON，随安装包内置：

```bash
python -m app.services.kb_export --format json > kb_seed.json
```

客户首次启动时自动导入（`kb_seed.json` 作为初始知识库，客户可增删改），这样交付即用，不用客户自己导。

## 四、LLM 配置（DeepSeek，界面填写）

### 位置

在用户端管理界面加一个「模型设置」页：

```
服务商：DeepSeek（默认，可切 OpenAI 兼容）
API Key：[____________]  🔘 显示
模型：   [deepseek-chat ▾]
Base URL：（留空用官方；填了就覆盖）
[测试连接]  [保存]
```

### 存储

- 存 SQLite 的 `settings` 表，**Key 用 Windows DPAPI 加密**（`CryptProtectData`），不落明文
- 配置文件里只存加密后的 blob
- 界面回显时只显示后 4 位：`sk-****abcd`

### 生效

`services/llm_provider.py` 已经是可替换的 Provider 层，只需把配置来源从 `.env` 改成读库：

```python
# 现在：settings.llm_api_key（来自环境变量）
# 改成：llm_config = get_llm_config(db)   # 优先库，回落到 .env
```

### 降级

交接文档提到「不配大模型也能正常回复」（`c3fd3a1`，模板模式）。这个能力保留：**没填 Key 时走模板回复，填了之后自动切 LLM**。客户可以先不填 Key 把系统跑起来，后面再补。

## 五、服务器端怎么管控（IP + 指令）

你说「通过 IP 链接到服务器来控制」。这里有个现实约束要先说清：

**客户 Windows 通常在家庭宽带或公司内网后面，没有公网 IP，服务器无法主动连进去。**

所以默认走**反向通道**（用户端出站），同时支持正向直连：

### 5.1 主通道：出站轮询（默认，不需要公网 IP）

```
用户端每 30 秒：
  POST /api/v1/agent/heartbeat
  { tenant_id, install_id, version, lan_ip, public_ip, port,
    kb_count, msg_today, license_state }
  ← { commands: [ {id, type, payload} ], min_version, license }

  POST /api/v1/agent/command/{id}/ack
  { ok: true, result: {...} }
```

支持的指令类型：

| type | 用途 |
|---|---|
| `config.set` | 改配置（模型、冷却时间、开关） |
| `kb.reload` | 重载知识库文件 |
| `app.restart` | 重启 Node/Python 进程 |
| `app.upgrade` | 下载新版 → 校验 → 替换 → 重启 |
| `log.upload` | 打包脱敏日志上传 |

### 5.2 辅通道：正向直连（客户有公网 IP 时）

用户端在 heartbeat 里上报 `public_ip` 和 `port`。服务器控制台显示在线列表：

```
租户        公网IP           端口   版本    知识库   今日消息   状态
华南-XX   113.108.x.x       8090   1.2.0   534      128      ● 在线
```

若客户做过端口映射，控制台可以直接「打开管理界面」——用服务器做一层反向代理，避免浏览器直接暴露客户 IP。

**这条通道是可选增强，不作为交付前提。** 客户不开端口也能用全部功能，只是远程操作延迟从秒级变成 30 秒。

### 5.3 安全

- 用户端只接受**带签名的指令**（服务器私钥签，用户端内置公钥验），防止伪造
- 出站请求带 `install_id` + `license_token`，服务器校验
- 指令一律**幂等**（带 id，重复执行无副作用）

## 六、采集端（我定的方案）

**并入用户端，作为独立进程，不单独部署。**

理由：

1. 采集必须和企微客户端同机同会话——只能是那台 Windows
2. 用户端也在同一台机器上，走 `127.0.0.1` 即可，不需要设备 token、不需要跨机认证
3. 少一个部署单元，客户只需双击一个启动器

具体形态：

```
启动器（bat / exe）
  ├─ node.exe        （后台）
  ├─ python.exe      （FastAPI :8090）
  └─ python.exe      （autopilot.py --watch，独立进程，因为它要抢前台/模拟键鼠）
```

autopilot 与用户端通过本机 HTTP 交互：

```
autopilot 发现新消息 → POST 127.0.0.1:8090/api/v1/agent/reply
                     ← { text: "..." }
autopilot 键鼠发送 → POST 127.0.0.1:8090/api/v1/agent/sent
```

**为什么 autopilot 不并进 FastAPI 进程**：它要抢前台、模拟键鼠，会被杀软/风控盯上；独立进程崩了不影响 Web 服务，重启也只重启它一个。

## 七、部署包结构

客户拿到的应该是一个 zip，解压双击 `启动.bat`：

```
city-recruit/
├─ 启动.bat              ← 一键拉起三个进程 + 打开浏览器
├─ 停止.bat
├─ node/
│   ├─ node.exe
│   └─ app/               Node 构建产物 + 前端静态
├─ python/
│   ├─ python.exe         embed 版
│   ├─ Lib/site-packages/
│   └─ app/               FastAPI + kb_*
├─ agent/
│   └─ autopilot.exe      PyInstaller 打包
├─ data/
│   ├─ app.sqlite         Node 业务库
│   ├─ kb.sqlite          知识库
│   ├─ kb_seed.json       初始知识库（534 条）
│   └─ attachments/       图片素材
├─ config.json            授权码、端口、模型配置（Key 加密）
└─ 使用说明.pdf
```

关键：**全部免安装，不写注册表，不需要管理员权限**（除首次可能要放行防火墙端口）。

## 九、与上一版的差异

| 项 | 上一版（Linux + Docker） | 本版（Windows 单机） |
|---|---|---|
| 知识库 | PostgreSQL，`kb_*` 零改动 | **SQLite，`kb_*` 需改造** |
| 部署 | docker-compose | **免安装 zip + bat** |
| 进程数 | 3 个容器 | 3 个进程，同机 |
| 管控通道 | 未定 | **出站轮询为主，正向直连为辅** |
| LLM Key | 环境变量 | **界面填写，DPAPI 加密** |
| 采集端 | 独立部署 | **并入用户端，独立进程** |

**代价**：知识库改造是新增的工作量（约 2 周），且召回率有回退风险。
**收益**：客户零运维门槛，一台 Windows 就能交付，服务器端成本几乎为零。
