# 遗留问题：地铁安检出现在「绑定工厂」里

记录日期：2026-11-15。本文记录一个已定位但**只做了临时处理**的数据模型问题，供后续收敛。

## 一、现象

后台「设备 → 绑定工厂」抽屉里，除了松下万宝、广州酒家这类真实工厂，还并列出现：

```
佛山  1 个    佛山地铁安检
广州  8 个    广州地铁安检
深圳  1 个    深圳地铁安检
```

勾选后设备会被锁定到 `factory_id=13` 这类地铁记录上，界面看不出任何区别。

## 二、根因

三件事叠加：

### 2.1 `factories` 表没有品类列

```
id, factory_name, city_id, status, data_json, created_at, updated_at, tenant_id
```

整张表**没有任何字段**能区分「工厂」和「地铁面试点」，数据库层面它们完全同质。

### 2.2 地铁安检确实被写进了 `factories`

[029_kb_real_subway.sql:65](../src/db/backfill/029_kb_real_subway.sql#L65) 直接插入 6 条：

| factory_id | 名称 | 城市 |
|---|---|---|
| 9 | 广州地铁安检 | 广州 |
| 10 | 佛山万通地铁安检 | 佛山 |
| 11 | 佛山百花地铁安检 | 佛山 |
| 12 | 南昌地铁安检 | 南昌 |
| 13 | 深圳地铁安检 | 深圳 |
| 14 | 南宁地铁安检 | 南宁 |

**为什么当初这么做**：`service_positions.factory_id` 外键要求岗位必须挂在某个 `factories` 行上，「安检员」岗位无处可挂，只能先造 6 条 factory 行。

### 2.3 绑定接口全量读取

[device-factories.ts:77](../src/shared/device-factories.ts#L77) 的 `FROM factories f` 没有品类过滤条件——因为表里没有可过滤的东西。

## 三、`employer` 表里其实是分好的

v3 结构里品类是清楚的：

```
vertical: 1=factory(工厂)  2=subway(地铁安检)  3=logistics  4=rpo  5=daily
employer: display_name + vertical_id
```

问题在于**两套表并存且不同步**：

| 表 | 品类信息 | 设备绑定 | 岗位挂载 | 话术取数 |
| --- | --- | --- | --- | --- |
| `factories` | **无** | 用这张 | 用这张 | — |
| `employer` | 有（vertical_id） | 不用 | 不用 | 用这张 |

更麻烦的是 `employer` 里**同一个名字存了两行**：

```
id= 9 | subway  | 广州地铁安检
id=29 | factory | 广州地铁安检   ← 重复
```

6 家地铁全部存在这种重复（9/29、10/30、11/31、12/32、13/33、14/34）。`employer` 表里另有 8 个城市（重庆、郑州、武汉、青岛、昆明、杭州、成都、沈阳）有 subway 招工方，但 `factories` 里**根本没有对应行**——两套表已经漂移。

## 四、已做的临时处理（方案 A）

**改动**：[public/theme/device-factories.js](../public/theme/device-factories.js)

绑定抽屉渲染前过滤掉 subway 品类的招工方，判定依据**不是猜关键字**：

1. `GET /api/v1/verticals` → 找 `code === 'subway'` 的 id（当前是 2）
2. `GET /api/v1/employers?vertical_id=2` → 取 `display_name` 名单
3. 用 `factory_name` 与名单逐字比对

```js
const pickable = (items, hidden) =>
  items.filter((factory) => selected.has(factory.id) || !hidden.has(factory.name));
```

四个刻意的设计：

| 决定 | 原因 |
| --- | --- |
| 按 `employer` 名单比对，不用「地铁/安检」关键字匹配 | 名字匹配迟早误伤真实工厂（将来若有「安检设备厂」） |
| 已勾选的不过滤 | 老设备若历史上绑过安检，还得能在抽屉里取消，否则永久绑死 |
| 取不到名单时降级为「不过滤」 | 宁可多显示几项，也不能让抽屉打不开 |
| 过滤在渲染层，`factories()` 缓存保留全量 | 行内文案要用缓存把 `factory_id` 翻成厂名，过滤缓存会让已绑定设备显示 `#13` |

**验证**：浏览器实测「绑定工厂」抽屉，8 项，地铁 0 项；真实工厂（本地示例工厂、松下万宝、广州酒家、广州华荻、广州华智、广汽商贸）全部保留。

## 五、为什么没动城市页的「厂区」抽屉

城市管理页的「厂区」抽屉走另一条链路（`GET /api/v1/cities/:id/factories`），那里**仍然会列出「广州地铁安检」**。

这是**故意的**：`service_positions` 里 6 个「安检员」岗位分别挂在 `factory_id` 9–14 上：

```
position 14 安检员 → factory 9  广州地铁安检
position 15 安检员 → factory 10 佛山万通地铁安检
...共 6 条
```

如果城市页也过滤掉，这 6 个岗位就失去了父节点，在「岗位管理」里会变成孤儿。**厂区抽屉必须保留它们**，否则岗位无法维护。

但代价是：城市页把这个东西叫「厂区」，而它其实是「地铁面试点」，命名仍然误导。

## 六、遗留问题清单

### P1：需要决策

| 事项 | 现状 | 待定 |
| --- | --- | --- |
| 「地铁安检」到底允不允许绑定设备 | 已从绑定抽屉隐藏 | 若业务允许（一台设备专做安检岗是合理场景），应改为改标题「绑定工厂/项目」，而不是隐藏 |
| `factories` 与 `employer` 双份真相 | 两套表并存，且已漂移 | 收敛到 `employer` 为唯一源，`factories` 降级为视图或直接废弃 |
| `employer` 里 subway 名字重复存了两行 | 6 组重复（id 9/29 … 14/34） | 清理重复行，确认哪一行被话术/知识库引用 |

### P2：工程债

| 事项 | 影响 |
| --- | --- |
| `factories` 缺品类列 | 任何按品类过滤的需求都只能靠名字比对或外部查表 |
| `employer` 比 `factories` 多 8 个城市的 subway 记录 | 这些城市的地铁岗位在 `factories` 里无父节点，可能挂不上 |
| 绑定抽屉标题叫「绑定工厂」 | 与实际的「招工方」语义不符 |
| 城市页厂区抽屉列出地铁面试点 | 命名误导，但不能直接过滤（见第五节） |

## 七、后续收敛路径（未实施）

按代价从小到大：

### B 方案：`factories` 加品类列

```sql
ALTER TABLE factories ADD COLUMN vertical_id INTEGER REFERENCES vertical(id);
UPDATE factories SET vertical_id = 2 WHERE factory_name IN (...6 家地铁...);
UPDATE factories SET vertical_id = 1 WHERE vertical_id IS NULL;
```

绑定时 `WHERE vertical_id = 1` 过滤。查询层一处改动，但仍与 `employer.vertical_id` 形成双份真相。

### C 方案：绑定改读 `employer`

设备直接绑 v3 招工方，弃用 `factories`。这是终态，但会动到设备过滤、岗位过滤、话术取数三条链路，需要完整回归。
