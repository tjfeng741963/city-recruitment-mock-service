## 二、每处改了什么

### ① 消息分段（两条路径都覆盖）

**问题**：运营在岗位话术里写好的【用人要求】【上班时间】【工资待遇】，客户收到一条糊在一起的长消息。

**根因**：`flow_engine.send_info_parts()` 命中话术时写死 `return [scripted]`——整段作为一条发出。客户端 `agent/autopilot.py` 本来就是 `for idx, raw_part in enumerate(parts)` 逐条发、间隔 2 秒，只是服务器从没给过多段。

**改法**：

- `backend/app/services/flow_engine.py` 新增 `split_script_sections()`：按空行、行首【标题】切段，段内一个字不改（工价是事故级数据）。
- `backend/app/api_flow.py` 新增 `split_by_section_heads()` 并做收口：模型组织的回复也按【标题】拆开，**只认行首标题、不按空行切**（模型正文也用空行分段，按空行切会把正常话拆碎）；标题不足 2 个时原样返回。

**注意**：`【图片:x】` 行不算段标题，跟着上一段走——否则客户端会收到一个只有标记、没有文字的段。

### ② 图片 / 视频

**根因**：岗位话术分支从没给 `media_material` 赋值，一直是 `kb_answer or ""` 的空串，于是 `allowed_media` 是空列表，`filter_parts` 把话术里所有 `【图片:x】【视频:x】` 当「未授权标记」全删了。**文字正常发出，图一张没有。**

**改法**：`api_flow.py` 的岗位话术分支补 `media_material = 话术原文`，白名单从本轮话术本身构造。

### ② 地点 —— 没做，这是能力缺口不是配置问题

`agent/wecom_io_core/send.py` 只有两个发送函数：

```
send()        # 文字：Ctrl+F 搜会话 → 输入 → 回车
paste_media() # 图片/视频：剪贴板放文件 → Ctrl+V
```

全文搜 `location` / `位置` / 坐标，`send.py` 与 `autopilot.py` 零匹配。企微发位置要在 UI 里「+ → 位置 → 搜点 → 发送」，五步都依赖弹窗层级，键鼠自动化任一步状态不对就可能发到错误会话——比不发更糟。

**当前替代**：面试地点作为文字出现在岗位卡和面试通知里（`interview_place` / `interview_notice`）。

### ③ 面试通知

**根因**：后台「面试通知模板」存在 `service_positions.data_json.base_sections.interview_notice`，但**全链路没有任何一处读它**——job-lookup 不下发，Python 侧也没有发送点。运营填了等于死数据。

**改法**：

- `profile.routes.ts` job-lookup 补下发 `interview_notice` / `interview_guide`。
- `flow_engine._book()` 约成后调 `_interview_notice_parts()` 按段落补发，占位符 `{{place}}` / `{{window}}` 由代码替换，整会话只发一次（`slots["interview_notice_sent"]`，改期不重复轰炸）。

### ④ 记录到网页

**发现**：客户端 `_queue_bridge_messages()` 里有 `if not cid or not msg_id or not text: continue`——**图片、视频、文件、位置这些没有文本的消息整条被丢掉**。所以「发图片视频，网页一条记录都没有」是真的，不只是显示问题。

**改法**（`agent/autopilot.py`）：只有「确实是媒体类型」（`content_type = type<数字>`）且正文为空的，才用占位标签 `[图片]` / `[视频]` / `[位置]` / `[文件]` / `[媒体]` 上报；`content_type` 为空或 `text` 的空正文仍按脏数据跳过。

**⚠️ 必须手动同步**：`Dockerfile` 不含 `agent/`，客户端跑的是目标机上的 `C:\agent` 副本。要在那台机器上执行：

```
python sync_from_github.py --target C:/agent --ref main --dry-run
python sync_from_github.py --target C:/agent --ref main --apply --restart
```

### ⑤ 邀约群默认不启用

**问题**：`readInviteGroupConfig()` 是 `enabled: raw.enabled === true`。运营配好群名/Webhook 但没点那个开关，就一直记「未启用自动发群」，人以为发了、实际一条没发。

**改法**：改成 `enabled: raw.enabled !== false`——只有明确关掉才不发。群名和 Webhook 都没配时仍落到「未配置邀约群」并记 skipped，不会误发。

### ⑥ 已签到误判（最严重的一处）

**问题**：默认事件规则里 `checked_in` 的关键词是「那就祝您面试顺利」「请准时到本公司面试」——这俩恰好出现在运营的面试通知模板里。运营一发通知，客户立刻从「报名成功」跳到「已签到」（`STATUS_RANK` 只升不降，跳上去退不回来），而他第二天才来。

**实测证据**（内存库探针，修复前）：

```
发送「请准时到本公司面试，带好身份证。」
→ {"event":"checked_in","matchedKeyword":"请准时到本公司面试","applied":true}
→ 会话状态 invited → checked_in
```

**根因**：规则匹配的是**我们自己发出去的话**。签到是「客户到场」的事实，我们没有任何到场信号源（`check_in_code` 字段存在但无人写入），从文字里推不出来。

**改法**：

- `src/shared/event-rules.ts` 与 `src/shared/response-serializers.ts` 的默认规则删掉 `checked_in`。运营仍可在「回复规则」里自己加，那是明确的自主决定。
- 补人工入口：编译版页面（`public/theme/candidate-registration-table.js`）新增「签到」列，确认后调 `POST /api/v1/agent/candidates/:id/mark`。

**这一条是删除自动规则连带出来的回归**：删完才发现线上跑的是 `public/` 编译版，那里 `CandidateView` 里 `mark` 出现 0 次——没有任何打标记的入口，「已签到」标签页会永远为空。所以补按钮和删规则必须在同一批里，否则等于把功能改没了。

### ⑦ 省字段

**问题**：OA 第 7 项要「省/市/区」。`flow_engine.extract_province()` 只认 `XX省` 后缀，客户说「广东深圳」「深圳」时抽出来是空（实测「我叫谢子鑫 18077352958 广东深圳」→ `province=None`）。

**改法**：`profile.routes.ts` 落库前按 `city` 反查 `cities.province` 补齐。只在 `province` 为空时生效（已有值不覆盖，符合部分更新语义），查不到就留空，不猜。

## 四、有风险的地方（上线后要盯）

### 4.1 【高】打标签在实盘链路上根本不执行

`applyEventRule()` 全仓库只有一个调用点：`message-automation.ts:177`，在**服务端生成并发出回复之后**。但同函数第 86 行有：

```js
if (deviceData.observe_only === true) {
  return { status: "processed", reply_status: "observe_only" };
}
```

而 `027_device_observe_only.sql` 把**所有存量设备**补成了 `observe_only=true`，`agent.routes.ts:103` 新建设备也是 `observe_only: true` 打底。

实盘是键鼠客户端在回复，服务端只观察。这条早退发生在 `applyEventRule` 之前，而客户端上报出站走的是 `/outbound` → `store.observeOutbound()`，那条路径也不调用规则引擎。

**结论：「回复规则打标签」这个功能在当前部署形态下一次都不会触发。** ⑤⑥⑦ 修的是判定规则本身，但**规则引擎仍然不跑**。

### 4.2 【高】「已签到」目前完全依赖人工

删掉自动规则后，唯一的入口是新加的「签到」按钮。这意味着：

- 运营不去点，这个标签页永远是空的；
- 没有任何自动化能填它（`check_in_code` 无写入方）；
- 客户真到了现场，系统不知道。

要做到自动签到，得先有到场信号（扫码 / 企微打卡 / OA 回传），那是另一件事。

### 4.3 【中】邀约群默认开启是行为变更

改之前是「配了也不发」，改之后是「配了就发」。如果某台设备的历史配置里留着测试群名或测试 Webhook，上线后会真的往那个群发名单。

**上线后第一件事**：检查 `GET /api/v1/agent/invite-group` 返回的 `groupName` / `webhookPreview` 是不是生产群；`GET /api/v1/agent/invite-group/sends` 看有没有异常发送记录。

### 4.4 【中】一人多行，OA 语义对不上

`applyEventRule()` 打标签是**新插一条** `candidate_events`，`ensureCommunicatingEvent()` 也是。同一个人可能同时有 `communicating` + `invited` + `checked_in` 三条，顶部 tab 按 `event_type` 过滤 → 每个 tab 都有他，总人数虚高。

OA 的语义是「一人一行、状态是字段」。这一条**没改**，需要先定口径（比如 `invited` 作为主记录、后续事件只更新 `status`），会影响激活复聊和看板统计。

### 4.5 【中】看板数据不实

`/api/v1/agent/status/dashboard` 9 个区块里 8 个是写死的：`active_today: 0`、`hourly` 恒为 0（根本没查）、`state_distribution: {}`、`daily_trend: []` 等。只有 `devices.total` / `messages.total` / `queue.pending` 有真实数据。

另外 `failed_today` 的 SQL **没有日期条件**，实际是历史累计失败数。运营看到这个数字会以为今天出事了。

### 4.6 【中】档案推送失败完全静默

`api_flow.py` 里：

```python
try:
    await profile_push.push(device_code, payload.session_key, out_profile)
except Exception:  # noqa: BLE001  推送是附加动作，不许影响客户收到话
    pass
```

注释是对的，但 `pass` 之外没有任何记录。4222 挂了、token 过期、超时，全部无声无息——**客户在微信里聊得好好的，网页候选人页永远是空的，没人知道为什么**。

### 4.7 【中】发送失败在网页上看不到

客户端发送结果只写本地 `reply_log.db`（`mark_sent` / `mark_failed` / …）。上报 4222 走的是企微解密库里的**实际消息**：

- 发送成功 → 库里有 → 上报 → 网页有记录
- **发送失败 → 库里没有 → 网页一条都没有**

运营看到的是「这条消息不存在」，而不是「发送失败」，两者含义完全不同。

### 4.8 【低】SSE 只有三种事件

`messageCreated` / `commandUpdated` / `deviceUpdated`，**没有候选人/档案事件**。候选人页和「沟通中」状态只能靠轮询，这是之前红点反复出现的根因。

### 4.9 【低】省字段只在落库时补

反查发生在 `POST /api/v1/agent/profile`。如果某条记录是别的路径写进 `candidate_events` 的（比如 `POST /api/v1/agent/candidates` 手工建），不会走这段逻辑，省字段仍是空。
