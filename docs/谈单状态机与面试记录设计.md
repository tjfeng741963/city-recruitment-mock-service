# 谈单状态机与面试记录设计

> 目标：知识库只负责回答「有什么岗位、多少钱、包不包吃住」；
> **谈单进展（约没约上、来没来、要不要）必须单独记录，并且要能统计。**

## 一、为什么不能只靠关键词

客户说「明天可以去面试吗」和「明天可以去面试吗？」在字面上一样，但上下文不同：

- 前面已经聊过岗位、年龄合适 → 这是**约面确认**
- 前面只是问「你们在招什么」 → 这是**打听**

同一句「行」：

- 接在「明天上午 9 点到番禺立信电子厂」后面 → **约面成功**
- 接在「你多大了」后面 → 只是回答了年龄

所以判定必须**同时看双方最近几轮对话**，不能只看最后一条消息。这就是要接 LLM 抽取的原因。

## 二、状态定义（10 个）

| stage | 中文 | 含义 | 谁触发 |
|---|---|---|---|
| `new` | 新来 | 只有打招呼，还没问实质内容 | 系统 |
| `asking` | 咨询中 | 在问岗位/工价/地点/年龄要求 | LLM |
| `intent` | 有意向 | 说想去，但**时间没定** | LLM |
| `booked` | 已约面 | **双方确认了具体时间** | LLM |
| `interviewed` | 已到面 | 人到了 | 人工 / 客户明说「我到了」 |
| `hired` | 已入职 | 上岗 | 人工 |
| `no_show` | 爽约 | 约的时间过了，人没来 | 系统推断 + 人工确认 |
| `gave_up` | 客户放弃 | 嫌远、嫌钱少、不去了 | LLM |
| `unsuitable` | 条件不符 | 超龄、性别不符、没健康证 | LLM |
| `dormant` | 沉默 | 超过 N 天没再说话 | 系统 |

### 主流程

```
new ──→ asking ──→ intent ──→ booked ──→ interviewed ──→ hired
                      │           │
                      │           └──→ no_show
                      ├──→ gave_up
                      └──→ unsuitable
```

## 三、判定规则（关键）

### 「已约面」必须同时满足三条

1. **客户表达了确定意愿**：可以 / 行 / 去 / 好的 / 没问题（或等价表达）
2. **有明确时间**：明天 / 周一 / 11月5号上午9点 —— 能解析成具体日期
3. **我方确认了**：我们说「可以，明天上午 9 点」而不是「你什么时候方便」

只满足 1、2 不满足 3 → `intent`（客户想去，我们还没答应）
只满足 1、3 不满足 2 → `intent`（答应了但没定时间）

**没有明确时间的一律不算 booked。** 这是最容易造假的地方——「有空过来」不是约面。

### 爽约的判定

`booked` 且 `interview_at + 宽限期(默认 3 小时) < now` 且没有到面记录 → 标 `no_show_pending`（待核实）。

**不自动判死**，因为：
- 客户可能改期了但没说
- 可能已经到了只是没在微信上说

待核实状态在后台可以一键改成 `interviewed`（到面）或确认 `no_show`（爽约）。

### 不允许倒退

`booked` 之后不能自动回到 `asking`。改期是 `booked → booked`（更新 `interview_at`，记一条 `rescheduled` 事件）。
要倒退只能人工操作。

## 四、数据模型

### `leads`（每个会话一条）

| 字段 | 说明 |
|---|---|
| `conversation_id` | 唯一，一会话一条 |
| `stage` | 上面 10 个之一 |
| `interview_at` | 约的时间（**booked 时必填**） |
| `interview_place` | 哪个厂 / 哪个集合点 |
| `job_title` | 约的哪个岗位 |
| `age` / `city` | 客户自述，用于后续筛选 |
| `intent` | 意向度 1-5 |
| `confidence` | 本次抽取置信度，< 0.65 不落库 |
| `updated_by` | llm / manual / system |

### `lead_events`（只追加，不改不删）

| 字段 | 说明 |
|---|---|
| `event_type` | `stage_change` / `scheduled` / `rescheduled` / `no_show` / `manual` / `note` |
| `from_stage` → `to_stage` | 状态流转 |
| `payload` | JSON：时间、地点、岗位、判定理由 |
| `message_id` | 触发它的那条消息，用于追溯和幂等 |

**为什么要事件表**：领导问「这个月约了多少面、来了多少」，只能靠流水算，不能靠当前状态。

## 五、怎么触发（三条路径，互不阻塞）

```
① LLM 自动抽取（实时）
   客户消息 → 我方回复发出后 → 带最近 12 条对话调抽取 → 有变化才落库

② 系统推断（定时，每 10 分钟）
   booked 且超过约定时间 3 小时 → no_show_pending
   超过 7 天无消息 → dormant

③ 人工标记（后台）
   到面 / 入职 / 改期 / 爽约确认 / 手动改状态
```

**抽取失败绝不影响发送**：先发消息，再抽取。抽取超时或报错只记日志。

## 六、接口

| 方法 | 路径 | 用途 | 鉴权 |
|---|---|---|---|
| POST | `/api/v1/leads/observe` | agent 上报对话，触发抽取 | 设备 token |
| GET | `/api/v1/leads` | 线索列表（按 stage/日期筛） | 管理员 |
| GET | `/api/v1/leads/stats` | 漏斗与转化统计 | 管理员 |
| POST | `/api/v1/leads/{conversation_id}/manual` | 人工改状态（到面/入职/爽约） | 管理员 |

## 七、统计口径

| 指标 | 算法 |
|---|---|
| 今日新线索 | `lead_events` 中 `to_stage='new'` 且当天 |
| 今日约面 | `event_type='scheduled'` 且当天 |
| 今日到面 | `to_stage='interviewed'` 且当天 |
| 今日爽约 | `to_stage='no_show'` 且当天 |
| 约面率 | 约面数 / 咨询数 |
| 到面率 | 到面数 / 约面数 |
| 爽约率 | 爽约数 / 约面数 |
| 按岗位 | 按 `job_title` 分组统计约面与到面 |

## 八、和知识库的分工

| 谁 | 负责 |
|---|---|
| 知识库 | 岗位事实：城市、厂名、工价、年龄、吃住 —— **不许编造** |
| LLM（回复生成） | 把事实改写成口语，接住追问 |
| LLM（状态抽取） | 判断谈单进展，输出结构化字段 —— **不生成回复** |
| 人工 | 到面、入职、爽约核实这类**只能靠人确认**的事 |

**两次 LLM 调用职责分开**，不放在同一个 prompt 里：回复要自然，抽取要严格，两者混在一起会互相干扰（之前回复被数字校验逼着重写就是例子）。

## 九、分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** | 表 + 抽取服务 + observe 接口 + agent 挂钩 | 真实对话能自动落到 `booked`，时间地点正确 |
| **P1** | 列表 + 漏斗统计 + 人工标记接口 | 后台能看到今天约了几个人 |
| **P2** | 定时推断（爽约、沉默）+ 前端看板 | 不用人工点也能出日报 |

## 十、已知边界

1. **时间解析靠 LLM**，「下周三」这类相对时间需要给定当前日期做基准，prompt 里会显式传入今天日期
2. **跨天对话**：昨晚说「明天」指的是今天，抽取时以消息时间为基准，不是以当前时间为基准
3. **群聊不做抽取**（`R:` 开头），只做单聊
4. **同一客户多个会话**（换号）视为不同线索，不合并
