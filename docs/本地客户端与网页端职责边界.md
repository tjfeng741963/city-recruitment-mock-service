# 本地客户端与网页端：职责边界与商业化取舍

> 起因：2026-11-07 讨论「既然必须装本地程序，网页版是不是没意义？」
> 结论：本地是手，网页是脑和眼睛。两者不可互相替代，也不该合并。

---

## 一、为什么必须在本地

有三个动作，浏览器在物理上做不到：

| 动作 | 为什么网页做不到 |
|---|---|
| 读企业微信本地加密数据库 | 需要从 `WXWork.exe` 进程内存里取密钥，浏览器拿不到其他进程的内存 |
| 模拟键鼠把消息发出去 | 企业微信没有开放发送接口，只能操作窗口、抢占前台、模拟按键 |
| 保持长期在线 | 浏览器标签页关闭即中断；客户消息是 7×24 进来的 |

所以「网页直接发消息」这条路不存在。**网页只能下发指令，真正的发送只能发生在本地。**

---

## 二、那网页有什么用

网页的用户不是坐席，是**老板 / 运营 / 管理者**。两者的需求在结构上就不同：

| 维度 | 本地客户端 | 网页后台 |
|---|---|---|
| 装在哪 | 坐席的电脑（登录着企微） | 不用装，浏览器打开 |
| 看得到什么 | 一个账号、一台机器 | 所有设备、所有会话、所有线索 |
| 主要动作 | 读消息、敲键盘 | 看全局、改知识库、审核、接管 |
| 数量 | 每台坐席机一个 | 一个入口 |

具体到业务场景：

| 场景 | 只做本地会怎样 | 网页解决什么 |
|---|---|---|
| 5 个坐席同时接待 | 要开 5 个窗口分别看 | 一个页面汇总 |
| 改一条知识库 | 5 台机器各改一次 | 改一次全局生效 |
| 坐席下班、电脑关机 | 历史会话查不到 | 会话已在服务器 |
| 老板在手机上看今天回了多少客户 | 做不到 | 移动端页面 |
| 人工接管某个难缠的客户 | 要在那台机器上操作 | 任意端点一下，指令下发到对应机器 |
| 审核设备是否该上线 | 无从管理 | 设备列表 + 状态 |

**一句话：网页的价值是「汇总」和「控制」，「操作」不在它这里。**

---

## 三、正确的职责划分

```
┌─────────────────────────────────────────────────────────┐
│  本地客户端（坐席电脑）—— 手                              │
│  · 读：解密本地库、拿到新消息                             │
│  · 报：上报会话与消息、发心跳                             │
│  · 敲：领取指令、模拟键鼠发送、回执                       │
│  不做任何业务判断                                       │
└─────────────────────────────────────────────────────────┘
                    ↓ 上报               ↑ 下发指令
┌─────────────────────────────────────────────────────────┐
│  服务器 —— 脑 + 账本                                     │
│  · 决定该不该回、回什么（知识库 / LLM）                   │
│  · 会话、线索、候选人状态的唯一真相                       │
│  · 冷却、去重、防重复回复、失败的补偿                     │
└─────────────────────────────────────────────────────────┘
                    ↓ 读写
┌─────────────────────────────────────────────────────────┐
│  网页端 —— 眼睛 + 控制台                                 │
│  · 看：会话、设备、线索、统计                             │
│  · 改：知识库、规则、设备配置                             │
│  · 管：人工发消息（转成指令）、接管、停用设备             │
└─────────────────────────────────────────────────────────┘
```

### 三条判据

任何一个功能，按这个顺序判断放哪：

1. **需要碰企微窗口或本地库吗？** → 是则必须在本地，没有例外
2. **需要跨设备看全局吗？** → 是则必须在服务器
3. **需要人做决策吗？** → 是则界面放网页

## 四、现状与目标的差距

**现在已经拆了一半：**

| 环节 | 现在在哪 | 目标 |
|---|---|---|
| 回复内容生成 | 服务器（`brain.py` 问 8090 知识库） | ✅ 已经对了 |
| 该不该回、回几条、冷却多久 | **本地**（`autopilot.py`） | ❌ 应该上云 |
| 会话存储 | 服务器 | ✅ 已经对了 |
| 人工发消息 | 网页下发指令 → 本地执行 | ✅ 已经对了 |

**要商业化，得把「该不该回」也搬到服务器。** 本地只留三个动作：读、报、敲。

## 五、商业化：代码放在客户电脑上意味着什么

### 5.1 事实：客户能读到代码

现在是纯 Python 源码，打包成 exe 也只是提高门槛。**要默认客户能看到本地程序在做什么。**

### 5.2 但核心代码本来就不是秘密

`agent/wecom_io_core/` 的解密与键鼠操作，来源是三个 MIT 开源项目：

```
agent/LICENSES/wecom-alert-suite-MIT.txt
agent/LICENSES/wecom-group-sender-MIT.txt
agent/LICENSES/wecom-reader-MIT.txt
```

这些项目公开在 GitHub 上，谁都能下载。**那部分从来不是壁垒。**

### 5.3 真正的壁垒在服务器

| 资产 | 在哪 | 客户能否拿走 |
|---|---|---|
| 知识库内容（534 条） | 服务器 | ❌ |
| 招聘业务的判断逻辑 | 服务器 | ❌ |
| 历史会话与线索 | 服务器 | ❌ |
| 客户关系 | 商务层 | ❌ |
| 解密与键鼠代码 | 本地 | ⚠️ 本来就是公开的 |

### 5.4 保护措施（按性价比排序）

| 措施 | 效果 | 成本 |
|---|---|---|
| **业务逻辑上云**（根本手段） | 高 | 中 |
| 租户绑定 + license 校验 | 中高 | 低 |
| 打包成 exe（PyInstaller / Nuitka） | 中（挡业余） | 低 |
| 代码混淆 / 加壳 | 低（纯拖延） | 中 |
| 服务协议禁止逆向 | 高（法律层） | 低 |

**法律 > 架构 > 打包 > 混淆。**

## 六、关于「用户要不要知道密钥」

**不要。** 密钥是给程序看的技术参数，不是给用户操作的。

正确形态：

```
安装包内置：服务器地址 + register_key
用户操作：双击图标，完成
```

网页上那个「自动生成设备码」按钮的定位要改：**它是给运维/实施人员用的工具**，不是给最终用户的流程。最终用户不应该看到"设备码"这个概念。

## 七、待办

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | 跑通本地链路 | 客户端自注册 → 网页看到在线 → 消息来回 |
| P1 | 安装包内置配置 | register_key 写进发行版，用户零配置 |
| P2 | 决策逻辑上云 | 把「何时回、回几条」从 `autopilot.py` 搬到服务器 |
| P3 | license + 租户校验 | 商业化前提 |
| P4 | 打包与协议 | PyInstaller + 服务条款 |

---

## 八、一句话总结

**本地程序是唯一能碰到企业微信的地方，网页是唯一能看全局的地方。**

合并会失去全局视野，分开才各司其职。而保护商业价值的关键不是藏代码，是**让本地程序里没有值得偷的东西**。
