# 本轮媒体标记校验

`POST /api/v1/flow/answer` 对模型回复中的 `【图片:名称】`、`【视频:名称】` 执行确定性白名单校验，不依赖审核模型是否配置、超时或同意放行。

## 白名单来源

- 本轮实际采用的运营话术或代码生成的岗位卡、岗位事实。
- 本轮提供给模型的设备素材，或本轮命中的知识库正文及 FAQ `media`。
- 当前已选岗位由 4222 下发的 `media` 数组。优先按固定 `position_id` 查找，查不到不借其他岗位；老会话没有 id 时才按本轮索引取。

客户原话、历史消息和模型草稿不作为白名单来源。匹配维度为「图片/视频类型＋名称」，同名文件不能更换类型；不按后缀猜测，也不从同城其他岗位借媒体。

标记协议与现有客户端一致：ASCII 冒号，名称最多 80 字。空名称、路径分隔符、换行、`..` 或全角冒号等不可用标记会被移除。此处不修改客户端或企微动作层。

运营配置明确引用的标记视为可信素材；该机制限制模型虚构，并不逐个下载文件验证可达性。4222 对结构化 `media` 仍按既有资源库规则解析；历史话术和 KB 配置的资源存在性应由运营维护。

## 回复处理

1. 审核前移除未授权标记，保留其余正文、合法媒体及消息分段。
2. 审核打回后，重写稿再次过滤；重写提示词显式提供本轮允许的标记。
3. 没配审核、审核超时或放行，均不会跳过媒体过滤。
4. 草稿只包含虚构媒体时，使用现有确定性短句兜底；阶段、动作及资料槽位保持原处理结果。
5. 回声兜底、KB 补媒体和重复应答之后，落库前再次过滤，事件历史保存最终实际返回的内容。

媒体文件名里的数字不当作工价声明；工价护栏仍校验标记以外的正文。删除虚构文件名不应导致有效正文和合法媒体一起被丢弃。

## KB 媒体与分段

FAQ 同时配置多个媒体时，只补入正文尚未包含的合法标记，按顺序全部进入 `parts`。始终保持 `reply == '\n'.join(parts)`，避免旧客户端读 reply、新客户端读 parts 时收到不同内容。

本轮运营话术、岗位卡、岗位事实、动作回复或设备素材优先采用时，不再补入未使用的 KB 媒体，也不将未采用的 KB 记为已发送。原有旧 KB 再次命中时的短句及媒体重发语义保留。
