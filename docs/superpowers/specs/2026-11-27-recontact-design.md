# 复聊板块设计

2026-11-27 · 方案 A

## 页面与入口

招聘者负责设置岗位的自动复聊，也需要筛选一段时间未联系的候选人，逐批确认跟进。两项操作集中在「复聊板块」。

```text
左侧「日常招聘」
  对话管理
  复聊板块
  候选人管理
  面试登记
  微信账号

复聊板块
  自动复聊 | 老客户复聊 | 发送记录
```

默认打开「自动复聊」。三个标签共用岗位和账号筛选条件。发送记录从候选人一栏进入原有「对话管理」核对，并可返回原筛选结果。旧「复聊激活」的直链继续用于查阅历史页面。采用现有招聘页的表格、表单和状态样式，说明只在填写、确认或异常时出现在对应控件旁。

## 自动复聊

- 招聘者在「自动复聊」选择岗位，填写启停、触发阶段、等待时长、可发送时段和消息顺序。首次创建为停用状态。示例规则为「答复上班地点后，30 分钟没有回复，补一次面试邀约」。30 分钟是表单建议值。
- 首版触发阶段为「已回复上班地点」和「已发面试邀约」。Agent 和 Dify 都由回复链路明确标记触发阶段，从对应回复最后一条经客户端确认发出时开始计时。后端记录原回复与候选人会话的关联。
- 同一轮沉默最多触发一次。待发期间，候选人回复、明确拒绝、已报名或会话被人工接管时，取消余下消息。暂停规则时取消尚未发送的任务。北京时间 09:00–21:00 为默认发送时段，可按岗位缩短。跨出时段的任务顺延，恢复发送前重新核对。
- Agent 画布原有的超时复聊按会话切换。已进入等待或已有结果的旧会话沿用原快照并记录归属，由原路径处理完这一轮。启用新规则后，新进入对应等待阶段的会话由服务器调度。只有能确认处理归属的会话才进入新队列，避免并行发送。已确认面试后的到期提醒沿用现有面试链路。

## 老客户复聊

- 招聘者按岗位、企微账号和最近联系时间筛选有过实际交流的候选人。建议筛选条件为最近一次收发已满 3 天、尚未报名，招聘者可调整时间范围。以当前登录账号下可核对的私聊为发送对象。
- 勾选候选人，选择岗位模板，预览每人的岗位、发送账号、消息内容和顺序后，再确认创建发送任务。模板在本标签内维护。跨岗位选人时按各岗位可用模板生成预览，缺少适用模板的候选人显示原因。
- 已拒绝、已报名、人工接管或已有待发复聊的候选人显示不可选原因。确认后再校验一遍，名单变化时在结果页显示跳过原因。近期发过复聊的人可以在发送记录查到，最近联系时间按实际消息更新。

## 消息与回执

- 自动复聊和老客户复聊共用同一种消息编辑器，可添加和重排文字、图片、视频、地点。每一项是一条消息，相邻两条可配置间隔。素材从本岗位及授权的通用素材中选择。首版的「地点」以地址和高德地图链接发送，使用岗位已保存的工作地址或面试点。只有地址的工作地点可以作为文字发送。
- 两种模式共用服务器调度和记录。服务器按保存的顺序逐条下发，从上一条确认发出后计算间隔。Windows 客户端通过现有企微发送路径执行。每条发送前校验设备、当前登录账号、收件人、最新来信和人工接管状态。账号或岗位切换使原任务失去适用条件时取消余下步骤。
- 同一租户、企微账号和私聊同一时刻只有一条活动复聊任务。用触发回复的事件标识去重，重启、切换回复模式或重复确认时沿用同一记录。先校验客户端发送能力，再开放真实执行。
- 「发送记录」可按岗位、账号、候选人和状态筛选。每条消息显示预计时间、是否执行、发送回执和失败原因。未取得明确回执时标为「待核对」，暂停后续步骤。人工核对后可继续未发步骤，已确认发出的步骤保留记录。只有收件端独立核对才能记录对方收到。

## 验收

| 场景 | 通过条件 |
| --- | --- |
| 页面与权限 | 可从左侧进入，选岗位后配置或选人发送，回看记录和真实对话。招聘者仅可访问有权限的岗位、账号和会话。 |
| 自动复聊 | 分别用 Agent 和 Dify 触发「问上班地点 → 答复 → 超时复聊」。校验实际发送回执、等待时间，以及回复、拒绝、报名、接管、停用和静默时段。 |
| 老客户复聊 | 能筛选、预览、确认和查记录。确认后出现来信的候选人被跳过，重复确认只生成一个任务。 |
| 顺序和间隔 | 用「地点 → 文字」和「文字 → 图片 → 视频 → 地点」分别实测，核对发件记录与实际收件顺序、视频播放和地图落点。 |
| 异常和切换 | 设备掉线、素材不可用或收件人无法核对时，在对应步骤显示原因。测试中途切换账号或回复模式、旧画布快照和回执待核对，确认没有重复发送。 |

先在受控测试会话验证 Agent 和 Dify，再按账号启用已通过实发验收的设备。规则保存、自动触发、客户端执行、对方实际收到分别记录验收结果。
