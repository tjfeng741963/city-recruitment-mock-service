# Dify 第二条回复路线

用户已确认：保留 C:\agent 收发，在 4222 按设备切换 Dify，先测试再切真实测试联系人。

## 路线

企微本地消息 → C:\agent → 4222 /api/v1/agent/chat → 按设备选 Agent 或 Dify → 返回现有 reply.messages 信封 → 原客户端发送与回读。

4222 bridge/inbound 继续只落库。禁止增加第二个自动回复触发器；禁止更改 wecom_io_core 或客户端动作。Hook 不是本期依赖。

## 配置与身份

独立 Dify 配置接口仅管理员可读写。Dify API URL 和应用密钥使用服务端环境变量，网页只保存 provider=agent/dify，不返回密钥。已选 Dify 但未配置时明确失败，不能回落 Agent。

Dify 会话表使用 device_code + 当前企微 account_id + session_key + 岗位 ID；应用配置变化时另开会话。每个会话串行处理；调用状态和耗时记账，不保留回复正文。客户端无事件 ID 的旧契约下不承诺所有重试都能去重或重放，不以相同文本判为重复消息。

## 数据与职责

从设备绑定岗位实时读取规范化岗位事实，并将中性岗位信息以 JSON 作为 position_data 输入 Dify。无需岗位人设和旧开场。Dify 的单独集成应用使用该输入，不能保留第三方历史岗位数据。工资、食宿、时间和地址由系统提供，缺少数据则询问招聘员，不编造。不做自动录用/拒绝，不按民族、健康等敏感资料作适岗判断。

本期首个闭环是消息读取、Dify 生成、兼容客户端返回、发送回执。姓名电话及面试意向先保留在 Dify 会话，未建立正式登记时不得说已报名/已预留名额。OA 与群通知不假装已接通，后续单独对接确定的结构化登记接口。

## 运行约束

只使用 deepseek-chat，不配置思考参数。普通 HTTP 只允许私网/回环；服务间通过服务器回环 SSH 隧道或已验证的内网地址访问；不得为连通性关闭 TLS 校验。

管理员调试允许 dry 读取输入但不执行模型。人工接管及停用设备在调用前、返回前均检查；Dify 不发送任何消息，只返回待客户端发送的文本。空回复、超时、非法响应、隐藏内部标记、媒体外链不能直接透传。

## 验收

- 默认设备继续走原 Agent。
- Dify 设备不拉旧开场，不调用 Agent complete。
- 最新岗位事实进入 Dify，多设备/多账号/岗位变更上下文隔离。
- 人工接管、配置失败、超时、空回复返回失败，客户端不发。
- 使用隔离设备与虚构联系人实测 Dify API；无需真实企微发送即可先验证服务边界。
- 真实发消息仅对用户指定测试联系人进行；未指定时不能向客户群发试验。
- 合并/发布前运行仓库要求的全部检查，只提交本次文件。
