# 企业微信选窗与发送状态修复方案

**目标**是拦住已识别的错误发送目标，并让经目标会话回读确认的开场文字恢复自动回复状态。

改动放在 `agent/autopilot.py` 的发送编排层。冻结的 `agent/wecom_io_core/` 及原有键鼠动作和时序按仓库规则保留。设备继续使用既有回复模式配置。

## 根因和现场证据

- Windows 选窗函数 `agent/wecom_io_core/win.py:45` 记录窗口是否可见，只按面积取最大窗口。`win.py:68` 会显示所选的隐藏窗口。文本和媒体发送分别在 `send.py:187` 和 `send.py:459` 内部选窗。用真实选择逻辑与模拟窗口复现了在可见聊天主窗口仍存在时选中隐藏窗口。00:18 与 00:28 的失败前出现了其他企微进程的窗口，随后输入校验失败。截图中的黑色缩略图缺少同期窗口句柄，具体归属待下次现场采样确认。
- 同一会话的「找工作」在北京时间 00:18:07 收到。第一次发送是 Agent 开场，00:18:58 校验失败，00:29:51 同一会话有一条开场文字通过客户端回读。开场成功分支没有清除连续失败计数。心跳用旧计数继续上报 `auto_send_failed`，定时运行的流程也会在计数非零时提前返回。

## 第一项修复 · 发送状态恢复

1. 在 `agent/autopilot.py` 的 Agent 开场文字分支，沿用 `_send_text()` 的结果。仅在状态为 `sent` 时清除 `_consecutive_send_failures` 与 `_last_error`。该状态要求本地企微库回读确认目标会话新增了唯一一条匹配正文的消息。
2. 保留失败、回读不确定与部分发送的原有账本处理。状态恢复后的心跳仍须满足企微在线、桌面可用、设备回复已启用等条件。补回归用例验证「失败 → 下一笔开场文字回读成功 → 心跳恢复」「失败 → 回读不确定 → 仍保留失败状态」以及回读成功但设备暂停时仍显示暂停。

## 第二项修复 · 发送前检查目标窗口

1. 在 `agent/autopilot.py` 的共用文本发送入口及图片、视频的实际发送入口，调用发送器前做一次只读检查。复用冻结核心的选窗结果，现场核对窗口仍存在、可见、可用且属于当前交互会话的企微。发现隐藏、失效或身份无法确认的目标时暂停当前发送；沿用账本保留待发或待核对状态，记录时间、发送路径、窗口句柄、进程号、可见性与拒绝原因。日志省略聊天正文和联系人资料。
2. 明确区分「发送前已拦截」和「已执行但结果不确定」。前者保留待处理记录，可在窗口恢复后按原有规则继续处理。若开场已发出部分内容、发送结果不确定，或本次操作前历史记录已经标记待核对，则保留原状态和进度，交由人工核对，避免旧消息或开场片段重复发送。发送拦截不能单独作为企微掉登录的依据。
3. 冻结的发送器会再次选窗。前置检查能拦下当时已经选到的隐藏窗口，两次选窗之间发生变化仍有竞争窗口。用模拟窗口变化测试这个边界，并以脱敏窗口日志观察现场。若该场景仍导致误选，完整修复需要经仓库批准的上游核心版本，由发送器在实际选窗时只接受经确认的可见聊天窗口，并在目标失效时中止本次动作。

## 验收与回滚

- 先用模拟窗口跑回归。复用现场的 `1412×647` 可见窗口和 `1180×715` 隐藏窗口，再将可见窗口缩为 `1100×640`。验证后者会触发拦截、发送器调用次数为零。另测无主窗口、桌面不可用、正常单窗口，以及预检后窗口切换。文本、图片、视频应分别覆盖。提交前按仓库发布规则运行全量检查，并确认冻结文件无差异。
- 云 Windows 分别验证 Agent 与 Dify。以一个测试联系人发送「找工作」，核对网页收到、实际回复模式、客户端执行、目标会话回读和测试端收到。再验证一次异常后的恢复，确认后台状态随新鲜心跳更新，旧记录保持原状态。实际收到以测试端为准。
- 两项修复可形成独立提交。安装前记录旧版 SHA 并备份客户端源码及版本记录。出现回归时暂停自动发送，保留发送日志和待核对记录，通过既有备份恢复相应客户端版本，再核实安装版本与心跳。若回退版本仍会误选窗口，保持暂停直到发送验收通过。
