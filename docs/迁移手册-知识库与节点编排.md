# 知识库与节点编排迁移手册（Node SQLite → Python 库）

> 目标：把 4222（Node/SQLite）侧的客户真实资料迁到 8090（Python/PostgreSQL），
> **先迁移、不切换**；验收通过后再开节点路由。
>
> 核心原则：每一步都可以单独回退，任何一步失败都不影响现有线上会话。

## 背景：为什么必须迁

4222 和 8090 是两个独立的库：

| 服务 | 库 | 用途 |
|------|-----|------|
| 4222 Node | `data/app.sqlite` | 后台管理、岗位、设备、话术、KB v3、节点图 |
| 8090 Python | `APP_DATABASE_URL`（生产 PostgreSQL） | 对话流程、kb_faq 检索、节点图读取 |

客户的真实资料（番禺 6 家厂 / 11 个岗位 / 地铁 12 城工资架构 / 206 条场景问答）
是通过 `src/db/migrations/`、`src/db/backfill/` 写进 **SQLite** 的。
8090 读的是 PostgreSQL，所以：

- `kb_faq.lookup()` 查不到 → 只剩早前导入的 534 条 `kb_entry` 存量话术
- `flow_graph.load_graph()` 查不到 `flow_nodes` → 抛异常 → 回空图 → 节点编排完全不生效

## 迁移分三步，每步独立可回退

### 第一步：迁知识库（只读数据，不改行为）

```bash
cd backend

# 1) 预演，看清要做什么，不写库
uv run python -m scripts.sync_kb_from_node

# 2) 确认数字合理后真正写入
uv run python -m scripts.sync_kb_from_node --apply
```

预期输出（首次）：

```
vertical             5
location            39
employer            34
employer_alias      36
kb_faq             140   （另有 66 条 position 作用域跳过）
```

**这一步是安全的**：`kb_faq` 没命中时 `api_flow` 会回落到旧路径（`kb_placeholder`），
所以即使迁过来的内容有问题，最差也只是"和现在一样"，不会更糟。

**脚本的三条保证**：

- 只增不改：已存在的行整个跳过，运营在后台改过的话术不会被冲掉
- 源库只读打开（`mode=ro`），绝不可能写坏 4222 正在用的库
- 幂等：重复执行第二遍新增 0 行

**回退**：按 `created_at` 删掉本批次写入的行即可；或直接恢复 PG 备份。

### 第二步：验收知识库（不动线上）

迁移完先在库里直接验证，不要直接放真实客户进来：

```bash
uv run python -c "
import asyncio, sys; sys.path.insert(0,'.')
from sqlalchemy import text
from app.db import SessionLocal
from app.services import kb_faq
async def main():
    async with SessionLocal() as s:
        eid = (await s.execute(text(\"SELECT id FROM employer WHERE employer_code='GZ-PY-004'\"))).scalar()
        for q in ['有纹身能进吗','要不要体检','包吃住吗','工资多少']:
            hit = await kb_faq.lookup(s, q, vertical_code='factory', employer_id=eid)
            print(q, '->', (hit.tier, hit.answer[:40]) if hit else '未命中')
asyncio.run(main())
"
```

判据：

- `有纹身能进吗` 必须命中 `employer` 层，答「华荻要查纹身，花臂进不去」
- 若命中 `global` 层且渲染出空串 → **设备的 `employer_id` 没绑上**，
  检查 `/config` 是否返回了非 0 的 `employer_id`（已加厂名/别名反查兜底）

### 第三步：迁节点表（这一步等于切换，务必最后做）

```bash
uv run python -m scripts.sync_kb_from_node --include-flow --apply
```

**为什么单独拎出来**：`load_graph()` 一旦读到节点，`step()` 里的 `_route_by_graph`
立刻生效，会话不再走写死的五阶段。这就是"切过来"。

切换前必须确认：

- [ ] 第一步的知识库已验证（否则节点分支里的侧问答不上来）
- [ ] 设备 `/config` 返回了正确的 `vertical_code`（factory / subway）
- [ ] 至少用一个测试会话走完全流程：加好友 → 岗位卡 → 问工资 → 答应面试 → 报姓名电话
- [ ] 确认「客户说『不去』」不会被登记成已约（`fe70373` 已修，需回归验证）

**回退**：`DELETE FROM flow_nodes; DELETE FROM flow_edges;`
删掉即回到写死流程，代码不需要回滚。

## 已知未解决的问题

### 1. position 作用域问答迁不过去（66 条）

028 里按工种分开的工价（华荻普工 24-26 / 焊工 35-40 / 叉车工 24-26）挂在
`scope_position_id`，而 Python 侧没有 `service_positions` 表，岗位 id 无从映射。

**影响**：客户问「焊工多少钱」拿不到焊工专属工价，会落到 employer 或 global 层。

**修法**（后续）：给 Python 侧建岗位表，或在 `/config` 里直接下发
`position_id` 并从 Node 侧同步岗位数据。

### 2. 岗位字段不全，占位符渲染出空串

`022_kb_faq_seed.sql` 里的通用问答用 `{medical}` `{tattoo_policy}` `{dorm}`
`{insurance}` `{regular}` `{advance}` `{relocate_policy}` 等占位符，
但 `/agent/jobs` 只透传 `wage_text` / `hours_text` / `age_text` / `welfare_text`。

**表现**：客户问「要不要体检」，`render()` 把整句丢掉，返回空串 → 走兜底话术。

**缓解**：真实资料的 93 条 employer 层问答是硬编码答案、不含占位符，
只要 `employer_id` 绑上了就不会踩这个坑。

**根治**：把这些字段从岗位 `data_json` 里透出 `/agent/jobs`。
