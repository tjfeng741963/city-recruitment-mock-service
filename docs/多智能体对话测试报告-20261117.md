### 2. 「白名单」是什么，是 Agent 判断吗？

**是 Agent 判断，白名单只是「喂给它的资料范围」**。机制分两层：

**第一层：事实卡白名单（buildFacts）** —— 决定 Agent 能看到哪些岗位信息。
data_json 里只有下列白名单键会进 Agent 的提示词，其他键（联系人电话等）它根本看不到：

| 白名单键 | 内容 |
|---|---|
| city / factory_name / job_title | 城市、工厂、岗位名 |
| wage_text | 薪资待遇 |
| hours_text | 班次与月休 |
| age_text / height_text | 年龄、身高要求 |
| basic_requirements | 基本要求（纹身/民族/健康限制等） |
| welfare_text | 福利 |
| place | 线路/工作地点 |
| interview_time / interview_time_text | 面试时间（两字段任写一个即可） |
| interview_address | 面试地址 |
| interview_material | 面试携带资料 |
| onboarding_notes | 上岗流程（培训等） |
| job_content / tattoo_policy / cert_text | 工作内容 / 纹身政策 / 证书 |
| interview_address_image / interview_video | 本岗位绑定的地点图/视频文件名（自动注入） |

**第二层：输出规范（OUTPUT_SPEC）** —— 约束 Agent 怎么用这些资料：
数字只能来自事实卡（不改一个字）、话术库相似就引用原文、面试时间/休息日严格按事实卡、
客户问怎么走发本岗位地点图（没有就文字讲）、客户说没收到就重发媒体。

所以**不是硬提取**——客户问「纹身行不行」，模型自己读 basic_requirements 里的
限制自己组织话术；客户问「周天行不行」，模型自己读 interview_time 里的
「周日休息」自己答复。白名单只保证它**看不到不该看的**（如队长电话）、
**说不出事实卡之外的数字**。

### 3. 媒体分层（上一轮定的，本轮加了防线）

- **通用池**：工作内容图、安检视频、宿舍图 —— 全岗位可发
- **岗位专属**：面试地点图，`media_assets.position_id` 绑定（当前：面试地点.png → 广州 id=3）
- 事实卡自动注入本岗位的地点图名字（`interview_address_image`），模型只看得到自己的

## 四、抓到的 3 个 Bug 与修复

| # | 问题 | 根因 | 修复 | 修复后验证 |
|---|---|---|---|---|
| 1 | 模型把字段名 `interview_address_image` 当图片文件名输出，客户端按名字找不到文件 | 输出规范只说「填字段里的名字」，模型理解成填字段名 | ① 输出规范改措辞：**字段的值**才是文件名；② **服务端兜底**：返回前 name 命中事实卡媒体字段 → 自动替换成字段值 | 广州重测：`name = 面试地点.png` ✓，重发同 ✓ |
| 2 | 深圳周日幻觉：事实卡写「周日休息」模型却说周日可以面试 | 长文本里「周日休息」被忽略 + 无明确红线 | 输出规范加红线：面试时间/休息日严格按事实卡，写明休息日的明确答复不含糊 | 深圳重测：「周日面试官休息，周一至周六都可以约」✓ |
| 3 | 深圳客户也可能收到广州的地点图（模型从提示词示例照抄文件名） | 输出规范示例里写了真实文件名，模型照抄 | **服务端串岗防线**：媒体名必须在「通用池 ∪ 本岗位绑定」集合内，否则剥掉不发 | 深圳重测：不再发出不属于本岗位的图 ✓ |

防线架构（三层，模型犯错也有兜底）：

```
模型输出媒体消息
  ① 服务端：name 命中事实卡字段 → 替换为真实文件名
  ② 服务端：name 不在「通用池 ∪ 本岗位绑定」→ 剥掉（串岗防线）
  ③ 客户端：先检索本地 → 缺了从服务器下载 → 粘贴发送
```

## 五、测试结论

| 维度 | 结果 |
|---|---|
| 薪资/班次数字准确性 | ✓ 两个岗位全部数字与事实卡一致，无编造 |
| 面试时间/休息日 | ✓（修复后）广州明确周日休息；深圳明确周日休息 |
| 约面推进与登记 | ✓ capture/interview 正常捕获，日期换算正确（明天=11-18） |
| 媒体：有图岗位 | ✓ 广州发「面试地点.png」+ 重发生效 |
| 媒体：无图岗位 | ✓ 深圳文字讲地址，不硬发 |
| 串岗防线 | ✓ 服务端强制过滤 |
| 登记信息完整性 | ⚠️ 测试号没给真实电话，capture.phone 为空——真实客户说号码会正常捕获（Evans_峰 实测过） |

**遗留观察**（非 bug）：

1. 模型第一轮会引用「上面的招聘要求」——模拟环境没真发开场序列；真实设备流程开场先发，模型引用成立
2. 深圳纹身答复「露出来的位置不行+发照片确认」比事实卡的「不能有纹身」宽松——建议深圳事实卡的 basic_requirements 补一句「外露部位纹身不可以」，模型就能直接明确答复
3. 广州 B 画像纹身答复直接拒绝 ✓（事实卡写了「不能有纹身」）——两岗位差异来自事实卡措辞，运营可通过补事实卡微调口径
