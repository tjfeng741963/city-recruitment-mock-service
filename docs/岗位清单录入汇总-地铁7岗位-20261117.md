## 三、回复逻辑（Agent 按事实卡自然应答，不做硬提取）

- 客户问「多少钱/几点上班/几号线/面试几点/怎么走/带什么」→ Agent 从事实卡对应键取数回答，数字不改
- 客户问面试地点（广州岗）→ 回答地址并可自动发送「面试地点.png」导览图（媒体库已登记，客户端先查本地、缺了从服务器下载再粘贴发送）
- 客户说「没收到图/视频」→ Agent 重发对应媒体条目（真实发送）
- 双方定下面试时间 → Agent 写进档案（interview.date/time），登记齐姓名+电话后自动推送到设备绑定的群聊
- 约好的面试在「面试登记」面板可标记 **正常到达 / 爽约**

## 五、媒体分层设计（2026-11-17 定型）

媒体库（media_assets）分两层，Agent 发图/视频时按名字引用，客户端「先检索本地 → 缺了从服务器下载 → 粘贴发送」：

| 层 | 素材 | 绑定 | 谁能发 |
|---|---|---|---|
| 通用池（position_id=0） | 工作内容(1).jpg、安检.mp4、地铁宿舍.jpg | 无岗位限制 | 任何岗位的 Agent 都可按名字发送 |
| 岗位专属（position_id=N） | 面试地点.png（当前绑广州 id=3） | 一个岗位一张 | 只有该岗位的 Agent 能发——事实卡 `interview_address_image` 字段注入素材名 |

**运行逻辑**：

1. `buildFacts` 组装事实卡时自动查 `media_assets WHERE position_id=岗位id`，把绑定的图片名注入 `interview_address_image`（视频则注入 `interview_video`）
2. 输出规范明确：客户问「怎么走 / 在哪面试 / 发个位置图」→ Agent 只能填事实卡里那个名字；事实卡没写 = 本岗位没有地点图，**用文字讲清地址，不许编造图片名**
3. 通用素材不受岗位限制——工作内容/宿舍/安检视频各岗位话术一致
4. 客户说「没收到」→ Agent 重输出媒体条目，系统真实重发

**后续新城市配图流程（现在全在前端）**：侧栏「面试登记」抽屉 → 「岗位素材库」区块 → 选文件 + 选绑定岗位 → 上传即生效（绑定下拉随时可改，0=通用）。无需改代码、无需进数据库。

## 五点五、不用知识库的架构说明（2026-11-17 定论）

用户确认：**不做复杂的动态知识库，就按现在「固定白名单 + 事实卡」的方式**——每个岗位一张事实卡（data_json），白名单字段喂给 Agent，模型按资料自由应答。这套机制天然支持后续的业务线扩展：

| 要素 | 现在的承载 | 后续工厂/其他业务线怎么办 |
|---|---|---|
| 岗位信息（薪资/班次/要求/面试时间/地址…） | 事实卡 data_json，固定白名单字段（agent-lab 可编辑） | 新建岗位行，同样填这些字段——同一套白名单，零代码改动 |
| 通用素材（工作内容/宿舍/视频） | media_assets position_id=0 | 上传进通用池即可 |
| 岗位专属素材（面试地点图等） | media_assets.position_id 绑定 | 上传时选绑定岗位 |
| 话术库（S1-S7 场景原文） | 已有话术表，模型相似时引用原文 | 各业务线自己配话术 |
| 开场序列 | position_opening 表，按岗位独立 | 每岗位自己配 |

**明确不做的**：kb-faqs 知识库问答（新链路已砍掉 kb 检索，表中数据闲置）、动态字段/自定义业务线模板——白名单字段不够用时**加白名单键**（一行代码）而不是做配置系统。

**前端运营入口汇总**（全部已实现）：
- 岗位管理页：事实卡编辑（agent-lab）、开场序列配置
- 「面试登记」抽屉：登记清单 + 到达状态 + 手动新建约面试 + 设备绑群聊 + **岗位素材库（上传/绑定）**
- 设备页：绑定岗位切换、只读在线状态
