# 智能体回复链路全面改造：节点工作流 + 复聊 + 持久化

> 时间：2026-11-19
> 范围：后端（Fastify/TS）、前端（`public/theme` 运行时脚本）、客户端（Python/企微键鼠）
> 依据：老板 6 张截图（深圳_地铁安检员真实会话 + Agent 配置界面）+ 线上代码 + 11-19 发错人事故记录
> 一句话：**把"9 条平铺连发"改成"节点 + 等待闸门 + 一次性复聊"，三端用同一份流程定义和同一套状态标记。**

---

## 0. 一页纸结论

| 问题 | 根因 | 改法 |
|---|---|---|
| 客户收到重复话术 | 首次接触时"播完开场"又"把这句拿去问模型" | 首次接触只跑流程，不再同轮调 chat |
| 图片/视频/宿舍一起砸过去 | 开场是平铺 seq 列表，没有闸门 | 节点化，await 节点发完必须停 |
| 客户不回就断线 | 没有复聊机制 | `followup` 节点：15 分钟无回复发 1 次，只发 1 次 |
| 断线重连重复/漏发 | 只有 `.greeted.json` 布尔 | SQLite 游标 + 发件箱 + 启动对账 |
| 运营看不懂会发什么 | 配置是列表弹窗 | 无限画布 + 微信气泡预览 |

三端分工：

```
前端（画布）  写流程定义、看预览        →  agent_flow_* 表
后端（4222）  存流程、下发流程、存会话状态 →  /api/v1/agent/flow、/agent/state
客户端（Win） 按流程执行、控节奏、发消息    →  flow_state.db（游标+发件箱）
```

## 2. 问题诊断（按截图逐条对应）

### 2.1 根因 1：开场与 chat 同轮双发 ★ 主因

`agent/autopilot.py::drain` L1200-1268：

```python
if not dry and _is_first_contact(cid, greeted):
    ores = _brain.opening()
    for item in ores["items"]:      # ← 9 条全发
        ...
if not hint and not dry:
    res = {...}
elif hint:
    res = _brain.chat(hint, cid)    # ← 同一条消息又拿去问模型
```

**同一条入站消息被处理两次**：一次是"按配置播开场"，一次是"让模型自由回复"。开场里已经有薪资，模型又答一遍薪资 → 截图里薪资段出现两次。

### 2.2 根因 2：开场没有闸门

`for item in ores["items"]` 一路到底，`delay_ms` 只是节流（2 秒），不是"等客户回复"。图片、视频、宿舍这些应该"客户表示兴趣后再发"的内容跟着一起出去：

- 客户还在看招聘要求，视频已经发完了
- 9 条消息在 20 秒内砸完，像机器人批量群发
- 客户没有插话的机会，转化钩子（"看完回复我"）被后面的消息冲掉

### 2.3 根因 3：整个开场注入模型，模型必然复述

`src/modules/agent/agent-orchestrator.ts::buildOrchestration` L171-188：

```ts
for (const item of options.opening || []) {
  messages.push({ role: "assistant", content: assistantEnvelope(...) });
}
```

每一轮都把 9 条开场当"我自己刚说过的话"喂给模型，但没有告诉它"哪些真发了、客户看没看"。模型被问薪资时，最自然的动作就是"再发一遍"。

### 2.4 根因 4：状态只有布尔，没有游标

`.greeted.json` 只能回答"这个会话打没打过招呼"，回答不了：

- 发到第几条了？
- 哪条失败了？
- 客户回没回？
- 该不该复聊？

所以断线重连后只能二选一：当成新会话重播（重复），或当成老会话全跳过（漏发）。

### 2.5 根因 5：落点校验失败不中断（11-19 事故）

`wecom_io_core.send` 用 `Ctrl+F` 搜索会话名 → `Enter`。搜不到时回车只是关搜索框，**仍停在上一个会话**。11-19 因此发错 3 个客户。当前 `drain` 在 `expect_id` 校验失败后只 `_consecutive_send_failures += 1` 继续下一条，会把错误放大成一串。

**改造必须带这条护栏**：复聊/续播前做落点校验，失败立即 `break` 本轮。

## 3. 目标模型

### 3.1 结构

```
流程 flow（一个岗位一张，version 递增）
  └─ 节点 node（一个节点 = 一组 parts，可含文本/图片/视频）
       └─ 边 edge（default / any_reply / timeout / keyword / giveup）
```

### 3.2 节点类型

| 类型 | 作用 | 关键字段 | 前端表现 |
|---|---|---|---|
| `text` | 发一组文本（1~6 条） | `parts[]`、delay_ms | 白卡 |
| `image` / `video` | 发媒体 | `parts[].media_name` | 紫卡（缩略图） |
| `followup` | 超时未回发一次 | wait_minutes、max_times（固定 1） | 橙色卡 + "只发 1 次" |
| `branch` | 只判断不发 | condition_value | 菱形/无正文 |
| `end` | 结束或转人工 | reason | 灰卡 |

**没有 `await` 节点类型。** "等客户回复"是节点上的 `await_reply` 布尔位：

- `node_type` 只回答"这个节点发什么"
- `await_reply` 回答"发完停不停"
- 同一个 `text` 节点可以 `await_reply=1`（发完停），也可以 `=0`（连发到下一节点）

`followup` 是独立节点，只能通过 `timeout` 边挂在 `await_reply=1` 的节点后面。

> 这一条是全文的类型基准：迁移 CHECK、前端工具栏、客户端 `run_flow` 都只认 6 个 `node_type`。任何地方出现 `await` 节点都是错的。

### 3.3 三条硬规则

1. **一个 `await_reply=1` 的节点 = 流程的分号**：发完必须停，客户不回不往下走。
2. **复聊只执行一次**：幂等键 `followup:{conv_id}:{node_key}` 落库 + 唯一约束；发过就再也不会触发。
3. **任何等待必须有终态**：

```
conv_state.phase（会话在流程里的位置，只有这 8 个值）
  idle → running → awaiting ──客户回复──▶ replied → running（下一节点）
                     │
                     ├──超时──▶ followup_due → followup_sent → expired（终态）
                     └──发送失败──▶ held（人工；不自动发、不调 chat）

outbox.status（单条消息的投递结果，与 phase 是两回事）
  sending → sent / failed / skipped
     └─进程崩溃残留 10 分钟──▶ unknown（不重发，人工核对）
```

**不允许留 `awaiting` 挂着**——这就是"回不回都要走一个标记"。

**`failed` / `unknown` / `skipped` 是 outbox 的状态，不是 phase。** phase 只表达"流程走到哪"，不表达"某条消息发没发出去"。三端混淆这两个概念是最容易出错的地方（后端状态表、客户端 SQLite、前端徽标都必须用 phase；投递明细只在 outbox）。

### 3.4 单轮单出口（避免再次双发）

同一条客户消息，**最多产生一组输出**：

| 会话当前状态 | 客户发来消息 | 处理 |
|---|---|---|
| 无记录 / `idle` | 第一句 | 跑流程（entry → 第一个 `await_reply=1` 的节点），**不调 chat** |
| `awaiting` | 任意文本 | 节点推进（`keyword` 边优先，其次 `any_reply`），**不调 chat** |
| `followup_due` | 任意文本 | 视同 `awaiting` 的回复：取消复聊，推进节点 |
| `replied` | 任意文本 | 上轮若中断则续跑，否则调 chat 答疑 |
| `followup_sent` / `expired` | 任意文本 | 调 chat 答疑（自由对话，不再推进节点） |
| `running`（上轮中断） | 不处理新消息 | 先续发，本轮跳过新消息 |
| `held` | 任意文本 | **不自动处理**；网页标"待人工"，人工重新入队才继续 |

> 取舍：P0 阶段"awaiting 时客户插问"会被当作回答推进（可能答非所问），P2 用 `branch` + 关键词兜住常见异议（"太远""多少钱""包吃吗"）。这是有意的：**宁可推进，也不重复轰炸**。

### 3.5 深圳岗位改造后的节奏

| # | node_key | 内容 | 结束 |
|---|---|---|---|
| 1 | `qualify` | 招聘要求（原 seq1） | await："看下符合吗🌹" |
| 2 | `wage` | 薪资架构（原 seq2） | await，timeout → `wage_followup` |
| 3 | `wage_followup` | 复聊："薪资这块看明白了吗？有不清楚的我再讲一下" | 发 1 次 → expired |
| 4 | `work_place` | 工作地点 + 工作内容（原 seq3-4） | await |
| 5 | `work_show` | "这是工作环境和内容" + 图 + 视频（原 seq5-7） | 不等待 |
| 6 | `dorm` | "这是宿舍" + 图（原 seq8-9） | await："宿舍这样能接受吗？" |
| 7 | `invite` | 面试邀约（新增） | await |

客户不回：停在 `wage`，15 分钟后收到**1 条**复聊；再不发。客户回了：进入 `work_place`，不会重复薪资。

### 4.2 新路由 `src/modules/agent/agent-flow.routes.ts`

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/v1/agent-flow?position_id=` | admin | 返回 flow + nodes + edges + canvas |
| PUT | `/api/v1/agent-flow` | admin | 整图保存（事务：节点 upsert + 边重写 + version+1） |
| POST | `/api/v1/agent-flow/migrate` | admin | 从 `position_opening` 生成流程（幂等） |
| GET | `/api/v1/agent/flow?device_code=` | 设备 token | 客户端拉取（按设备绑定的岗位） |
| POST | `/api/v1/agent/state` | 设备 token | 客户端上报会话状态 |
| GET | `/api/v1/agent/state?device_code=` | 设备 token | 重连对账 |

关键实现点：

1. **整图保存用事务**：`BEGIN` → 逐节点 upsert（按 `node_key`）→ 删掉不在列表里的节点和边 → 重写边 → `version = version + 1` → `COMMIT`。版本号变了下轮心跳客户端就会热更。
2. **校验**（不通过返回 422）：
   - 必须有且只有一个 `end` 可达路径（防孤儿节点）
   - `followup` 必须挂在某个 `await_reply=1` 节点的 `timeout` 边上
   - `followup.max_times` 接口层强制写 1（DB CHECK 放宽到 0-3，只作兜底）
   - `to_key` 允许空串（= 流程结束），非空时必须指向本流程已存在的 `node_key`
   - `node_type` 只接受 6 个值（`text/image/video/followup/branch/end`），出现 `await` 直接 400
   - `image/video` 的 `media_name` 必须在 `media_assets` 且属于本岗位或通用池
   - 文本里的数字必须命中岗位字段白名单（防"160/班"与岗位表打架）
3. **序列化约定**：DB 里是 `parts_json`（字符串），接口出参统一转成 `parts`（数组）；入参接受 `parts`，落库时 `JSON.stringify`。客户端只认 `parts`，永远不解析 `parts_json`。
4. **`/api/v1/agent/flow` 响应带 `version` 和 `position_id`**，客户端缓存到 `config.remote.json`，拉不到时用缓存跑。
5. **`position_opening` 兼容**：`/api/v1/agent/opening` 保留。**默认仍走旧列表**，只有请求带 `?mode=flow` 时才返回"第一个 await 之前"的展开结果——避免 P1 后端一上线，未升级的 P0 客户端突然只收到 2 条。等客户端全部升级后再把默认切到 flow。

### 4.5 复聊：合并到 `followup.ts` 还是独立？

### 6.2 修改 `autopilot.py`：`drain()` 拆成两段

现有 `drain()` 从 L1094 到 L1447，是"一条消息 → 一次回复"。改成：

```python
def drain(store, cfg, *, dry=False, wecom_state="online"):
    ...前置检查（系统会话/接管/流失/名字）不变...
    for it in sorted(newest.values(), ...):
        state = flow_state.get(cid)
        if state and state["phase"] == "running":
            advance_flow(...)        # 续发，不处理新消息
            continue

            continue
```

**`start_flow` / `advance_flow` 的共同实现**：

```python
def run_flow(store, cfg, conv, state, flow, log):
    nodes = {n["node_key"]: n for n in flow["nodes"]}
    cur = nodes.get(state["node_key"]) or entry_node(flow)
    while cur:
        idx = state["step_index"]
        while idx < len(cur["parts"]):
            part = cur["parts"][idx]
            payload = json.dumps(part, ensure_ascii=False, sort_keys=True)
            rowid = flow_state.claim_step(cid, cur["node_key"], idx, part["kind"], payload)
            if rowid is None:                  # 已发过 → 跳过
                idx += 1
                flow_state.set_step(cid, cur["node_key"], idx)   # ★ 游标必须跟着走
                continue
            ok, detail = send_part(store, conv, part, cfg)   # 复用现有 core_send
            flow_state.finish_step(rowid, "sent" if ok else "failed", detail)
            if not ok:
                if "发到了别的会话" in detail:  # ★ 11-19 护栏
                    log("[落点] 发错会话，本轮立即停止")
                    return "aborted"
                flow_state.set_phase(cid, "held", error=detail)
                return "failed"
            idx += 1
            flow_state.set_step(cid, cur["node_key"], idx)       # ★ 发一条推一条
            time.sleep(max(part.get("delay_ms", 2000) / 1000, 0))
        # 节点发完
        if cur["await_reply"]:
            flow_state.set_phase(cid, "awaiting", await_since=time.time())
            return "awaiting"
        nxt = next_node(flow, cur, trigger="default")
        if not nxt:                            # to_key 为空 = 结束
            flow_state.set_phase(cid, "expired")
            return "done"
        cur = nxt
        state = {"node_key": cur["node_key"], "step_index": 0}
        flow_state.set_step(cid, cur["node_key"], 0)
```

> `step_index` 必须在**每条发送后立即落库**（不是节点发完才写）。断线时才知道该从第几条续。

**`answer_with_brain`**：原 chat 分支，但请求体加 `sent_summary`（从 `conv_state` + flow 已发节点算出来）。

### 6.3 新增 `tick_followups()`

```python
def tick_followups(store, cfg, wecom_state):
    if wecom_state != "online": return
    if in_quiet_hours(): return                    # 21:00-09:00 不发（本地时间）
    for row in flow_state.due_followups(time.time()):
        node = followup_node_for(row["node_key"])   # timeout 边指向的节点
        if not node:
            flow_state.set_phase(row["conv_id"], "expired"); continue
        if not flow_state.mark_followup(row["conv_id"], node["node_key"]):
            continue                                # 已发过 → 幂等跳过
        # 复聊也走 run_flow：outbox 幂等、落点校验、逐条回执、step_index 全部复用
        run_flow(store, cfg, conv, {"node_key": node["node_key"], "step_index": 0}, flow, log)
        flow_state.set_phase(row["conv_id"], "followup_sent",
                             followup_sent_at=time.time(), followup_round=1)

def tick_expire(now):
    """复聊发出后 30 分钟仍无回复 → expired（终态，永不再发）。
    没有这一步，followup_sent 会永远挂着——正是要避免的"没有终态"。"""
    for row in flow_state.stale(phase="followup_sent", older_than=1800, now=now):
        flow_state.set_phase(row["conv_id"], "expired")
```

节奏：主循环每 60 秒扫一次；单设备每分钟最多 1 条复聊（全局变量 `_last_followup_at`）。

> 复聊节点的 `wait_minutes` 不用——复聊只发一次，发完由 `tick_expire` 统一收敛。节点上的 `wait_minutes` 只在 `await_reply=1` 时生效。

## 7. 三端连携

### 7.1 新客户加好友

```
企微本地库写入
   │ collector 解密（collector.decrypt_snapshot）
   ▼
reply_log(pending)  ──▶  drain()
                          │ flow_state.get(cid) = None
                          ▼
                     brain.flow() ← GET /api/v1/agent/flow?device_code=
                          │ 返回 nodes/edges/version（缓存到 config.remote.json）
                          ▼
                     run_flow(entry)
                       ├─ claim_step(qualify, 0) → outbox(sending)
                       ├─ core_send.send(...)   → outbox(sent)
                       ├─ ... 节点内多条 ...
                       └─ await_reply=1 → conv_state(phase=awaiting, await_since=now)
                          │
                          ▼
                     POST /api/v1/agent/state（服务端镜像）
                     POST /api/v1/agent/opening/log（逐条回执，保留）
                          │
                     ✗ 不再调 /agent/chat  ← 这是修重复的关键
```

### 7.2 客户回复

```
新消息入 reply_log
   │
   ▼ drain()
flow_state.get(cid).phase == "awaiting"
   │
   ├─ 命中该节点的 keyword 边 → 目标节点
   └─ 否则 any_reply 边 → 目标节点
   │
   ▼
run_flow(目标节点)   ← 不调 chat，不会复述
   │
   ├─ 节点还有 await → phase=awaiting（重置 await_since）
   └─ 节点是 end → phase=replied
```

### 7.3 15 分钟无回复（复聊）

```
主循环每 60s
   │
   ▼ tick_followups()
flow_state.due_followups(now)
   │  SELECT * FROM conv_state WHERE phase='awaiting' AND now-await_since >= wait_minutes*60
   ▼
mark_followup(cid, node)  ← 幂等：followup_round=1 或 followup_sent_at 非空 → 返回 False
   │ True
   ▼
发送复聊内容（同 run_flow 的 outbox 幂等）
   │
   ▼
phase='followup_sent', followup_sent_at=now, followup_round=1
   │
   ├─ 客户回了 → phase='replied'（进入自由对话）
   └─ 仍不回   → 下一轮 reconcile：phase='expired'（终态，永不再发）
```

### 7.4 断线重连

```
进程启动 / 心跳 offline→online
   │
   ▼ reconcile(now)
   ├─ outbox.status='sending' 且 created_at 超过 10 分钟 → 'unknown'（不重发，网页标黄）
   ├─ phase='awaiting' 且超时 → 'followup_due'（入复聊队列）
   ├─ phase='running'（节点发到一半） → 从 step_index 续发（outbox 幂等跳过已发）
   ├─ phase='awaiting' 未超时 → 保持
   └─ phase='followup_due' 且已过静默期 → 保持，等 tick_followups 发
   （followup_sent → expired 不在这里做，由主循环 tick_expire 每轮扫）
   │
   ▼
GET /api/v1/agent/state?device_code=   ← 服务端镜像兜底
   ├─ 本地没有、服务端有 → 按服务端状态补一条 conv_state
   └─ 两边冲突 → 以"进度更靠后"的为准（node 序号大 / step_index 大）
   │
   ▼
POST /api/v1/agent/state（把 reconcile 结果回写服务端）
```

> `reconcile` 只在启动和 offline→online 时跑；`followup_sent → expired` 是常态收敛，必须放主循环（`tick_expire`），否则复聊发完的会话会永远挂着。

### 7.5 运营改配置

```
前端画布保存 → PUT /api/v1/agent-flow → version+1
   │
   ▼ 客户端心跳（60s）
RemoteConfig.sync() 发现 version 变化 → 重新 GET /api/v1/agent/flow（只保留一份最新 flow）
   │
   ├─ 正在 awaiting 的会话：保留 node_key，在新流程里找同名节点
   │    ├─ 找到 → 从该节点 step_index=0 继续
   │    └─ 找不到 → phase='expired'，网页提示"流程已变更"
   └─ 新会话：直接用新 version
   │
   ▼ 日志
[流程] version=7 → 12 个节点，热更；2 个等待中会话的节点已不存在 → expired
```

> 客户端只缓存一份 flow，做不到"按旧 version 走完"（要做就得多版本缓存 + 每个会话存快照，代价远大于收益）。所以规则是：**节点还在就继续，节点没了就结束**，并且把结果明确标成 `expired`，不留悬空状态。

### 8.2 `POST /api/v1/agent/state` 请求

```jsonc
{
  "device_code": "pc-win-01",
  "items": [
    {
      "session_key": "S:1688855894882096_xxx",
      "position_id": 1,
      "flow_version": 7,
      "node_key": "wage",
      "step_index": 0,
      "phase": "awaiting",
      "await_since": "2026-11-19T11:20:00Z",
      "followup_sent_at": null,
      "followup_round": 0
    }
  ]
}
```

**时间格式**：客户端内部 `conv_state` 用 Unix 秒（REAL），上报时转 UTC ISO8601（`2026-11-19T11:20:00Z`），服务端存 TEXT。下发/对账时反过来转回 REAL。不要在任何一端混用两种格式。

**键名对应**：客户端 `conv_id` ≡ 服务端 `session_key`（都是 `S:`/`R:` 前缀的企微会话 ID），上报时字段名用 `session_key`，值直接填 `conv_id`。

### 8.3 `conv_state.phase` 枚举

| phase | 含义 | 下一状态 |
|---|---|---|
| `idle` | 还没开始 | `running` |
| `running` | 节点发送中 | `awaiting` / `expired` / `held` |
| `awaiting` | 等客户回复 | `replied` / `followup_due` |
| `followup_due` | 到点待复聊 | `followup_sent` / `expired` |
| `followup_sent` | 复聊已发 | `replied` / `expired` |
| `replied` | 客户回了 | `running`（下一节点）/ 自由对话 |
| `expired` | 流程结束/超时放弃 | 终态 |
| `held` | 发送失败待人工 | 人工重新入队 → `running` |

> 只有这 8 个值。`failed` / `unknown` / `skipped` / `sent` 是 **outbox.status**（单条消息投递结果），不是 phase。后端 `agent_conversation_state.phase`、客户端 `conv_state.phase`、前端徽标三处必须用同一套 8 值枚举。

## 13. 一句话总结

**后端**把"平铺开场"换成"流程图 + 会话状态镜像"；**前端**把"配置弹窗"换成"无限画布 + 气泡预览"；**客户端**把"布尔标记"换成"SQLite 游标 + 发件箱 + 启动对账"。三端用同一份 `node_key` 和同一个 `phase` 枚举串起来：客户不回只发一次复聊，断了线只推进不重发。
