# 分析：问候语、掉线可观测、服务器看会话、面试登记

> 结论先行：**前三个问题根因是同一个——autopilot 只读本地库、只按键鼠发送，从不和服务器通信。**
> 第四个小：地点字段能抽到，但页面没有登记入口。

## 二、问候语：为什么会落到"没查到"

### 根因
`kb_answer.answer()` 的第一件事就是检索知识库。`"你好"` 检索不到任何条目，于是走 `no_match` 兜底：

```python
if resolved_city is None and not wants_clarification(...):
    reply = "这个我这边暂时没查到，你方便说一下是哪个城市、什么厂吗？"
```

**问候语根本没有被识别成问候**，它和"问一个不存在的厂"走了同一条路。

### 正确做法：先分意图，再查库

```
客户消息
  ├─ 寒暄（你好/在吗/在不在）      → 不查库，直接欢迎 + 探需求
  ├─ 问岗位（有什么厂/哪些厂）      → 查库
  ├─ 问条件（多少钱/包吃住/多大）    → 查库（缺城市先反问）
  ├─ 约面（明天能去吗/几点到）      → 查库 + 给时间地点
  └─ 否定（太远/不去了/再想想）      → 不查库，挽回或记录放弃
```

### 关于"人性化、不固定、多回一次也没关系"

同意，而且这是对的。具体做法不是写一堆死模板，而是：

1. **寒暄给模型自由发挥**，只约束三件事：不超过 30 字、不编造工价/年龄、必须落到一个具体问题上
2. **给 3~5 个开头变体**做种子，避免每次一模一样（"你好呀" / "在的" / "哎你好"）
3. **允许重复回**：人本来就会重复打招呼。只拦一种情况——同一会话 10 分钟内已经回过的同一类寒暄，不再回第二遍，避免刷屏

一句话：**寒暄不查库、不写死、允许重复，但要收敛到一个引导问题。**

## 三、企微掉线：三层才闭环

现在只有第二层的一半（接口有，没人调）。

### 第一层：本地自检（agent 自己知道）

autopilot 每轮轮询时检查三件事：

| 检查 | 判断 |
|---|---|
| `WXWork.exe` 进程在不在 | 不在 → `not_running` |
| 主窗口类名 | `WeChatLogin` → `login_required`（被踢） |
| 窗口是否可见 | `false` 且进程在 → `hidden`（可能已被风控隐藏） |

状态变化时**立即停止发送**，不要继续盲试——之前被强退就是因为窗口隐藏了还在点。

### 第二层：心跳上报（服务器知道）

autopilot 每 30 秒调一次（不产生任何键鼠动作）：

```http
POST /api/v1/devices/pc-office-01/heartbeat
X-Device-Token: ...
{ "agent_version": "1.0", "wecom_state": "online|login_required|not_running|hidden",
  "queue_size": 0, "last_error": "" }
```

接口已有，只需加一个 `wecom_state` 字段存下来。

### 第三层：服务器判离线 + 推前端

新增一个 60 秒的扫描（可复用已有 worker 模式）：

```
last_heartbeat_at < now - 90s  →  status = offline
状态变化时 → WS 推 device.status 事件 → 页面顶部红条
```

`ws/hub.py` 里 `EVT_DEVICE_STATUS` 常量已经有了，只是没人发。

### 前端表现

```
┌─────────────────────────────────────────────┐
│ ⚠ 采集端离线 12 分钟，期间消息收不到        │
│   最后在线 19:31 · 原因：企业微信已退出登录  │
└─────────────────────────────────────────────┘
```

## 四、服务器看会话：autopilot 必须增量上报

### 为什么现在看不到

`POST /api/v1/agent/ingest` 是通的，但只有 `agent/main.py --once`（早期采集脚本）会调。
`autopilot.py`（现在真正在跑的那个）**一行上报代码都没有**。

### 怎么补（增量，不重传）

```
每 30 秒：
  1. 读本地 message.db，取 id > 上次游标的消息（通常 0~3 条）
  2. POST /agent/ingest {account_uid, conversations: [涉及的会话], messages: [新消息]}
  3. 成功后保存游标到本地 state 文件
  4. 失败不重试，下一轮自然补上（游标没推进）
```

注意三点：

1. **只传增量**，别每轮全量（现有数据库 147 条，全量传会越来越慢）
2. **上报失败不影响回复**（和线索抽取一样，失败只记日志）
3. 群聊 `R:` 也上报，但线索判定跳过（已实现）

补完之后：服务器能看到实时会话 → 看板/接待台/统计才有意义。

## 五、约好面试去哪里 + 后台登记

### 地点从哪来

| 来源 | 可靠性 | 说明 |
|---|---|---|
| LLM 从对话里抽 | 中 | 实测抽出"番禺厂门口"，但如果客户没问、我们没说，就抽不到 |
| 知识库岗位字段 | 高 | **建议加**：`kb_entry.interview_place`（集合点），约面话术自动带上 |
| 人工登记 | 高 | 兜底，必须有 |

**建议：回复模板里固定包含「时间 + 地点 + 联系人」三件套**，不要靠模型自由发挥。
现在的回复"明天下午两点过来是吧"是合格的，但没给地点；客户下一句就会问"去哪"。

### 后台登记怎么办

现在 `POST /leads/{id}/manual` 支持 `interview_at` / `interview_place` / `note`，
但看板页只有「改期」能填日期，**地点没入口**。

补一个最小交互（不弹窗）：

```
今日约面  青冥   11-05 14:00   番禺厂门口 [改]
                                  ↑ 点一下变输入框，回车即存

每行按钮：到了 / 没来 / 地点 / 改期
```

「地点」点开就是行内输入框，回车提交 `{interview_place: "..."}`，和「改期」同一套逻辑。

## 六、优先级

| 级别 | 事项 | 不做的后果 |
|---|---|---|
| **P0** | autopilot 心跳 + 掉线自检 | 服务器永远显示 offline，出了事没人知道 |
| **P0** | autopilot 增量上报 | 服务器看不到今天的会话，看板全是旧数据 |
| **P1** | 服务器超时判离线 + 前端红条 | 顾问以为系统正常，其实消息没进来 |
| **P1** | 看板「地点」登记入口 | 约了面但不知道去哪，只能翻聊天记录 |
| **P1** | 寒暄意图分流 + 不固定回复 | 客户第一句就被回"没查到"，第一印象差 |
| **P2** | 知识库加集合点字段 | 回复里地点靠模型猜，不稳定 |

## 七、风险与边界

1. **心跳和上报都是纯 HTTP，不产生任何键鼠动作**，不增加风控面
2. 上报频率 30 秒一次，单机 1 个设备，服务器压力可忽略
3. 心跳失败不能阻塞回复——autopilot 的主职责仍是收发消息
4. 掉线自检发现 `login_required` 后要**停手**，等人扫码，绝不自动重登
