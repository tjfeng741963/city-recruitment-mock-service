# Dify 模式二：单联系人发送验收

2026-11-21，北京时间。用户授权使用云电脑现有企微选择一位联系人测试，只对这一人发送。

## 测试范围

云 Windows `134.175.40.31` / 主机 `10_1_4_8`，企微 PID 4444 与 autopilot PID 7688 均在 Session 2。现有普通单聊只有 Daylan，客户端 target 也是 Daylan。没有更换 Hook、修改冻结核心、键鼠动作或时序。

本次是 Dify 生成 → 4222 定向发送队列 → C:\agent 原发送函数 → 数据库回读与回执。为避免旧 Agent 同时答复，仅测试期间临时接管 Daylan，会后恢复原 takeover=0。pc-win-01 全局来源仍为 agent，未切换其他会话。

## 结果

- 第一条指令 `e8d8646b-2b2e-4a90-8019-9001553d44e5`：failed，无消息 ID。日志显示抢不到前台；只读检查确认 Administrator Session 2 断开且存在 LogonUI。未新增自动重投。
- 用户连接并解锁后，Session 2 显示运行中，企微仍在该会话。
- 第二条指令 `3628cc20-0b09-49ab-b134-776bf34b8acb`：succeeded，simulated=0，真实消息 ID 结尾 `:35`。
- 使用现有 compat.apply_pb_text() 解码本地消息记录，确认 ID 35 的正文与 Dify 生成的摘要一致，开头为“【模式二 · Dify 工作流测试】”，说明工资和班次，并明确标注定向测试、不是正式招聘承诺。
- 两次都只向 Daylan 定向；测试完成后接管状态已恢复。

## 结论边界

已证明 Dify 输出可以经现有客户端实际发送并读回，失败回执也能上报。锁屏/断开桌面仍会阻止现有桌面发送，Dify 本身不能解决这个接入层限制。

尚未在该真实账号上验证“求职者新消息 → 自动选择 Dify → 自动回复”的长驻闭环。现有客户端有旧流程快照，不能把一次定向队列发送说成已完成整账号切换。前端明确为模式一「系统 Agent」与模式二「Dify 工作流」，后续启用须核对独立状态或设计按联系人来源隔离。
