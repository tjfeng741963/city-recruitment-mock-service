# 接手可靠性修复

日期：2026-11-06。基线：`0c2ab63`。本批不改变企微键鼠发送动作。

## 根因与改动

- Linux CI 导入 autopilot 时未隔离 `ctypes.WinDLL`，且失败模块留在 `sys.modules`，造成后续连锁失败。测试使用统一加载器，替换 Windows API 与发送模块，退出时恢复模块和路径；失败导入也不残留。CI 同时覆盖 Ubuntu、Windows。
- `config.json` 的运行参数未合并，命令行默认值覆盖了只观察设置。现在依次应用默认值、配置文件、显式 CLI 参数，支持 `interval_seconds` 兼容字段；`--dry` 始终强制只观察。配置损坏或参数类型、时长无效时返回退出码 2，禁止进入发送循环。
- 主上报成功推进游标后，桥接失败的消息没有重传依据。现在先把入站待传记录保存至 `.report_state.json` 的 `bridge_pending`，再允许主上报推进游标；失败在后续周期重试，重启后继续。稳定 event_id 供服务端幂等去重；每轮最多发送 50 条，首个网络错误后停止本轮。待传记录绑定服务器地址和设备，切换桥接目标不把旧消息发到新目标。

只涉及 `agent/autopilot.py` 的配置、HTTP 上报编排，以及测试、CI 配置。`agent/wecom_io_core/` 和 `agent/compat.py` 不变。

## 第二批：双向消息与知识库失败处理

- 新增设备 token 认证的 `POST /api/v1/bridge/devices/:code/outbound`。记录企微已发出的文本，支持独立设备/会话映射、event_id 幂等与冲突检查；不调用自动回复，不新增发送指令或投递，不增加客户未读数。新增消息才推送 SSE，重复上报不重复通知。
- agent 的持久化队列扩展为双向消息，保留真实时间和稳定消息 ID；兼容缺少 direction 的旧入站待传记录。按消息原始时间维护会话摘要，迟到消息不覆盖更新的摘要。文本上报上限从 4000 扩展为 20000，与新接口一致。
- 人工发送在既有发送函数前后只读取已解密数据库；只有核心回读确认会话，且只出现一条新的同内容自发消息时，才把真实 `contact_id:message_id` 作为回执。通过这个 ID 合并人工气泡与观察记录，支持回执先到/后到；不按内容直接去重。换行会统一比较，实际相同内容的多条消息仍保留。
- 回执更新与去重合并在一个数据库事务内完成；保留合并记录中较大的数字 ID，避免 SQLite 复用最大 ID 导致 `after_id` 客户端漏消息。
- 知识库失败、异常、空回复和没有文本的消息改为 `held`。该状态不会由轮询或重启自动重试，错误原因保存在回复历史并通过心跳提示。dry-run 不改变记录。明确配置的 fixed 模式仍使用配置文本；kb 配置缺少地址或模式拼错会停止启动。
- 人工核实故障和积压记录后，可在停止常驻 agent 的情况下运行 `python autopilot.py --retry-held`，将全部 held 重新入队并退出；该命令自身不初始化企微 Store、不发送。之后正常启动 agent。已有较新会话进展时应先检查旧消息是否仍需回复。

## 第三批：人工执行记录与回执补传

根因：原人工发送路径调用一次 receipts，HTTP 失败后只打印日志。即使消息已发出，网页状态也可能不更新；进程在发送期间退出时，重启无法区分已执行与未执行。

- 在已有 `reply_log.db` 新增 `manual_commands`，启动时自动建表，不改已有回复记录。领到人工指令后、任何发送动作之前，先以服务器、设备、command_id、lease_token 为键提交 unknown 记录。写盘失败停止该条发送。同一执行租约不执行第二次；此前 succeeded 或 unknown 的指令即使换租约也不自动再发。明确失败后，服务器分配新租约才允许人工重试。
- 发送结果先持久化，再上报 HTTP 回执。断网、服务端错误、认证失败或未收到 `{ok:true}` 时保留 pending；后续周期和重启后只补传回执，不重走键鼠。服务端已接收但客户端没写下确认的情况，会重复同一回执，由服务端幂等接收。
- 回执恢复在企微 offline/hidden 时也可进行，dry-run 完全跳过。每轮最多 50 条，失败后至少隔 10 秒再尝试；有未确认回执时暂停领取新的人工指令，自动回复与心跳继续沿原流程运行。
- 409/422 回执保留为 rejected，显示待人工核对，不自动改写结果或重发。401/403 保留 pending，等待认证、设备权限或旧租约问题处理。更换服务器/设备后不会把原回执发往新目标。
- 执行中退出、核心抛异常或回读显示落点不符时，用 unknown 保留不确定性；发送之前的校验失败仍为 failed。服务端消息 API 返回 unknown，不重新入队；同一租约迟到的成功回执可推进为 sent，并保持幂等。
- 增加 `python autopilot.py --flush-receipts`，仅处理当前桥接目标的 HTTP 回执后退出，不创建企微 Store、不发键鼠事件。退出码 0 表示当前目标无 pending/rejected；1 表示仍有待处理项；2 表示桥接配置缺失。dry-run 不补传。`--list` 优先展示 pending/rejected 执行记录，输出不包含 lease_token。
- 本地 SQLite 执行记录含租约，必须按运行数据保管。已有 agent 忽略规则覆盖 `.db`、WAL、SHM；本批补充忽略 `.db-journal`。

验证：本地 TypeScript 类型检查通过，Node 全量 42 个文件、252 passed，Python 全量 529 passed、130 个既有警告。本批新增 28 个 Python 用例及 1 个 Node 回归，覆盖断网、进程中断、三处写盘失败、未确认响应、错误分类、跨目标隔离、并发执行记录和无输入 CLI。原人工发送测试改用真实临时 SQLite 执行记录，窗口与键鼠继续使用桩。

本批服务端无新增迁移。发布仍先服务端、后 agent；远端 CI、生产更新和真实企微验收未执行。回滚前保留本地数据库并确认 pending/rejected 已处理；旧 agent 不会补传新表中的回执，不能把删除执行记录当成重试方式。第二批的真实消息 ID 不明确、非文本和历史消息边界继续存在。

## 第七批：人工发送必须有唯一的新消息 ID

实机发送前的只读预检复现了冻结核心的回读兼容问题：本机 SQLite 将 `rowid` 列命名为其主键别名 `message_id`，核心 `_find_new_sent()` 按 `row["rowid"]` 取值抛出 IndexError。核心会在发送后回读异常时返回 ok 和空会话 ID，旧编排因此仍可报告 succeeded 并生成 keyboard 临时标识。用户确认具体非动作层方案后执行本批修复。

- 仅调整 `autopilot.pump_commands()` 已有发送调用返回后的结果判断，复用既有前后快照。预期会话中必须新增恰好一个本人发出的消息 ID，且规范化正文相同，才报告 succeeded，回执为真实 `contact_id:message_id`。核心未给出会话 ID 时也必须有该证据；明确返回其他会话则不成功。
- 快照不可读、无新增 ID、多条新增同文、只有入站或其他会话消息，一律 unknown、空 message_id，不计入 sent。沿用冷却、先持久化后回执及重启只补传机制；unknown 不允许通过新租约自动再发。历史已落盘的 keyboard 回执原样补传，不自动改写或重发。
